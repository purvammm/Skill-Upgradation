# Authoring guide for the two Infosys DSA textbooks

The books are built from Markdown by `build.py`. Each of the 29 chapters exists twice, with the
same number, which is also the day number of the 29-day plan:

| File | Becomes |
|---|---|
| `theory/chNN.md` | Chapter NN of **Volume I · Theory** (the textbook) |
| `workbook/chNN.md` | Chapter NN of **Volume II · Practice Workbook** (exercises the reader completes by hand) |

`theory/ch02.md` and `workbook/ch02.md` are the reference chapters. Read both, and the rendered
pages, before writing anything. Match their depth, tone and structure.

The reader is Purvam Prajapati, preparing in Java for the Infosys Specialist Programmer (SP) / Digital
Specialist Engineer (DSE) coding assessment on 6 December 2026. He reads the theory chapter, then
works the workbook chapter and the day's problems on LeetCode / Codeforces / OneCompiler.

## Theory chapter structure (`theory/chNN.md`)

```markdown
---
title: Greedy Algorithms with Heaps          # textbook-style title for the day's topic
short: Greedy with heaps                     # running header, ≤ 28 characters
prereqs: Chapter 4 (sorting and exchange arguments)
objectives:                                  # 4–6 items, each completing "After this chapter you should be able to:"
  - explain how a binary heap supports insert and extract-min in O(log n);
  - ...
---

Introductory paragraphs (no heading): the problem family, why it matters, what the chapter covers.

## First numbered section {#sec-5-heap}
...
## Summary
## Review questions
:::answers
...
:::
## Further reading
```

The opener (chapter number, date, part, handbook cards, objectives box), the **Key terms** list and the
**Problems** table are generated by the build. Do not write them yourself.

Required content for a learning chapter:

* **5–8 numbered sections** (`## Title`). They are numbered N.1, N.2, … automatically.
* **Definitions** (`:::definition`) for every new concept, with the term marked `[[like this]]` so it reaches
  the index and the chapter's key-terms list. Mark 4–10 key terms per chapter.
* **A correctness argument for every algorithm**: a `:::theorem` / `:::lemma` / `:::claim` followed by a
  `:::proof`. Use invariants, exchange arguments, induction, or a counting argument. Keep proofs short and
  rigorous; a reader with school mathematics must be able to follow them.
* **Worked examples** (`:::example`), at least two per chapter, with traces in ```` ```trace ```` blocks or
  tables. **Every number in a trace must come from running code**, not from mental arithmetic.
* **Listings** (```` ```java {#lst-N-name} Title ````) for every template. Where the handbook has a template
  (`/projects/sandbox/work/sources/cards/<id>.md`), use its code verbatim or with minimal changes: it was tested
  against brute force on random inputs. New code must be tested the same way (see Verification).
* **Complexity** for every algorithm: time and memory, with the reason.
* **Figures** (```` ```fig ````), at least two per learning chapter, where a picture explains the idea
  (array states, trees, graphs, DP tables, intervals, histograms).
* Boxes where they help: `:::keyidea`, `:::java` (Java-specific detail), `:::pitfall` (from the handbook's
  "Traps"), `:::tip` (exam technique), `:::infosys` (why this matters for the Infosys paper; only facts that
  appear in `/projects/sandbox/work/sources/plan/*.md`).
* **Summary**: 5–9 bullets. **Review questions**: 6–10 conceptual questions (not the day's problems), with full
  answers inside `:::answers` (moved to Appendix C automatically). **Further reading**: 2–4 items from the
  vetted list below.

Length: a learning chapter with one pattern is about 3,500–5,000 words; with two or three patterns,
4,500–7,000. Mock, repair, consolidation and rest chapters are 2,500–4,500 words. Depth matters more than
length: explain *why* before *how*, and never leave a step of an argument to "it is easy to see".

### Problems and spoilers

* Cite only problems that appear in `data/plan.json`, `data/mocks.json` or the handbook cards' practice links,
  with the exact label and title given there (e.g. "LeetCode 502 (IPO)", "Codeforces 1526C2"). Never invent a
  problem number.
* **Core** problems that are direct applications of a template, or the standard illustration of the technique
  (as LeetCode 560 is for prefix counting, or LeetCode 834 for rerooting), may be worked examples with full code.
  Prefer to leave at least two core problems per day for the reader to solve without a printed solution.
* For **bonus** problems, teach the technique on a different small example and at most name the key
  observation. Do not print a full solution.
* **Mock problems** (Days 9, 16, 23, 25, 27): no solutions in the body. A final section
  "After the mock" (marked with a `:::pitfall` box saying "Read only after the mock") may give each problem's
  key idea in 2–5 sentences, verified by your own solution.
* Facts about Infosys come only from `/projects/sandbox/work/sources/plan/*.md`. Do not add new claims about the
  assessment, cut-offs or pay.

## Workbook chapter structure (`workbook/chNN.md`)

```markdown
---
title: Greedy Algorithms with Heaps
short: Greedy with heaps
---

{{plan}}

{{recall}}

## Exercises

One-paragraph introduction.

:::exercise{#exr-5-gaps} Fill the gaps
...
:::

:::answers
**Exercise 5.1.** ...
:::

{{problems}}

{{resolve}}

{{end}}
```

`{{plan}}` (time plan and notes), `{{recall}}` (spaced review list), `{{problems}}` (a worksheet per problem,
with hints in Appendix A), `{{resolve}}` and `{{end}}` (error log, reflection) are generated from the plan data.
On mock days put `{{mock}}` (mock rules, planning grid, score sheet, post-mortem) where it belongs; problem
worksheets are not generated for mock days.

Write **6–9 exercises** per learning chapter (4–6 on mock/rest days), mixing these kinds, in roughly this order
(worked example → faded example → independent work, then retrieval):

1. **Fill the gaps**: a template from the theory chapter with 3–6 blanks (`______`), in a ```` ```java {.nocompile} ```` block.
2. **Trace by hand**: an input and an empty trace table (inside `:::plain{.trace-table}` so the rows are tall).
3. **Faded trace**: the first rows filled in, the rest blank.
4. **Concept check**: true/false with reasons, or short answers.
5. **Design before you code**: a *new* small problem (not in the plan) that uses the chapter's idea; the reader
   writes the state / key / invariant and the complexity.
6. **Find the bug**: a plausible buggy version of a template (it must compile), a failing input to find, the fix.
7. **Complexity and limits**: given limits, choose the approach and justify it.
8. **Write it from memory**: a `:::write{lines=N}` or `:::grid{rows=N}` space.

Every exercise has a full answer in `:::answers` (moved to Appendix B). Compute every number in an answer with
code.

## Markdown dialect

| Syntax | Result |
|---|---|
| `## Title {#sec-N-x}` | numbered section; Summary / Key terms / Review questions / Further reading / Exercises stay unnumbered |
| `### Title` | unnumbered subsection |
| ```` ```java {#lst-N-x} Title ```` | "Listing N.k Title" with line numbers |
| ```` ```java ```` | highlighted snippet without number |
| ```` ```java {.nocompile} ```` | skipped by the compile check (blanks, deliberately wrong code) |
| ```` ```java {.fragment} ```` | statements only; compiled inside a method body |
| ```` ```trace ```` | monospace block for traces and sample input/output |
| ```` ```fig {#fig-N-x} Caption ```` + JSON body | "Figure N.k" (types below) |
| `:::definition{#def-N-x} Title` … `:::` | numbered box; also `theorem`, `lemma`, `claim`, `example`, `exercise` |
| `:::proof` … `:::` | "Proof." paragraph ending with ∎ |
| `:::keyidea`, `:::note`, `:::tip`, `:::pitfall`, `:::infosys`, `:::java`, `:::history`, `:::hint`, `:::task`, `:::checklist`, `:::solution` | unnumbered boxes with an optional title |
| `:::plain{.trace-table}` … `:::` | no box; makes empty table cells tall |
| `:::columns` … `:::` | two columns |
| `:::write{lines=4} Prompt` … `:::` | ruled writing space (workbook) |
| `:::grid{rows=10} Prompt` … `:::` | 5 mm squared paper (workbook) |
| `:::answers` … `:::` | moved to the answers appendix |
| `[[term]]`, `[[shown text\|Index entry]]` | bold key term + index entry |
| `^[text]` | footnote at the bottom of the page |
| `@lst-N-x`, `@fig-…`, `@def-…`, `@thm-…`, `@lem-…`, `@ex-…`, `@exr-…`, `@sec-…`, `@tbl-…` | "Listing 5.2" etc., clickable |
| `@T:lst-N-x` (workbook only) | "Theory Listing 5.2" |
| `Table: {#tbl-N-x} Caption` on the line before a table | "Table N.k Caption" |

Containers nest (`:::write` inside `:::exercise`). Close every container with a line containing only `:::`.

**Labels are global within a book, so every id must contain the chapter number**: `lst-5-ipo`, `fig-5-heap`,
`thm-5-exchange`, `exr-5-trace`. Refer to other chapters in words ("Chapter 20"), not with `@` labels, unless you
wrote that chapter too.

## Style

* Plain, direct English, British spelling (memorise, optimise, colour). Short paragraphs, one idea per
  sentence, active voice. Address the reader as "you".
* Explain why before how. Name the mechanism and the number ("each index enters and leaves the deque once, so
  the loop does at most 2n deque operations"), not impressions ("this is very efficient").
* No filler, no hype, no chatbot phrases, no "delve", "leverage", "robust", "crucial", "powerful", "simply".
  Avoid em-dash chains; use commas, colons and full stops.
* Notation: arrays are 0-indexed `a[0..n−1]`; `a[l..r]` is inclusive; half-open ranges are [l, r);
  log means log₂. Put variables in italics in prose (`*n*`), code in backticks. Use Unicode: ≤ ≥ ≠ − × · ⌊ ⌋ ⊕
  Σ → ⇔ ≡ ∈ ≈ and superscripts 10⁵, 2ⁿ. In code use ASCII only.
* Java 8 only: no `var`, records, `List.of`, switch expressions, text blocks. Prefer `ArrayDeque` to `Stack`,
  `long` for sums, `Integer.compare` in comparators, iterative code for depth above ~10⁴.
