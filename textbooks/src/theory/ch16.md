Today is the second full mock: three Codeforces problems in three hours, with number theory and dynamic programming now part of what you know. The chapter is about the ten or fifteen minutes before you type anything. Strong contestants do not solve problems faster because they type faster; they spend those minutes deciding *what* the problem is, *how big* it is, and *what could go wrong*, so that the code they write is the right code the first time.

The sections follow that order. First, turning a story into a mathematical model. Then the tools for judging whether an idea is fast enough: amortised analysis for loops whose cost varies, and concrete budgets for Java's operations and memory. Then the two checks that catch most wrong answers after the idea is right: types and modular arithmetic, and hand-made edge cases. A map from signals to techniques collects Parts I and II in one table. The chapter ends with the mock protocol and, behind a warning box, the key ideas of the three mock problems for after you have tried them.

## From story to model {#sec-16-model}

Infosys statements are long stories, and so are many Codeforces ones. The story is there to be removed.

:::definition{#def-16-model} Model of a problem
The [[model|problem model]] of a problem is the statement with the story removed. It has three parts: the **objects** (an array, a string, a grid, a graph or tree, a set of intervals, numbers), the **question type** (count, optimise, decide or construct), and the **limits** (the largest sizes and values).
:::

:::infosys
The plan's analysis of the official sample paper describes the style to expect: long story-style statements, input with one value per line, often a function such as `get_ans(...)` to complete, typical limits of *n* ≤ 10⁵, and answers modulo 10⁹ + 7. Its Lesson 2 is about modelling too: in the sample Medium problem the written input format and the samples disagree about where *p* comes, and only the order used by the samples gives the expected outputs. Check your reading of the input against the samples before writing any logic.
:::

### The objects

Translate every noun of the story into one of a handful of structures. "Tables in a row", "days", "houses along a street": an array or a string. "Cities and roads", "servers and cables", "cells you can walk between": a graph. "Employees and managers", "a parent array": a tree. "Meetings", "trains with arrival and departure times": intervals. A good test is to redraw the sample input as that structure on paper; if the sample answer is obvious on the drawing, the model is right.

### The question type

Each question type has a short list of usual techniques.

Table: {#tbl-16-questions} Question types and where they usually lead
| Type | Typical wording | Usual techniques |
|---|---|---|
| count | "how many ways", "number of pairs", "modulo 10⁹ + 7" | prefix counts with a map, DP, combinatorics |
| optimise | "minimum cost", "maximum length", "fewest moves" | greedy with an exchange proof, DP, BFS, binary search on the answer |
| decide | "is it possible", "YES or NO" | usually an optimisation in disguise: compute the best and compare |
| construct | "print any arrangement", "output the order" | a greedy rule with a proof, or DP with reconstruction |

### The limits

The largest *n* nearly decides the complexity before you have an idea. The handbook's table is worth knowing by heart; it assumes roughly 10⁸ to 3 · 10⁸ simple operations per second in Java.

Table: {#tbl-16-limits} From the largest n to the complexity that fits (handbook)
| Largest *n* | Complexity that fits | Usual technique |
|---|---|---|
| ≤ 10–12 | O(*n*! · *n*) | permutations, backtracking |
| ≤ 20–22 | O(2ⁿ · *n*) | bitmask DP, subset enumeration |
| ≤ 500 | O(*n*³) | interval DP, Floyd–Warshall |
| ≤ 5 000 | O(*n*²) | two-dimensional DP, all pairs |
| ≤ 2 · 10⁵ | O(*n* log *n*) | sorting, heaps, segment trees, binary search |
| ≤ 10⁶–10⁷ | O(*n*) | prefix sums, two pointers, sieve |
| ≤ 10¹²–10¹⁸ | O(√*n*) or O(log *n*) | divisors up to √*n*, binary search, fast power |

Values matter as well as sizes. Values up to 10⁶ can index an array (counting, sieves, DP over values); values up to 10⁹ cannot, and need sorting, compression or a hash map. A sum of 10⁵ values of size 10⁹ is 10¹⁴, which needs `long`.

:::example{#ex-16-model} Three stories, three models
*Story A.* "A gardener has a row of *n* ≤ 10⁵ trees with heights up to 10⁹. He may cut down trees, and wants the remaining heights, read left to right, never to decrease. How few trees must he cut?" Objects: an array. Question: optimise (fewest removals). The kept trees form a non-decreasing subsequence, so the answer is *n* minus the longest non-decreasing subsequence. Limits: *n* = 10⁵ rules out O(*n*²) and allows patience sorting with upper bound (Chapter 13).

*Story B.* "*n* ≤ 10⁵ servers are linked by *m* ≤ 2 · 10⁵ cables. Some servers are infected; each second, every infected server infects the servers linked to it. After how many seconds is every server infected, or will some never be?" Objects: a graph. Question: optimise (a time). The infection time of a server is its distance to the nearest initially infected server, so the answer is the largest multi-source BFS distance, or −1 if some server is unreachable (Chapter 15). Limits: O(*n* + *m*) is about 3 · 10⁵ steps.

*Story C.* "Count the strings of length *n* ≤ 10⁵ over the letters a, b, c with no two equal neighbours, modulo 10⁹ + 7." Objects: strings, but the question only depends on the previous letter. Question: count. A DP over (position, last letter) with 3 states, or the closed form 3 · 2ⁿ⁻¹ for *n* ≥ 1, which fast power computes in O(log *n*) (Chapter 10).
:::

## Amortised analysis {#sec-16-amortised}

Many loops do not cost the same at every step. A sliding window's inner `while` sometimes moves the left pointer many times and sometimes not at all; an `ArrayList.add` is usually instant but occasionally copies the whole array. Bounding each step by its worst case gives a uselessly large bound. Amortised analysis bounds the **total** instead.

:::definition{#def-16-amortised} Amortised cost
A sequence of *k* operations has [[amortised cost|amortised analysis]] *c* per operation if the total cost of any *k* consecutive operations from the start is at most *c* · *k*. Individual operations may cost much more than *c*.
:::

### The aggregate method

The simplest technique is to count the total work directly, usually by charging it to something that can only happen a limited number of times. This is the [[aggregate method]].

:::theorem{#thm-16-pointers} Two pointers move O(n) times
If two indices *l* ≤ *r* both start at 0, only ever increase, and never exceed *n*, then all the loop iterations that move one of them number at most 2*n* in total, however those moves are distributed among the steps of an outer loop.
:::

:::proof
Every iteration that moves a pointer increases *l* + *r* by at least 1. The sum starts at 0 and never exceeds 2*n*, so there are at most 2*n* such iterations.
:::

That is why the sliding window of Chapter 3 is O(*n*) even though its inner `while` can run *n* times in one step. The same argument applies to a monotonic stack: charge each operation to the index it pushes or pops.

```java {#lst-16-stack} Aggregate counting: a monotonic stack does at most 2n stack operations
// next[i] = index of the first element to the right of i that is larger than a[i], or -1.
// ops counts pushes and pops; each index is pushed once and popped at most once.
static long ops;

static int[] nextGreater(int[] a) {
    int n = a.length;
    int[] next = new int[n];
    Arrays.fill(next, -1);
    ArrayDeque<Integer> stack = new ArrayDeque<>();    // indices whose answer is still unknown
    ops = 0;
    for (int i = 0; i < n; i++) {
        while (!stack.isEmpty() && a[stack.peek()] < a[i]) {
            next[stack.pop()] = i;                     // a[i] is the first larger value
            ops++;
        }
        stack.push(i);
        ops++;
    }
    return next;
}
```

Each index is pushed exactly once, and popped at most once because a popped index never returns. So `ops` ≤ 2*n*. Measured on 10⁶ elements: a random array gave 1,999,980 operations, a strictly increasing one 1,999,999 (every index pushed and then popped by its neighbour), and a strictly decreasing one 1,000,000 (nothing is ever popped). A single step of the `for` loop can pop thousands of indices; the total cannot exceed 2*n*.

### Growing an array by doubling

`ArrayList` stores its elements in an ordinary array. When the array is full, `add` allocates a bigger one and copies every element across. With doubling, the code looks like this.

```java {#lst-16-intlist} A growable int array that doubles its capacity
// What ArrayList does, with doubling instead of its factor 1.5. Counts the copying work.
static final class IntList {
    int[] data = new int[1];
    int size = 0;
    long copies = 0;                                  // elements copied by all resizes so far

    void add(int x) {
        if (size == data.length) {
            data = Arrays.copyOf(data, 2 * data.length);  // every element is copied once
            copies += size;
        }
        data[size++] = x;
    }

    int get(int i) { return data[i]; }
}
```

```fig {#fig-16-doubling} The cost of each of the first 17 appends to IntList, counting one unit per element written. Most appends cost 1; the appends that trigger a resize cost 1 plus the number of elements copied (2, 3, 5, 9, 17). The tall bars get rarer exactly as fast as they get taller.
{"type": "bars", "values": [1, 2, 3, 1, 5, 1, 1, 1, 9, 1, 1, 1, 1, 1, 1, 1, 17], "unit": 6, "bar": 24,
 "colors": {"1": "amber", "2": "amber", "4": "amber", "8": "amber", "16": "amber"}}
```

:::theorem{#thm-16-doubling} Doubling gives O(1) amortised appends
Starting from capacity 1, *n* appends to @lst-16-intlist copy fewer than 2*n* elements in total, so the total work is less than 3*n* element writes.
:::

:::proof
Resizes happen when the size reaches 1, 2, 4, …, 2ᵏ, where 2ᵏ is the largest power of two below *n*. They copy 1 + 2 + 4 + ⋯ + 2ᵏ = 2ᵏ⁺¹ − 1 elements. Since 2ᵏ < *n*, this is less than 2*n*. Adding the *n* ordinary writes gives less than 3*n*.
:::

For *n* = 10⁶ the count is 1,048,575 copies, just above *n*. Java's `ArrayList` grows by a factor 1.5 instead of 2 (the new capacity is the old one plus half of it, starting from 10). The same geometric-series argument bounds the copies by about 3*n*; simulating its rule for 10⁶ appends gives 30 resizes and 2,430,972 copies. A smaller factor wastes less memory and copies more often. If you know the final size, `new ArrayList<>(n)` avoids every resize.

:::keyidea
"O(1) amortised" is a statement about the total. It is safe inside a loop that runs *n* times, but it does not promise that every single call is fast. A Java `HashMap` that doubles its table behaves the same way.
:::

## Operation and memory budgets in Java {#sec-16-budgets}

A complexity class tells you how the cost grows; the limits need an actual number. The planning figure from the handbook is 10⁸ to 3 · 10⁸ simple operations per second in Java. Which operations count as "simple" matters as much as how many there are.

Table: {#tbl-16-time} Measured costs on the machine used for this book (one run each; approximate)
| Work | Time |
|---|---|
| 10⁹ iterations of a simple arithmetic loop | 0.40 s |
| 10⁸ multiply-then-modulo steps (`x * 31 % MOD`) | 0.43 s |
| 10⁸ sequential reads of an `int[]` | 0.06 s |
| 10⁸ random reads of a 64 MB `int[]` | 0.80 s |
| 10⁶ `HashMap.merge` calls with random `Integer` keys | 0.23 s |
| 10⁶ increments of an `int[]` counter with the same keys | 0.02 s |
| sorting 10⁶ `int`s with `Arrays.sort(int[])` | 0.13 s |
| sorting 10⁶ `Integer`s with `Arrays.sort(Integer[])` | 0.71 s |

The machine was an Intel Xeon at 2.5 GHz running OpenJDK 25; a judge may be two or three times slower, and the just-in-time compiler makes short benchmarks noisy. Treat the table as orders of magnitude. Three lessons survive any machine. Random memory access is more than ten times slower than sequential access. Hash maps cost about ten times more than arrays indexed by the key. [[Boxing]], storing an `int` inside an `Integer` object, costs several times more than the plain `int`, in sorting and everywhere else.

### Memory

Table: {#tbl-16-memory} Approximate memory per item, measured on a 64-bit JVM with compressed references
| Structure, 10⁶ items | Bytes per item |
|---|---|
| `int[]` | 4 |
| `long[]` | 8 |
| `Integer[]` (filled with distinct objects) | about 20: a 16-byte object plus a 4-byte reference |
| `ArrayList<Integer>` | about 23 |
| `HashSet<Long>` | about 69 |
| `HashMap<Integer, Integer>` | about 77 |
| `int[n][2]` (10⁶ rows of two) | about 29 per row |
| `int[2][n]` (two rows of 10⁶) | about 8 per pair |

The last two lines are the same data. Every Java array is an object with a header of about 16 bytes, so a million tiny rows cost more than three times as much as two long rows. When you store pairs, prefer two parallel arrays or `int[2][n]` to `int[n][2]`.

To budget memory, multiply cells by bytes before you allocate. A `long[5000][5000]` DP table is 2 · 10⁸ bytes, about 200 MB, too much for a typical 256 MB judge limit once the JVM's own memory is added; `long[2 · 10⁵][2]` as two arrays is 3.2 MB.

### The call stack

Recursion depth is the third budget. On this machine the default stack held about 24,700 nested calls of a method with one `int` parameter and about 11,400 of a method with three, but only about 9,800 and 7,400 when the same methods ran interpreted, before the JIT compiled them. A tree with 10⁵ nodes in a chain needs 10⁵ nested calls. Plan for iterative traversals (Chapter 15) whenever depth can exceed a few thousand.

:::example{#ex-16-budget} Budgeting before coding
A statement has *n* ≤ 2 · 10⁵ and values up to 10⁹, and your idea sorts the values and then does a binary search for each one. Sorting is about *n* log *n* ≈ 3.5 · 10⁶ comparisons and the searches the same again: well under a second, even at the slow end of the budget. Values up to 10⁹ do not fit an array index, but sorting does not need one. If instead your idea is "for every pair", that is (2 · 10⁵)² = 4 · 10¹⁰ steps, more than a hundred seconds: write it only as the brute force for the stress test. If the idea needs a `HashMap<Integer, Integer>` with one entry per element, the map costs about 2 · 10⁵ × 77 bytes ≈ 15 MB, which is fine.
:::

## Choosing types and checking modular arithmetic {#sec-16-types}

[[Integer overflow]] in Java is silent: `int` and `long` arithmetic wraps around without an exception. A correct idea with a wrong type fails on the large tests only, which is the worst way to fail, because the samples pass.

Table: {#tbl-16-types} Bounds to remember
| Quantity | Bound | Type |
|---|---|---|
| `Integer.MAX_VALUE` | 2,147,483,647 ≈ 2.1 · 10⁹ | |
| `Long.MAX_VALUE` | 9,223,372,036,854,775,807 ≈ 9.2 · 10¹⁸ | |
| a sum of 10⁵ values up to 10⁹ | 10¹⁴ | `long` |
| a product of two values up to 10⁹ | 10¹⁸ | `long`, just |
| a product of two residues below 10⁹ + 7 | about 1.0 · 10¹⁸ | `long`; reduce before the next multiplication |
| a product of three values up to 10⁶ | 10¹⁸ | `long`, just |

:::pitfall
`(long) (a * b)` multiplies in `int` first and converts the already wrong result. For *a* = *b* = 100000 it gives 1,410,065,408; `(long) a * b` converts first and gives 10,000,000,000. The cast must touch an operand, not the result.
:::

### Modular arithmetic, checked

When the answer is "modulo *m*", reduce after **every** addition and multiplication, so every intermediate value stays below *m* and every product of two of them below *m*². Subtraction needs care because Java's `%` keeps the sign of the left operand: `-7 % 3` is −1, while `Math.floorMod(-7, 3)` is 2. Division is multiplication by an inverse, which exists for every non-zero value only when *m* is prime (Chapter 10); for a composite modulus like 10000, avoid division altogether (Chapter 14 builds binomials with Pascal's rule for that reason).

Two cheap checks catch most mistakes while you test.

```java {#lst-16-checked} Let Java report overflow while you test
// Sum of a[i] * b[i]. The Exact methods throw ArithmeticException instead of wrapping around.
static long dotChecked(int[] a, int[] b) {
    long s = 0;
    for (int i = 0; i < a.length; i++)
        s = Math.addExact(s, Math.multiplyExact((long) a[i], (long) b[i]));
    return s;
}
```

`Math.addExact` and `Math.multiplyExact` behave like `+` and `*` but throw `ArithmeticException` on overflow. Two pairs of 10⁹ · 10⁹ give 2 · 10¹⁸, which fits; ten pairs of 2 · 10⁹ · 2 · 10⁹ throw "long overflow". Run your solution with them on the largest values once, then switch back if speed matters.

For modular formulas, compare with exact arithmetic on small inputs. `BigInteger` never overflows.

```java {#lst-16-modcheck} Checking modular arithmetic against exact arithmetic
// The product of all a[i] modulo m, computed two ways. On small random inputs, both must agree.
static long productMod(long[] a, long m) {
    long p = 1 % m;
    for (long x : a) p = p * Math.floorMod(x, m) % m;     // floorMod: x may be negative
    return p;
}

static boolean agreesWithBigInteger(long[] a, long m) {
    BigInteger exact = BigInteger.ONE;
    for (long x : a) exact = exact.multiply(BigInteger.valueOf(x));
    return exact.mod(BigInteger.valueOf(m)).longValue() == productMod(a, m);
}
```

On 5,000 random arrays with values between −10⁹ and 10⁹, the two agreed every time. The same check with `x % m` in place of `Math.floorMod(x, m)` disagreed on 2,532 of 5,000 arrays, every one of them containing a negative value. `BigInteger.mod` always returns a non-negative result, which is what the problem means by "modulo".

## Designing your own tests {#sec-16-tests}

The samples in a statement are chosen to explain the problem, not to break your code. Before submitting, run [[edge cases|edge case]]: small inputs that you designed to break it.

:::checklist Edge cases to try on every problem
- **The smallest input**: *n* = 1, an empty string, a graph with one vertex. Loops that assume two elements, and answers initialised to the wrong value, fail here.
- **All values equal.** Separates strict from non-strict comparisons (strict LIS is 1, non-decreasing LIS is *n*) and finds `<` written for `<=`.
- **Sorted and reverse-sorted.** Extreme cases for greedy choices, for monotonic stacks (nothing is popped, or everything is), and for subsequences.
- **Maximum values** at the maximum size. Finds overflow and time limits at once.
- **Negative values and zeros**, if allowed. Find `%` on negatives, sums that start at 0 instead of the first element, and sliding windows that assume positive values.
- **Duplicates.** Break `Arrays.binarySearch` on repeated keys, `TreeSet` (which drops duplicates) and "first occurrence" logic.
- **Disconnected or unreachable** parts, for graph problems: is the answer −1, 0 or something else?
:::

A small generator keeps these cases at hand.

```java {#lst-16-edge} Edge-case inputs to run before you submit
// A few small arrays that break wrong solutions surprisingly often. maxV = the largest allowed value.
static List<int[]> edgeCases(int n, int maxV) {
    List<int[]> out = new ArrayList<>();
    out.add(new int[]{maxV});                              // n = 1
    int[] equal = new int[n], up = new int[n], down = new int[n], big = new int[n], signs = new int[n];
    for (int i = 0; i < n; i++) {
        equal[i] = 7;                                      // all values equal
        up[i] = i + 1;                                     // sorted, strictly increasing
        down[i] = n - i;                                   // reverse-sorted
        big[i] = maxV;                                     // every value at the limit: overflow
        signs[i] = i % 2 == 0 ? -maxV : maxV;              // negatives, alternating signs
    }
    out.add(equal);
    out.add(up);
    out.add(down);
    out.add(big);
    out.add(signs);
    return out;
}
```

For *n* = 5 and *maxV* = 10⁹ it produces [10⁹], [7, 7, 7, 7, 7], [1, 2, 3, 4, 5], [5, 4, 3, 2, 1], five copies of 10⁹, and [−10⁹, 10⁹, −10⁹, 10⁹, −10⁹]. Run your solution on each, and work out the expected answer by hand or with the brute force. Then run the random stress test of Chapter 9 for the cases you did not think of. Edge cases and random tests complement each other: random inputs rarely contain *n* = 1 or all-equal arrays, and hand-made cases rarely contain the strange combination that breaks a greedy rule.

### The review, with a DP focus

The post-mortem takes about an hour, and its order matters.

1. **Score first.** Enter each problem's estimated share of tests and the weighted score.
2. **For each unsolved problem**, read the editorial, close it, and write the solution yourself. Reading is not solving; the solution you can retype from memory is the only one that will be there in December.
3. **Log the cause** of every failure in the error log: misread, wrong idea, overflow, off-by-one, time limit, input, edge case, stack overflow, or ran out of time. The workbook's post-mortem table has a column for it.
4. **For DP failures, find the broken step** of the recipe of Chapter 11: was the state wrong (it forgot something the transition needed, as in Chapter 13's "ends at *i*"), the transition incomplete, the base case wrong, the evaluation order wrong (Chapter 14's "by increasing length"), or the answer read from the wrong cell?
5. **Pick the weakest topic** and schedule two of its core problems for tomorrow.

:::tip
A mistake that appears twice in the error log deserves a rule written in the margin of your template. "Cast before multiplying" or "lower bound for strict, upper bound for non-decreasing" is cheaper to remember than to rediscover under exam pressure.
:::

## After the mock {#sec-16-after}

:::pitfall Read only after the mock
The key idea of each Mock 2 problem, for your review. Each was checked by a solution of my own against a brute force on 5,000 random small inputs.

**Codeforces 1367C (Social Distance).** Scan the tables from left to right and occupy a free table whenever no occupied table, original or newly placed, lies within distance *k* on either side. Precompute the position of the next original 1 to the right so that each check is O(1). Taking the leftmost possible table is safe by an exchange argument: any optimal placement can move its first new table left to the greedy one without creating a conflict. The whole scan is O(*n*) per test.

**Codeforces 1373D (Maximum Sum on Even Positions).** Reversing a subarray of odd length keeps every element on a position of the same parity, so it never helps. Reversing an even-length subarray swaps the elements of each adjacent pair inside it, so the gain is a sum of pair differences: a[2*j* + 1] − a[2*j*] for pairs that start at an even index, or a[2*j* − 1] − a[2*j*] for pairs that start at an odd one. The best gain is the maximum subarray sum (Kadane, allowing the empty choice) of either difference sequence. Add it to the original sum of even positions, and use `long`.

**Codeforces 1475G (Strange Beauty).** The kept elements must form a divisibility chain once sorted (Chapter 14), with equal values allowed. Count each value, and let dp[*v*] be the largest kept set whose maximum is *v*: dp[*v*] = cnt[*v*] + max dp[*d*] over the proper divisors *d* of *v*. Push from each *v* to its multiples in increasing order, which costs about 2.5 · 10⁶ steps for values up to 2 · 10⁵. The answer is *n* minus the largest dp value.
:::

## Summary

- Before coding, write the model: objects, question type (count, optimise, decide, construct) and limits. Redraw the sample as the model to check it.
- The largest *n* nearly fixes the complexity; values up to 10⁶ can be array indices, values up to 10⁹ cannot.
- The aggregate method bounds a loop's total work by charging it to events that happen a limited number of times: pointer moves, pushes and pops. Doubling an array makes appends O(1) amortised, with fewer than 2*n* copies for *n* appends.
- Budget with 10⁸ to 3 · 10⁸ simple operations per second, but remember that hash maps, boxing and random memory access each cost an order of magnitude more than plain arrays.
- Memory is cells times bytes plus object overhead: about 77 bytes per `HashMap<Integer, Integer>` entry and about 16 bytes for every array header. The default stack holds only thousands of frames.
- Use `long` for sums and products, cast before multiplying, reduce after every modular operation, and verify with `Math.multiplyExact` and `BigInteger` on small cases.
- Test *n* = 1, all-equal, sorted, reverse-sorted, maximum values, negatives and duplicates before submitting, then stress test against a brute force.
- Mock 2's checkpoint is Q1 and Q2 fully solved with a weighted score of at least 50.

## Review questions

1. Model this story: "A library has *n* ≤ 2 · 10⁵ books on a shelf, each with a thickness. A reader wants the longest run of adjacent books whose total thickness is at most *W*." Give the objects, the question type, the technique and the complexity.
2. A loop has an outer `for` over *i* = 0..*n* − 1 and an inner `while` that increments *j*, which is never reset. Why is the total work O(*n*) and not O(*n*²)?
3. In @lst-16-intlist, how many elements are copied in total for *n* = 17 appends? Check your answer against the proof of @thm-16-doubling.
4. Why would growing an array by a constant amount (say 1000 elements each time) not give O(1) amortised appends? Estimate the copies for *n* = 10⁶.
5. A solution stores 10⁶ pairs as `int[1000000][2]`. About how much memory does it use, and how would you cut it to a quarter?
6. Which of these overflow, with *a*, *b* of type `int` up to 10⁹: `long s = a + b;`, `long p = (long) a * b;`, `long q = a * b % 1_000_000_007;`?
7. Why does `BigInteger.mod` make a good reference for a modular computation, while `%` on `long` values does not?
8. Name the edge case from @sec-16-tests most likely to break each of: a strict LIS written with upper bound; a sum stored in `int`; a sliding window that assumes positive values.

:::answers
1. Objects: an array of thicknesses. Question: optimise (the longest run). Thicknesses are positive, so the window sum grows when the right end moves and shrinks when the left end moves: a sliding window (Chapter 3) in O(*n*), with the sum in `long` if thicknesses can be large.
2. Each `while` iteration increments *j*, which starts at 0, never decreases and is bounded by *n*. So the inner loop runs at most *n* times **in total** over all values of *i*, and the work is O(*n*) for the inner loop plus O(*n*) for the outer one (@thm-16-pointers).
3. Resizes happen at sizes 1, 2, 4, 8 and 16, copying 1 + 2 + 4 + 8 + 16 = 31 elements, which matches the program's count. The proof gives 2ᵏ⁺¹ − 1 with 2ᵏ = 16 < 17, that is 31 < 2 · 17 = 34.
4. Resizes then happen every 1000 appends, and the *i*-th resize copies about 1000*i* elements. For *n* = 10⁶ there are 1000 resizes copying about 1000 · (1 + 2 + ⋯ + 1000) ≈ 5 · 10⁸ elements in total, which is quadratic in *n* (about *n*²/2000), not linear.
5. About 29 bytes per row, so roughly 29 MB, because each of the 10⁶ rows is a separate array object with its own header. Two parallel `int[10⁶]` arrays, or `int[2][10⁶]`, use about 8 MB.
6. `a + b` is computed in `int`, but with both values at most 10⁹ the sum is at most 2 · 10⁹, just below `Integer.MAX_VALUE`, so it does not overflow; three such values would. `(long) a * b` is safe: at most 10¹⁸. `a * b % 1_000_000_007` overflows, because the product is computed in `int` before the remainder is taken.
7. `BigInteger` never overflows, so the exact value is right whatever the inputs, and its `mod` always returns a value in [0, *m*), the mathematical remainder. With `%` on `long`, intermediate products can wrap around and negative operands give negative remainders, so a wrong result can look plausible.
8. Strict LIS with upper bound: all values equal (it returns *n* instead of 1). A sum in `int`: maximum values at maximum size. A positive-only sliding window: negative values and zeros.
:::
