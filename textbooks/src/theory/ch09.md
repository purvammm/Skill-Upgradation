Today is the first full mock: three Codeforces problems in three hours, under the rules of the real assessment. The chapter prepares you for it and for what comes after it. It is short on new algorithms and long on method, because the habits it teaches decide how many marks your algorithms actually earn.

The central habit is to write the slow, obviously correct solution first. A brute force earns the marks of the small tests, it tells you whether your fast solution is right, and it often shows you the pattern that leads to the fast idea. Sections @sec-9-why to @sec-9-limits develop that habit: what to enumerate, how to compare a fast and a slow program automatically, and how to read the limits so that you know in advance which tests each version will pass. Sections @sec-9-protocol and @sec-9-errors are about the mock itself and the review afterwards. @sec-9-map collects the patterns of Chapters 1–8 into one table for revision, and @sec-9-after gives the key ideas of the three mock problems, to be read only once you have tried them.

## Why brute force first {#sec-9-why}

:::definition{#def-9-brute} Brute force
A [[brute force|brute force (complete search)]] solution tries every candidate answer allowed by the statement (every subarray, every subset, every order, every value) and keeps the best or counts the good ones. It is correct by construction, because it checks the definition directly, and slow, because the number of candidates grows quickly with the input size.
:::

On the Infosys paper, according to the plan's summary of the scoring, marks come from the test cases you pass, and partial solutions score. A problem's tests normally range from tiny to the full limits, so a correct brute force collects every test it can finish in time. The plan's walkthrough of the official sample paper makes the point concrete: for the Hard problem, trying every subsequence works up to *N* ≈ 20, and a correct program on those tests scores while a blank one does not. The exam-day rule in the plan says it in one sentence: a correct brute force scores more than a fast wrong solution.

A brute force has two more uses that matter as much as partial marks.

:::definition{#def-9-oracle} Test oracle
A [[test oracle]] is a program whose output on an input is trusted to be correct. A brute force is the usual oracle in algorithm work: slow, but simple enough to be right.
:::

* **It is an oracle.** When your fast solution passes the samples but fails a hidden test, the brute force is the only tool that can find the input it fails on. @sec-9-stress automates the search.
* **It is a thinking tool.** Running a brute force on many small inputs and printing the answers often shows the structure of the problem: an answer that only depends on the maximum, a pattern in powers of two, a greedy order that is always optimal. Several fast ideas in this book were first seen in a table of brute-force outputs.

:::infosys
The plan's target section quotes one detailed report: a candidate who solved three problems fully and passed 6 of 12 tests on a fourth was shortlisted for the SP L3 interview. Its advice is to plan for Q1 and Q2 fully correct plus real progress on Q3, and the marks reported for the three problems are 20, 30 and 50. Real progress on Q3 usually starts as a brute force.
:::

:::tip
Budget 5–10 minutes for the brute force of every problem, and write it *before* you start on the fast idea. If the fast idea works, the brute force has cost you ten minutes and bought you a test oracle. If it does not, the brute force is already submitted.
:::

## Complete search patterns {#sec-9-complete}

Almost every brute force is one of a few enumerations. Knowing their costs lets you say, before writing a line, which limits they will handle.

Table: {#tbl-9-enum} The standard enumerations and the sizes they fit (about 10⁸ simple steps per second)
| Enumerate | Candidates | Typical cost | Fits roughly |
|---|---|---|---|
| all pairs *i* < *j* | *n*(*n* − 1)/2 | O(*n*²) | *n* ≤ 10⁴ |
| all subarrays, with a running value | *n*(*n* + 1)/2 | O(*n*²) | *n* ≤ 10⁴ |
| all subarrays, recomputed from scratch | *n*(*n* + 1)/2 | O(*n*³) | *n* ≤ 500 |
| all triples | about *n*³/6 | O(*n*³) | *n* ≤ 500 |
| all subsets (bitmask) | 2ⁿ | O(2ⁿ · *n*) | *n* ≤ 20 |
| all orders (permutations) | *n*! | O(*n*! · *n*) | *n* ≤ 10 |
| every candidate answer *x* | *V* | O(*V* · check) | *V* · *n* ≤ 10⁸ |

The numbers in the last column come from counting: 20 · 2²⁰ = 20,971,520 steps, 10 · 10! = 36,288,000 and 500³ = 1.25 · 10⁸. One more element doubles a subset search and multiplies a permutation search by *n* + 1, which is why the limits are so sharp: 11 · 11! is already 439,084,800.

### Subsets by bitmask

Number the elements 0..*n* − 1. Every integer *mask* in 0..2ⁿ − 1 describes one subset: element *i* is in it exactly when bit *i* of *mask* is 1 (Chapter 8).

:::lemma{#lem-9-masks} Masks and subsets
The map from *mask* ∈ {0, …, 2ⁿ − 1} to the subset {*i* : bit *i* of *mask* is 1} is a bijection onto the subsets of {0, …, *n* − 1}. So the loop `for (int mask = 0; mask < (1 << n); mask++)` visits every subset exactly once.
:::

:::proof
Each subset *S* is the image of exactly one mask, Σ over *i* ∈ *S* of 2ⁱ, because every integer below 2ⁿ has exactly one binary representation with *n* digits.
:::

```java {#lst-9-subsets} Brute force over all subsets: the largest subset sum that does not exceed S
static long bestSubsetSum(int[] a, long S) {                 // O(2^n * n): n <= 20 or so
    int n = a.length;
    long best = 0;                                           // the empty subset
    for (int mask = 0; mask < (1 << n); mask++) {
        long sum = 0;
        for (int i = 0; i < n; i++) if ((mask & (1 << i)) != 0) sum += a[i];
        if (sum <= S) best = Math.max(best, sum);
    }
    return best;
}
```

`1 << n` is only safe for *n* ≤ 30, which is far beyond any feasible subset search anyway. The same loop counts subsets with a property, finds the best one, or tests every way to split the elements into two groups (bit *i* says which group element *i* joins).

### Permutations

Java has no `next_permutation`, so it is worth having one that you trust. It rearranges the array into the next arrangement in lexicographic order (Chapter 7), and reports when there is none.

```java {#lst-9-nextperm} The next permutation in lexicographic order
static boolean nextPermutation(int[] a) {          // false (and a sorted again) after the last one
    int i = a.length - 2;
    while (i >= 0 && a[i] >= a[i + 1]) i--;        // a[i+1..] is the longest non-increasing suffix
    if (i < 0) {
        reverse(a, 0);
        return false;
    }
    int j = a.length - 1;
    while (a[j] <= a[i]) j--;                      // the rightmost element larger than a[i]
    int t = a[i];
    a[i] = a[j];
    a[j] = t;
    reverse(a, i + 1);                             // the suffix becomes its smallest arrangement
    return true;
}

static void reverse(int[] a, int from) {
    for (int l = from, r = a.length - 1; l < r; l++, r--) {
        int t = a[l];
        a[l] = a[r];
        a[r] = t;
    }
}
```

:::lemma{#lem-9-nextperm} Correctness of the next permutation
If *a* is not the largest arrangement of its elements, @lst-9-nextperm turns it into the smallest arrangement that is lexicographically larger than *a*.
:::

:::proof
The suffix *a*[*i* + 1..] is non-increasing, so it is already the largest arrangement of its elements, and no larger arrangement keeps *a*[0..*i*] unchanged. Every larger arrangement that keeps *a*[0..*i* − 1] must put at position *i* an element of the suffix that is larger than *a*[*i*]; the smallest such arrangement puts there the *smallest* element of the suffix larger than *a*[*i*], and then the remaining elements in non-decreasing order. Because the suffix is non-increasing, the rightmost element larger than *a*[*i*] is the smallest such element (the rightmost of its equal copies). After the swap the suffix is still non-increasing, so reversing it makes it non-decreasing. Any arrangement that changes a position before *i* to a larger value is larger still, so the result is the next one.
:::

Start from the sorted array and loop `do { ... } while (nextPermutation(a));` to visit every distinct arrangement exactly once, in increasing order. With repeated values this visits fewer than *n*! arrangements, which is usually what you want. For the array [1, 2, 2] it visits [1, 2, 2], [2, 1, 2] and [2, 2, 1].

Recursion is the other way, and it is easier to adapt when the order is built step by step and some steps are not allowed. The next listing is the brute force for one of the plan's Infosys repeat problems: you start with experience *e*, monster *i* can be beaten when *e* ≥ power[*i*] and then adds bonus[*i*], a lost fight ends the run, and you want the largest number of monsters beaten in some order.

```java {#lst-9-orders} Brute force over all orders, by recursion with undo
static int bestFights(long e, int[] power, int[] bonus, boolean[] used) {   // O(n! * n): n <= 9 or so
    int best = 0;
    for (int i = 0; i < power.length; i++) {
        if (used[i] || e < power[i]) continue;          // already beaten, or this fight would be lost
        used[i] = true;
        best = Math.max(best, 1 + bestFights(e + bonus[i], power, bonus, used));
        used[i] = false;                                // undo the choice before trying the next one
    }
    return best;
}
```

It never starts a fight it would lose, because a lost fight ends the run and adds nothing. Comparing this with the fast greedy of the repeat card (sort by power, fight while you can) on random small inputs is exactly the stress test of the next section, and the two agree when the bonuses are non-negative.

### Trying every answer

The brute force for a "search on the answer" problem (Chapter 6) tries the candidates one by one with the same check: *x* = *lo*, *lo* + 1, … until ok(*x*) is true. It is O(*V* · *C*) instead of O(*C* log *V*), but it shares the check with the fast version, so it tests the search and the bounds, not the check. When the check is the doubtful part, the oracle must avoid it: enumerate the schedules, partitions or placements directly.

## Stress testing {#sec-9-stress}

:::definition{#def-9-stress} Stress testing
[[Stress testing]] runs a fast solution and a brute force on many random small inputs and stops at the first input where their answers differ. That input is a counterexample: since the brute force is trusted, the fast solution is wrong on it.
:::

A stress tester has four parts: a **generator** of random small inputs, the **brute force**, the **fast solution**, and a **loop** that compares them and prints the first input where they disagree. The handbook template is a complete program with all four. Its example pair is the maximum subarray sum: Kadane's O(*n*) scan against an O(*n*²) loop over all subarrays.

```java {#lst-9-stress} Stress tester: fast solve() against brute() on 100,000 tiny random inputs (handbook template)
import java.util.*;

/** Compare a fast solve() with an obviously-correct brute() on thousands of tiny random inputs. */
public class Stress {
    public static void main(String[] args) {
        Random rnd = new Random(1);
        for (int iter = 1; iter <= 100000; iter++) {
            int n = 1 + rnd.nextInt(8);                    // tiny inputs expose bugs fastest
            int[] a = new int[n];
            for (int i = 0; i < n; i++) a[i] = rnd.nextInt(21) - 10;
            long fast = solve(a), slow = brute(a);
            if (fast != slow) {
                System.out.println("Mismatch on iteration " + iter + ": " + Arrays.toString(a));
                System.out.println("fast=" + fast + "  brute=" + slow);
                return;                                     // smallest failing case is now on screen
            }
        }
        System.out.println("All random tests passed");
    }

    // Example: maximum subarray sum. Replace both methods with your problem.
    static long solve(int[] a) {                           // Kadane, O(n)
        long best = Long.MIN_VALUE, cur = 0;
        for (int x : a) { cur = Math.max(x, cur + x); best = Math.max(best, cur); }
        return best;
    }

    static long brute(int[] a) {                           // every subarray, O(n^2)
        long best = Long.MIN_VALUE;
        for (int l = 0; l < a.length; l++) {
            long s = 0;
            for (int r = l; r < a.length; r++) { s += a[r]; best = Math.max(best, s); }
        }
        return best;
    }
}
```

The fixed seed `new Random(1)` makes every run produce the same inputs, so a failure can be reproduced after you change the code. The comparison is with the brute force, never with what you *expect* the answer to be.

:::example{#ex-9-kadane} A stress test finds an edge-case bug
Change one token of `solve`: initialise `best` to 0 instead of `Long.MIN_VALUE`. The samples of a typical problem still pass, because they contain a positive element. The stress tester prints:

```trace
Mismatch on iteration 11: [-4]
fast=0  brute=-4
```

An array whose elements are all negative has a negative maximum, but the buggy version never goes below its starting value 0. The input is a single number, so the cause is visible at once.
:::

### Shrinking a failing input

Often the first failing input is longer than it needs to be. A smaller one is easier to trace by hand, so it pays to shrink it automatically: try small changes (delete an element, delete two neighbours, move a value towards 0) and keep any change after which the two programs still disagree. Repeat until no change keeps the failure.

```java {#lst-9-shrink} Shrinking a failing input while fast and slow still disagree
static int[] shrink(int[] a, ToLongFunction<int[]> fast, ToLongFunction<int[]> slow) {
    boolean changed = true;
    while (changed) {
        changed = false;
        for (int len = 1; len <= 2 && !changed; len++) {
            for (int i = 0; i + len <= a.length && !changed; i++) {     // try deleting a[i..i+len-1]
                int[] b = new int[a.length - len];
                for (int j = 0, k = 0; j < a.length; j++) if (j < i || j >= i + len) b[k++] = a[j];
                if (b.length > 0 && fast.applyAsLong(b) != slow.applyAsLong(b)) { a = b; changed = true; }
            }
        }
        for (int i = 0; i < a.length && !changed; i++) {                // try moving a[i] towards 0
            int[] b = a.clone();
            b[i] = a[i] / 2;
            if (b[i] != a[i] && fast.applyAsLong(b) != slow.applyAsLong(b)) { a = b; changed = true; }
        }
    }
    return a;
}
```

Call it from the stress loop as `shrink(a, Stress::solve, Stress::brute)` once a mismatch is found.

:::lemma{#lem-9-shrink} The shrinker stops, and its result still fails
@lst-9-shrink terminates, returns an input on which `fast` and `slow` disagree, and no single deletion of one or two neighbouring elements and no single halving of one value of the result keeps the disagreement.
:::

:::proof
Each accepted change either shortens the array or replaces some value *v* by *v*/2 (rounded toward zero) with |*v*/2| < |*v*|, so the pair (length, Σ |values|) decreases in the lexicographic sense and cannot decrease for ever. A change is accepted only if the programs still disagree, so the result disagrees. The loop ends only after a full round in which no change was accepted, which is the last claim.
:::

The result is *locally* minimal, not necessarily the smallest failing input, but in practice it is small enough to trace by hand.

:::example{#ex-9-shrink} Shrinking a wrong idea
The maximum sum of non-adjacent elements (all values ≥ 0) has a tempting wrong solution: take the better of "all even positions" and "all odd positions". A stress test with values 0..9 fails at once, and the shrinker reduces the input:

```trace
Mismatch on iteration 1: [8, 7, 3, 4, 4, 4]
fast=15  brute=16
shrunk to [1, 0, 0, 1]   fast=1  brute=2
```

On [1, 0, 0, 1] the right answer takes both ends, positions 0 and 3, which have different parities. That one line shows why the idea is wrong, which the six-element input hid.
:::

### Rules that make stress tests work

* **Tiny inputs.** *n* ≤ 8 and values in −10..10 find almost every bug, run the brute force instantly, and give counterexamples you can check on paper.
* **Generate what the statement allows, and nothing else.** If values are positive, generate positive values; if the array is a permutation, generate a permutation. A "failure" on an illegal input wastes time.
* **Add special generators.** Some bugs need a structure that random inputs rarely produce: all values equal, a sorted array, *n* = 1, the largest value. Run each for a few thousand iterations too.
* **Compare outputs that are unique.** If several answers are correct (any optimal subset, any valid order), compare the *value* of the answer, or write a checker that verifies the fast output.

### Using it without a judge

The plan's Infosys repeat problems have no online judge, and the plan's advice for them is to run the samples in OneCompiler and then stress-test against a brute force. The template needs no input, so paste it, replace `solve` and `brute` with your two methods and the generator with one that matches the statement, and run it. Java requires a public class to live in a file of the same name, so if the online editor's file is called `Main.java`, rename `Stress` to `Main`.

### Reading Codeforces verdicts

Codeforces has no partial marks, but the plan uses its verdict to estimate the share of tests you would pass on a test-case-scored paper. The tests are run in order and judging stops at the first failure, so "Wrong answer on test 7" means tests 1–6 passed, and the samples are normally the first test. "Time limit exceeded on test *k*" is the most informative verdict for a brute force: the small tests passed and the first large one did not. Two habits make the estimate honest. Record the first failing test number on the score sheet, and after the mock run your stress tester on the problem: a bug that only appears on special inputs (all equal, *n* = 1) would cost a few tests, while one that appears on most random inputs would cost most of them.

## Estimating complexity from the limits {#sec-9-limits}

The limits in a statement are a hint about the intended solution. Java performs very roughly 10⁸ simple operations per second, so the largest *n* tells you which complexities fit in a 1–2 second limit.

Table: {#tbl-9-limits} From the largest n to a target complexity (the full version is Theory Appendix A)
| Largest *n* | Target complexity | Steps at the limit | Typical technique |
|---|---|---|---|
| ≤ 10 | O(*n*! · *n*) | 10 · 10! ≈ 3.6 · 10⁷ | all orders |
| ≤ 20 | O(2ⁿ · *n*) | 20 · 2²⁰ ≈ 2.1 · 10⁷ | all subsets, bitmask DP |
| ≤ 500 | O(*n*³) | 1.25 · 10⁸ | triple loops, interval DP |
| ≤ 5,000 | O(*n*²) | 2.5 · 10⁷ | all pairs, 2-D DP |
| ≤ 10⁵ to 2 · 10⁵ | O(*n* log *n*) or O(*n* √*n*) | 1.7 · 10⁶ to 3.2 · 10⁷ | sorting, heaps, binary search, segment trees |
| ≤ 10⁶ | O(*n*) or O(*n* log *n*) | 10⁶ to 2 · 10⁷ | prefix sums, two pointers, stacks |
| ≥ 10⁹ (a value, not a length) | O(log *n*) or O(√*n*) | 30 or 3 · 10⁴ | binary search, number theory |

Read the table both ways. Before you code, it tells you which idea the setter expects. During the mock, it tells you which tests your brute force will pass: an O(*n*²) brute force on a problem with *n* ≤ 2 · 10⁵ passes every test with *n* up to a few thousand.

:::pitfall
Many Codeforces problems have *t* test cases with a bound on the *sum* of *n* over all of them (for example *t* ≤ 10⁴ and Σ *n* ≤ 2 · 10⁵). The work must be proportional to that sum. Resetting a global array of size 2 · 10⁵ with `Arrays.fill` in every test case costs 10⁴ × 2 · 10⁵ = 2 · 10⁹ writes, a time-limit failure even though each test case is small. Allocate or clear only the first *n* entries of each test case.
:::

Memory has a budget too. Count the cells and multiply by their size: an `int[]` of 10⁷ entries takes 40 MB, a `long[5000][5000]` takes 200 MB, and the trie layouts of Chapter 8 differ by a factor of two for the same nodes. A `HashMap` costs several times its entries in object overhead (Chapter 2).

## The mock protocol {#sec-9-protocol}

A mock is only a measurement if it is taken under the same conditions every time. The plan fixes the rules for all five mocks.

:::checklist Mock rules
* Timer at 180 minutes, one sitting, phone in another room.
* Minutes 0–15: read every problem. On paper, write the limits, your idea and its complexity for each.
* Solve the problem you are surest of first. That is not always Q1.
* Test on the samples with Codeforces Custom test before you submit.
* By minute 150, every problem has a submission, even if it is only a brute force.
:::

The plan's exam-day schedule divides the 180 minutes the same way, and the mock is the place to practise it.

Table: {#tbl-9-minutes} The 180 minutes, from the plan's exam-day page
| Minutes | Do |
|---|---|
| 0–15 | Read every problem with its limits and samples. Write the idea, its complexity and the brute-force fallback for each, and rank them by how sure you are. |
| 15–60 | Solve the surest problem fully. Run the samples and two edge cases you write yourself (*n* = 1, all values equal, largest values). Submit. |
| 60–120 | The second problem, same routine. Still stuck at minute 100? Submit a brute force and move on. |
| 120–165 | The hard problem. No full idea after 15 minutes: write the brute force for small limits, collect those marks, then try to optimise. |
| 165–180 | Make sure every problem has a submission that compiles. Do not touch code that already passes. |

### Grading yourself

For each problem, estimate the share of tests your best submission would pass (1 for an accepted solution, an estimate from the verdict otherwise, 0 for nothing). The weighted score is

  score = 20 · share(Q1) + 30 · share(Q2) + 50 · share(Q3).

For example, Q1 accepted, Q2 failing on about half of its tests and a brute force for Q3 that passes roughly a fifth gives 20 + 15 + 10 = 45.

:::infosys
The plan's checkpoint for Mock 1, its own estimate rather than an Infosys figure, is Q1 fully solved and Q2 at least half the tests. If you are below it, the plan says to skip the bonus problems in week 2 and redo the core problems of your weakest day.
:::

After the mock the plan allows about 60 minutes: enter the scores, read the editorial of every unsolved problem, close it and write the solution yourself, log the cause of each failure, and pick the weakest topic to redo two of its core problems the next day.

## The post-mortem and an error taxonomy {#sec-9-errors}

A mistake you cannot name is a mistake you will repeat. The plan's error log classifies every failure into one of nine causes, and each entry gets a **rule**, a sentence that would have prevented it. The examples below are small Java fragments that compile and contain the error.

**Misread statement.** The code solves a different problem from the one asked. The most common forms are 0-based versus 1-based output, "subsequence" read as "subarray", and "at most" read as "exactly".

```java {.fragment}
// The statement asks for the 1-based position of the maximum.
int[] a = {4, 9, 2};
int best = 0;
for (int i = 1; i < a.length; i++) if (a[i] > a[best]) best = i;
System.out.println(best);           // prints 1, expected 2: print best + 1
```

Rule: before coding, write the output format of the first sample next to your own trace of it.

**Wrong idea.** The algorithm is implemented correctly but the idea is false. Greedy choices are the usual suspects: for coins {1, 3, 4} and the amount 6, "always take the largest coin that fits" uses 4 + 1 + 1 (three coins) while 3 + 3 uses two.

```java {.fragment}
int[] coins = {4, 3, 1};            // largest first
int amount = 6, used = 0;
for (int c : coins) while (amount >= c) { amount -= c; used++; }
System.out.println(used);           // 3, but the optimum is 2
```

Rule: prove a greedy choice (an exchange argument, Chapter 4) or stress-test it before trusting it.

**Overflow / mod.** A product or sum exceeds `int` and wraps silently, or a modulus is taken too late.

```java {.fragment}
int x = 100000, y = 100000;
long bad = x * y;                   // 1410065408: the int product wrapped before widening
long good = (long) x * y;           // 10000000000
```

Rule: default to `long`; cast the first factor; reduce mod 10⁹ + 7 after every multiplication.

**Off-by-one.** A loop bound, an inclusive versus half-open range, or a binary search boundary is one step wrong (Chapter 6 lists four classic ones).

```java {.fragment}
int[] a = {3, 1, 2};
long sum = 0;
try {
    for (int i = 0; i <= a.length; i++) sum += a[i];      // i = 3 is out of bounds
} catch (ArrayIndexOutOfBoundsException e) {
    System.out.println("crash: use i < a.length");
}
```

Rule: write every range as half-open [*l*, *r*) unless the statement forces otherwise, and test *n* = 1.

**TLE / complexity.** The program is correct and too slow, either because the idea is too slow for the limits or because of a hidden cost such as per-test resets, `String` concatenation in a loop or `Scanner` on 10⁶ numbers.

```java {.fragment}
int t = 10000;                      // test cases, with the sum of n bounded by 2e5
int[] cnt = new int[200001];
for (int tc = 0; tc < t; tc++) {
    Arrays.fill(cnt, 0);            // 2e5 writes per test: 2e9 in total
    // ... the work for this test case uses only its own n entries ...
}
```

Rule: before submitting, multiply the cost of one test case by *t*, and clear only what you used.

**Input reading.** The program reads the input in the wrong order or format. The plan's walkthrough of the sample paper found one where the written format and the samples disagree, and only the samples' order was right. With `Scanner`, `nextLine()` right after `nextInt()` returns the empty rest of the line.

```java {.fragment}
Scanner sc = new Scanner("3\nabc def\n");
int k = sc.nextInt();
String line = sc.nextLine();        // "" : the rest of the first line, not "abc def"
```

Rule: check your reading code against every sample before writing the logic; use FastScanner (Chapter 1).

**Edge case.** The idea is right for typical inputs and wrong for a special one: *n* = 1, all values equal, all negative, an empty answer, the largest values. @ex-9-kadane is this kind.

```java {.fragment}
int[] a = {-4};
long best = 0, cur = 0;             // should start at Long.MIN_VALUE
for (int v : a) { cur = Math.max(v, cur + v); best = Math.max(best, cur); }
System.out.println(best);           // 0, but the answer is -4
```

Rule: for every problem, test *n* = 1, all equal and the extreme values before submitting.

**Stack overflow.** Recursion deeper than the call stack allows, typically a DFS on a tree that is a long chain. On the sandbox's JVM with default settings, a simple recursive method overflowed at a depth of about 28,000, and `depthRec` below failed on a chain of 10⁵ nodes while `depthLoop` returned 99,999.

```java {#lst-9-depth} Recursion versus a loop on a long chain
static int depthRec(int[] next, int v) {         // depth of the recursion = length of the chain
    return next[v] == -1 ? 0 : 1 + depthRec(next, next[v]);
}

static int depthLoop(int[] next, int v) {        // the same walk with a loop: no call stack needed
    int d = 0;
    for (; next[v] != -1; v = next[v]) d++;
    return d;
}
```

Rule: if a recursion can be deeper than about 10⁴, rewrite it with an explicit stack or a BFS order (Chapter 18), or run it on a thread with a large stack.

**Ran out of time.** A problem has no submission at the end. This is a process error, not a coding error.

Rule: by minute 150 every problem has a submission, even a brute force; stop debugging Q2 at minute 100.

:::keyidea
The rule matters more than the label. "Be careful with overflow" is not a rule; "cast the first factor of every product of two ints to long" is. A good rule is specific enough that you could check your code against it in ten seconds.
:::

## After the mock {#sec-9-after}

:::pitfall Read only after the mock
This section gives the key idea of each Mock 1 problem. Reading it before the mock wastes the measurement. Take the mock first, grade it, write your own post-mortem, and only then compare.
:::

Each idea below was checked with my own solution, which passes the problem's samples and agrees with a brute force on 20,000 random small inputs per problem. Write and test your own version before you compare it with an editorial.

**CF 1343C (Alternating Subsequence).** Cut the sequence into maximal blocks of equal sign. A longest alternating subsequence takes exactly one element from every block, since two elements from one block cannot be neighbours and skipping a block shortens the result. To maximise the sum, take the largest element of each block. One pass in O(*n*); the sum needs `long`.

**CF 1475D (Cleaning the Phone).** Split the applications by their convenience points (1 or 2) and sort each group by memory, largest first; for a fixed number of applications from each group, taking the largest ones is best. For each count *j* of 2-point applications, the fewest 1-point applications that free enough memory is found from prefix sums, either by binary search (Chapter 6) or with a pointer that only moves left as *j* grows. The answer is the minimum of *i* + 2*j*, or −1 if all the memory together is not enough.

**CF 1251D (Salary Changing).** Search on the answer (Chapter 6): can the median be at least *M*? Everyone is paid at least their lower bound; at least (*n* + 1)/2 employees must earn ≥ *M*; employees whose upper bound is below *M* cannot help, and among the others the cheapest to raise are those with the largest lower bounds, so take them greedily. The check is monotone because a lower target never costs more, so the largest feasible *M* is found by binary search with the midpoint rounded up.

## Summary

- Marks come from passed tests, so a correct brute force is worth real marks; write it first, in 5–10 minutes, for every problem.
- The standard enumerations and their limits: pairs and subarrays O(*n*²) for *n* ≤ 10⁴, subsets O(2ⁿ · *n*) for *n* ≤ 20, orders O(*n*! · *n*) for *n* ≤ 10.
- A bitmask from 0 to 2ⁿ − 1 visits every subset once; `nextPermutation` from the sorted array visits every distinct order once.
- A stress tester compares the fast solution with the brute force on tiny random inputs with a fixed seed and prints the first counterexample; a shrinker reduces it to a locally minimal one.
- The largest *n* in the limits points to the intended complexity; with multiple test cases, the bound on the sum of *n* is what the work must respect.
- Take every mock under the same rules: read everything first, solve the surest problem first, a submission for every problem by minute 150.
- Grade by weighted share of tests, and log each failure under one of nine causes with a specific rule that would have prevented it.
- Revise Part I by signals: the phrases and limits that point to each pattern.

## Review questions

1. Why is a correct O(*n*²) solution worth writing for a problem with *n* ≤ 2 · 10⁵? Which tests can it pass?
2. A problem has *n* ≤ 18. Which enumeration fits, and roughly how many steps does it take?
3. Why must a stress tester compare with a brute force rather than with answers you work out yourself?
4. In @lst-9-nextperm, why does the method look for the *rightmost* element larger than *a*[*i*]? What would go wrong with the leftmost one?
5. Why does @lst-9-shrink keep only changes after which the two programs still disagree? Could it ever return an input on which they agree?
6. A Codeforces submission gets "Wrong answer on test 3" and another gets "Time limit exceeded on test 12". Which do you expect to score more on a test-case-scored paper, and why can you not be sure?
7. A problem has *t* ≤ 10⁴ test cases and Σ *n* ≤ 2 · 10⁵. Your solution is O(*n* log *n*) per test case but allocates `new int[200001]` in each. Is it fast enough? What about clearing a global array with `Arrays.fill` each time?
8. Classify each bug: (a) `int` sum of 10⁵ values up to 10⁹; (b) printing indices from 0 when the statement counts from 1; (c) a greedy that sorts by the wrong key; (d) a recursive DFS on a 10⁵-node path.
9. Write the weighted score of a mock with Q1 accepted, Q2 passing about 30 % of its tests and nothing for Q3. Is it on track by the Mock 1 checkpoint?

:::answers
1. Tests are scored one by one, and most problems include small tests. An O(*n*²) solution finishes any test with *n* up to a few thousand (*n* = 5,000 is 2.5 · 10⁷ steps) within the time limit, so it earns those marks, and it is the oracle for the fast solution.
2. All subsets by bitmask: 2¹⁸ · 18 ≈ 4.7 · 10⁶ steps, well inside the limit.
3. Your hand-worked answers come from the same understanding that produced the bug, so they share its mistakes, and there are too few of them. The brute force checks the definition directly and can answer thousands of random inputs.
4. The suffix *a*[*i* + 1..] is non-increasing, so the rightmost element larger than *a*[*i*] is the smallest such element. Swapping with a larger one (for example the leftmost) would give a valid but not the *next* permutation, and the suffix after the swap might not be non-increasing, so reversing it would not give its smallest arrangement.
5. The aim is a smaller input that still shows the bug; a change that makes the programs agree has removed the bug from the input. No: it starts from a disagreeing input and accepts only disagreeing changes (@lem-9-shrink).
6. Probably the TLE on test 12: eleven tests passed, and a time-limit failure usually means the remaining tests are the large ones. You cannot be sure because tests are not equal in number or difficulty across problems, and a wrong answer on test 3 could be a small bug that fails only a few later tests too; the stress tester tells you which.
7. Allocating 2 · 10⁵ ints 10⁴ times is 2 · 10⁹ cells of zeroing plus garbage, far too slow; so is `Arrays.fill` of the whole array each time (2 · 10⁹ writes). Allocate or clear only *n* + 1 entries per test case, which totals O(Σ *n*).
8. (a) overflow / mod; (b) misread statement (output format); (c) wrong idea; (d) stack overflow.
9. 20 · 1 + 30 · 0.3 + 50 · 0 = 29. Below the checkpoint, which asks for Q2 at least half the tests; the plan's response is to skip week 2's bonus problems and redo the core problems of your weakest day.
:::
