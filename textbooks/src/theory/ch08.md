XOR problems look like puzzles until you see that they are arithmetic in disguise. The exclusive-or of two numbers adds their bits without carries, so every bit position behaves independently of the others, and every number is its own inverse. Those two facts turn "sum of XORs over all pairs" into 31 small counting problems, "subarray with XOR *k*" into the prefix-count scan of Chapter 2, "pair with the largest XOR" into a walk down a tree of bits, and "subset with the largest XOR" into Gaussian elimination.

The Infosys question bank leans on these ideas: two of its most reported repeat problems are about XOR, and so is the Hard problem of the official sample paper. This chapter builds the toolkit from the bottom. It starts with how Java stores and shifts bits, proves the algebra of XOR, uses bit independence for sums, and then develops two data structures, the binary trie for questions about *pairs* and the linear basis for questions about *subsets*.

## Binary representation and Java's bit operators {#sec-8-repr}

A non-negative integer *x* is written in binary as bits *x*<sub>*B*−1</sub> … *x*₁ *x*₀ with *x* = Σ *x*<sub>*b*</sub> · 2ᵇ. Bit *b* is "set" when *x*<sub>*b*</sub> = 1. Java's `int` has 32 bits and `long` has 64, and both are signed.

:::definition{#def-8-twos} Two's complement
In [[two's complement]] with *w* bits, the bit pattern *b*<sub>*w*−1</sub> … *b*₀ stands for −*b*<sub>*w*−1</sub> · 2<sup>*w*−1</sup> + Σ<sub>*i* < *w*−1</sub> *b*ᵢ · 2ⁱ. The top bit is the sign bit, with weight −2<sup>*w*−1</sup>.
:::

Three facts follow and all of them matter in practice:

* −*x* = ~*x* + 1, where ~*x* flips every bit. For example ~12 = −13, so −12 = ~12 + 1.
* −1 is all ones: `Integer.toBinaryString(-13)` is `11111111111111111111111111110011`, 32 characters.
* The range is asymmetric: `Integer.MIN_VALUE` = −2³¹ has no positive partner, so `-Integer.MIN_VALUE` and `Math.abs(Integer.MIN_VALUE)` both return −2147483648.

### The operators

Table: {#tbl-8-ops} Java's bit operators, with a = 12 (binary 1100) and b = 10 (binary 1010)
| Expression | Meaning | Value |
|---|---|---|
| `a & b` | AND: 1 where both have 1 | 8 (1000) |
| `a | b` | OR: 1 where either has 1 | 14 (1110) |
| `a ^ b` | XOR: 1 where exactly one has 1 | 6 (0110) |
| `~a` | NOT: flip every bit | −13 |
| `a << 2` | shift left, fill with 0 (multiply by 4) | 48 |
| `a >> 2` | shift right, copy the sign bit (floor-divide by 4) | 3 |
| `-16 >> 2` | arithmetic shift keeps the sign | −4 |
| `-16 >>> 2` | logical shift fills with 0 | 1073741820 |

Two shift rules catch people out. First, `>>` copies the sign bit, so it divides negative numbers by powers of two rounding *down*, while `>>>` treats the bits as unsigned. Second, Java uses only the low 5 bits of the shift distance for an `int` (the low 6 for a `long`). So `1 << 31` is −2147483648 (the sign bit), `1 << 32` is 1 (the shift distance 32 becomes 0) and `1 << 33` is 2. To build 2ᵏ for *k* ≥ 31, write `1L << k`, which is correct up to *k* = 62 (`1L << 63` is `Long.MIN_VALUE`).

:::pitfall
Precedence. Shifts bind more loosely than `+` and `-`, so `1 << k + 1` means `1 << (k + 1)` (8 for *k* = 2, not 5), and `x >> 1 + 1` means `x >> 2`. The bitwise operators `&`, `^`, `|` bind more loosely than `==`, so `a & b == 0` means `a & (b == 0)`; for `int` operands Java rejects this with "bad operand types for binary operator '&'", which at least stops the bug at compile time. Write brackets around every bit expression: `((x >> b) & 1) == 1`.
:::

### Library methods and standard tricks

| Call | Returns | For 12 |

| `Integer.bitCount(x)` | number of set bits | 2 |
| `Integer.highestOneBit(x)` | the *value* 2ᵏ of the top set bit (0 for 0) | 8 |
| `Integer.lowestOneBit(x)` | the value of the lowest set bit, same as `x & -x` | 4 |
| `Integer.numberOfTrailingZeros(x)` | index of the lowest set bit (32 for 0) | 2 |
| `Integer.numberOfLeadingZeros(x)` | zeros above the top set bit (32 for 0) | 28 |

| `Integer.parseInt(s, 2)` | read a binary string | 12 for "1100" |

`highestOneBit` returns a power of two, not an index; that confusion is a common bug. Two expressions are worth knowing by heart. `x & -x` keeps only the lowest set bit, because −*x* = ~*x* + 1 flips every bit above the lowest 1 and keeps that 1. `x & (x - 1)` clears the lowest set bit, because subtracting 1 turns the lowest 1 into 0 and the zeros below it into ones. Hence *x* > 0 is a power of two exactly when `(x & (x - 1)) == 0`.

```java {#lst-8-bits} Bit-level building blocks (handbook template)
// Bit b of x:      ((x >> b) & 1) == 1
// Set / clear / flip bit b:  x | (1 << b),  x & ~(1 << b),  x ^ (1 << b)
// Lowest set bit:  x & -x          Number of 1 bits:  Integer.bitCount(x)
// Highest set bit: 31 - Integer.numberOfLeadingZeros(x)   (x > 0)
// Use 1L << b when b can be 31 or more.
static boolean bitIsSet(int x, int b) {
    return ((x >> b) & 1) == 1;
}
```

A set of up to 31 small elements fits in one `int` as a bitmask: bit *i* says whether element *i* is in the set. Union is `|`, intersection is `&`, and `for (int m = 0; m < (1 << n); m++)` visits every subset of an *n*-element set. Chapter 9 uses this for brute force and Chapter 22 for bitmask DP.

## The algebra of XOR {#sec-8-xor}

:::definition{#def-8-xor} Exclusive or
The [[XOR|exclusive or (XOR)]] of two bits is 1 when exactly one of them is 1. For integers, *a* ⊕ *b* (Java `a ^ b`) applies this to every bit position separately. Bit by bit, XOR is addition modulo 2: 0 ⊕ 0 = 0, 0 ⊕ 1 = 1 ⊕ 0 = 1, 1 ⊕ 1 = 0.
:::

:::theorem{#thm-8-laws} Laws of XOR
For all integers *a*, *b*, *c*: (1) *a* ⊕ 0 = *a*; (2) *a* ⊕ *a* = 0; (3) *a* ⊕ *b* = *b* ⊕ *a*; (4) (*a* ⊕ *b*) ⊕ *c* = *a* ⊕ (*b* ⊕ *c*); (5) *a* ⊕ *b* = *c* if and only if *a* = *b* ⊕ *c*.
:::

:::proof
XOR acts on each bit position independently, so it suffices to check the laws for single bits, where ⊕ is addition modulo 2. Addition modulo 2 has 0 as identity (1), satisfies *x* + *x* = 2*x* ≡ 0 (2), and is commutative (3) and associative (4) because ordinary addition is. For (5), XOR both sides of *a* ⊕ *b* = *c* with *b*: by (4), (2) and (1) the left side becomes *a*, the right side *c* ⊕ *b* = *b* ⊕ *c*. The converse is the same step backwards.
:::

Because of (3) and (4), the XOR of a list does not depend on the order or the grouping of its elements, and by (2) equal elements cancel in pairs.

:::claim{#thm-8-odd} Pairs cancel
The XOR of a list of numbers equals the XOR of the distinct values that occur an odd number of times in it.
:::

:::proof
Reorder the list so that equal values are adjacent; by (3) and (4) the result does not change. Each value occurring *m* times contributes *v* ⊕ *v* ⊕ ⋯ (*m* copies), which is 0 when *m* is even and *v* when *m* is odd, by (2) and (1).
:::

LeetCode 136 (Single Number) is the special case where every value appears twice except one: the XOR of the whole array is the single value, in O(*n*) time and O(1) memory. For [7, 3, 5, 3, 7] it is 5.

### Prefix XOR

:::definition{#def-8-prefix} Prefix XOR
The [[prefix XOR]] array of *a*[0..*n* − 1] is *X*[0..*n*] with *X*[0] = 0 and *X*[*i* + 1] = *X*[*i*] ⊕ *a*[*i*], so *X*[*i*] is the XOR of the first *i* elements.
:::

Exactly as for sums in Chapter 2, xor(*a*[*l*..*r*]) = *X*[*r* + 1] ⊕ *X*[*l*]: both prefixes contain *a*[0..*l* − 1], which cancels by (2). The difference from sums is pleasant: the "subtraction" is XOR again, and there is no overflow.

The prefix-count scan of Chapter 2 therefore counts subarrays with XOR equal to *k*. By law (5), *X*[*j*] ⊕ *X*[*i*] = *k* exactly when *X*[*i*] = *X*[*j*] ⊕ *k*, so the look-up key is `prefix ^ k`.

```java {#lst-8-subxor} Subarrays with XOR exactly k (handbook template)
// Number of subarrays with XOR exactly k: prefix XOR + HashMap (same idea as prefix sums)
static long countSubarraysWithXor(int[] a, int k) {
    Map<Integer, Integer> seen = new HashMap<>();
    seen.put(0, 1);
    int prefix = 0;
    long count = 0;
    for (int x : a) {
        prefix ^= x;
        count += seen.getOrDefault(prefix ^ k, 0); // earlier p with prefix ^ p == k
        seen.merge(prefix, 1, Integer::sum);
    }
    return count;
}
```

### Triplets with equal XOR

LeetCode 1442 (Count Triplets That Can Form Two Arrays of Equal XOR) asks for the number of triples *i* < *j* ≤ *k* with xor(*a*[*i*..*j* − 1]) = xor(*a*[*j*..*k*]). Call the two sides *A* and *B*. By law (5) with *c* = 0, *A* = *B* exactly when *A* ⊕ *B* = 0, and *A* ⊕ *B* is the XOR of the whole block *a*[*i*..*k*]. In prefix terms:

  *A* = *B*  ⇔  xor(*a*[*i*..*k*]) = 0  ⇔  *X*[*k* + 1] = *X*[*i*].

The condition does not mention *j*. So once a block *a*[*i*..*k*] has XOR 0, **every** split point *j* with *i* < *j* ≤ *k* works, and there are *k* − *i* of them.

:::theorem{#thm-8-triplets} Counting the triplets
Write *p* = *i* and *q* = *k* + 1. The number of triplets is the sum, over all pairs *p* < *q* of prefix indices with *X*[*p*] = *X*[*q*], of *q* − *p* − 1.
:::

:::proof
A triplet (*i*, *j*, *k*) is valid exactly when *X*[*i*] = *X*[*k* + 1] and *i* < *j* ≤ *k*. For a fixed pair (*p*, *q*) = (*i*, *k* + 1) with equal prefixes, the valid *j* are *i* + 1, …, *k*, which is *k* − *i* = *q* − *p* − 1 values (zero when *q* = *p* + 1, as it should be, because then *i* = *k* leaves no room for *j*). Different pairs give different triplets, and every triplet arises from its own pair, so the total is the sum.
:::

Summing over all pairs costs O(*n*²), already fast enough for the problem's limit of *n* ≤ 300. The sum can also be collected in one pass: when the scan reaches *q*, let *c* be the number of earlier *p* with *X*[*p*] = *X*[*q*] and *s* the sum of those *p*. Their contribution is Σ (*q* − 1 − *p*) = *c*(*q* − 1) − *s*, so a map from each prefix value to its (count, index sum) gives O(*n*).

:::example{#ex-8-triplets} Triplets in [6, 2, 4, 1, 7, 6]
The prefix XORs are *X* = [0, 6, 4, 0, 1, 6, 0]. The pairs with equal values are (0, 3), (0, 6), (3, 6) for the value 0 and (1, 5) for the value 6, contributing 2 + 5 + 2 + 3 = 12. The one-pass version produces the same total:

```trace
q   X[q]   earlier with same X: count c, index sum s   adds c(q-1) - s   total
0    0               0, 0                                      0            0
1    6               0, 0                                      0            0
2    4               0, 0                                      0            0
3    0               1, 0                                      2            2
4    1               0, 0                                      0            2
5    6               1, 1                                      3            5
6    0               2, 3                                      7           12
```

A brute force over all triples also counts 12.
:::

## Bit independence: sums of XORs and choosing X {#sec-8-perbit}

A sum of XORs mixes bits only through the final addition. Each bit position can therefore be counted on its own and weighted by its power of two. A second fact about bits makes greedy choices safe.

:::lemma{#lem-8-top} The top bit dominates
Let *x*, *y* be non-negative integers that agree on every bit above position *b*, with *x*<sub>*b*</sub> = 1 and *y*<sub>*b*</sub> = 0. Then *x* > *y*, whatever their lower bits are.
:::

:::proof
The common high bits contribute equally. Bit *b* adds 2ᵇ to *x* and nothing to *y*. The lower bits add at most 2⁰ + ⋯ + 2<sup>*b*−1</sup> = 2ᵇ − 1 to *y* and at least 0 to *x*. So *x* − *y* ≥ 2ᵇ − (2ᵇ − 1) = 1.
:::

The lemma says that comparing numbers is comparing their bit strings from the top, like words in a dictionary. Every greedy algorithm in the rest of the chapter rests on it: decide the highest bit first, and never give up a higher bit for any combination of lower ones.

### The sum of XORs over all pairs

:::theorem{#thm-8-pairsum} Sum of pairwise XORs
For *a*[0..*n* − 1] with values below 2<sup>*B*</sup>, let *c*<sub>*b*</sub> be the number of elements with bit *b* set. Then

  Σ over *i* < *j* of (*a*[*i*] ⊕ *a*[*j*]) = Σ over *b* of 2ᵇ · *c*<sub>*b*</sub> · (*n* − *c*<sub>*b*</sub>).
:::

:::proof
Write each XOR as Σ<sub>*b*</sub> 2ᵇ · [bit *b* of *a*[*i*] ≠ bit *b* of *a*[*j*]], where [·] is 1 if the condition holds and 0 otherwise. Swap the two sums: for a fixed *b*, the number of pairs whose bits differ is the number of ways to pick one element with the bit and one without, *c*<sub>*b*</sub> · (*n* − *c*<sub>*b*</sub>).
:::

```java {#lst-8-pairxor} Sum of a[i] xor a[j] over all pairs, bit by bit (handbook template)
// Sum of (a[i] xor a[j]) over all pairs i < j. Bits are independent, so count per bit.
static long sumPairXor(int[] a) {
    long total = 0;
    for (int b = 0; b < 31; b++) {
        long ones = 0;
        for (int x : a) ones += (x >> b) & 1;
        long pairs = ones * (a.length - ones);     // one number has the bit, the other doesn't
        total += pairs << b;
    }
    return total;
}
```

The cost is O(31 · *n*) instead of O(*n*²). For [5, 9, 12, 7] (binary 0101, 1001, 1100, 0111) the counts of ones are 3, 1, 3, 2 for bits 0 to 3, so the pairs differing at each bit are 3, 3, 3, 4, and the total is 3 · 1 + 3 · 2 + 3 · 4 + 4 · 8 = 53, the same as adding the six XORs directly. Note `ones` is a `long`, so `ones * (a.length - ones)` cannot overflow even for *n* = 10⁵.

### Choosing X to maximise a sum of XORs

For a fixed *X*, the same argument gives Σᵢ (*X* ⊕ *a*[*i*]) = Σ<sub>*b*</sub> 2ᵇ · *g*<sub>*b*</sub>(*X*<sub>*b*</sub>), where the gain of bit *b* is

  *g*<sub>*b*</sub>(1) = *n* − *c*<sub>*b*</sub>  (bit *b* of *X* = 1 makes the XOR bit 1 for the elements without the bit),
  *g*<sub>*b*</sub>(0) = *c*<sub>*b*</sub>  (bit *b* of *X* = 0 keeps the bit for the elements that have it).

Without other constraints each bit of *X* is chosen on its own: set it when *n* − *c*<sub>*b*</sub> > *c*<sub>*b*</sub>.

One of the Infosys repeat problems (6 reports in the plan's question bank) adds an upper limit: choose *X* in [0, *K*] to maximise Σ (*X* ⊕ *A*[*i*]). Now the bits are no longer free, because setting a high bit of *X* may push it above *K*. The way out is the structure of the numbers ≤ *K*.

:::lemma{#lem-8-leK} The shape of the numbers below K
A non-negative integer *X* < *K* agrees with *K* on all bits above some position *b*, has *X*<sub>*b*</sub> = 0 where *K*<sub>*b*</sub> = 1, and has arbitrary bits below *b*. Conversely every number of that form is < *K*.
:::

:::proof
If *X* < *K*, let *b* be the highest position where they differ. Above *b* they agree, so by @lem-8-top the larger number has the 1 at position *b*; since *X* < *K*, *K*<sub>*b*</sub> = 1 and *X*<sub>*b*</sub> = 0. The converse is @lem-8-top applied to *K* and *X*.
:::

So the candidates are *X* = *K* itself, plus one family for each set bit *b* of *K*: copy *K* above *b*, put 0 at *b*, and below *b* choose every bit freely by its own gain. Each family's best member is found bit by bit, giving at most 32 candidates and O(31 · 31) work after counting the bits. This is the same "follow the limit, then branch off below it" walk that digit DP formalises in Chapter 22; the full Infosys solution, with its input format and edge cases, is in Chapter 24.

:::example{#ex-8-chooseX} Choosing X ≤ 6 for A = [1, 4, 6, 3, 2]
Three bits suffice. With *n* = 5 the counts and gains are:

```trace
bit b   c_b   gain if X_b = 0 (c_b * 2^b)   gain if X_b = 1 ((n - c_b) * 2^b)   free choice
  2      2              8                              12                          1
  1      3              6                               4                          0
  0      2              2                               3                          1
```

The free choice is *X* = 101₂ = 5, which happens to be ≤ 6, but the walk does not know that in advance. *K* = 6 = 110₂ has set bits 2 and 1:

```trace
candidate                          X (binary)   sum of X xor A[i]
X = K                              110 = 6      12 + 4 + 2 = 18
branch at bit 2: 0, then free      001 = 1       8 + 6 + 3 = 17
branch at bit 1: 1, 0, then free   101 = 5      12 + 6 + 3 = 21
best: X = 5 with 21
```

A brute force over *X* = 0..6 agrees: the maximum is 21 at *X* = 5. With *K* = 4 instead, the branch at bit 2 gives 17 and *X* = *K* = 4 gives 20, which is then the answer.
:::

### Minimising an XOR with a fixed number of bits

LeetCode 2429 (Minimize XOR), a bonus problem today, asks for the *X* with a given number of set bits that makes *X* ⊕ num1 as small as possible. The key observation is @lem-8-top read the other way: a 1 in the XOR at a high position costs more than all lower positions together. So spend the available set bits of *X* on the highest set bits of num1 first (each one turns a 1 of the XOR into a 0), and if bits remain, place them at the lowest positions where num1 has a 0.

## The binary trie {#sec-8-trie}

Per-bit counting handles sums over all pairs. It cannot answer "which partner *y* in the set gives the largest *x* ⊕ *y*?", because that needs the *same* *y* for all bits. A tree of bit prefixes can.

:::definition{#def-8-trie} Binary trie
A [[binary trie]] over *B*-bit numbers is a rooted tree in which every node has at most two children, labelled 0 and 1. Each stored number is the root-to-leaf path that reads its bits from bit *B* − 1 down to bit 0. Every node also stores `cnt`, the number of stored numbers whose path passes through it.
:::

A node at depth *d* stands for one *d*-bit prefix, and its subtree holds exactly the stored numbers that start with that prefix. Inserting a number creates at most *B* nodes; numbers that share a prefix share its nodes. @fig-8-trie, after the listing, shows a small example.


The handbook template stores the trie in arrays: `child[node][bit]` is the index of a child, with 0 meaning "missing". Node 0 is the root, and the root is never anyone's child, so 0 is free to mean "none".

```java {#lst-8-trie} Binary trie for XOR queries over non-negative ints (handbook template)
// Binary trie over non-negative ints, highest bit first
static final class XorTrie {
    static final int B = 31;
    final int[][] child;           // child[node][bit], 0 = missing (the root is never a child)
    final int[] cnt;               // how many inserted numbers pass through this node
    int size = 1;

    XorTrie(int maxInserts) {
        child = new int[maxInserts * B + 1][2];
        cnt = new int[child.length];
    }

    void insert(int x) {
        int node = 0;
        for (int b = B - 1; b >= 0; b--) {
            int bit = (x >> b) & 1;
            if (child[node][bit] == 0) child[node][bit] = size++;
            node = child[node][bit];
            cnt[node]++;
        }
    }

    // max of (x ^ y) over inserted y. Trie must not be empty.
    int maxXor(int x) {
        int node = 0, res = 0;
        for (int b = B - 1; b >= 0; b--) {
            int want = ((x >> b) & 1) ^ 1;          // the opposite bit makes this xor bit 1
            if (child[node][want] != 0) {
                res |= 1 << b;
                node = child[node][want];
            } else {
                node = child[node][want ^ 1];
            }
        }
        return res;
    }

    // how many inserted y have (x ^ y) < k
    long countXorLess(int x, int k) {
        long res = 0;
        int node = 0;
        for (int b = B - 1; b >= 0; b--) {
            int xb = (x >> b) & 1, kb = (k >> b) & 1;
            if (kb == 1) {
                if (child[node][xb] != 0) res += cnt[child[node][xb]];   // xor bit 0 < 1: all count
                node = child[node][xb ^ 1];                               // xor bit 1: keep going
            } else {
                node = child[node][xb];                                   // xor bit must be 0
            }
            if (node == 0) break;
        }
        return res;
    }
}
```

### Maximum XOR with a stored number

:::theorem{#thm-8-maxxor} The greedy walk finds the maximum XOR
For a non-empty trie and any *x*, `maxXor(x)` returns max over stored *y* of *x* ⊕ *y*.
:::

:::proof
Let *M* be the true maximum. We show by induction on the number of levels processed that, after handling bits *B* − 1..*b*, the bits of `res` above and at *b* equal those of *M*, and `node` is the trie node for the prefix of some stored *y* with *x* ⊕ *y* = *M* on those bits. Before any level, both statements are about no bits and `node` is the root. At bit *b*, the subtree of `node` holds exactly the stored numbers *y* whose XOR with *x* matches *M* on the higher bits. If the child with the opposite bit exists, some such *y* has XOR bit *b* equal to 1; by @lem-8-top every maximiser must then have bit *b* equal to 1, so *M* has it, and the walk sets it and enters that child. If the child does not exist, every *y* in the subtree has XOR bit *b* equal to 0, so *M* has 0 there, and the walk enters the only child. After bit 0, `res` = *M*.
:::

For LeetCode 421 (Maximum XOR of Two Numbers in an Array), insert every number and take the maximum of `maxXor` over all of them; a number paired with itself gives 0, which never beats a real pair unless all numbers are equal. The cost is O(31 · *n*).

On the trie of @fig-8-trie with *x* = 4 = 100₂: at bit 2 the walk wants 0 and finds it, at bit 1 it wants 1 and finds it, at bit 0 it wants 1 and finds it, reaching *y* = 3 with 4 ⊕ 3 = 7. The other candidates give 4 ⊕ 2 = 6, 4 ⊕ 5 = 1 and 4 ⊕ 6 = 2.

### Counting pairs with XOR below a bound

The second query counts stored *y* with *x* ⊕ *y* < *k*. By @lem-8-leK, *x* ⊕ *y* < *k* exactly when, at the highest bit *b* where *x* ⊕ *y* and *k* differ, *k* has 1 and *x* ⊕ *y* has 0. The walk follows the path on which *x* ⊕ *y* equals *k* bit by bit, and collects the branches that leave it at a 1-bit of *k*.

:::theorem{#thm-8-less} Counting XOR below k
`countXorLess(x, k)` returns the number of stored *y* with *x* ⊕ *y* < *k*.
:::

:::proof
For each stored *y* with *x* ⊕ *y* < *k*, let *b* be the highest bit where *x* ⊕ *y* and *k* differ; then *k*<sub>*b*</sub> = 1, *y*<sub>*b*</sub> = *x*<sub>*b*</sub>, and above *b*, *y*<sub>*t*</sub> = *x*<sub>*t*</sub> ⊕ *k*<sub>*t*</sub>. So the *y* counted "at bit *b*" are exactly those in the subtree reached by following the bits *x*<sub>*t*</sub> ⊕ *k*<sub>*t*</sub> from the top down to bit *b* + 1 and then the bit *x*<sub>*b*</sub>. The walk does exactly this: on each level it moves to the child *x*<sub>*t*</sub> ⊕ *k*<sub>*t*</sub> (the code's `xb ^ 1` when *k*<sub>*t*</sub> = 1 and `xb` when *k*<sub>*t*</sub> = 0), and at each level with *k*<sub>*b*</sub> = 1 it first adds the count of the child *x*<sub>*b*</sub>. Different *b* give disjoint sets of *y*, so nothing is counted twice; a *y* with *x* ⊕ *y* = *k* never leaves the path and is never counted, which is right because *k* is not < *k*. If the path runs into a missing child, no stored *y* continues it, and the loop stops with all branches already added.
:::

On the trie of @fig-8-trie, `countXorLess(4, 3)` runs as follows (with *B* = 3 for the picture):

```trace
bit  x_b  k_b  action                                          running count
 2    1    0   XOR bit must be 0: go to child 1 {5, 6}               0
 1    0    1   add child 0 {5} (count 1), go to child 1 {6}          1
 0    0    1   add child 0 {6} (count 1), go to child 1 (missing)    2
result 2: the y with 4 xor y < 3 are 5 (4 xor 5 = 1) and 6 (4 xor 6 = 2)
```

Pairs with XOR in a range [*lo*, *hi*] are countXorLess(*hi* + 1) − countXorLess(*lo*). To count pairs *i* < *j* rather than ordered pairs, query each element against the trie *before* inserting it; that is the whole idea of LeetCode 1803 (Count Pairs With XOR in a Range).

### Offline queries

LeetCode 1707 (Maximum XOR With an Element From Array), a bonus problem, asks many queries "the maximum of *x* ⊕ *y* over the array elements *y* ≤ *m*". The trie cannot ignore large elements, but the queries do not have to be answered in the given order. The key observation is to sort the queries by *m* and the array ascending, and before each query insert every element ≤ *m* that is not yet in the trie; a query with an empty trie has no answer. Answering queries in a convenient order and putting the answers back in the original positions is called [[offline processing|offline queries]].

### Memory

Each insertion creates at most *B* nodes, so the trie never has more than *n* · *B* + 1 nodes, which is how the template sizes its arrays. For *n* = 2 · 10⁵ and *B* = 31 that is 6.2 · 10⁶ nodes. The layout matters: `new int[nodes][2]` makes one small array object per node, and on a 64-bit JVM each costs about 28 bytes including its reference. Measured on the sandbox JVM, the `child` array took 174 MB and `cnt` another 25 MB. Storing the two children of node *v* at `next[2 * v]` and `next[2 * v + 1]` of one flat `int[]` needs 8 bytes per node instead, 75 MB for `next` and `cnt` together.

```java {#lst-8-flat} The same trie in flat arrays (about 12 bytes per node)
static final class FlatXorTrie {
    static final int B = 31;
    final int[] next;              // children of node v: next[2 * v] (bit 0), next[2 * v + 1] (bit 1)
    final int[] cnt;
    int size = 1;

    FlatXorTrie(int maxInserts) {
        int nodes = maxInserts * B + 1;
        next = new int[2 * nodes];
        cnt = new int[nodes];
    }

    void insert(int x) {
        int node = 0;
        for (int b = B - 1; b >= 0; b--) {
            int slot = 2 * node + ((x >> b) & 1);
            if (next[slot] == 0) next[slot] = size++;
            node = next[slot];
            cnt[node]++;
        }
    }

    int maxXor(int x) {            // trie must not be empty
        int node = 0, res = 0;
        for (int b = B - 1; b >= 0; b--) {
            int want = ((x >> b) & 1) ^ 1;
            if (next[2 * node + want] != 0) {
                res |= 1 << b;
                node = next[2 * node + want];
            } else {
                node = next[2 * node + (want ^ 1)];
            }
        }
        return res;
    }
}
```

:::tip
Choose *B* from the limits. Values below 2³⁰ (about 1.07 · 10⁹) need only *B* = 30; values below 2²⁰ (about 10⁶) need 20, which cuts both time and memory by a third. Non-negative `int`s need 31.
:::

## The XOR basis {#sec-8-basis}

The last tool answers questions about **subsets**: "what is the largest XOR of any subset of these numbers?" and "can some subset XOR to *v*?". There are 2ⁿ subsets, but their XORs have a lot of structure.

Think of a number below 2<sup>*B*</sup> as a vector of *B* bits. XOR adds two vectors coordinate by coordinate modulo 2. The bits {0, 1} with addition and multiplication modulo 2 form the smallest field, written [[GF(2)]], and the *B*-bit numbers form a vector space over it. Multiplying by a scalar is trivial (by 1 keeps a vector, by 0 gives 0), so a "linear combination" of numbers is just the XOR of a subset of them.

:::definition{#def-8-basis} Span, independence and basis
The **span** of a set *S* of numbers is the set of XORs of all subsets of *S* (the empty subset gives 0). *S* is **independent** if no non-empty subset of it has XOR 0. A [[XOR basis|linear basis (XOR basis)]] of a span is an independent set whose span is that span.
:::

The handbook template keeps at most one basis number for each highest bit, the arrangement produced by Gaussian elimination.

```java {#lst-8-basis} Linear XOR basis (handbook template)
// Linear XOR basis: the XOR of any subset can be built from at most 61 basis numbers
static final class XorBasis {
    final long[] b = new long[61];               // b[i] has highest bit i, or is 0

    boolean add(long x) {                        // returns false if x was already reachable
        for (int i = 60; i >= 0; i--) {
            if (((x >> i) & 1) == 0) continue;
            if (b[i] == 0) {
                b[i] = x;
                return true;
            }
            x ^= b[i];
        }
        return false;
    }

    long max() {                                 // maximum XOR of any subset
        long r = 0;
        for (int i = 60; i >= 0; i--) r = Math.max(r, r ^ b[i]);
        return r;
    }
}
```

:::theorem{#thm-8-basis} What the basis maintains
After `add` has been called on *x*₁, …, *x*<sub>*m*</sub>, in that order, with values below 2⁶¹: (1) every non-zero `b[i]` has highest set bit *i*; (2) the non-zero `b[i]` are independent; (3) their span equals the span of {*x*₁, …, *x*<sub>*m*</sub>}; (4) `add(x)` returns false exactly when *x* was already in the span.
:::

:::proof
Assume (1)–(3) hold before `add(x)`, and let *x*₀ be the original value. During the loop, *x* changes only by XOR with basis numbers, so *x* ⊕ *x*₀ always lies in the old span.

When the loop reaches bit *i* with *x*<sub>*i*</sub> = 1, all higher bits of *x* are 0: each higher set bit *j* was either cleared by `x ^= b[j]` (which clears bit *j*, because *b*[*j*] has highest bit *j*, and changes only lower bits) or would have stopped the loop there. If *b*[*i*] = 0, the new basis number *x* has highest bit *i*, keeping (1). It is not in the old span: by (1), the basis numbers have distinct highest bits, so any non-empty XOR of them has as its highest bit the largest highest bit involved, which is never *i*. Hence the enlarged set stays independent, giving (2). The new span is the old span plus *x*, which is the old span plus *x*₀ because they differ by an element of the old span, giving (3).

If the loop ends without storing, every set bit met was cleared, so *x* = 0 and *x*₀ = *x* ⊕ *x*₀ is in the old span: the span does not change and the method returns false. If *x*₀ was in the old span, then so is the final *x*, which therefore cannot be stored (shown above), so the method returns false; otherwise it returns true. That is (4).
:::

:::claim{#thm-8-size} Size of the basis and of the span
A basis of numbers below 2<sup>*B*</sup> has at most *B* elements. If it has *r* elements, every value in the span is the XOR of exactly one subset of the basis, so the span has exactly 2ʳ values. Every value in the span is also the XOR of at most *r* of the *original* numbers.
:::

:::proof
The highest bits are distinct and lie in 0..*B* − 1, so *r* ≤ *B*. If two different subsets of the basis had the same XOR, the XOR of their symmetric difference would be 0, contradicting independence; so the 2ʳ subsets give 2ʳ different values. For the last statement, the *r* original numbers whose `add` returned true have, by (3), the same span as the basis (each successful `add` enlarged the span by exactly its own original number, each failed one by nothing). Any span value is the XOR of a subset of these *r* numbers.
:::

### The maximum subset XOR

:::theorem{#thm-8-max} The greedy maximum
`max()` returns the largest XOR of any subset of the inserted numbers.
:::

:::proof
By @thm-8-size each span value is the XOR of a unique subset *T* of the basis. Bit *i* of that XOR depends only on whether *b*[*i*] ∈ *T* and on the basis numbers above *i*, because the ones below have no bit *i*. So reading from the top, at each basis position *i* the choice "include *b*[*i*] or not" is exactly the choice of bit *i*, given the higher choices.

Let *M* be the largest span value. *M* has a 1 at every basis position *i*: otherwise *M* ⊕ *b*[*i*] agrees with *M* above *i* and has bit *i* set, so it is larger by @lem-8-top. The greedy loop processes positions from the top; at a basis position, `r` and `r ^ b[i]` agree above *i* and differ at bit *i*, so `Math.max` keeps the one with bit *i* equal to 1 (and at non-basis positions *b*[*i*] = 0 changes nothing). So `r` ends with a 1 at every basis position, and since the subset is determined by the bits at the basis positions, `r` = *M*.
:::

The cost is O(61) per insertion and per maximum, or O(*B*) with a smaller array when the values are small. Membership is the same reduction as `add` without the store.

```java {#lst-8-canmake} Can some subset XOR to v? Reduce v by the basis
static boolean canMake(long[] b, long v) {       // b = the array of an XorBasis
    for (int i = 60; i >= 0; i--)
        if (((v >> i) & 1) == 1 && b[i] != 0) v ^= b[i];
    return v == 0;
}
```

:::example{#ex-8-basis} Building a basis for [12, 9, 7, 5]
In 4-bit binary the numbers are 1100, 1001, 0111 and 0101.

```trace
add(12) 1100:  b[3] empty                           -> b[3] = 1100 (12)
add(9)  1001:  bit 3: xor b[3] -> 0101 (5); b[2] empty -> b[2] = 0101 (5)
add(7)  0111:  bit 2: xor b[2] -> 0010 (2); b[1] empty -> b[1] = 0010 (2)
add(5)  0101:  bit 2: xor b[2] -> 0000              -> false (5 = 12 xor 9)
max():  r = 0 -> 12 (take b[3]) -> 12 (skip b[2]: 12 xor 5 = 9) -> 14 (take b[1]) -> 14

The basis has rank 3, so the subsets of the four numbers produce exactly 2³ = 8 distinct XORs: 0, 2, 5, 7, 9, 11, 12, 14. The maximum 14 = 1110₂ is 9 ⊕ 7. A brute force over all 16 subsets confirms both facts.
:::

### What the basis cannot answer

The basis forgets *how many* numbers were used and *which positions* they came from. It answers "is *v* reachable by some subset?" and "what is the largest reachable value?", and with a fully reduced basis also "what is the *k*-th smallest reachable value?". It cannot answer:

* **Questions with a size limit.** The Infosys repeat "Maximum XOR choosing at most *N*/2 elements" (13 reports in the plan's question bank) has the sample [1, 2] with answer 2: the basis says 1 ⊕ 2 = 3, but that uses two elements and the limit is one. @thm-8-size shows when the limit is harmless: the maximum is the XOR of at most *r* original numbers, and *r* ≤ 20 for values below 2²⁰, so the basis answer is correct whenever *N*/2 ≥ *r*, in particular for *N* ≥ 40. For smaller *N* the problem needs a different method, an XOR knapsack over the 2²⁰ possible values, which Chapter 26 develops.
* **Questions about contiguous pieces.** "Maximum XOR of a subarray" is a pair question about prefix XORs (*X*[*j*] ⊕ *X*[*i*]), so it belongs to the trie: insert prefixes and query each new one.
* **Exactly *k* elements**, or any condition on which elements are used. A related counting fact does follow from the rank, though: each reachable value is the XOR of exactly 2<sup>*n*−*r*</sup> of the 2ⁿ subsets, because the *n* − *r* numbers that `add` rejected can be included or left out freely, and each choice is completed to the target in exactly one way by the *r* accepted numbers.

## Choosing the right XOR tool {#sec-8-choose}

The four ideas of this chapter cover most XOR questions, and the shape of the question picks the tool.

Table: {#tbl-8-tools} Which tool for which XOR question
| The question is about | Tool | Cost |
|---|---|---|
| one element that does not cancel, parity of counts | XOR of everything (@thm-8-odd) | O(*n*) |
| subarrays with XOR *k*, blocks with XOR 0 | prefix XOR + hash map (@lst-8-subxor) | O(*n*) |
| a sum of XORs over all pairs, or Σ (*X* ⊕ *a*[*i*]) | per-bit counting (@thm-8-pairsum) | O(*B* · *n*) |
| choosing *X* bit by bit, possibly ≤ *K* | gains per bit + the walk of @lem-8-leK | O(*B*²) after counting |
| the best partner of *x*, pairs with XOR < *k* or in a range | binary trie (@lst-8-trie) | O(*B*) per query |
| the best subset, reachable values, rank | XOR basis (@lst-8-basis) | O(*B*) per insert |
| subsets with a size limit | not the basis: XOR knapsack (Chapter 26) | O(*n* · 2<sup>*B*</sup>) |

:::infosys
XOR runs through the plan's Infosys material. Besides the two repeats above (the size-limited subset maximum and choosing *X* ≤ *K*), the question bank reports a longest increasing subsequence whose adjacent pairs satisfy (*x* & *y*) · 2 < (*x* | *y*), a condition that turns out to depend only on the highest set bits; a reported interview task counts pairs with XOR < *K* whose sum is prime, where the trie of @sec-8-trie replaces the nested loops; and the Hard problem of the official sample paper is a longest non-decreasing subsequence whose XOR is at least *M*, solved with an extra XOR dimension in a DP. ## Summary

- Java integers are two's complement: −*x* = ~*x* + 1, −1 is all ones, and `Integer.MIN_VALUE` has no positive partner. `>>` keeps the sign, `>>>` fills with zeros, and shift distances are taken mod 32 (mod 64 for `long`): use `1L << k` for *k* ≥ 31.
- Bracket every bit expression: shifts bind more loosely than `+`, and `&`, `^`, `|` more loosely than `==`.
- XOR is bitwise addition mod 2: it has identity 0, every number is its own inverse, and order does not matter. Equal values cancel in pairs.
- Prefix XORs work like prefix sums: xor(*l*..*r*) = *X*[*r* + 1] ⊕ *X*[*l*]. A block has XOR 0 exactly when its two end prefixes are equal, which counts the triplets of LeetCode 1442 as Σ (*q* − *p* − 1) over equal pairs.
- In a sum of XORs every bit is independent: count the ones per bit and weight by 2ᵇ. A higher bit outweighs all lower bits together, which justifies every greedy choice from the top.
- The numbers ≤ *K* are *K* itself and, for each 1-bit of *K*, "copy *K* above, 0 here, anything below". Walking *K*'s bits this way maximises a per-bit objective under the limit.
- A binary trie answers pair questions in O(*B*) per query: the maximum XOR by taking the opposite bit when possible, and the count of XOR < *k* by following *k*'s bits and adding the branches at its 1-bits. Size it as *n* · *B* + 1 nodes and prefer flat arrays for large *n*.
- A linear basis keeps at most one number per highest bit. It spans exactly the subset XORs, has at most *B* elements, gives the maximum subset XOR greedily, and ignores how many elements are used.

## Review questions

1. What are `1 << 31`, `1 << 32` and `1L << 32` in Java, and why? Which expression gives 2ᵏ for 31 ≤ *k* ≤ 62?
2. Explain why `x & -x` isolates the lowest set bit of *x* > 0. What does `x & (x - 1)` do?
3. Prove that the XOR of a list is unchanged when two equal elements are removed from it. Which laws do you use?
4. For *a* = [4, 4, 4, 4], list the prefix XORs and count the triplets of LeetCode 1442 with the formula of @thm-8-triplets.
5. Using @thm-8-pairsum, why can the sum of XORs over all pairs never exceed (*n*²/4) · (2<sup>*B*</sup> − 1)?
6. In the "choose *X* ≤ *K*" walk, why is it safe to choose the bits below the branching bit independently of each other?
7. In `countXorLess`, why is a number *y* with *x* ⊕ *y* = *k* never counted? How do you count pairs with *lo* ≤ *x* ⊕ *y* ≤ *hi*?
8. A trie stores 10⁵ numbers below 2²⁰. How many nodes can it have at most, if you choose *B* well?
9. Insert 3, 5, 6 into an XOR basis. What does the basis look like, what is the maximum subset XOR, and how many distinct subset XORs are there?
10. Why can the basis not solve "maximum XOR of at most *N*/2 elements" in general, and when does its answer happen to be correct?

:::answers
1. `1 << 31` is −2147483648, because bit 31 of an `int` is the sign bit. `1 << 32` is 1, because Java uses only the low 5 bits of the shift distance, so 32 acts as 0. `1L << 32` is 4294967296, because the left operand is a `long` and the distance is taken mod 64. Use `1L << k`.
2. −*x* = ~*x* + 1. In ~*x* the lowest 1 of *x* becomes 0 and the zeros below it become ones; adding 1 carries through those ones and turns that position back into 1, leaving every higher bit flipped. ANDing with *x* keeps only that position. `x & (x - 1)` clears the lowest set bit, because *x* − 1 turns the lowest 1 into 0 and the zeros below it into 1s, while the higher bits stay.
3. By commutativity and associativity the two equal elements can be moved next to each other and grouped; their XOR is 0 by *a* ⊕ *a* = 0, and XOR with 0 changes nothing.
4. *X* = [0, 4, 0, 4, 0]. Equal pairs: (0, 2), (0, 4), (2, 4) for 0 and (1, 3) for 4, contributing 1 + 3 + 1 + 1 = 6. A brute force also gives 6.
5. For each bit, *c*<sub>*b*</sub>(*n* − *c*<sub>*b*</sub>) ≤ *n*²/4, because a product of two non-negative numbers with sum *n* is largest when both are *n*/2. Summing 2ᵇ times this over all bits gives at most (*n*²/4) · Σ 2ᵇ = (*n*²/4)(2<sup>*B*</sup> − 1).
6. Below the branching bit *X* is already smaller than *K* (by @lem-8-top), so any lower bits keep *X* < *K*; there is no constraint left, and the objective is a sum of independent per-bit gains.
7. Such a *y* follows the path of *k*'s bits all the way down; the walk only adds subtrees that branch off at a 1-bit of *k* with XOR bit 0, and *y* never branches off. That is correct because *k* is not less than *k*. For a range, count countXorLess(*hi* + 1) − countXorLess(*lo*), summed over the elements, querying each before inserting it.
8. With *B* = 20 bits, at most 10⁵ · 20 + 1 = 2,000,001 nodes; in fact also at most 2²¹ − 1 = 2,097,151 because there are only that many prefixes of length ≤ 20, and the first bound is smaller.
9. 3 = 011 goes to *b*[1]; 5 = 101 goes to *b*[2]; 6 = 110 reduces by *b*[2] to 011 and by *b*[1] to 000, so it is dependent (6 = 3 ⊕ 5). The rank is 2, so there are 2² = 4 distinct subset XORs (0, 3, 5, 6), and the maximum is 6: `max()` takes *b*[2] = 5, then 5 ⊕ 3 = 6 > 5.
10. The basis treats every subset as allowed, so its maximum may need more than *N*/2 elements, as in the sample [1, 2] where it gives 3 but only one element may be chosen. Its maximum is always the XOR of at most *r* original numbers (rank *r* ≤ number of bits), so whenever *N*/2 ≥ *r* the limit does not bind and the basis answer is correct; for values below 2²⁰ that holds for all *N* ≥ 40.
:::
