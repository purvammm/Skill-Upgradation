## Why the last day is a rest day {#sec-29-rest}

The plan's exam-day page is explicit: no new topics after Thursday 3 December, and Saturday 5 December is a rest day. The reason is arithmetic about attention. A technique learned tonight would be used tomorrow at half speed, if at all. An hour of sleep lost tonight costs attention across all 180 minutes, and attention is what the error log's most common causes need: a misread statement, a forgotten edge case, an off-by-one. The plan's list of signs that you are tired (two problems in a row past their time limit, re-reading the same line of a statement, pasting code you do not understand) describes exactly the state you want to avoid at minute 120 tomorrow.

:::definition{#def-29-rest} Rest day
A [[rest day]] is a day with no new problems and no new material. It keeps the routine with one short warm-up and light reading of your own notes, and it spends the rest of its time on the practical preparation for the exam: route, bag, meals and sleep.
:::

The workbook's plan for today has three blocks. The handbook review is the patterns due today, written as shapes in a few minutes each, without chasing details. The warm-up is LeetCode 1480. The review block is reading, not re-solving: Chapter 28 moved every re-solve due today to yesterday. If one is still due, re-solve at most one, in the morning, and stop at the block's 20 minutes whatever happens.

## The one-page template sheet {#sec-29-sheet}

Chapter 28 ended with the paper for today: the template details you rated *Again* or *Shaky*, the rules of the failed re-solves, the error-log rules and the playbook card. The sheet is that paper made short enough to read in a few minutes.

:::definition{#def-29-sheet} One-page template sheet
A [[one-page template sheet|template sheet]] is one side of one sheet, in your own handwriting, holding only the lines of code and the rules that have cost you marks. It is read twice: once today and once on the morning of the exam. It is not a copy of the handbook.
:::

One page is the point. A full re-read of the handbook is a day of new work; a page is a few minutes, and everything on it is something you have already got wrong once. The sheet stays at home. You cannot assume that notes are allowed into the hall (Chapter 27), so the sheet does its work before you leave.

A model sheet has two halves. The top half is the playbook in one line per block (read until 15, the surest problem until 60, the second until 120 with a brute force at 100, the hard problem until 165, checks only after that, every problem submitted by 150) and your three personal rules from Chapter 27. The bottom half is code: the few lines per template that decide whether it works. @lst-29-sheet is a model for that half, built from the template details of Chapter 28. Yours should contain only the templates you rated lowest.

```java {#lst-29-sheet} The code half of a model sheet: the lines that decide whether each template works
// Ch 6: first index with a[i] >= x (a.length if none); use a[mid] > x for the upper bound
static int lowerBound(int[] a, int x) {
    int lo = 0, hi = a.length;                       // the answer is in [lo, hi]
    while (lo < hi) {
        int mid = (lo + hi) >>> 1;
        if (a[mid] >= x) hi = mid; else lo = mid + 1;
    }
    return lo;
}

// Ch 10: b^e mod m; every product of two values below m fits a long when m < 3e9
static long power(long b, long e, long m) {
    long r = 1 % m;
    b = Math.floorMod(b, m);
    for (; e > 0; e >>= 1, b = b * b % m)
        if ((e & 1) == 1) r = r * b % m;
    return r;
}

// Ch 17: the root of x, with path halving; union: parent[find(a)] = find(b)
static int find(int[] parent, int x) {
    while (parent[x] != x) {
        parent[x] = parent[parent[x]];               // path halving
        x = parent[x];
    }
    return x;
}

// Ch 20: Fenwick tree, 1-indexed, t.length == n + 1
static void add(long[] t, int i, long v) {
    for (; i < t.length; i += i & -i) t[i] += v;
}

static long sum(long[] t, int i) {                   // a[1] + ... + a[i]
    long s = 0;
    for (; i > 0; i -= i & -i) s += t[i];
    return s;
}

// Ch 20: segment tree sum over a[l..r-1]; leaves at t[n..2n-1], t[i] = t[2i] + t[2i+1]
static long query(long[] t, int n, int l, int r) {
    long s = 0;
    for (l += n, r += n; l < r; l >>= 1, r >>= 1) {
        if ((l & 1) == 1) s += t[l++];
        if ((r & 1) == 1) s += t[--r];
    }
    return s;
}

// Ch 18: BFS order from a parent array (par[root] == -1); walk it backwards for subtree values
static int[] bfsOrder(int[] par) {
    int n = par.length;
    int[] head = new int[n], next = new int[n], order = new int[n];
    Arrays.fill(head, -1);
    int tail = 0;
    for (int v = 0; v < n; v++) {
        if (par[v] == -1) order[tail++] = v;
        else { next[v] = head[par[v]]; head[par[v]] = v; }
    }
    for (int k = 0; k < tail; k++)
        for (int c = head[order[k]]; c != -1; c = next[c]) order[tail++] = c;
    return order;
}

// Always: (long) a * b before multiplying; Math.floorMod(x, m); Integer.compare in comparators;
// one out.flush() at the end; mark a vertex when you push it; no recursion deeper than 1e4.
```

Every method is a compressed form of a listing proved in its chapter, and each was checked again here against a brute force: 29,000 random cases in all, from lower bounds on short sorted arrays and fast powers against `BigInteger.modPow` to BFS orders and subtree sizes on random trees. `bfsOrder` also ran on a chain of 10⁶ vertices, where a recursive traversal would have overflowed the stack. The segment-tree query keeps one accumulator because a sum is commutative; for an operation where order matters, Chapter 20 keeps a left and a right result.

:::pitfall
A sheet that grows to three pages is the handbook again. If it does not fit, remove the templates rated *Solid* in Chapter 28, then shorten the rest to their deciding lines.
:::

## The evening, the night and the morning {#sec-29-evening}

The plan fixes three things about the night: lay out tomorrow's things tonight, sleep 7–8 hours, and leave early. They interact through a single fixed time, the reporting time, so plan them backwards from it.

:::definition{#def-29-backward} Backward plan
A [[backward plan]] is a schedule computed from a fixed end time by subtracting the length of each block in reverse order. Here the end time is the reporting time *R*, and the blocks are the margin, the travel, the morning routine and the sleep.
:::

The inputs come from four places. *R* comes from the invite. The travel time *T* comes from today's route check: look up the route for the time of day you will travel, and include the walk from the entrance to the room if the venue is large. The margin *M* is your choice; the plan says only "leave early", and at least 30 minutes is a reasonable floor. The morning block *B* covers washing, breakfast, the five-minute FastScanner warm-up and a last check of the bag. Then

  leave = *R* − *M* − *T*,  wake = leave − *B*,  bed = wake − 8 hours,

and the hour before bed has no problems and no screens.

:::example{#ex-29-backward} A backward plan
Suppose, as an example only, that the invite says *R* = 09:00, the route takes *T* = 50 minutes, you choose *M* = 30 minutes, and the morning takes *B* = 75 minutes. Then you arrive at 08:30, leave at 07:40, wake at 06:25, and are in bed by 22:25 for eight hours of sleep, or 23:25 at the latest for seven. The wind-down starts at 21:25. Replace every number with your own; only the subtractions carry over.
:::

**This evening.** Pack exactly what the invite lists and lay it out where you will see it in the morning. Write *R*, the leaving time and the wake-up time on one line on the sheet. Set two alarms. Read the template sheet and the playbook card once, then put them away. ## The first ten minutes in the hall {#sec-29-hall}

Chapter 27 fixed minutes 0–15: read every problem with its limits and samples, write one row of paper notes per problem (limits, idea, complexity, brute-force fallback, edge cases, how sure you are), rank the problems by sureness, and start the surest at minute 15. Nothing in that changes tomorrow; do not re-plan it in the hall. What is new is the setting, and it is worth one look before minute 0 and in the first minutes:

* **The platform.** Choose Java. Find where the samples run and how a submission is made, before you need either.
* **The form of each problem.** With a function stub, keep its name, parameters and return type and fill in the body. Without one, type the exam file of Chapter 27 from memory. Either way, check your input reading against the samples before writing the logic (the plan's Lesson 2).
* **Your notes.** On paper if paper is provided; otherwise as comments at the top of the first file.

If the machine or the platform misbehaves, tell an invigilator at once instead of working around it quietly. The playbook's minute markers then apply to the time you actually have.

:::keyidea
In the hall the playbook decides and you follow it. Every decision that could be made in advance has been made: the order of reading, the minute markers, the brute force at minute 100, a submission on every problem by minute 150, no new code after 165.
:::

## Summary

- The day before the exam is a rest day: no new topics and no new problems, one five-minute warm-up, light reading of your own notes, and the practical preparation.
- The warm-up, LeetCode 1480, rehearses the workflow, not an idea. If it goes wrong, fix it and stop.
- The one-page template sheet holds only the lines and rules that have cost you marks. Read it today and tomorrow morning, at home.
- Facts about the hall come only from the plan's sources and your invite, admit card or e-mail.
- Plan the night backwards from the reporting time: leave = *R* − margin − travel, wake = leave − morning, bed = wake − 8 hours.
- In the hall, run Chapter 27's first fifteen minutes unchanged, after one look at the platform, the form of each problem and where your notes go.
