Chapter 18 showed how to visit a tree without recursion: walk the BFS order backwards to finish children before parents, forwards to finish parents before children. This chapter puts real computations into those two loops. All three of its main techniques answer a question **for every vertex at once**, which is the shape of most hard tree problems.

**Tree DP** (@sec-19-dp) gives each vertex a small table of values, one per *state* (chosen or not, matched or not), and computes it from the children's tables. **Rerooting** (@sec-19-reroot) answers "what if the tree were rooted here?" for all *n* roots with one extra pass instead of *n* traversals. **Small-to-large merging** (@sec-19-s2l) keeps a whole set or map per subtree, which sounds like O(*n*²) memory and time, and shows that pouring the smaller collection into the larger makes it O(*n* log *n*). In between, @sec-19-aggregates handles the cheap case of small alphabets, and @sec-19-parity treats operations that change both ends of an edge, a pattern behind the sample paper's hardest problem.

Throughout, a tree is given by `par` with `par[root] = -1` and its BFS order `order` from Chapter 18 (`bfsOrder` or `bfsOrderArrays`; `parentsFromEdges` for an edge list). Every listing takes `order` as a parameter so that it never recurses.

## Tree DP with states {#sec-19-dp}

:::definition{#def-19-treedp} Tree DP
A [[tree DP]] assigns to every vertex *v* and every *state* *s* from a small set a value dp[*v*][*s*]: the best (or the number of) solutions restricted to the subtree of *v*, among those in which *v* is in state *s*. The values of *v* are computed from the values of its children, so the vertices are processed children first.
:::

The method rests on one structural fact. The subtrees of the children of *v* share no vertex and no edge; the only edges that connect them to the rest of the tree are the edges from each child to *v*. So once the state of *v* is fixed, the choice made inside one child's subtree cannot affect what is allowed inside another's. Each child can be optimised separately, subject only to the rule on the single edge between it and *v*.

### Maximum-weight independent set

:::definition{#def-19-mis} Independent set
A set of vertices is [[independent|independent set]] if no edge has both ends in it. Given a weight *w*[*v*] ≥ 0 for every vertex, the task is to find an independent set of maximum total weight.
:::

On a general graph this problem is hard (no polynomial algorithm is known). On a tree two states per vertex solve it: take[*v*] is the best weight in the subtree of *v* with *v* in the set, and skip[*v*] is the best with *v* not in the set.

:::theorem{#thm-19-mis} Transitions for the independent set
For every vertex *v* with children *c*₁, …, *c*ₘ,

take[*v*] = *w*[*v*] + Σ skip[*c*ᵢ]  and  skip[*v*] = Σ max(take[*c*ᵢ], skip[*c*ᵢ]),

and the answer is max(take[root], skip[root]).
:::

:::proof
By induction on the height of *v*. For a leaf, take = *w*[*v*] and skip = 0, which the formulas give with empty sums. Now let *v* have children, and assume the values of the children are correct. An independent set *I* of the subtree of *v* consists of *v* or not, together with one independent set *I*ᵢ inside each child's subtree; the only extra condition is on the edges (*v*, *c*ᵢ). If *v* ∈ *I*, no child may be in *I*, so each *I*ᵢ must avoid *c*ᵢ, and the best total is *w*[*v*] plus the best of each, Σ skip[*c*ᵢ]. If *v* ∉ *I*, the edges (*v*, *c*ᵢ) impose nothing, so each *I*ᵢ is the best set of its subtree, with or without *c*ᵢ: Σ max(take[*c*ᵢ], skip[*c*ᵢ]). Because the subtrees share no edge, any combination of valid *I*ᵢ is valid, so these sums are achievable as well as upper bounds.
:::

The handbook template computes both sums without children lists: when the backward loop reaches *v*, both of its values are complete (all children came later in BFS order and were reached earlier), so *v* adds its contribution to its parent at once.

```java {#lst-19-mis} Maximum-weight independent set: dp[v][taken] (handbook template)
// dp[v][state] built from the children. Example: maximum-weight set of nodes, no two adjacent.
// take[v] = best in v's subtree with v chosen, skip[v] = best with v not chosen.
static long maxIndependentSet(int[] par, int[] order, int[] w) {   // order = BFS order of the tree
    int n = par.length;
    long[] take = new long[n], skip = new long[n];
    for (int i = n - 1; i >= 0; i--) {                   // children are finished first
        int v = order[i];
        take[v] += w[v];
        int p = par[v];
        if (p == -1) continue;
        take[p] += skip[v];                              // parent chosen -> child must be skipped
        skip[p] += Math.max(take[v], skip[v]);           // parent skipped -> child is free
    }
    int root = order[0];
    return Math.max(take[root], skip[root]);
}
```

:::example{#ex-19-mis} Take or skip, by hand
The tree has par = [−1, 0, 0, 1, 1, 2, 2] and weights *w* = [5, 3, 4, 2, 6, 1, 3] (@fig-19-mis). The BFS order is 0..6, so the loop runs *v* = 6, 5, …, 0.

:::

There, recursion is fine, and the natural return value is the pair {take, skip} as a `long[2]` (or `int[2]`). Writing it is left to you; the transitions are exactly @thm-19-mis.

### The cost of a tree DP

Each edge (*v*, *c*) is used once, when *c* sends its values to *v*. If there are *S* states and every state of *v* looks at every state of *c*, the work per edge is O(*S*²), so the whole DP costs O(*n* · *S*²) time and O(*n* · *S*) memory. For the independent set *S* = 2. The point of choosing states carefully is to keep *S* tiny.

### Choosing one child: maximum matching

Some constraints involve *one* child instead of all of them. A [[matching]] is a set of edges no two of which share a vertex; with edge weights, find a matching of maximum total weight. Now a vertex *v* is either matched to one of its children, or not matched to any child (in which case it may still be matched to its parent). Two values per vertex describe this:

* free[*v*]: the best matching in the subtree of *v* in which *v* is **not** matched to a child;
* any[*v*]: the best matching in the subtree of *v*, with no restriction.

:::theorem{#thm-19-matching} Transitions for the matching
With *w*(*c*) the weight of the edge (*c*, *v*) to the parent,

free[*v*] = Σ any[*c*] over the children *c*, and any[*v*] = free[*v*] + max(0, maxₖ ( *w*(*c*) + free[*c*] − any[*c*] )).
:::

:::proof
If *v* is matched to no child, the children's subtrees are independent and unrestricted, giving Σ any[*c*]. If *v* is matched to the child *c*, then *c* is used by that edge and may not be matched to one of its own children, so *c*'s subtree contributes free[*c*] instead of any[*c*], plus the edge weight *w*(*c*), while every other child still contributes any. That total is free[*v*] − any[*c*] + free[*c*] + *w*(*c*). any[*v*] is the best of "no child" and all the single-child choices, which is the formula. Correctness of the children's values follows by induction on height as in @thm-19-mis.
:::

```java {#lst-19-matching} Maximum-weight matching in a tree: choose one child
// Choose edges, no two sharing a vertex, to maximise the total weight. w[v] = weight of
// the edge (v, par[v]). free[v] = best in v's subtree when v is NOT matched to a child
// (v may still be matched to its parent); any[v] = best with no restriction on v;
// gain[v] = the best extra from matching v to one of its children (0 if none helps).
static long maxMatching(int[] par, int[] order, long[] w) {
    int n = par.length;
    long[] free = new long[n], any = new long[n], gain = new long[n];
    for (int i = n - 1; i >= 0; i--) {                   // children are finished first
        int v = order[i];
        any[v] = free[v] + gain[v];
        int p = par[v];
        if (p == -1) continue;
        free[p] += any[v];                               // p unmatched: each child is unrestricted
        gain[p] = Math.max(gain[p], w[v] + free[v] - any[v]);   // or match p with v
    }
    return any[order[0]];
}
```

Keeping only the best gain over the children turns "try every child" into O(1) work per edge, so the DP is O(*n*). On the tree of @fig-19-mis with edge weights 4, 2, 3, 5, 6, 1 for the edges from vertices 1..6 to their parents, the loop gives any[2] = 6 (edge 2–5), any[1] = 5 (edge 1–4), free[0] = 11 and gain[0] = 0, so the maximum matching weighs 11: matching the root to either child would give up more than it gains.

:::infosys
The official sample paper's fourth problem (the "Complex" one, rated 2400+ in the plan) chooses a matching of tree edges and changes both ends of every chosen edge, then asks about patterns on root-to-leaf paths. The plan's advice is to aim for partial marks there. Two ideas from this chapter are the building blocks: the "choose one child" matching DP above, and the parity view of edge operations in @sec-19-parity.
:::

## Per-subtree aggregates {#sec-19-aggregates}

The simplest "answer for every vertex" is an aggregate over the subtree: its size, its sum, its maximum, or a count for each letter of a small alphabet. Each is computed by the backward loop, adding a child's aggregate into its parent's.

LeetCode 1519 (Number of Nodes in the Sub-Tree With the Same Label) asks, for each vertex *v*, how many vertices in its subtree carry the same letter as *v*. With 26 letters, keep a count array per vertex. The listing below solves a neighbouring question, the number of **distinct** letters in each subtree; LeetCode 1519 needs a different read-out of the same `cnt` arrays and an edge list rooted first with `parentsFromEdges` from Chapter 18.

```java {#lst-19-letters} Count arrays merged upwards: distinct letters in every subtree
// cnt[v][c] = number of vertices in v's subtree whose label is letter c.
static int[] distinctLetters(int[] par, int[] order, String labels) {
    int n = par.length;
    int[][] cnt = new int[n][26];
    int[] distinct = new int[n];
    for (int i = n - 1; i >= 0; i--) {                   // children are merged in before v is used
        int v = order[i];
        cnt[v][labels.charAt(v) - 'a']++;
        for (int c = 0; c < 26; c++) if (cnt[v][c] > 0) distinct[v]++;
        int p = par[v];
        if (p == -1) continue;
        for (int c = 0; c < 26; c++) cnt[p][c] += cnt[v][c];
    }
    return distinct;
}
```

**Cost.** Each vertex adds its 26 counters into its parent once: 26(*n* − 1) additions, plus 26*n* for the read-out, so O(26 *n*) time. Memory is the real cost: `new int[n][26]` for *n* = 10⁵ is 2.6 · 10⁶ `int`s (10.4 MB) plus 10⁵ row objects. That is acceptable, but it grows with the alphabet: for values up to 10⁹ instead of letters, a count array per vertex is impossible, and @sec-19-s2l takes over.

When only the count of **one** key per vertex is needed, as in LeetCode 1519, one global array of 26 counters is enough, thanks to @thm-18-interval.

:::theorem{#thm-19-before} Counting with one global array
Run the iterative DFS of Chapter 18 with a global array cnt[26]. When *v* is entered, record before[*v*] = cnt[label[*v*]] and then increment cnt[label[*v*]]. When *v* is left, the number of vertices in the subtree of *v* with the same label as *v* is cnt[label[*v*]] − before[*v*].
:::

:::proof
Between entering and leaving *v*, the DFS enters exactly the vertices of the subtree of *v*, including *v* itself, each once (@thm-18-interval). Each entry increments the counter of its own label, so the counter of label[*v*] grows during that time by the number of subtree vertices with that label.
:::

This uses O(*n*) memory in total, independent of the alphabet size, but it needs a depth-first order rather than the BFS order.

## Rerooting {#sec-19-reroot}

:::definition{#def-19-reroot} Rerooting
[[Rerooting]] computes, for every vertex *r*, a quantity defined as if the tree were rooted at *r*. It roots the tree once, computes answers *inside* subtrees in a backward pass, and then moves the root from each parent to each child in a forward pass, correcting the answer with a formula.
:::

Running a separate traversal from every vertex costs O(*n*²), which for *n* = 3 · 10⁴ is already 9 · 10⁸ steps and for 10⁵ is out of the question. Rerooting does it in O(*n*).

### Sum of distances: the standard example

LeetCode 834 (Sum of Distances in Tree) asks, for every vertex *r*, for the sum of the distances from *r* to all other vertices. Root the tree at vertex 0 and define

* size[*v*]: the number of vertices in the subtree of *v*;
* down[*v*]: the sum of the distances from *v* to the vertices of its own subtree.

:::lemma{#lem-19-down} Pass 1: sums inside subtrees
size[*v*] = 1 + Σ size[*c*] and down[*v*] = Σ ( down[*c*] + size[*c*] ) over the children *c* of *v*.
:::

:::proof
The first formula is the size loop of @lst-18-bfs. For the second, every vertex *x* in the subtree of a child *c* is one edge further from *v* than from *c*, since its path to *v* is its path to *c* followed by the edge (*c*, *v*). Summing over the size[*c*] vertices of that subtree gives down[*c*] + size[*c*]; the vertex *v* itself contributes distance 0.
:::

At the root, down[0] is the full answer: ans[0] = down[0]. The second pass moves the root.

:::theorem{#thm-19-reroot} Pass 2: moving the root across an edge
If *c* is a child of *p*, then ans[*c*] = ans[*p*] − size[*c*] + (*n* − size[*c*]).
:::

:::proof
Compare each vertex's distance to *p* and to *c*. The size[*c*] vertices in the subtree of *c* reach *p* through *c*, so each is exactly one step closer to *c* than to *p*. The other *n* − size[*c*] vertices reach *c* through *p*, so each is exactly one step further from *c*. Adding up the changes gives the formula. Here size[*c*] is the subtree size in the tree rooted at 0, which is correct because the edge (*p*, *c*) splits the tree into the same two parts whichever vertex is the root.
:::

The formula needs ans[*p*] before ans[*c*], so the second pass walks the BFS order **forwards**.

```java {#lst-19-sumdist} Rerooting: sum of distances from every vertex (handbook template)
// Answer for EVERY root in O(n). Sum of distances from each node to all others (LeetCode 834).
static long[] sumOfDistances(int[] par, int[] order) {   // par from parentsFromEdges, BFS order
    int n = par.length;
    int[] size = new int[n];
    long[] down = new long[n];                           // down[v] = sum of distances inside v's subtree
    Arrays.fill(size, 1);
    for (int i = n - 1; i > 0; i--) {                    // pass 1: children before parents
        int v = order[i], p = par[v];
        size[p] += size[v];
        down[p] += down[v] + size[v];                    // every node below v is 1 step further from p
    }
    long[] ans = new long[n];
    ans[order[0]] = down[order[0]];
    for (int i = 1; i < n; i++) {                        // pass 2: parents before children
        int v = order[i];
        ans[v] = ans[par[v]] - size[v] + (n - size[v]);  // size[v] nodes get closer, the rest further
    }
    return ans;
}
```

Both passes are single loops over the order, so the time is O(*n*) and the memory O(*n*). For LeetCode 834, call `parentsFromEdges(n, edges, 0)` and the BFS order from Chapter 18 first, then copy the `long` answers into the `int[]` the problem returns (its limits keep the sums within `int`, but compute in `long`).

                     down = [8, 2, 1, 0, 0, 0]       down[1] = (0+1)+(0+1), down[0] = (2+3)+(1+2)
pass 2 (forwards):   ans[0] = down[0]           = 8

### A general recipe

The same two passes work for many other quantities. What changes is how the root's answer is split into parts and how a part is moved across an edge.

:::keyidea
**Rerooting recipe.** (1) Root at any vertex and compute down[*v*], the answer for the subtree of *v* alone, in the backward pass. (2) In the forward pass compute up[*v*], the contribution of everything **outside** the subtree of *v*, as seen from *v*; it is built from up[par[*v*]] and from the down values of *v*'s siblings. (3) Combine: ans[*v*] = combine(down[*v*], up[*v*]). If contributions are sums, "the siblings of *v*" is the parent's total minus *v*'s own share, as in @thm-19-reroot. If they are maxima, which cannot be subtracted, keep the two best child values at every vertex.
:::

The second case appears when the question is about the **farthest** vertex rather than the sum. The eccentricity of *v* is the largest distance from *v* to any vertex, the height of the tree if it were rooted at *v*. Pass 1 stores the two longest downward chains at each vertex (as in @lst-18-longest) and remembers which child gives the longest. Pass 2 computes up[*v*], the longest path that starts at *v* and leaves through its parent *p*: one edge to *p*, then either further up (up[*p*]) or down into a sibling of *v*. The best sibling chain is down1[*p*], unless that chain goes through *v* itself, in which case it is down2[*p*].

```java {#lst-19-ecc} Rerooting with the two best chains: the farthest distance from every vertex
// ecc[v] = the largest distance from v to any vertex = the height of the tree rooted at v.
static int[] eccentricities(int[] par, int[] order) {
    int n = par.length;
    int[] down1 = new int[n], down2 = new int[n], via = new int[n], up = new int[n], ecc = new int[n];
    Arrays.fill(via, -1);                                // via[p] = the child giving down1[p]
    for (int i = n - 1; i > 0; i--) {                    // pass 1: two longest downward chains
        int v = order[i], p = par[v], chain = down1[v] + 1;
        if (chain > down1[p]) {
            down2[p] = down1[p];
            down1[p] = chain;
            via[p] = v;
        } else if (chain > down2[p]) {
            down2[p] = chain;
        }
    }
    for (int i = 1; i < n; i++) {                        // pass 2: longest path leaving v upwards
        int v = order[i], p = par[v];
        int sideways = via[p] == v ? down2[p] : down1[p];    // best chain from p that avoids v
        up[v] = 1 + Math.max(up[p], sideways);
    }
    for (int v = 0; v < n; v++) ecc[v] = Math.max(down1[v], up[v]);
    return ecc;
}
```

:::claim{#thm-19-ecc} Correctness of the eccentricity passes
For every vertex *v*, `ecc[v]` is the largest distance from *v* to any vertex.
:::

:::proof
A farthest vertex from *v* lies either in the subtree of *v*, at distance down1[*v*] at most and exactly for the deepest one, or outside it. A path from *v* to a vertex outside its subtree starts with the edge to *p* = par[*v*] and then either continues up from *p* (best length up[*p*], computed earlier because *p* precedes *v* in BFS order) or goes down from *p* into the subtree of a sibling of *v*. The longest chain from *p* into a child other than *v* is down1[*p*] if the longest chain does not use *v*, and down2[*p*] (the best chain through any other child, or 0) if it does. For the root, up = 0 because nothing lies outside its subtree.
:::

For the handbook tree the passes give down1 = [2, 1, 1, 0, 0, 0], up = [0, 3, 3, 4, 4, 4] and ecc = [2, 3, 3, 4, 4, 4]. The vertices of smallest eccentricity are the best roots for a tree of minimum height; LeetCode 310 (Minimum Height Trees), listed on the rerooting card as extra practice, asks for exactly those.

LeetCode 2858 (Minimum Edge Reversals So Every Node Is Reachable) is rerooting over edge directions. Root at 0 and count the edges that point towards the root: those must be reversed for 0 to reach everything. Its key observation is that moving the root from *p* to a child *c* changes the count by exactly one, up or down depending only on the direction of the edge between them.

## Small-to-large merging {#sec-19-s2l}

Count arrays work when keys come from a small alphabet. When values are up to 10⁹, each subtree needs a real `HashSet` or `HashMap`. The obvious method, building each vertex's collection by copying all its children's collections into a new one, copies every element once for each of its ancestors, which on a path of 10⁵ vertices is about 5 · 10⁹ copies.

Two changes fix this. First, a vertex does not build a new collection: it **reuses** one of its children's collections, adding the others into it. Second, it always reuses the **largest** one, so that only the smaller collections are copied.

:::definition{#def-19-s2l} Small-to-large merging
[[Small-to-large merging]] combines two collections by inserting every entry of the one with fewer entries into the one with more, and keeping the larger object as the result. Swapping the two references, not their contents, makes "keep the larger one" free.
:::

:::theorem{#thm-19-s2l} Small-to-large costs O(n log n)
Suppose every vertex starts with one entry and collections are combined only by small-to-large merging. Then the total number of entries moved over all merges is O(*n* log *n*).
:::

:::proof
Look at one merge, in which a collection with *s* entries is poured into one with *t* ≥ *s* entries. Of the *s* moved entries, say *a* have keys that are already in the larger collection, so they disappear into existing entries, and *b* = *s* − *a* are new keys.

Suppose first that keys never repeat (*a* = 0, as for sets of distinct colours). Then the merged collection has *t* + *s* ≥ 2*s* entries, so every entry that moves lands in a collection at least twice as large as the one it left. A collection never has more than *n* entries, so an entry moves at most log₂ *n* times, and the *n* entries move O(*n* log *n*) times in total.

With repeated keys, split the merges into two kinds. If *a* ≥ *b*, the merge costs *s* ≤ 2*a*; but an entry can disappear only once, and only *n* entries are ever created, so all merges of this kind together cost at most 2*n*. If *a* < *b*, then *b* > *s*/2 and the merged collection has *t* + *b* > 1.5 · *s* entries; charge the cost *s* < 2*b* to the *b* surviving entries, two units each. Each of them is now in a collection more than 1.5 times larger than before, so it can be charged at most log₁.₅ *n* times. Together the cost is O(*n* log *n*).
:::

With `HashMap` or `HashSet`, each move is O(1) expected, so the merging takes O(*n* log *n*) expected time. The handbook template computes the number of distinct values in every subtree.

```java {#lst-19-distinct} Small-to-large: distinct values in every subtree (handbook template)
// Distinct colours in every subtree. Merge the SMALLER set into the LARGER one:
// each value moves O(log n) times, so the total is O(n log n).
static int[] distinctInSubtree(int[] par, int[] order, int[] color) {   // order = BFS order
    int n = par.length;
    int[] ans = new int[n];
    @SuppressWarnings("unchecked")
    HashSet<Integer>[] set = new HashSet[n];
    for (int i = n - 1; i >= 0; i--) {                   // children are merged in before v is used
        int v = order[i];
        if (set[v] == null) set[v] = new HashSet<>();
        set[v].add(color[v]);
        ans[v] = set[v].size();
        int p = par[v];
        if (p == -1) continue;
        if (set[p] == null) {
            set[p] = set[v];                             // first child: just hand the set over
        } else {
            HashSet<Integer> big = set[p], small = set[v];
            if (big.size() < small.size()) {
                HashSet<Integer> t = big;
                big = small;
                small = t;
            }
            big.addAll(small);
            set[p] = big;
        }
        set[v] = null;
    }
    return ans;
}
```

Three details make the listing work. When *v* is reached by the backward loop, all its children have already poured their sets into `set[v]` (or handed theirs over), so `ans[v]` is read at the right moment, before *v*'s own set leaves. The first child to finish simply hands its set to the parent, so a chain never copies anything. And `set[v] = null` drops the reference to a set that now belongs to the parent; reading it afterwards would be a bug.

:::pitfall
When the child's set is the larger one, swap the **references** (`big` and `small`) and store `big` in `set[p]`. Copying the large set into the parent's small one gives the right answer but destroys the O(*n* log *n*) bound: on a caterpillar (a long path with a leaf hanging from every vertex), the leaf can finish first and grab its parent's slot, and then every step copies the whole path below.
:::

### Counting equal-key pairs in every subtree

A common variant asks, for every vertex *v*, how many unordered pairs {*x*, *y*} of vertices in the subtree of *v* have equal keys. Use a map key → count per subtree instead of a set. The new pairs appear exactly at the moments when two groups of vertices first meet.

:::theorem{#thm-19-pairs} Pairs counted at merges
Merge the children's maps into the parent small-to-large, and when an entry (*k*, *c*) of the smaller map meets a count *b* of the same key in the larger map, add *b* · *c* to the parent's pair count. When *v* adds its own key *k* to its map, add the count of *k* already in the map. Then pairs[*v*] counts every pair of the subtree of *v* exactly once.
:::

:::proof
Take two vertices *x*, *y* with equal keys in the subtree of *v*, and let *u* be their LCA. If *u* is *x* (or *y*), the pair is counted when *u* adds its own key, because the other vertex is already in the map collected from *u*'s children, and nowhere else. Otherwise *x* and *y* are in the subtrees of different children of *u*. Before the merges at *u* they are in different maps; the pair is counted at the merge where the map containing *x* meets the map containing *y* (each merge at *u* combines one child's map with the union of the children before it), and never again, because afterwards they are in one map. Pairs inside one child's subtree were counted below and are passed up with `pairs[p] += pairs[v]`.
:::

```java {#lst-19-pairs} Small-to-large maps: pairs of equal keys inside every subtree
// pairs[v] = number of unordered pairs {x, y} in v's subtree with key[x] == key[y].
static long[] equalKeyPairs(int[] par, int[] order, long[] key) {
    int n = par.length;
    long[] pairs = new long[n];
    @SuppressWarnings("unchecked")
    HashMap<Long, Integer>[] mp = new HashMap[n];        // key -> how many times in the subtree
    for (int i = n - 1; i >= 0; i--) {                   // children are merged in before v is used
        int v = order[i];
        if (mp[v] == null) mp[v] = new HashMap<>();
        int same = mp[v].getOrDefault(key[v], 0);
        pairs[v] += same;                                // v pairs with each equal key below it
        mp[v].put(key[v], same + 1);
        int p = par[v];
        if (p == -1) continue;
        if (mp[p] == null) {                             // first child: hand the map over
            mp[p] = mp[v];
            pairs[p] += pairs[v];
        } else {
            HashMap<Long, Integer> big = mp[p], small = mp[v];
            if (big.size() < small.size()) {
                HashMap<Long, Integer> t = big;
                big = small;
                small = t;
            }
            long cross = 0;                              // pairs with one end on each side
            for (Map.Entry<Long, Integer> e : small.entrySet()) {
                int have = big.getOrDefault(e.getKey(), 0);
                cross += (long) have * e.getValue();
                big.put(e.getKey(), have + e.getValue());
            }
            mp[p] = big;
            pairs[p] += pairs[v] + cross;
        }
        mp[v] = null;
    }
    return pairs;
}
```

:::example{#ex-19-pairs} Merging maps with a swap
Take par = [−1, 0, 0, 1, 1, 3, 4, 2] with keys [1, 2, 1, 3, 1, 2, 4, 1] (@fig-19-pairs). The BFS order is [0, 1, 2, 3, 4, 7, 5, 6], so the loop runs 6, 5, 7, 4, 3, 2, 1, 0.

```trace
v  key  own pairs  map of v after adding its key    then
6   4      0       {4:1}                             handed to 4
5   2      0       {2:1}                             handed to 3
7   1      0       {1:1}                             handed to 2
4   1      0       {1:1, 4:1}                        handed to 1
3   3      0       {2:1, 3:1}                        merged into 1 (2 entries move, cross 0)
2   1      1       {1:2}                             handed to 0, pairs[0] = 1
1   2      1       {1:1, 2:2, 3:1, 4:1}              merged into 0: 0's map {1:2} is smaller,
                                                     SWAP; 1 entry moves, cross = 1*2 = 2
0   1      3       {1:4, 2:2, 3:1, 4:1}              pairs[0] = 1 + 1 + 2 + 3 = 7
```

The final counts are pairs = [7, 1, 1, 0, 0, 0, 0, 0]. Check the root directly: key 1 occurs at vertices 0, 2, 4 and 7, giving 6 pairs, and key 2 at vertices 1 and 5, giving 1 more. At the last merge the child's map had four entries and the parent's only one, so after the swap a single entry moved instead of four.
:::

On the machine used to test this book, both small-to-large listings, together with the rerooting listings, processed trees of 10⁵ vertices shaped as a path, a star and a caterpillar in 38–154 ms per tree.

:::infosys
The official sample paper's Easy problem has exactly this structure: for every node, count the pairs inside its subtree that satisfy a condition, then sum over all nodes, with *n* up to 10⁵ given as a parent array. Once each value is replaced by a key such that "the pair satisfies the condition" becomes "the keys are equal", it is @lst-19-pairs plus a final sum. Chapter 25 shows which key to use and the full solution; solve it under exam conditions there first.
:::

Other questions keep more information next to each map. In Codeforces 600E (Lomsat gelral) every vertex needs the sum of the colours that occur most often in its subtree. Counts in the larger map only ever increase during a merge, so the map can carry two extra numbers, the highest count so far and the sum of the colours that reach it, updated whenever a count changes; that is its key observation. Such fields must travel with the map when references are swapped, so it helps to wrap the map and its fields in one small class. LeetCode 2003 (Smallest Missing Genetic Value in Each Subtree) can also be solved with small-to-large sets, although its hint points to a faster idea that uses only the path from the vertex with value 1 to the root.

## Parity and edge operations {#sec-19-parity}

LeetCode 3068 (Find the Maximum Sum of Node Values) gives a tree, a value nums[*v*] on every vertex and a number *k*. One operation picks an edge (*u*, *v*) and replaces both nums[*u*] and nums[*v*] by their XOR with *k*. Operations may be repeated any number of times; maximise the sum of the values. The tree looks essential, but it is not.

Applying the XOR with *k* twice restores a value, so only the **parity** of the number of operations touching each vertex matters. Let *S* be the set of vertices touched an odd number of times. The final value of *v* is nums[*v*] ⊕ *k* if *v* ∈ *S* and nums[*v*] otherwise.

:::lemma{#lem-19-even} Reachable sets are the even-sized sets
In a connected graph, a set *S* of vertices can be the set of vertices touched an odd number of times exactly when |*S*| is even.
:::

:::proof
Each operation changes the parity of exactly two vertices, so the size of *S* changes by −2, 0 or +2, and it starts at 0. So |*S*| is always even. Conversely, let |*S*| be even and pair its vertices up arbitrarily. For a pair (*a*, *b*), apply the operation once to every edge of the path from *a* to *b*. Each inner vertex of the path lies on two of those edges and is touched twice; *a* and *b* lie on one edge each and are touched once. So this flips exactly *a* and *b*. Doing this for every pair flips exactly the vertices of *S*, because parities add up independently.
:::

So the problem is: choose an even-sized set *S* of vertices to maximise Σ nums[*v*] + Σ_{*v* ∈ *S*} *g*(*v*), where *g*(*v*) = (nums[*v*] ⊕ *k*) − nums[*v*] is the **gain** of flipping *v*. The edges no longer matter.

:::theorem{#thm-19-parity} The parity greedy
Let *P* be the set of vertices with positive gain and *m* = min over all *v* of |*g*(*v*)|. If |*P*| is even, the answer is Σ nums + Σ_{*P*} *g*. If |*P*| is odd, it is Σ nums + Σ_{*P*} *g* − *m*.
:::

:::proof
Without the parity condition, *P* is the best set, since it contains exactly the vertices that add something. If |*P*| is even it is allowed. If |*P*| is odd, every even set *S* differs from *P* in at least one vertex. Removing a vertex of *P* loses its gain *g*(*v*) > 0 = |*g*(*v*)|, and adding a vertex outside *P* adds *g*(*v*) ≤ 0, that is, loses |*g*(*v*)|. So the value of *S* is at most the value of *P* minus Σ |*g*(*v*)| over the vertices where *S* and *P* differ, which is at most the value of *P* minus *m*. Flipping the membership of a single vertex *u* with |*g*(*u*)| = *m* gives an even set with exactly that value.
:::

The same result comes out of a two-state DP over the vertices in any order, with best[0] and best[1] the best sum so far using an even or odd number of flips: for each value *x*, best′[*p*] = max(best[*p*] + *x*, best[1 − *p*] + (*x* ⊕ *k*)), starting from best = [0, −∞]. The answer is best[0]. The DP generalises better: if flipping a vertex had a cost, or the operations were restricted, the greedy would break but the DP would only need new transitions.

:::example{#ex-19-parity} Gains and parity
Take nums = [2, 3, 5, 1] and *k* = 6, on any tree with four vertices.

```trace
x   x XOR 6   gain     DP after x:  even  odd
2      4       +2                    2     4
3      5       +2                    9     7
5      3       -2                   14    12
1      7       +6                   19    21
```

The base sum is 11 and the positive gains are 2, 2 and 6: three of them, an odd number. The smallest |gain| is 2, so the answer is 11 + 10 − 2 = 19, the same as the DP's final even value. One optimal choice is to flip the first and the last vertex, giving 4 + 3 + 5 + 7 = 19; by @lem-19-even it is reachable on every tree with four vertices.
:::

Writing LeetCode 3068 from here is left to you; remember that the sum can exceed `int` and must be a `long`.

:::note
Parity states also appear in tree DPs where the tree *does* matter: if each edge can be used at most once, with a cost, or only edges of a matching may be chosen (as in the sample paper's Complex problem), then dp[*v*][parity of operations on the edge to the parent] carries the information a child must report to its parent, and the transitions combine children's parities one at a time.
:::

## Choosing a technique {#sec-19-choose}

The three techniques answer different shapes of question. The wording of a problem usually tells you which one it needs.

Table: {#tbl-19-choose} Signals in the statement and the technique they point to
| The statement says | Technique | Typical cost |
|---|---|---|
| choose vertices or edges with a rule between neighbours (no two adjacent, a matching, cover every edge) | tree DP with states per vertex | O(*n* · *S*²) |
| an operation changes both ends of an edge | parity of each vertex (@sec-19-parity), or a DP with a parity state | O(*n*) |
| for each vertex, something about its subtree with a small alphabet (26 letters, values ≤ 100) | count arrays merged upwards | O(*n* · alphabet) |
| for each vertex, something about its subtree with large values (distinct values, pairs, most frequent) | small-to-large maps or sets | O(*n* log *n*) |
| "for every vertex as the root", "sum over all other vertices", "the best root" | rerooting | O(*n*) |
| a sum over all pairs or all paths | per-edge contributions from size[*v*] (Chapter 18) | O(*n*) |
| many queries about paths between two given vertices | LCA and root prefixes (Chapter 18) | O(log *n*) per query |

When two rows seem to apply, try the cheaper one on paper first. Many "for every subtree" questions with a small alphabet do not need small-to-large, and many "for every root" questions turn out to be a sum over edges of size[*v*] · (*n* − size[*v*]), with no second pass at all.

## Summary

- A tree DP gives each vertex a few states; because children's subtrees share nothing, each child is optimised separately subject to the rule on its edge. Run it in reverse BFS order; cost O(*n* · *S*²).
- Independent set: take[*v*] = *w*[*v*] + Σ skip[*c*], skip[*v*] = Σ max(take[*c*], skip[*c*]). Matching: free[*v*] = Σ any[*c*], any[*v*] = free[*v*] + max(0, best single-child gain).
- Per-subtree counts over a small alphabet merge upwards in O(alphabet · *n*); for one key per vertex, a global counter with entry and exit times needs only O(*n*) memory.
- Rerooting computes answers inside subtrees in a backward pass and moves the root in a forward pass. For the sum of distances, ans[*c*] = ans[*p*] − size[*c*] + (*n* − size[*c*]). When contributions are maxima, keep the two best children.
- Small-to-large: reuse the largest child's collection and pour the others into it, swapping references. Every entry moves O(log *n*) times, so the total is O(*n* log *n*).
- Equal-key pairs are counted when two maps meet: an entry (*k*, *c*) meeting count *b* adds *b* · *c*.
- Operations that XOR both ends of an edge can flip exactly the even-sized vertex sets of a connected tree, so the tree drops out and a parity greedy or a two-state DP remains.

## Review questions

1. In @thm-19-mis, why is skip[*v*] built from max(take[*c*], skip[*c*]) while take[*v*] uses only skip[*c*]? Compute take and skip for the path 0–1–2–3 rooted at 0 with weights [1, 3, 3, 1].
2. Why does the matching DP need the state "not matched to a child" (free) rather than simply "matched" and "unmatched"?
3. Estimate the memory of `int[][] cnt = new int[n][26]` for *n* = 10⁵, and explain how @thm-19-before avoids it.
4. In @lst-19-sumdist, why must the second pass walk the BFS order forwards? What does the formula give for a leaf *c* whose parent is *p*?
5. In @lst-19-ecc, give a tree on which using down1[*p*] instead of the "sideways" value gives a wrong eccentricity.
6. In a star with centre 0 and *n* − 1 leaves, how many entries does @lst-19-distinct move in total, and why is that consistent with @thm-19-s2l?
7. A student's version of @lst-19-pairs writes `pairs[p] += cross;` but forgets `pairs[v]`. Which pairs are lost?
8. On the path 0–1–2–3, which operations of LeetCode 3068 flip exactly the vertices 0 and 3? Why can no sequence of operations flip only vertex 0?
9. For each statement, name the technique: (a) for every vertex, the number of distinct values (up to 10⁹) in its subtree; (b) for every vertex, the sum of the depths of all vertices if the tree were rooted there; (c) the largest total weight of vertices with no two adjacent.

:::answers
1. If *v* is taken, its children cannot be, so each child must be in its skip state. If *v* is skipped, the edge to a child imposes nothing, so each child takes its better state. For the path with weights [1, 3, 3, 1]: vertex 3 gives (take, skip) = (1, 0); vertex 2 gives (3 + 0, max(1, 0)) = (3, 1); vertex 1 gives (3 + 1, max(3, 1)) = (4, 3); vertex 0 gives (1 + 3, max(4, 3)) = (4, 4). The answer is 4, for example {1, 3} or {0, 2}.
2. Whether *v* may be matched to its parent depends only on whether it is already matched to a child. "Matched" would mix two different situations from the parent's point of view: matched to a child (the edge to the parent is forbidden) and, after the parent's decision, matched to the parent. Recording "not matched to a child" (free) and "anything" (any) gives the parent exactly what it needs.
3. 26 · 10⁵ = 2.6 · 10⁶ `int`s, about 10.4 MB, plus 10⁵ row objects with headers of about 16 bytes each (1.6 MB). @thm-19-before keeps one array of 26 counters and two numbers per vertex, because a subtree's vertices are entered consecutively in a depth-first traversal.
4. ans[*c*] is computed from ans[*p*], so the parent must be finished first, and in BFS order every parent precedes its children. For a leaf, size[*c*] = 1, so ans[*c*] = ans[*p*] − 1 + (*n* − 1) = ans[*p*] + *n* − 2.
5. The path 0–1–2 rooted at 0. For *v* = 1, the longest chain from 0 is down1[0] = 2, and it goes through 1 itself. Using it would give up[1] = 1 + 2 = 3, but the farthest vertex from 1 through its parent is 0, at distance 1. The sideways value is down2[0] = 0, giving up[1] = 1 and ecc[1] = max(1, 1) = 1, which is correct.
6. The first leaf to finish hands its set to the centre. Each of the other *n* − 2 leaves has a set of size 1 and the centre's set is at least as large, so one entry moves per leaf: *n* − 2 moves in total. The bound O(*n* log *n*) allows more; it is an upper bound, and here every moved entry lands in a set at least twice its old size, as in the proof.
7. The pairs whose two vertices both lie inside the child's subtree *v* (but not involving *p*). They were counted in pairs[*v*] and must be passed up; `cross` contains only pairs with one end on each side of the merge.
8. Apply the operation to the edges 0–1, 1–2 and 2–3 once each: vertices 1 and 2 are touched twice, 0 and 3 once. Flipping only vertex 0 would make |*S*| = 1, which is odd, and @lem-19-even shows that |*S*| is always even.
9. (a) Small-to-large sets (@lst-19-distinct), because the values are too large for count arrays. (b) Rerooting: it is the sum of distances from each vertex, @lst-19-sumdist. (c) A tree DP with two states, @lst-19-mis.
:::
