Many greedy algorithms ask one question again and again: *which option is the best one available right now?* The set of options keeps changing. Options become available as your capital grows or as you walk along a street, chosen options leave, and sometimes you want to take back an earlier choice. Sorting once does not help when the set changes, and scanning it costs O(*n*) per question. A priority queue answers in O(log *n*) and absorbs each change in O(log *n*).

Chapter 1 used Java's `PriorityQueue` as a black box and promised that this chapter would build one. The first three sections do that: the array layout of a binary heap, the two repair operations with proofs, and a linear-time way to build a heap. The fourth returns to `PriorityQueue`: comparators, the cost of each call, and how to delete items it cannot delete quickly.

The second half applies the heap to two greedy patterns. In **unlock and heap** (LeetCode 502, IPO) options become available in a known order and you take the best available one. In the **regret greedy** (LeetCode 1642) you accept every option, and when a limit breaks you undo the cheapest earlier choice. Both get proofs, because greedy rules that sound right are often wrong (Chapter 4). The chapter ends with a counting argument that needs no heap.

## The binary heap {#sec-5-heap}

A priority queue supports three operations: insert a value, look at the smallest, and remove the smallest. A sorted array makes insertion O(*n*); an unsorted array makes finding the minimum O(*n*). A balanced search tree (`TreeMap`) does all three in O(log *n*), but it keeps every value in order, which is more than the three operations need. A heap keeps just enough order to find the minimum.

:::definition{#def-5-heap} Binary heap
A [[binary heap]] is an array *a*[0..*n* − 1] read as a binary tree: the children of index *i* are 2*i* + 1 and 2*i* + 2 (when they are less than *n*), and the parent of index *i* ≥ 1 is ⌊(*i* − 1)/2⌋. A min-heap satisfies [[heap order]]: *a*[parent(*i*)] ≤ *a*[*i*] for every *i* ≥ 1.
:::

The tree is filled level by level, from left to right, with no gaps, because the indices 0, 1, 2, … are used in that order. No pointers are stored: the arithmetic on indices is the tree.

Heap order compares a node only with its parent. It says nothing about siblings, so 3 may sit left of 5 or right of it, and many different arrays are heaps of the same values. Yet it is enough to locate the minimum: follow the parents from any index *i* to the root, and the values never increase on the way up, so *a*[0] ≤ *a*[*i*]. The smallest value is always at index 0.

:::lemma{#lem-5-depth} Depth and height
Index *i* lies at depth ⌊log₂(*i* + 1)⌋ (the root has depth 0). A heap with *n* ≥ 1 elements has height ⌊log₂ *n*⌋.
:::

:::proof
We show that depth *d* consists of the indices 2ᵈ − 1, …, 2ᵈ⁺¹ − 2. For *d* = 0 this is the single index 0. If it holds for depth *d*, the children of those indices run from 2(2ᵈ − 1) + 1 = 2ᵈ⁺¹ − 1 to 2(2ᵈ⁺¹ − 2) + 2 = 2ᵈ⁺² − 2, which is the claim for depth *d* + 1. So index *i* has depth *d* exactly when 2ᵈ ≤ *i* + 1 < 2ᵈ⁺¹, that is *d* = ⌊log₂(*i* + 1)⌋. The deepest index is *n* − 1, at depth ⌊log₂ *n*⌋.
:::

A heap of 10⁶ values therefore has height 19. Both repair operations below walk along one root-to-leaf path, so they make at most 19 swaps.

## Sift-up and sift-down {#sec-5-sift}

Insertion and removal each break heap order in one place and then repair it along one path.

**Insert.** Put the new value at index *n*, the next free leaf. Only the pair (new leaf, its parent) can now be out of order. The [[sift-up]] repair swaps the value with its parent while it is smaller than the parent.

**Remove the minimum.** Save *a*[0], move the last leaf *a*[*n* − 1] into the root and shrink the heap by one. Only the pairs (root, child) can now be out of order. The [[sift-down]] repair swaps the value with its **smaller** child while that child is smaller than it.

```java {#lst-5-minheap} A min-heap of int values, written from scratch
// A min-heap of ints stored in an array: children of i are 2i+1 and 2i+2, parent is (i-1)/2
static class IntMinHeap {
    private int[] a = new int[16];
    private int size = 0;

    int size() { return size; }
    boolean isEmpty() { return size == 0; }
    int peek() { return a[0]; }                     // call only when !isEmpty()

    void add(int x) {
        if (size == a.length) a = Arrays.copyOf(a, 2 * size);
        a[size] = x;                                // new leaf at the end of the array
        siftUp(size++);
    }

    int poll() {                                    // call only when !isEmpty()
        int top = a[0];
        a[0] = a[--size];                           // move the last leaf to the root
        siftDown(0);
        return top;
    }

    private void siftUp(int i) {
        while (i > 0) {
            int p = (i - 1) / 2;
            if (a[p] <= a[i]) return;               // order restored
            swap(i, p);
            i = p;
        }
    }

    private void siftDown(int i) {
        while (true) {
            int l = 2 * i + 1, r = l + 1, m = i;    // m = smallest of i and its children
            if (l < size && a[l] < a[m]) m = l;
            if (r < size && a[r] < a[m]) m = r;
            if (m == i) return;                     // order restored
            swap(i, m);
            i = m;
        }
    }

    private void swap(int i, int j) { int t = a[i]; a[i] = a[j]; a[j] = t; }
}
```

Why do the loops repair the heap rather than move the problem around? Each keeps an invariant that pins the only possible violation to one position, and that position moves one level per step until the violation is gone.

:::lemma{#lem-5-siftup} Sift-up restores heap order
Suppose that, at the start of an iteration of `siftUp`, every parent–child pair is in order except possibly the pair (parent of *i*, *i*), and that the parent of *i* (if *i* > 0) is at most every child of *i*. Then the same holds after the iteration for the new *i*, and when the loop ends the whole array is a heap.
:::

:::proof
Initially *i* is the new leaf: it has no children, and every other pair was in order in the old heap. In an iteration with parent *p*, if *a*[*p*] ≤ *a*[*i*] every pair is in order and the method returns. Otherwise swap *x* = *a*[*i*] with the larger *y* = *a*[*p*], so *x* moves to *p* and *y* to *i*. The pair (*p*, *i*) now reads *x* < *y*. For the other child *s* of *p*, the old pair (*p*, *s*) gave *y* ≤ *a*[*s*], so *x* < *a*[*s*]. For each child *c* of *i*, the second half of the invariant gave *y* ≤ *a*[*c*], and *y* is now the parent of *c*. Only the pair (parent of *p*, *p*) can be out of order, which is the first half of the invariant for the new *i* = *p*. For the second half, the old parent *g* of *p* satisfied *g* ≤ *y* ≤ *a*[*s*], so *g* is at most both children of *p*. Each iteration lowers *i*, so the loop ends, either by returning or at *i* = 0, which has no parent.
:::

:::lemma{#lem-5-siftdown} Sift-down restores heap order
Suppose that, at the start of an iteration of `siftDown`, every parent–child pair is in order except possibly the pairs (*i*, child of *i*), and that the parent of *i* (if *i* > 0) is at most every child of *i*. Then the same holds after the iteration for the new *i*, and when the loop ends the whole array is a heap.
:::

:::proof
Initially *i* = 0 holds the moved leaf. Every pair whose parent is not the root was in order in the old heap, and the root has no parent. In an iteration, *m* is the index of the smallest of *a*[*i*] and its children. If *m* = *i*, the pairs (*i*, child) are in order too and the method returns. Otherwise swap *y* = *a*[*i*] with the smaller *x* = *a*[*m*], which is also at most the other child *o* of *i*. The pair (*i*, *m*) reads *x* < *y*, and (*i*, *o*) holds because *x* ≤ *a*[*o*]. If *i* has a parent *q*, the second half of the invariant gave *a*[*q*] ≤ *x*, so (*q*, *i*) holds. Only the pairs (*m*, child of *m*) can be out of order, which is the first half of the invariant for the new *i* = *m*. For the second half, the new parent of *m* holds *x*, and the old pairs (*m*, *c*) gave *x* ≤ *a*[*c*] for each child *c* of *m*. Each iteration raises *i*, so the loop ends, by returning or at a leaf, which has no children.
:::

Both loops make one swap per level, and by @lem-5-depth there are at most ⌊log₂ *n*⌋ levels, so `add` and `poll` cost O(log *n*); sift-down makes at most two comparisons per level. `peek` is O(1). The occasional array doubling costs O(1) amortised, as for `ArrayList` in Chapter 1. Memory is O(*n*). The class agreed with `java.util.PriorityQueue` on 5,000 random sequences of adds and polls (672,240 operations), with many duplicates in half of the runs and values near `Integer.MIN_VALUE` and `Integer.MAX_VALUE` in others.

## Building a heap in linear time {#sec-5-heapify}

To turn *n* given values into a heap, you could call `add` *n* times. That costs O(*n* log *n*) and the bound is reached: on a decreasing input each new value is the smallest so far and climbs all the way to the root. For *n* = 10⁶ decreasing values this made 17,951,445 swaps.

There is a faster way, called [[heapify|heapify (bottom-up)]]. Every leaf is already a one-element heap. Go through the internal nodes from the **last one to the first** and sift each one down inside its own subtree. When node *i* is processed, both of its child subtrees are already heaps, so one sift-down makes the subtree of *i* a heap.

```java {#lst-5-heapify} Bottom-up heapify on a plain array
// Turn a[0..n-1] into a min-heap in O(n): sift down every internal node, last one first
static void heapify(int[] a) {
    for (int i = a.length / 2 - 1; i >= 0; i--) siftDown(a, a.length, i);
}

static void siftDown(int[] a, int n, int i) {
    while (true) {
        int l = 2 * i + 1, r = l + 1, m = i;
        if (l < n && a[l] < a[m]) m = l;
        if (r < n && a[r] < a[m]) m = r;
        if (m == i) return;
        int t = a[i]; a[i] = a[m]; a[m] = t;
        i = m;
    }
}
```

The loop starts at ⌊*n*/2⌋ − 1 because that is the last index with a child: its left child is 2⌊*n*/2⌋ − 1 ≤ *n* − 1, while index ⌊*n*/2⌋ has left child 2⌊*n*/2⌋ + 1 ≥ *n*.

:::theorem{#thm-5-heapify} Heapify is correct
When @lst-5-heapify finishes, *a* is a min-heap holding the same values.
:::

:::proof
Values only move by swaps, so the multiset is unchanged. The loop invariant is: before the iteration for *i*, the subtree rooted at every index *j* > *i* is a heap. Before the first iteration, every *j* > ⌊*n*/2⌋ − 1 is a leaf, and a single node is a heap. In the iteration for *i*, both child subtrees of *i* are heaps by the invariant, so inside the subtree of *i* the only pairs that may be out of order are (*i*, child of *i*), and *i* has no parent inside its subtree. This is the starting situation of @lem-5-siftdown, so after `siftDown(a, n, i)` the subtree of *i* is a heap, and so is every subtree inside it. Subtrees outside it were not touched. After the iteration for *i* = 0, the subtree of the root, which is the whole array, is a heap.
:::

:::theorem{#thm-5-linear} Heapify makes fewer than 2*n* swaps
On an array of *n* values, @lst-5-heapify makes fewer than 2*n* swaps and runs in O(*n*) time.
:::

:::proof
Let *h* = ⌊log₂ *n*⌋ be the height. A value that starts at depth *d* can move down at most *h* − *d* levels, one swap per level, and depth *d* contains at most 2ᵈ indices. So the number of swaps is at most the sum of 2ᵈ · (*h* − *d*) over *d* = 0, 1, …, *h*. Write *k* = *h* − *d* for the distance to the bottom level. The term for *k* is 2ʰ · *k*/2ᵏ, so the sum equals 2ʰ · *S* with

*S* = 1/2 + 2/4 + 3/8 + ⋯ + *h*/2ʰ.

Halving *S* shifts every term one place to the right: *S*/2 = 1/4 + 2/8 + ⋯ + *h*/2ʰ⁺¹. Subtracting term by term gives *S* − *S*/2 = 1/2 + 1/4 + ⋯ + 1/2ʰ − *h*/2ʰ⁺¹, which is less than 1. So *S* < 2, and since 2ʰ ≤ *n*, there are fewer than 2*n* swaps. Each level of a sift-down costs at most two comparisons and one swap, and each of the ⌊*n*/2⌋ calls costs O(1) more to stop, so the total time is O(*n*).
:::

Most nodes are near the bottom: half are leaves and do no work, a quarter move at most one level, an eighth at most two, and only the root can travel the full height. The true maximum is even lower than 2*n*, because a value can move at most the height of its own subtree; for *n* = 10⁶ those heights add up to 999,993. A decreasing input of that size made 999,988 swaps and a random one 744,244, against 17,951,445 for *n* calls of `add`.

:::example{#ex-5-heapify} Heapify step by step
Take *a* = [9, 5, 8, 2, 7, 6, 1, 4, 3, 0], so *n* = 10 and the internal nodes are 4, 3, 2, 1, 0.

```trace

Six swaps in total. In the last call the 9 travels from the root to index 8 along 0 → 1 → 3 → 8, swapping with 0, then 2, then 3.
:::

On 5,000 random arrays of up to 40 values, the output of @lst-5-heapify was always heap-ordered and held the same values as its input. Java's `new PriorityQueue<>(collection)` uses the same bottom-up method. Two uses follow. **Heap sort** heapifies and then polls *n* times, sorting in O(*n* log *n*) with no extra array (with a max-heap, each polled maximum goes into the slot just freed at the end). And the *k* smallest of *n* values cost O(*n* + *k* log *n*): heapify, then poll *k* times.

## Java's PriorityQueue {#sec-5-pq}

`java.util.PriorityQueue` is the heap of @lst-5-minheap made generic: an `Object[]` array, sift-up and sift-down, and a `Comparator` instead of `<`. In an exam you use it rather than your own class, so what matters is the comparator, the cost of each call, and what it cannot do.

### Comparators and constructors

```java {.fragment}
PriorityQueue<Integer> minHeap = new PriorityQueue<>();                                // smallest first
PriorityQueue<Integer> maxHeap = new PriorityQueue<>(Collections.reverseOrder());      // largest first
PriorityQueue<Integer> sized = new PriorityQueue<>(1 << 16, Collections.reverseOrder()); // capacity hint
PriorityQueue<Integer> built = new PriorityQueue<>(Arrays.asList(5, 1, 4, 2, 3));      // heapify, O(n)
PriorityQueue<int[]> pairs = new PriorityQueue<>(
        (x, y) -> x[0] != y[0] ? Integer.compare(y[0], x[0])                           // larger x[0] first
                               : Integer.compare(x[1], y[1]));                         // ties: smaller x[1]
```

For the pairs heap, adding {3, 7}, {5, 2}, {3, 1}, {5, 9} and {1, 4} and polling until empty gives {5, 2}, {5, 9}, {3, 1}, {3, 7}, {1, 4}. The comparator decides everything, so write it with `Integer.compare` or `Long.compare`. The tempting `(x, y) -> y - x` for a max-heap overflows when the values differ by more than 2³¹ − 1 and then orders them wrongly (Chapter 4).

Table: {#tbl-5-pq} What PriorityQueue calls cost, for a heap of size n
| Call | Cost | Why |
|---|---|---|
| `add(x)`, `offer(x)` | O(log *n*) | one sift-up; array growth is amortised O(1) |
| `poll()` | O(log *n*) | one sift-down; returns `null` when empty |
| `peek()` | O(1) | reads index 0; returns `null` when empty |
| `remove(x)`, `contains(x)` | O(*n*) | linear search through the array, then one sift |
| `size()`, `isEmpty()` | O(1) | a stored counter |
| `new PriorityQueue<>(collection)` | O(*n*) | bottom-up heapify |
| `addAll` of *m* items | O(*m* log(*n* + *m*)) | one `add` per item |
| iterator, `toString()` | O(*n*) | internal array order, not sorted |

:::java
Only the top is ordered. Printing `built` gives `[1, 2, 4, 5, 3]`, its internal array. Printing `maxHeap` after adding 5, 1, 4, 2, 3 gives `[5, 3, 4, 1, 2]`. To see the values in order, poll them. Ties come out in no guaranteed order, so add a second key (an index) when ties matter. A `PriorityQueue` refuses `null`, and `int v = pq.poll();` on an empty queue throws a `NullPointerException` while unboxing.
:::

:::pitfall
Never change the key of an object while it is inside a heap, for example by writing into an `int[]` that the queue holds. The heap does not notice, its order is silently broken, and later polls return wrong values. Remove the object and insert a new one instead, or use lazy deletion.
:::

The plain max-heap is all that LeetCode 1046 (Last Stone Weight) needs: its worksheet hint describes the whole simulation, and it is a good first problem of the day.

### Lazy deletion

`remove(x)` costs O(*n*) because the heap has no index from values to positions. If a problem deletes arbitrary values many times (tasks are cancelled, items expire, a value changes), *n* such deletions cost O(*n*²). The standard fix is not to delete at once.

:::definition{#def-5-lazy} Lazy deletion
With [[lazy deletion]], a deleted value stays in the heap and is only recorded as "to be deleted". Whenever a recorded value reaches the top, it is popped and discarded before the top is used.
:::

```java {#lst-5-lazy} A min-heap with lazy deletion of arbitrary values
// Min-heap that can delete any value: deleted values are dropped when they reach the top
static class LazyMinHeap {
    private final PriorityQueue<Integer> heap = new PriorityQueue<>();
    private final Map<Integer, Integer> pending = new HashMap<>();  // value -> copies still to delete
    private int live = 0;

    void add(int x) { heap.add(x); live++; }
    void remove(int x) { pending.merge(x, 1, Integer::sum); live--; }   // x must be present
    int size() { return live; }
    int peek() { clean(); return heap.peek(); }     // call only when size() > 0
    int poll() { clean(); live--; return heap.poll(); }

    private void clean() {                          // pop tops that are waiting to be deleted
        Integer c;
        while ((c = pending.get(heap.peek())) != null) {
            int v = heap.poll();
            if (c == 1) pending.remove(v); else pending.put(v, c - 1);
        }
    }
}
```

:::claim{#thm-5-lazy} Lazy deletion returns the smallest live value
Let *L* be the multiset of live values (added and not yet removed or polled) and *D* the multiset recorded in `pending`. At all times the heap holds exactly *L* together with *D*. After `clean()`, if *L* is not empty, the top of the heap is the smallest value of *L*.
:::

:::proof
`add` puts *x* into the heap and into *L*. `remove(x)` moves one copy of *x* from *L* to *D* and leaves the heap alone; that copy is in the heap because *x* was live. `clean` pops the top while its value has a copy in *D*, and removes that copy from *D*, so the heap still equals *L* together with *D*. When `clean` stops, the top's value has no copy in *D*, so the top belongs to *L*; being the smallest value in the heap, it is the smallest of *L*. (If *L* is not empty, `clean` cannot empty the heap, because it never pops a copy belonging to *L*.) `poll` then removes that live top from both the heap and *L*.
:::

Each added value enters the heap once and leaves it once, either through `poll` or inside `clean`. So *N* operations cost O(*N* log *N*) in total, O(log *N*) amortised each, against O(*N*²) for repeated `remove(x)`. The price is memory: deleted values stay in the heap until they surface, so the heap can hold all *N* values even when few are live. The class matched a brute-force multiset on 5,000 random sequences (378,066 operations) of adds, deletions of random live values, peeks and polls. Chapter 17 uses the same idea in Dijkstra's algorithm, where an outdated distance stays in the queue and is skipped when it surfaces.

## Pattern 1: unlock options and take the best {#sec-5-unlock}

In the first pattern, every option has an **unlock key** and a **value**. An option becomes available once some resource reaches its key, and taking an option makes the resource grow. You may take at most *k* options and want the most value.

LeetCode 502 (IPO) is the model. You start with capital *w* and may finish at most *k* distinct projects, one after another. Project *i* can be started only when your current capital is at least capital[*i*], and finishing it adds profit[*i*] ≥ 0 to your capital (the requirement is not spent). The task is the largest final capital.

:::definition{#def-5-unlock} Unlock and heap
The [[unlock-and-heap greedy]] sorts the options by their unlock key, moves a pointer along the sorted list to push every option whose key the resource has reached into a heap ordered by value, and takes the heap's best option at each step.
:::

```java {#lst-5-ipo} Unlock and heap for LeetCode 502 (handbook template)
// Unlock + heap (LeetCode 502 IPO): do at most k projects, each needs capital <= w and adds profit
static long maxCapital(int k, long w, int[] profit, int[] capital) {
    int n = profit.length;
    Integer[] idx = new Integer[n];
    for (int i = 0; i < n; i++) idx[i] = i;
    Arrays.sort(idx, (x, y) -> Integer.compare(capital[x], capital[y]));   // unlock order
    PriorityQueue<Integer> unlocked = new PriorityQueue<>(Collections.reverseOrder());
    int i = 0;
    while (k-- > 0) {
        while (i < n && capital[idx[i]] <= w) unlocked.add(profit[idx[i++]]);
        if (unlocked.isEmpty()) break;
        w += unlocked.poll();                     // best project we can afford right now
    }
    return w;
}
```

The pointer only moves forward, and that is safe because *w* never decreases: profits are non-negative, so a project that was affordable once stays affordable. At every moment the heap holds exactly the projects not yet taken whose requirement is at most the current *w*. The sort is by index (`Integer[] idx`), so that profit and capital stay paired.

:::theorem{#thm-5-ipo} Taking the best unlocked project is optimal
With non-negative profits, @lst-5-ipo returns the largest capital that any valid plan of at most *k* projects can reach.
:::

:::proof
By induction on *k*. For *k* = 0 the method returns *w*, which is correct. Let *k* ≥ 1. If no project has capital[*i*] ≤ *w*, none can ever be started, and the method correctly stops with *w*. Otherwise let *g* be its first choice: a largest profit among the projects with capital[*i*] ≤ *w*. An exchange argument shows that some optimal plan starts with *g*. Take an optimal plan *P* = *p*₁, …, *p*ₘ with *m* ≤ *k*. If *m* = 0, the plan "*g* alone" is valid and no worse, because profit(*g*) ≥ 0.

*Case 1: g appears in P.* Move it to the front. *g* is affordable at the start. Every other project now has before it the same finished projects as in *P*, or those plus *g*; profits are non-negative, so its starting capital has not fallen and it is still affordable. The final capital is unchanged.

*Case 2: g does not appear in P.* Replace *p*₁ by *g*. Since *p*₁ was affordable with capital *w*, the choice of *g* gives profit(*p*₁) ≤ profit(*g*). Every later project starts with profit(*g*) − profit(*p*₁) ≥ 0 more capital than in *P*, so it is still affordable, and the final capital does not fall.

So an optimal plan starts with *g*, and the rest of it is a valid plan of at most *k* − 1 projects for the smaller instance with starting capital *w* + profit(*g*) and *g* removed. Conversely, any such plan placed after *g* is valid for the original. Hence the two optima are equal. After taking *g*, the method's heap holds exactly the projects of the smaller instance that are affordable with its starting capital, the state it would reach if started on that instance, so by induction it returns that optimum.
:::

The sort costs O(*n* log *n*). Each project is pushed at most once and at most *k* are polled, so the heap work is O((*n* + *k*) log *n*). Memory is O(*n*). The template matched an exhaustive search over all orders of at most *k* projects on 20,000 random instances with up to six projects.

:::example{#ex-5-ipo} Three projects from six
Start with *w* = 1 and *k* = 3. The projects, already in unlock order, are (capital, profit) = (0, 1), (1, 2), (2, 5), (3, 3), (5, 4) and (9, 8).

```trace
step  unlocked now        heap of profits   take   w after
 1    (0,1) (1,2)         2 1                 2       3
 2    (2,5) (3,3)         5 3 1               5       8
 3    (5,4)               4 3 1               4      12
```

The answer is 12, which the exhaustive search confirms. The project (9, 8) is unlocked only after the third step; with *k* = 4 it would be taken next, for 20. The profit 1 is never taken: it was unlocked first, but something better was always available.
:::

:::java
LeetCode's method returns `int`, and the statement guarantees that the answer fits. The template keeps *w* in a `long` for other versions of the problem; call it as `(int) maxCapital(k, w, profits, capital)`.
:::

### When no heap is needed

One of the plan's most reported Infosys problems has the same shape. You start with experience *e*; monster *i* can be beaten when *e* ≥ power[*i*] and then adds bonus[*i*] ≥ 0; you want the largest **number** of monsters beaten. Experience never falls, so every unlocked monster can be beaten in turn, and the order among unlocked monsters does not change the count. The heap disappears: sort by power and walk while *e* ≥ power, adding each bonus to *e* (a `long`). IPO needs the heap only because *k* limits how many unlocked options you take, so *which* one you take matters. Chapter 9 writes a brute force for the monsters problem and Chapter 24 solves it in full.

:::infosys
"RPG: maximum monsters defeated" has 11 reports in the plan's question bank (SP, 2022–2026), and the plan names LeetCode 502 as its practice twin. Read the limits: the sort-and-walk greedy relies on non-negative bonuses, and the experience can exceed the `int` range.
:::

The bonus problem LeetCode 871 (Minimum Number of Refueling Stops) unlocks options by distance: the stations you have driven past form the heap, and you decide only when the tank runs dry which of them you should have stopped at.

## Pattern 2: the regret greedy {#sec-5-regret}

In the second pattern the options arrive in a fixed order and you cannot see ahead, so deciding at once is risky: a resource spent now may be needed for a bigger demand later. The regret greedy postpones the decision.

:::definition{#def-5-regret} Regret greedy
A [[regret greedy]] processes options in a fixed order, commits to each one, records the commitments in a heap, and whenever a constraint is violated undoes the recorded commitment whose removal costs the least.
:::

### Keeping the k largest

The smallest version of the idea keeps the *k* largest values of a stream. A min-heap of size *k* holds the current members, and its top is the weakest member. A new value always joins; if the heap now has *k* + 1 members, the weakest leaves.

```java {#lst-5-topk} The k largest values of a stream with a min-heap of size k
// The k largest values of a stream, k >= 1: a min-heap of size k whose top is the weakest member
static long sumOfKLargest(int[] a, int k) {
    PriorityQueue<Integer> best = new PriorityQueue<>();
    long sum = 0;
    for (int x : a) {
        best.add(x);
        sum += x;
        if (best.size() > k) sum -= best.poll();     // evict the smallest of k + 1
    }
    return sum;
}
```

:::lemma{#lem-5-topk} The heap holds the k largest so far
After each step of @lst-5-topk, the heap holds the min(*k*, *t*) largest of the first *t* values (as a multiset), and `sum` is their sum.
:::

:::proof
By induction on *t*; at *t* = 0 the heap is empty. Suppose the heap holds a set *T* of the *k* largest of the first *t* values, and the new value is *x*. Every earlier value outside *T* is at most every value in *T*, so in the first *t* + 1 values at least *k* values (those of *T*) are at least as large as it; hence the *k* largest of the first *t* + 1 values can be chosen from *T* together with *x*. Those are *k* + 1 values, and removing the smallest leaves the *k* largest. While fewer than *k* values have arrived, nothing is removed and the heap holds all of them. `sum` changes exactly as the heap does.
:::

For [5, 1, 9, 3, 7, 2, 8] and *k* = 3, the evictions are 1, 3, 2 and 5, the heap ends as {7, 8, 9}, and the sum is 24. Each step costs O(log *k*), because the heap never holds more than *k* + 1 values. The method agreed with "sort and add the *k* largest" on 20,000 random arrays.

### Furthest building with bricks and ladders

LeetCode 1642 (Furthest Building You Can Reach) gives building heights *h*[0..*n* − 1], a number of bricks *B* and a number of ladders *L*. You walk from building 0 to the right. Stepping down or level is free. A climb of *c* > 0 from building *i* to building *i* + 1 needs either one ladder or *c* bricks. Find the furthest building index you can reach.

A ladder is worth most on a big climb, but when you meet a climb you do not know whether bigger ones are coming. The regret greedy gives every climb a ladder tentatively. When it runs out of ladders, it takes back the ladder from the smallest climb so far and pays for that climb with bricks. This is @lem-5-topk with *k* = *L*: the ladders always sit on the *L* largest climbs seen so far, and bricks pay for the rest.

```java {#lst-5-ladders} The regret greedy for LeetCode 1642 (handbook template)
// Regret greedy (LeetCode 1642): give ladders to the biggest climbs seen so far
static int furthestBuilding(int[] h, int bricks, int ladders) {
    PriorityQueue<Integer> ladderClimbs = new PriorityQueue<>();   // min-heap
    for (int i = 0; i + 1 < h.length; i++) {
        int climb = h[i + 1] - h[i];
        if (climb <= 0) continue;
        ladderClimbs.add(climb);
        if (ladderClimbs.size() > ladders) bricks -= ladderClimbs.poll();  // smallest pays bricks
        if (bricks < 0) return i;
    }
    return h.length - 1;
}
```

Two facts make it correct: for a fixed target building the best use of the ladders is clear, and the reachable buildings form a prefix, so it is enough to find the first unreachable one.

:::lemma{#lem-5-reach} When a building can be reached
Let *S*(*j*) be the sum of the positive climbs between buildings 0 and *j*, and *T*(*j*) the sum of the largest min(*L*, number of those climbs) of them. Building *j* can be reached if and only if *S*(*j*) − *T*(*j*) ≤ *B*. Moreover *S*(*j*) − *T*(*j*) never decreases as *j* grows, so the reachable buildings are 0, 1, …, *J* for some *J*.
:::

:::proof
If *S*(*j*) − *T*(*j*) ≤ *B*, put the ladders on the largest climbs and pay for the others with bricks: that needs *S*(*j*) − *T*(*j*) bricks. Conversely, any way of reaching *j* puts ladders on at most *L* of the positive climbs. Their sum is at most *T*(*j*), because no *L* or fewer of the climbs add up to more than the *L* largest, so the bricks used are at least *S*(*j*) − *T*(*j*), and they cannot exceed *B*. For the second statement, a step down leaves both sums unchanged. A new climb *c* > 0 raises *S* by *c* and *T* by at most *c*: the new *L* largest either leave out *c*, and then they are the old *L* largest, or they contain *c* together with at most *L* − 1 old climbs, whose sum is at most the old *T*.
:::

:::theorem{#thm-5-ladders} The regret greedy finds the furthest building
@lst-5-ladders returns the largest reachable index *J*.
:::

:::proof
By @lem-5-topk applied to the positive climbs, after each processed climb into building *i* + 1 the heap holds the min(*L*, count) largest positive climbs so far. Every other positive climb so far was subtracted from `bricks` exactly once, when it left the heap (possibly right after entering it). So at the check `bricks < 0`, the variable equals *B* − (*S*(*i* + 1) − *T*(*i* + 1)). By @lem-5-reach the check fails exactly when building *i* + 1 cannot be reached. The method checks at every positive climb, and steps down do not change *S* − *T*, so the first failure is at the first unreachable building *i* + 1 = *J* + 1, and the method returns *i* = *J*. If no check fails, every building is reachable and it returns *n* − 1.
:::

:::example{#ex-5-ladders} Bricks and ladders, step by step
Heights [2, 7, 5, 6, 12, 13, 10, 18, 20, 22, 21, 27] with *B* = 8 bricks and *L* = 2 ladders. Each row is one step of the loop.

```trace

0     2 -> 7          5      {5}                  -           8
1     7 -> 5         -2      skip                             8

:::

:::pitfall
Two details in @lst-5-ladders are easy to get wrong. The `continue` for `climb <= 0` is essential: a negative "climb" in the heap would be the smallest, and paying for it would *add* bricks. And the method returns *i*, not *i* + 1, because the failed climb leads into building *i* + 1, which is not reached.
:::

:::keyidea
**Regret.** The proof of a regret greedy has two parts. For a fixed prefix, the best set of choices has a simple form (here: ladders on the largest climbs). The heap maintains that set as the prefix grows.
:::

The two bonus problems are regret greedies with a different limit. In LeetCode 630 (Course Schedule III), with courses taken in order of deadline, the course to give up when time runs out is the longest one taken so far. In Codeforces 1526C2 (Potions (Hard Version)), the potion to give up when health would turn negative is the most harmful one drunk so far. Each needs its own version of @lem-5-reach, which is the real work of those problems.

## A greedy count without a heap {#sec-5-rises}

The last core problem of the day has an answer that can be counted directly. LeetCode 1526 (Minimum Number of Increments on Subarrays to Form a Target Array) starts from zeros and allows one operation: add 1 to every element of a chosen subarray. It asks for the fewest operations that produce a target *t*[0..*n* − 1] of non-negative values. Read backwards, this is the fewest "subtract 1 from a subarray" operations that turn *t* into zeros.

:::theorem{#thm-5-rises} Fewest increments equal the positive rises
With *t*[−1] = 0, the fewest operations are R = Σ max(0, *t*[*i*] − *t*[*i* − 1]) over *i* = 0..*n* − 1.
:::

:::proof
*Lower bound.* Use the difference array of Chapter 2: *d*[*i*] = *t*[*i*] − *t*[*i* − 1] with *t*[−1] = 0. By the range-add theorem of Chapter 2, one operation on *t*[*l*..*r*] adds 1 to *d*[*l*] and, if *r* + 1 < *n*, subtracts 1 from *d*[*r* + 1]; nothing else in *d* changes. Track the quantity *Q* = Σ max(0, *d*[*i*]). Raising one entry by 1 raises *Q* by at most 1, and lowering an entry never raises *Q*, so each operation raises *Q* by at most 1. *Q* starts at 0 for the zero array and must end at R, so at least R operations are needed.

*Upper bound.* Build *t* from left to right while keeping exactly *t*[*i*] operations "open" at position *i*; each open operation will cover a contiguous run of positions. At *i* = 0, open *t*[0] operations. Moving from *i* − 1 to *i*, if *t*[*i*] > *t*[*i* − 1], keep all open operations and open *t*[*i*] − *t*[*i* − 1] new ones; otherwise end *t*[*i* − 1] − *t*[*i*] of them at position *i* − 1 and keep the rest. Each operation covers one contiguous run, so it is a legal subarray operation, and position *i* is covered exactly *t*[*i*] times. The number of operations opened is exactly R.
:::

```fig {#fig-5-rises} The target [3, 1, 4, 4, 2, 5, 1]. The blue bars rise above their left neighbour (or above 0 at the start) by 3, 3 and 3; only those rises open new operations, so the answer is 9.
{"type": "bars", "values": [3, 1, 4, 4, 2, 5, 1], "colors": {"0": "blue", "2": "blue", "5": "blue"}, "unit": 20}
```

For *t* = [3, 1, 4, 4, 2, 5, 1] the rises are 3, 0, 3, 0, 0, 3, 0, so 9 operations suffice and are needed. A breadth-first search over all intermediate arrays agreed with the formula on 3,000 random targets with up to five values in 0..3. The upper bound is a greedy construction: never end an operation early, never open one that is not forced. The one-pass solution is left for the problem worksheet. Watch the type of the sum: 10⁵ values alternating between 10⁵ and 1 give 4,999,950,001, more than an `int` holds, so keep it in a `long` unless the statement promises a small answer.

## Summary

- A binary heap is an array read as a complete binary tree: children 2*i* + 1 and 2*i* + 2, parent ⌊(*i* − 1)/2⌋. Heap order puts the minimum at index 0; the height is ⌊log₂ *n*⌋.
- Insert appends and sifts up; remove-min moves the last leaf to the root and sifts down, swapping with the smaller child. An invariant pins the only violation to one moving position, so each costs O(log *n*).
- Bottom-up heapify sifts down the internal nodes from last to first and makes fewer than 2*n* swaps. `new PriorityQueue<>(collection)` does the same.
- `PriorityQueue`: `add` and `poll` O(log *n*), `peek` O(1), `remove(x)` and `contains(x)` O(*n*). Build a max-heap with `Collections.reverseOrder()` or `Integer.compare`, never subtraction. Only the top is ordered.
- Lazy deletion records deletions and discards recorded values when they reach the top: O(log *N*) amortised, but deleted values stay in memory.
- Unlock and heap: sort by the unlock key, push options as the resource reaches them, take the best. An exchange argument proves it when taking an option never lowers the resource.
- Regret greedy: commit to every option, keep the commitments in a heap, undo the cheapest when a limit breaks. For bricks and ladders, the ladders sit on the *L* largest climbs so far, and reachability is a prefix.
- The fewest subarray increments that build *t* equal Σ max(0, *t*[*i*] − *t*[*i* − 1]), by a difference-array lower bound and a left-to-right construction.

1. At most 19 each. Both walk along one path between the root and a leaf and make at most one swap per level, and by @lem-5-depth a heap of 10⁶ values has height ⌊log₂ 10⁶⌋ = 19.
2. Parent ⌊(9 − 1)/2⌋ = 4, children 19 and 20 (they exist only when *n* > 19 and *n* > 20), depth ⌊log₂ 10⌋ = 3.
