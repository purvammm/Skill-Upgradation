Many array problems ask about *contiguous* pieces of the array: a range of days, a run of characters, a block of cells. Asking about every piece directly is expensive, because an array of length *n* has *n*(*n* + 1)/2 non-empty contiguous pieces. This chapter shows how one pass of preprocessing turns each question about a piece into a question about two *points*, and how a hash map then answers "how many earlier points match this one?" in constant time. The same trick, run backwards, applies thousands of range updates in time proportional to the array length.

The chapter is short on new code and long on one idea. That idea comes back in sliding windows (Chapter 3), Fenwick trees (Chapter 20) and XOR problems (Chapter 8), so it is worth understanding completely.

## The range-sum problem {#sec-rangesum}

Suppose an array *a* of *n* integers is fixed and you must answer *q* questions of the form "what is *a*[*l*] + *a*[*l* + 1] + ⋯ + *a*[*r*]?". Adding the elements for each question costs O(*n*) per query and O(*nq*) in total, which for *n* = *q* = 10⁵ is 10¹⁰ additions: far beyond the roughly 10⁸ simple operations Java performs in a second.

The fix is to precompute running totals once.

:::definition{#def-prefix} Prefix sum
For an array *a*[0..*n* − 1], the [[prefix-sum array]] *P* has *n* + 1 entries: *P*[0] = 0 and *P*[*i*] = *a*[0] + *a*[1] + ⋯ + *a*[*i* − 1] for 1 ≤ *i* ≤ *n*. Equivalently, *P*[*i* + 1] = *P*[*i*] + *a*[*i*].
:::

The extra leading zero is deliberate. *P*[*i*] is the sum of the first *i* elements, a **half-open** range [0, *i*). With that convention every range sum is a single subtraction and there is no special case for ranges that start at index 0.

:::theorem{#thm-rangesum} Range sums from prefix sums
For 0 ≤ *l* ≤ *r* < *n*, *a*[*l*] + ⋯ + *a*[*r*] = *P*[*r* + 1] − *P*[*l*].
:::

:::proof
*P*[*r* + 1] = *a*[0] + ⋯ + *a*[*r*] and *P*[*l*] = *a*[0] + ⋯ + *a*[*l* − 1]. Subtracting cancels the common terms *a*[0], …, *a*[*l* − 1] and leaves exactly *a*[*l*] + ⋯ + *a*[*r*]. When *l* = 0 the second sum is empty and *P*[0] = 0, so the formula still holds.
:::

```java {#lst-prefix} Building prefix sums and answering a range query
// P[i] = a[0] + ... + a[i-1], so sum(a[l..r]) = P[r + 1] - P[l]
static long[] prefixSums(int[] a) {
    long[] p = new long[a.length + 1];
    for (int i = 0; i < a.length; i++) p[i + 1] = p[i] + a[i];
    return p;
}

static long rangeSum(long[] p, int l, int r) {   // inclusive l..r
    return p[r + 1] - p[l];
}
```

Building *P* costs O(*n*) time and O(*n*) memory; each query afterwards costs O(1). For *q* queries the total is O(*n* + *q*) instead of O(*nq*).

:::java
The prefix array is `long[]` even though *a* is `int[]`. With *n* = 10⁵ values of size up to 10⁹, a running total reaches 10¹⁴, which overflows `int` (maximum about 2.1 · 10⁹) silently: Java does not throw an exception on integer overflow. Use `long` for every running sum unless you have checked the bound.
:::

The prefix array is a small example of a general bargain in algorithm design: spend time once on preprocessing so that each later question is cheap. The bargain only pays when the array does not change. If values change between queries, every prefix after the changed position is wrong, and you need the Fenwick tree of Chapter 20.

## Counting subarrays with a given sum {#sec-count}

Now a harder question. Given *a* and a target *k*, how many subarrays have sum exactly *k*? This is LeetCode 560, the first problem of Day 2, and the template for a whole family.

By @thm-rangesum, the subarray *a*[*l*..*r*] has sum *k* exactly when *P*[*r* + 1] − *P*[*l*] = *k*. Writing *j* = *r* + 1 and *i* = *l*, the question becomes:

> How many pairs of indices *i* < *j* in the prefix array satisfy *P*[*j*] − *P*[*i*] = *k*, that is, *P*[*i*] = *P*[*j*] − *k*?

A question about subarrays has become a question about **pairs of points**. Checking every pair is O(*n*²), which is the brute force you would write for partial marks. The faster idea is to scan *j* from left to right and ask, at each *j*, how many *earlier* prefix values equal *P*[*j*] − *k*. A hash map from "prefix value" to "how many times seen so far" answers that in O(1) on average.

:::keyidea
Scan left to right. Before you record the current prefix, look up how many earlier prefixes equal `prefix − k`. Each one is the left end of a subarray that ends here with sum *k*.
:::

```java {#lst-count-k} Number of subarrays with sum exactly k (negative values allowed)
static long countSubarraysWithSum(int[] a, long k) {
    Map<Long, Integer> seen = new HashMap<>();   // prefix value -> how many times seen so far
    seen.put(0L, 1);                            // the empty prefix P[0] = 0
    long prefix = 0, count = 0;
    for (int x : a) {
        prefix += x;
        count += seen.getOrDefault(prefix - k, 0);   // earlier prefix p with prefix - p == k
        seen.merge(prefix, 1, Integer::sum);
    }
    return count;
}
```

:::example{#ex-trace-k} Tracing the count for k = 3
Take *a* = [1, 2, −1, 2, 1] and *k* = 3. The map starts as {0: 1}. Each row shows the state after reading *a*[*i*].

```trace
i  a[i]  prefix  look up prefix-k  found  total   map after this step
0    1      1          -2            0      0     {0:1, 1:1}
1    2      3           0            1      1     {0:1, 1:1, 3:1}        a[0..1] = 1+2
2   -1      2          -1            0      1     {0:1, 1:1, 2:1, 3:1}
3    2      4           1            1      2     {..., 4:1}              a[1..3] = 2-1+2
4    1      5           2            1      3     {..., 5:1}              a[3..4] = 2+1
```

The answer is 3. Notice row 1: the subarray *a*[0..1] starts at index 0, and it is found only because the map was seeded with the empty prefix.
:::

:::theorem{#thm-count} Correctness of the prefix-count scan
When the loop has processed *a*[0..*j* − 1], `count` equals the number of subarrays with sum *k* that end at an index ≤ *j* − 1, and `seen` maps each value *v* to the number of indices *i* ≤ *j* with *P*[*i*] = *v*.
:::

:::proof
By induction on *j*. Before the loop (*j* = 0) no subarray has been processed, `count` = 0, and `seen` = {0: 1} records *P*[0] = 0, so the invariant holds. Suppose it holds after *j* elements and the loop reads *a*[*j*]. Then `prefix` becomes *P*[*j* + 1]. The subarrays with sum *k* that end exactly at index *j* are *a*[*i*..*j*] with *P*[*i*] = *P*[*j* + 1] − *k* and 0 ≤ *i* ≤ *j*; by the invariant `seen` holds exactly the count of those *i*, so adding it to `count` keeps the first half of the invariant. Recording *P*[*j* + 1] in `seen` restores the second half. After the last element, `count` is the number of all subarrays with sum *k*.
:::

Order matters inside the loop. Looking up *before* recording the current prefix guarantees *i* < *j* + 1, so the empty subarray is never counted when *k* = 0. Swap the two lines and LeetCode 560 with *k* = 0 counts every position once too often.

:::pitfall
Forgetting `seen.put(0L, 1)` is the most common bug in this pattern. It silently misses every subarray that starts at index 0, and the samples often still pass.
:::

### Why a sliding window does not work here

If every *a*[*i*] were positive, the sum of a window would grow when the right end moves and shrink when the left end moves, and the two-pointer window of Chapter 3 would find all windows with sum *k* in O(*n*). With negative numbers that monotonicity is gone: extending a window can lower its sum. The prefix-count method makes no assumption about signs, which is why it is the default whenever the problem allows negatives or zeros.

### Cost

The loop does *n* map operations. A Java `HashMap` performs `get`, `put` and `merge` in O(1) *expected* time, so the scan is O(*n*) expected time and O(*n*) memory for up to *n* + 1 distinct prefix values. Section @sec-hashing looks at what "expected" hides.

## One key, many questions {#sec-variants}

The scan in @lst-count-k has three moving parts: the **key** stored for each prefix, the **look-up** made at each step, and **what is stored** (a count or an index). Changing them solves a family of problems.

Table: {#tbl-variants} Variants of the prefix-and-map scan
| Question | Key stored for each prefix | Look up | Store |
|---|---|---|---|
| subarrays with sum *k* | *P* | *P* − *k* | count |
| subarrays with sum divisible by *k* | *P* mod *k* (non-negative) | the same remainder | count |
| subarrays with odd sum | parity of *P* | the opposite parity | count |
| longest subarray with sum *k* | *P* | *P* − *k* | first index |
| longest subarray with equal 0s and 1s | *P* after mapping 0 → −1 | the same *P* | first index |
| subarrays with XOR *k* | *X* = *a*[0] ⊕ ⋯ ⊕ *a*[*i* − 1] | *X* ⊕ *k* | count |

### Remainders

A subarray sum *P*[*j*] − *P*[*i*] is divisible by *k* exactly when *P*[*j*] ≡ *P*[*i*] (mod *k*), so the key is the remainder of the prefix and the look-up is the same remainder. The number of good subarrays is then Σ *c*(*c* − 1)/2 over the counts *c* of each remainder, or equivalently the running sum of "how many earlier prefixes had my remainder".

:::java
Java's `%` keeps the sign of the left operand: `-3 % 5` is `-3`, not `2`. Two prefixes with remainders −3 and 2 are congruent mod 5 but would be stored under different keys. Use `Math.floorMod(prefix, k)`, which always returns a value in [0, *k*).
:::

```java {#lst-divisible} Subarrays whose sum is divisible by k (LeetCode 974)
static int subarraysDivByK(int[] a, int k) {
    int[] cnt = new int[k];          // remainders are 0..k-1, so an array beats a map
    cnt[0] = 1;                      // the empty prefix
    int prefix = 0, total = 0;
    for (int x : a) {
        prefix = Math.floorMod(prefix + x, k);
        total += cnt[prefix];
        cnt[prefix]++;
    }
    return total;
}
```

When the keys come from a small range, as remainders 0..*k* − 1 do, an `int[]` replaces the map. It is faster, uses no boxing, and has no worst case.

### Longest instead of how many

To find the *longest* subarray with sum *k*, keep for each prefix value the *first* index where it appeared and never overwrite it. At index *j*, if *P*[*j*] − *k* was first seen at index *i*, the subarray *a*[*i*..*j* − 1] has length *j* − *i*, the longest ending at *j*. LeetCode 525 (Contiguous Array) is this question after rewriting every 0 as −1: a subarray with as many 0s as 1s is a subarray with sum 0.

```java {#lst-longest} Longest subarray with sum k: store first occurrences
static int longestWithSum(int[] a, long k) {
    Map<Long, Integer> first = new HashMap<>();
    first.put(0L, 0);                         // P[0] = 0 appears at index 0
    long prefix = 0;
    int best = 0;
    for (int j = 1; j <= a.length; j++) {
        prefix += a[j - 1];                   // prefix == P[j]
        Integer i = first.get(prefix - k);
        if (i != null) best = Math.max(best, j - i);
        first.putIfAbsent(prefix, j);         // keep the earliest index only
    }
    return best;
}
```

### Parity, and why counting can be even simpler

For "how many subarrays have an odd sum" (LeetCode 1524) the key is the parity of *P*, which has only two values. A subarray is odd exactly when its two end prefixes have different parities, so the answer is (number of even prefixes) × (number of odd prefixes), counting *P*[0] = 0 as even. A one-line formula replaces the map entirely. When a variant's key space is tiny, look for such a closed form.

## Hashing in Java {#sec-hashing}

The O(*n*) bound in @sec-count rests on hash-map operations taking constant time. It is worth knowing what that means.

A [[hash table]] stores entries in an array of *buckets*. To find key *x*, Java computes `x.hashCode()`, mixes its bits, and uses the low bits as a bucket index. Entries whose hashes land in the same bucket form a short list. When the table is more than 75 % full (the default [[load factor]]), it doubles its bucket array and redistributes the entries, which costs O(*n*) once but O(1) **amortised** per insertion.

If the keys spread evenly, each bucket holds O(1) entries and every operation is O(1) on average. If an adversary picks keys that all collide, a bucket becomes long. Since Java 8, a bucket with more than eight entries is converted into a balanced tree, so the worst case is O(log *n*) per operation, not O(*n*). Contest problems occasionally include such "anti-hash" tests for `HashMap<Long, …>`; the Infosys tests are not reported to.

There are also constant-factor costs that the O(1) hides:

- **Boxing.** `HashMap<Long, Integer>` stores objects, not primitives. Every `put` may allocate a `Long` and an `Integer`, and every look-up unboxes. For 10⁶ operations this is noticeable but fine; for 10⁷ it can exceed a 1–2 second limit.
- **Small key ranges.** When keys lie in a known range of size up to about 10⁷, an array indexed by the key (shifted by an offset if keys can be negative) is several times faster.
- **Pre-sizing.** `new HashMap<>(2 * n)` avoids the repeated doublings when you know roughly how many keys are coming.

:::java
Three map calls do most of the work in this chapter. `getOrDefault(k, 0)` returns 0 for a missing key instead of `null` (unboxing `null` throws a `NullPointerException`). `merge(k, 1, Integer::sum)` adds 1 to the count, inserting 1 if the key is new. `putIfAbsent(k, v)` writes only when the key is missing, which is exactly "remember the first index".
:::

## Difference arrays {#sec-diff}

The second half of the chapter runs the prefix idea in reverse. Suppose you receive *m* updates of the form "add *v* to every element of *a*[*l*..*r*]" and only need the final array. Applying each update element by element costs O(*n*) per update and O(*nm*) in total.

:::definition{#def-diff} Difference array
The [[difference array]] of *a*[0..*n* − 1] is *d*[0..*n*] with *d*[0] = *a*[0], *d*[*i*] = *a*[*i*] − *a*[*i* − 1] for 1 ≤ *i* < *n*, and *d*[*n*] = 0 as a spare slot.
:::

Taking prefix sums of *d* gives back *a*: *d*[0] + *d*[1] + ⋯ + *d*[*i*] telescopes to *a*[*i*]. So *d* and *a* carry the same information, and some changes are much cheaper to make in *d*.

:::theorem{#thm-diff} Range add as two point updates
Adding *v* to every element of *a*[*l*..*r*] changes the difference array in exactly two places: *d*[*l*] increases by *v* and *d*[*r* + 1] decreases by *v*.
:::

:::proof
Inside the range, *a*[*i*] and *a*[*i* − 1] both increase by *v*, so their difference is unchanged. At *i* = *l*, only *a*[*l*] increases, so *d*[*l*] grows by *v*. At *i* = *r* + 1, only *a*[*r*] increased, so *d*[*r* + 1] = *a*[*r* + 1] − *a*[*r*] falls by *v*. Every other difference involves two unchanged elements.
:::

```java {#lst-diff} Applying many range additions with a difference array
// Apply many "add v to a[l..r]" updates, then read the array once. O(n + updates).
static long[] applyRangeAdds(int n, int[][] updates) {   // each update = {l, r, v}, inclusive
    long[] d = new long[n + 1];
    for (int[] u : updates) {
        d[u[0]] += u[2];          // start adding at l
        d[u[1] + 1] -= u[2];      // stop after r
    }
    long[] a = new long[n];
    long running = 0;
    for (int i = 0; i < n; i++) {
        running += d[i];
        a[i] = running;
    }
    return a;
}
```

The array *d* has *n* + 1 slots so that *d*[*r* + 1] exists when *r* = *n* − 1; that last slot is never read back. The total cost is O(*n* + *m*).

:::example{#ex-flights} Corporate flight bookings
LeetCode 1109 gives *n* flights numbered 1..*n* and bookings (*first*, *last*, *seats*): reserve *seats* on every flight from *first* to *last*. It asks for the total seats on each flight. This is @lst-diff after shifting the 1-based flight numbers to 0-based indices: `d[first - 1] += seats; d[last] -= seats;` followed by one running sum.
:::

### Counting coverage

A special case appears constantly: given intervals [*s*, *e*], how many intervals cover each point? Each interval is a range addition of 1. After the running sum, *a*[*x*] is the number of intervals covering *x*, and the maximum of *a* is the largest overlap. That maximum is the answer to "minimum number of meeting rooms" and "minimum railway platforms", an Infosys repeat problem you will meet again with a sweep line in Chapter 4.

:::tip
A difference array needs every update before any read. If updates and reads are interleaved ("add 5 to [2..7]; what is a[4] now?"), switch to a Fenwick tree with range update (Chapter 20) or a lazy segment tree (Chapter 21).
:::

## Two dimensions {#sec-2d}

Both ideas extend to a grid *g* with *R* rows and *C* columns. Define *S*[*i*][*j*] as the sum of the rectangle of rows 0..*i* − 1 and columns 0..*j* − 1, with a row and a column of zeros at index 0.

:::theorem{#thm-2d} Rectangle sums by inclusion–exclusion
*S*[*i* + 1][*j* + 1] = *g*[*i*][*j*] + *S*[*i*][*j* + 1] + *S*[*i* + 1][*j*] − *S*[*i*][*j*], and the sum of rows *r*1..*r*2 and columns *c*1..*c*2 is
*S*[*r*2 + 1][*c*2 + 1] − *S*[*r*1][*c*2 + 1] − *S*[*r*2 + 1][*c*1] + *S*[*r*1][*c*1].
:::

The subtraction removes the strip above the rectangle and the strip to its left; their overlap was removed twice, so it is added back once. This is the [[inclusion–exclusion principle]] in its smallest form.

```java {#lst-2d} Two-dimensional prefix sums (LeetCode 304)
static long[][] prefix2D(int[][] g) {
    int R = g.length, C = g[0].length;
    long[][] s = new long[R + 1][C + 1];
    for (int i = 0; i < R; i++)
        for (int j = 0; j < C; j++)
            s[i + 1][j + 1] = g[i][j] + s[i][j + 1] + s[i + 1][j] - s[i][j];
    return s;
}

static long rectSum(long[][] s, int r1, int c1, int r2, int c2) {   // inclusive corners
    return s[r2 + 1][c2 + 1] - s[r1][c2 + 1] - s[r2 + 1][c1] + s[r1][c1];
}
```

The two-dimensional difference array is the same reasoning backwards: to add *v* to a rectangle, add *v* at (*r*1, *c*1), subtract it at (*r*1, *c*2 + 1) and (*r*2 + 1, *c*1), and add it back at (*r*2 + 1, *c*2 + 1). A 2-D prefix sum of the result rebuilds the grid.

## Summary

- A prefix-sum array with a leading zero turns any range sum into one subtraction, *P*[*r* + 1] − *P*[*l*], after O(*n*) preprocessing.
- "Subarray with property X" usually becomes "pair of prefixes with property Y". Scanning left to right with a hash map of earlier prefixes counts such pairs in O(*n*) expected time.
- Seed the map with the empty prefix, look up before you record, and use `long` for sums and `Math.floorMod` for remainders.
- Store counts to answer "how many", first indices to answer "how long".
- Prefer an `int[]` to a `HashMap` when the keys lie in a small known range.
- A difference array applies a range addition with two point updates; one running sum rebuilds the array. It needs all updates before any read.
- In two dimensions, inclusion–exclusion gives rectangle sums and rectangle additions in O(1) each.

## Review questions

1. Why does the prefix array have *n* + 1 entries instead of *n*? What would the range-sum formula look like without the leading zero?
2. In @lst-count-k, what goes wrong if the `getOrDefault` line and the `merge` line are swapped? Give an input where the answer changes.
3. An array contains only positive numbers. Name two methods that count subarrays with sum *k* in O(*n*) and say which one uses less memory.
4. Why is `Math.floorMod(prefix, k)` needed in @lst-divisible? Give values of `prefix` and *k* for which `prefix % k` and `Math.floorMod(prefix, k)` differ.
5. How many subarrays of [1, 1, 1] have an odd sum? Compute it with the parity formula of @sec-variants and check by listing them.
6. You need the longest subarray with sum 0. Why must the map keep the *first* index of each prefix and not the latest?
7. Five updates add 1 to the ranges [0..2], [1..3], [2..4], [0..4] and [3..3] of an array of length 5. Write the difference array after all updates and the final array.
8. Give the 2-D formula for the sum of a single cell (*i*, *j*) using *S*, and check that it reduces to *g*[*i*][*j*].

:::answers
1. The leading zero makes *P*[*i*] the sum of the half-open range [0, *i*), so every range is *P*[*r* + 1] − *P*[*l*], including ranges that start at 0. Without it, with *Q*[*i*] = *a*[0] + ⋯ + *a*[*i*], the sum is *Q*[*r*] − *Q*[*l* − 1] and the case *l* = 0 needs a separate branch.
2. The current prefix would be counted as its own earlier prefix. When *k* = 0, every index then contributes one extra "subarray" of length zero. For *a* = [1, 2] and *k* = 0 the correct answer is 0, but the swapped loop returns 2.
3. The prefix-and-map scan (O(*n*) memory) and the sliding window of Chapter 3, which uses O(1) extra memory because, with positive values, the window sum moves monotonically with each pointer.
4. Java's `%` returns a negative remainder for a negative left operand, so congruent prefixes could get different keys and array indices could be negative. For `prefix` = −3 and *k* = 5, `-3 % 5` is −3 while `Math.floorMod(-3, 5)` is 2.
5. The prefixes are 0, 1, 2, 3 with parities even, odd, even, odd: two even and two odd, so 2 × 2 = 4 odd subarrays. Listing: [1] three times and [1, 1, 1] once, which is 4.
6. For a fixed right end *j*, the longest subarray uses the smallest left index *i* with *P*[*i*] = *P*[*j*] − *k*. Overwriting with later indices would only ever give shorter subarrays.
7. Each update adds +1 at its left end and −1 just after its right end: [0..2] touches *d*[0] and *d*[3]; [1..3] touches *d*[1] and *d*[4]; [2..4] touches *d*[2] and *d*[5]; [0..4] touches *d*[0] and *d*[5]; [3..3] touches *d*[3] and *d*[4]. So *d* = [2, 1, 1, 0, −2, −2], and the running sums give *a* = [2, 3, 4, 4, 2]. Check one entry by hand: index 3 is covered by [1..3], [2..4], [0..4] and [3..3], four ranges.
8. With *r*1 = *r*2 = *i* and *c*1 = *c*2 = *j*: *S*[*i* + 1][*j* + 1] − *S*[*i*][*j* + 1] − *S*[*i* + 1][*j*] + *S*[*i*][*j*]. By the recurrence in @thm-2d this equals *g*[*i*][*j*].
:::
