This chapter collects three DP families that look different but share a habit of thought: find the right **order** in which subproblems become independent. For divisibility, the order is numerical: sort, and a set in which every pair divides becomes a chain that can be built left to right. For intervals, the order is by length: the answer for a segment depends only on shorter segments inside it. For games, the order is again by length, because every move removes an element and leaves a shorter game for the other player.

The divisor part prepares one of the most frequently reported Infosys problems, counting arrays in which each element divides the next. The interval and game parts give two templates from the handbook that cover a whole page of LeetCode Hards: cutting sticks, bursting balloons, merging piles and taking coins from either end of a row.

## Chains under divisibility {#sec-14-divisible}

:::definition{#def-14-divisible} Divisible subset and divisor chain
A set of positive integers is a [[divisible subset]] if for every two of its members *x*, *y*, either *x* divides *y* or *y* divides *x* (written *x* ∣ *y*). A [[divisor chain]] is a sequence *x*₁ < *x*₂ < ⋯ < *x*ₖ with *x*ᵢ ∣ *x*ᵢ₊₁ for every *i*.
:::

The definition of a divisible subset talks about **all pairs**, which suggests checking O(*k*²) conditions. The first step is to see that consecutive pairs are enough once the set is sorted.

:::lemma{#lem-14-chain} Pairwise divisibility is a chain condition
A set of distinct positive integers is a divisible subset if and only if, listed in increasing order, it is a divisor chain.
:::

:::proof
Suppose the sorted list *x*₁ < ⋯ < *x*ₖ is a divisor chain, and take *i* < *j*. Then *x*ᵢ ∣ *x*ᵢ₊₁, *x*ᵢ₊₁ ∣ *x*ᵢ₊₂, …, *x*ⱼ₋₁ ∣ *x*ⱼ. Divisibility is transitive (if *x* ∣ *y* and *y* ∣ *z*, then *y* = *px* and *z* = *qy* = *pqx*), so *x*ᵢ ∣ *x*ⱼ by induction on *j* − *i*. Conversely, in a divisible subset take consecutive members *x*ᵢ < *x*ᵢ₊₁. One divides the other, and a positive integer cannot be divisible by a larger one, so *x*ᵢ ∣ *x*ᵢ₊₁.
:::

So the largest divisible subset is the longest divisor chain among the sorted values. That is the LIS of Chapter 13 with the condition "*a*[*j*] < *a*[*i*]" replaced by "*a*[*j*] ∣ *a*[*i*]". Sorting matters: divisibility implies ≤ for positive integers, so a chain can only be read in increasing order. Without the sort, the DP on [4, 2, 8] links 4 → 8 and 2 → 8 but never 2 → 4, and reports 2 instead of 3.

:::theorem{#thm-14-divisible} The divisibility DP
Sort the values as *a*[0] < ⋯ < *a*[*n* − 1] and let *f*[*i*] be the size of the largest divisible subset whose largest member is *a*[*i*]. Then *f*[*i*] = 1 + max{ *f*[*j*] : *j* < *i*, *a*[*j*] ∣ *a*[*i*] } (the maximum of an empty set is 0).
:::

:::proof
By @lem-14-chain a divisible subset with largest member *a*[*i*] is a divisor chain ending at *a*[*i*]. If it has more than one element, its second-largest member *a*[*j*] has *j* < *i* and *a*[*j*] ∣ *a*[*i*], and removing *a*[*i*] leaves a chain ending at *a*[*j*], so its size is at most *f*[*j*] + 1. Conversely, if *a*[*j*] ∣ *a*[*i*], every member of a chain ending at *a*[*j*] divides *a*[*j*] and hence *a*[*i*], so appending *a*[*i*] gives a chain of size *f*[*j*] + 1. This is the same exchange as in Chapter 13, with divisibility in place of "smaller".
:::

```java {#lst-14-divisible} Largest divisible subset: sort, LIS-style DP, parent pointers
// Largest subset of distinct positive values in which every pair divides one way or the other.
static List<Integer> largestDivisibleSubset(int[] nums) {
    int[] a = nums.clone();
    Arrays.sort(a);                                  // a chain must be read in increasing order
    int n = a.length, bestEnd = 0;
    int[] f = new int[n], parent = new int[n];       // f[i] = longest chain ending with a[i]
    for (int i = 0; i < n; i++) {
        f[i] = 1;
        parent[i] = -1;
        for (int j = 0; j < i; j++)
            if (a[i] % a[j] == 0 && f[j] + 1 > f[i]) {
                f[i] = f[j] + 1;
                parent[i] = j;
            }
        if (f[i] > f[bestEnd]) bestEnd = i;
    }
    LinkedList<Integer> out = new LinkedList<>();
    for (int i = (n == 0 ? -1 : bestEnd); i >= 0; i = parent[i]) out.addFirst(a[i]);
    return out;
}
```

The double loop makes *n*(*n* − 1)/2 divisibility tests, about 5 · 10⁵ for *n* = 1000, which is the limit in LeetCode 368 (Largest Divisible Subset). Memory is two `int` arrays.

## Looping over multiples {#sec-14-multiples}

When the values are not a short list but **every** integer from 1 to *N*, the pairwise loop is too slow: it would test about *N*²/2 pairs. A better order is to let each value *push* its information to its multiples.

There are two ways to visit all pairs (*d*, *m*) with *d* ∣ *m* and *m* ≤ *N*. **Pull**: for each *m*, find its divisors, by trial division up to √*m*, costing about *N*√*N* in total. **Push**: for each *d*, walk *m* = *d*, 2*d*, 3*d*, …, which visits exactly the pairs and nothing else:

```java {.fragment}
int N = 20;
int[] hits = new int[N + 1];
for (int v = 1; v <= N; v++)
    for (int m = 2 * v; m <= N; m += v)      // the proper multiples of v
        hits[m]++;                            // hits[m] = number of proper divisors of m
```

The inner loop runs ⌊*N*/*v*⌋ − 1 times for each *v*, and the total is governed by the harmonic series.

:::theorem{#thm-14-harmonic} The harmonic bound
For every *N* ≥ 1, ⌊*N*/1⌋ + ⌊*N*/2⌋ + ⋯ + ⌊*N*/*N*⌋ ≤ *N*(⌊log *N*⌋ + 1).
:::

:::proof
Each term ⌊*N*/*v*⌋ is at most *N*/*v*, so the sum is at most *N* · *H*, where *H* = 1 + 1/2 + ⋯ + 1/*N*. Split the terms of *H* into blocks of the form 1/2ʲ + 1/(2ʲ + 1) + ⋯ + 1/(2ʲ⁺¹ − 1) for *j* = 0, 1, 2, …. Block *j* has 2ʲ terms, each at most 1/2ʲ, so it sums to at most 1. The terms up to 1/*N* fill at most ⌊log *N*⌋ + 1 blocks (the last one possibly incomplete). So *H* ≤ ⌊log *N*⌋ + 1.
:::

The true constant is smaller: *H* is close to ln *N* + 0.58, and ln *N* ≈ 0.69 log *N*. The table shows the exact sums.

Table: {#tbl-14-harmonic} Total work of the loop over multiples, computed exactly
| *N* | Σ ⌊*N*/*v*⌋ | *N* ln *N* | bound *N*(⌊log *N*⌋ + 1) |
|---|---|---|---|
| 10³ | 7,069 | 6,908 | 10,000 |
| 10⁴ | 93,668 | 92,103 | 140,000 |
| 10⁵ | 1,166,750 | 1,151,293 | 1,700,000 |
| 10⁶ | 13,970,034 | 13,815,511 | 20,000,000 |

So a loop over multiples up to 10⁶ costs about 1.4 · 10⁷ steps, a fraction of a second. This is the same loop as the sieve of Eratosthenes in Chapter 10, where the inner loop runs only for primes and the total drops to about *N* ln ln *N*.

```java {#lst-14-multiples} Looping over multiples: divisor counts and longest divisor chains
// divs[v]  = number of divisors of v, for every v in 1..N.
// chain[v] = most distinct values in a chain d1 | d2 | ... | v of numbers in 1..N.
// The inner loop runs N/v times, about N ln N steps in total.
static int[][] divisorsAndChains(int N) {
    int[] divs = new int[N + 1], chain = new int[N + 1];
    for (int v = 1; v <= N; v++) {
        chain[v] = Math.max(chain[v], 1);            // every divisor of v was pushed already
        for (int m = v; m <= N; m += v) {
            divs[m]++;
            if (m > v) chain[m] = Math.max(chain[m], chain[v] + 1);
        }
    }
    return new int[][]{divs, chain};
}
```

The push order is correct because every proper divisor of *v* is smaller than *v*, so by the time the outer loop reaches *v*, all of them have already pushed into `chain[v]`. This is the general rule for DP over divisibility: process values in increasing order, exactly as you process a DAG in topological order (Chapter 15).

For *v* = 1, …, 12 the listing gives divs = [1, 2, 2, 3, 2, 4, 2, 4, 3, 4, 2, 6] and chain = [1, 2, 2, 3, 2, 3, 2, 4, 3, 3, 2, 4]. Up to 10⁵, the most divisors is 128 (at 83,160), and the longest chain has 17 values, ending at 65,536 = 2¹⁶.

:::claim{#thm-14-omega} How long a divisor chain can be
The longest divisor chain of distinct values ending at *v* has Ω(*v*) + 1 elements, where Ω(*v*) is the number of prime factors of *v* counted with multiplicity. Consequently a chain of distinct values in 1..*N* has at most ⌊log *N*⌋ + 1 elements.
:::

:::proof
In a chain *x*₁ ∣ *x*₂ ∣ ⋯ with *x*ᵢ < *x*ᵢ₊₁, each quotient *x*ᵢ₊₁/*x*ᵢ is an integer at least 2, so it contributes at least one prime factor: Ω grows by at least 1 at each step, and Ω(*x*₁) ≥ 0. A chain ending at *v* therefore has at most Ω(*v*) + 1 elements. Multiplying in the prime factors of *v* one at a time, starting from 1, gives a chain of exactly that length. Each step at least doubles the value, so a chain of *k* distinct values in 1..*N* has *x*ₖ ≥ 2ᵏ⁻¹, which forces *k* ≤ ⌊log *N*⌋ + 1.
:::

The last fact is small but decisive in the next section: however long an array is, it can contain at most 17 *distinct* values if each divides the next and all are at most 10⁵.

## Counting divisor arrays {#sec-14-count}

Now count, instead of optimise. How many arrays *b*[0..*K* − 1] with values in 1..*N* satisfy *b*[*i*] ∣ *b*[*i* + 1] for every *i*? Equal neighbours are allowed, since every number divides itself.

:::infosys
This is the repeat "Count arrays where each element divides the next", reported 13 times between 2021 and 2025 for DSE, with the answer printed modulo 10000. Its samples are (*N* = 2, *K* = 1) → 2, (2, 2) → 3 and (3, 2) → 5. The same problem modulo 10⁹ + 7 with large *K* is the bonus problem LeetCode 2338. Chapter 24 returns to the Infosys version.
:::

### The direct DP

Let *W*(*k*, *v*) be the number of valid arrays of length *k* that end with *v*. Then *W*(1, *v*) = 1, and an array of length *k* ending in *v* extends to length *k* + 1 by appending any multiple *m* of *v*, including *v* itself. That is the push loop over multiples, once per length, so the cost is O(*K* · *N* log *N*). For *N* = 6 the rows are *W*(2, 1..6) = 1, 2, 2, 3, 2, 4 and *W*(3, 1..6) = 1, 3, 3, 6, 3, 9, so there are 25 arrays of length 3. This is the method for small *K*.

### Distinct values and stars and bars

When *K* is large (say 10⁴) and *N* is 10⁴ as well, O(*K* · *N* log *N*) is about 10⁹ and too slow. The way out is to separate **which** values appear from **how often** each one repeats.

Squash every run of equal neighbours in a valid array into one value. What remains is a strictly increasing divisor chain of *s* distinct values, and by @thm-14-omega, *s* ≤ ⌊log *N*⌋ + 1, a tiny number. Conversely, an array is determined by its chain and the lengths of the *s* runs, which are positive and sum to *K*.

:::theorem{#thm-14-stars} Stars and bars
The number of ways to write *K* as an ordered sum of *s* positive integers is C(*K* − 1, *s* − 1). Hence the number of valid arrays is

Σ over *s* ≥ 1 of (number of divisor chains with *s* distinct values in 1..*N*) × C(*K* − 1, *s* − 1).
:::

:::proof
Write *K* stars in a row. There are *K* − 1 gaps between neighbouring stars. Choosing *s* − 1 of the gaps and putting a bar in each cuts the row into *s* non-empty groups, read left to right, and every ordered sum of *s* positive parts arises from exactly one such choice. So there are C(*K* − 1, *s* − 1) of them. For the arrays: the map "array ↦ (its chain of distinct values, its run lengths)" is a bijection between valid arrays and pairs (chain with *s* values, ordered sum of *K* into *s* positive parts), because the chain and the run lengths rebuild the array and every such pair gives a valid array. Summing over *s* gives the formula. This is an instance of [[stars and bars]].
:::

The chain counts come from the same push loop with one more index. Let cnt(*s*, *v*) be the number of strictly increasing divisor chains with *s* values ending at *v*. Then cnt(1, *v*) = 1, and cnt(*s* + 1, *m*) is the sum of cnt(*s*, *v*) over the proper divisors *v* of *m*.

:::example{#ex-14-stars} Counting arrays for N = 6, K = 3
The chain counts for *v* = 1..6 are:

```trace
s    cnt(s, 1..6)         chains with s values   C(K-1, s-1)   contribution
1    1  1  1  1  1  1             6                C(2,0) = 1        6
2    0  1  1  2  1  3             8                C(2,1) = 2       16
3    0  0  0  1  0  2             3                C(2,2) = 1        3
                                                              total  25
```

For instance cnt(2, 6) = 3 counts the chains (1, 6), (2, 6) and (3, 6), and cnt(3, 6) = 2 counts (1, 2, 6) and (1, 3, 6). The chain (1, 2, 6) gives C(2, 2) = 1 array, [1, 2, 6], while (2, 6) gives two, [2, 2, 6] and [2, 6, 6]. The total, 25, matches the direct DP above and a brute force over all 6³ = 216 arrays. The same formula gives 2, 3 and 5 on the Infosys samples, and 39 for *N* = 6, *K* = 4.
:::

The chain counts cost O(*S* · *N* log *N*) with *S* = ⌊log *N*⌋ + 1, independent of *K*. The binomials need care with the modulus. 10⁹ + 7 is prime, so C(*n*, *r*) can use factorials and modular inverses (Chapter 10). 10000 = 2⁴ · 5⁴ is **not** prime, so inverses of many numbers do not exist; build C(*n*, *r*) for *r* < *S* with Pascal's rule C(*n*, *r*) = C(*n* − 1, *r* − 1) + C(*n* − 1, *r*), which only adds.

:::pitfall
Do not reduce the problem to "count chains" and forget the repeats: the samples (2, 2) → 3 already include the arrays [1, 1] and [2, 2]. And do not count arrays of length *K* with distinct values only; that is the special case *s* = *K*.
:::

## Interval DP {#sec-14-interval}

:::definition{#def-14-interval} Interval DP
An [[interval DP]] has one state per contiguous segment, dp[*l*][*r*] for *a*[*l*..*r*], whose value is computed from the values of **shorter segments inside it**. The answer is usually dp[0][*n* − 1].
:::

You met this shape in Chapter 12: the longest palindromic subsequence of *s*[*l*..*r*] depends on *s*[*l* + 1..*r* − 1], *s*[*l* + 1..*r*] and *s*[*l*..*r* − 1]. The new ingredient here is the **split point**: many interval problems are answered by trying every *k* between *l* and *r* and combining dp[*l*][*k*] with dp[*k* + 1][*r*].

### Evaluation order

:::lemma{#lem-14-order} Why "by increasing length" works
If every dp[*l*][*r*] reads only entries dp[*l*′][*r*′] with *l* ≤ *l*′ ≤ *r*′ ≤ *r* and (*l*′, *r*′) ≠ (*l*, *r*), then filling the table in order of increasing length *r* − *l* + 1 reads only entries that are already filled. So does the order "*l* from *n* − 1 down to 0, and for each *l*, *r* from *l* up to *n* − 1".
:::

:::proof
A proper sub-segment of [*l*, *r*] is strictly shorter, so it belongs to an earlier length and has been filled. For the second order, a read entry has either *l*′ > *l*, so it belongs to an earlier pass of the outer loop, or *l*′ = *l* and *r*′ < *r*, so it was filled earlier in the current pass.
:::

The natural-looking order "*l* from 0 up, *r* from *l* up" breaks the rule: dp[0][*r*] needs dp[1][*r*], which belongs to a later pass of the outer loop and is still 0. The program compiles, runs and returns a wrong number. This is the handbook's trap for this card.

### The template: the cheapest way to multiply matrices

Multiplying a *p* × *q* matrix by a *q* × *s* matrix costs *p* · *q* · *s* scalar multiplications. A product of *n* matrices can be bracketed in many ways, all giving the same result at very different costs. If matrix *i* is *d*[*i*] × *d*[*i* + 1], what is the cheapest bracketing?

:::theorem{#thm-14-matrix} The last multiplication
Let dp[*l*][*r*] be the cheapest cost of multiplying matrices *l*..*r*. Then dp[*l*][*l*] = 0 and, for *l* < *r*,
dp[*l*][*r*] = min over *l* ≤ *k* < *r* of ( dp[*l*][*k*] + dp[*k* + 1][*r*] + *d*[*l*] · *d*[*k* + 1] · *d*[*r* + 1] ).
:::

:::proof
In any bracketing, some multiplication is performed **last**. It multiplies the product of matrices *l*..*k* (a *d*[*l*] × *d*[*k* + 1] matrix) by the product of *k* + 1..*r* (a *d*[*k* + 1] × *d*[*r* + 1] matrix) for some *k*, and costs *d*[*l*] · *d*[*k* + 1] · *d*[*r* + 1]. Before it, the two halves were computed independently, each by some bracketing of its own, costing at least dp[*l*][*k*] and dp[*k* + 1][*r*]. So every bracketing costs at least the right-hand side for its *k*. Conversely, for each *k*, combining optimal bracketings of the halves achieves exactly that sum. The minimum over *k* is therefore the optimum.
:::

```java {#lst-14-matrix} Interval DP: the cheapest order of matrix multiplications
// dp[l][r] = best answer for the segment l..r, filled by increasing length.
// Matrix chain: matrix i is d[i] x d[i+1]. Cheapest order of multiplications.
static long matrixChain(int[] d) {
    int n = d.length - 1;
    long[][] dp = new long[n][n];                      // dp[l][l] = 0
    for (int len = 2; len <= n; len++)
        for (int l = 0; l + len - 1 < n; l++) {
            int r = l + len - 1;
            dp[l][r] = Long.MAX_VALUE;
            for (int k = l; k < r; k++)                // last multiplication splits at k
                dp[l][r] = Math.min(dp[l][r],
                        dp[l][k] + dp[k + 1][r] + (long) d[l] * d[k + 1] * d[r + 1]);
        }
    return dp[0][n - 1];
}
```

## Cutting a stick, and the last operation {#sec-14-cut}

LeetCode 1547 (Minimum Cost to Cut a Stick) is the core interval problem of the day. A stick of length *L* must be cut at given positions; cutting a piece costs the piece's current length; the cuts may be made in any order. Find the minimum total cost.

The order matters. For *L* = 10 and cuts at 2, 4, 7: cutting in the order 2, 4, 7 costs 10 + 8 + 6 = 24; the order 7, 4, 2 costs 10 + 7 + 4 = 21; the order 4, 2, 7 costs 10 + 4 + 6 = 20, which is the minimum.

### Modelling

The positions along the stick can be up to 10⁶, but there are at most 100 cuts, so the state must be over the **cuts**, not over lengths. Add the two ends as extra points and sort: *p*[0] = 0 < *p*[1] < ⋯ < *p*[*m*] < *p*[*m* + 1] = *L*, where *m* is the number of cuts. Every piece that ever exists during the process runs from one point to another, *p*[*i*] to *p*[*j*], with all the cuts strictly between them still to be made.

:::theorem{#thm-14-stick} The stick recurrence
Let dp[*i*][*j*] be the minimum cost of making all cuts strictly between *p*[*i*] and *p*[*j*] on the piece [*p*[*i*], *p*[*j*]]. Then dp[*i*][*i* + 1] = 0, and for *j* ≥ *i* + 2,
dp[*i*][*j*] = (*p*[*j*] − *p*[*i*]) + min over *i* < *k* < *j* of ( dp[*i*][*k*] + dp[*k*][*j*] ).
The answer is dp[0][*m* + 1].
:::

:::proof
If *j* = *i* + 1 there is nothing to cut. Otherwise some cut *p*[*k*] with *i* < *k* < *j* is made **first** on this piece, and it costs the full length *p*[*j*] − *p*[*i*], whichever *k* it is. After it, the two pieces [*p*[*i*], *p*[*k*]] and [*p*[*k*], *p*[*j*]] never interact again: every later cut lies in exactly one of them and its cost depends only on that piece. So the remaining cost is at least dp[*i*][*k*] + dp[*k*][*j*], and an optimal schedule for each piece achieves it. Minimising over the first cut *k* gives the recurrence.
:::

This is the matrix-chain template with two changes: the cost of a step is the piece's length, and the split point *k* is shared by both halves. Writing it out is your core exercise for the day.

### The last operation instead of the first

In the stick, the **first** cut separates the problem into independent halves. Sometimes the first operation does the opposite. In the bonus problem LeetCode 312 (Burst Balloons), bursting balloon *k* earns the product of its value and its current neighbours' values, and the burst makes its two neighbours adjacent. Choosing the first balloon to burst therefore changes the neighbours inside both halves, which are no longer independent.

The fix is to choose the balloon burst **last** inside an open interval (*l*, *r*), where *l* and *r* are balloons that are still standing (pad the row with a 1 at each end). While the balloons strictly between *l* and *k* are being burst, *k* is still there, so the left part's neighbours are fixed as *l* and *k*; the right part likewise sees *k* and *r*. When *k* finally goes, its neighbours are *l* and *r*. So

dp[*l*][*r*] = max over *l* < *k* < *r* of ( dp[*l*][*k*] + dp[*k*][*r*] + *v*[*l*] · *v*[*k*] · *v*[*r*] ).

:::example{#ex-14-burst} The last balloon
For values [3, 1, 5], padded to *v* = [1, 3, 1, 5, 1], the three choices for the last balloon on the whole row are:

```trace
last balloon   left part dp[0][k]   right part dp[k][4]   last burst 1*v[k]*1   total
     3                 0                   30                   3                33
     1                 3                    5                   1                 9
     5                30                    0                   5                35
```

The maximum is 35: burst 1 first (3 · 1 · 5 = 15), then 3 (1 · 3 · 5 = 15), then 5 (1 · 5 · 1 = 5). A brute force over all 3! orders agrees.
:::

:::keyidea
For a split recurrence, ask which single operation, **first** or **last**, leaves the rest of the work in independent pieces whose costs do not depend on each other. Cutting a stick splits on the first cut; bursting balloons and merging piles split on the last operation. The bonus problem LeetCode 664 (Strange Printer) is a third variant, where two prints of the same character can merge.
:::

## Two-player games {#sec-14-games}

In a game DP, two players alternate moves on a shared position, both see everything, and both play perfectly. The DP must describe what perfect play means.

:::definition{#def-14-game} Positions, winning and losing
A **position** is everything that determines the rest of the game, including whose turn it is. In a game where the player who cannot move loses, a position is [[winning|winning position]] if the player to move can force a win, and **losing** otherwise.
:::

:::theorem{#thm-14-winlose} Winning means "some move to a losing position"
In a finite game without draws where the player who cannot move loses, a position is losing if and only if every move from it leads to a winning position; in particular a position with no moves is losing.
:::

:::proof
By induction on the longest remaining game from the position. If some move leads to a losing position, the player to move makes it and the opponent, now to move in a losing position, cannot force a win; so the position is winning. If every move leads to a winning position, whatever the player does, the opponent can force a win; so the position is losing. A position with no moves falls in the second case vacuously.
:::

```java {#lst-14-winlose} Winning and losing positions of a take-away game
// A pile of s stones; a move removes 1, 3 or 4 stones; a player who cannot move loses.
// win[s] = true if the player to move from s stones wins with perfect play.
static boolean[] winningPositions(int maxS) {
    int[] moves = {1, 3, 4};
    boolean[] win = new boolean[maxS + 1];               // win[0] = false: no move available
    for (int s = 1; s <= maxS; s++)
        for (int m : moves)
            if (m <= s && !win[s - m]) {                 // a move to a losing position
                win[s] = true;
                break;
            }
    return win;
}
```

For this game the losing positions up to 14 are 0, 2, 7, 9 and 14: the pattern repeats with period 7 (losing exactly when *s* mod 7 is 0 or 2), a regularity you can find by printing the table and then prove by induction. Games on arbitrary graphs, and sums of games with the Sprague–Grundy theorem, extend this idea; see the further reading.

### Games with scores: minimax

Many problems give points instead of a win or a loss. Two players alternately take a number from the left or the right end of a row *a*[0..*n* − 1]; each adds what they take to their score. This is the setting of LeetCode 486 (Predict the Winner).

The [[minimax]] principle says that the player to move picks the move whose resulting position is best **for them**, assuming the opponent then does the same. Writing that with two scores is awkward. One number suffices.

:::definition{#def-14-diff} Score difference
For a segment *a*[*l*..*r*] with some player to move, let *D*(*l*, *r*) be the largest value of (the mover's total from now on) − (the opponent's total from now on) that the mover can guarantee.
:::

:::theorem{#thm-14-diff} The difference recurrence
*D*(*l*, *l*) = *a*[*l*], and for *l* < *r*, *D*(*l*, *r*) = max( *a*[*l*] − *D*(*l* + 1, *r*), *a*[*r*] − *D*(*l*, *r* − 1) ).
Moreover, if each player tries to maximise **their own** total, the first player's total is (*S* + *D*(0, *n* − 1))/2, where *S* is the sum of all elements.
:::

:::proof
With one element the mover takes it, so the difference is *a*[*l*]. Otherwise, suppose the mover takes *a*[*l*]. The rest of the game is the segment *a*[*l* + 1..*r*] with the **opponent** to move, who by induction can guarantee a difference of *D*(*l* + 1, *r*) in their own favour, and cannot be held below it. From the mover's side the final difference is *a*[*l*] minus that. Taking *a*[*r*] is symmetric. The mover chooses the larger.

For the second part: on any segment the two players' totals from now on add up to the segment's sum, which is fixed. If own + other = *T*, then own − other = 2 · own − *T*, so maximising one's own total and maximising the difference are the same goal, and the optimal moves coincide. Then the first player's total *x* satisfies *x* + *y* = *S* and *x* − *y* = *D*(0, *n* − 1), so *x* = (*S* + *D*)/2.
:::

So the first player wins or ties exactly when *D*(0, *n* − 1) ≥ 0, which is what LeetCode 486 asks (a tie counts as a win for the first player there). Each entry reads two shorter segments, so the table has *n*(*n* + 1)/2 useful entries and the time is O(*n*²).

```java {#lst-14-game} Game DP: the first player's best score difference
// Two players take from either end; both play perfectly. dp = my score minus the opponent's.
static long bestScoreDifference(int[] a) {
    int n = a.length;
    long[][] dp = new long[n][n];
    for (int i = 0; i < n; i++) dp[i][i] = a[i];
    for (int len = 2; len <= n; len++)
        for (int l = 0; l + len - 1 < n; l++) {
            int r = l + len - 1;
            dp[l][r] = Math.max(a[l] - dp[l + 1][r], a[r] - dp[l][r - 1]);
        }
    return dp[0][n - 1];                               // first player wins if >= 0 (LC 486)
}
```

:::example{#ex-14-game} Why greedy loses
Take *a* = [3, 9, 1, 2]. If both players greedily take the larger end, the first takes 3, the second takes 9, then 2 and 1 follow, and the first player ends with 5 against 10. The table *D* tells a different story:

```fig {#fig-14-game} The table D(l, r) for a = [3, 9, 1, 2], filled by diagonals. The corner, 7, is the first player's guaranteed margin.
{"type": "grid", "cell": 50, "cellh": 30,

At the corner, taking 3 gives 3 − *D*(1, 3) = 3 − 8 = −5, while taking 2 gives 2 − *D*(0, 2) = 2 − (−5) = 7. So the first player takes the **smaller** end, 2. The second player then faces [3, 9, 1], where either choice leaves 9 exposed: by *D*(0, 2) = −5 the mover there loses by 5. With perfect play the totals are 11 and 4 (sum 15, difference 7, and indeed (15 + 7)/2 = 11).
:::

There is a pretty fact behind the review questions: when *n* is even, the first player never loses this game. Colour the positions alternately; the first player can always take all even-indexed elements or all odd-indexed elements, whichever sum is larger, because each of their moves exposes only elements of the other colour. On 5,000 random even-length rows the DP never returned a negative value.

### When the score of a move depends on what is left

In LeetCode 1690 (Stone Game VII) the player who removes the leftmost or the rightmost stone scores the **sum of the stones that remain**, and the statement says outright that the first player wants to maximise the difference and the second wants to minimise it. The difference recurrence is then the definition of optimal play, not a theorem about it, and only the score of a move changes: removing *a*[*l*] from *a*[*l*..*r*] scores the sum of *a*[*l* + 1..*r*], which a prefix-sum array gives in O(1) (Chapter 2). A segment with one stone left scores nothing for either player. On the row [2, 7, 1, 4], the first player's best margin works out to 11: removing the 2 scores 7 + 1 + 4 = 12, after which the opponent's best margin on [7, 1, 4] is 1.

:::pitfall
Do not mix the two viewpoints. Either store the difference for "the player to move" and subtract the child's value, as above, or store two separate scores and swap them at each level. Storing "player one's score" and adding the child's value treats both players as allies, and gives the answer to a different, cooperative game.
:::

## Choosing the order and the limits {#sec-14-order}

### Memoisation or a table

An interval DP can be written top-down: a recursive method `solve(l, r)` that checks a memo table, computes the value from the recurrence by recursive calls, and stores it. Memoisation needs no thought about order, because recursion computes each sub-segment when it is first needed, and it skips states that are never reached. Its costs are a method call per state and a recursion depth equal to the longest chain of nested calls, here at most *n* (each call shrinks the segment). How deep Java can go depends on the stack size and on the frame size of the method. On the machine used for this book, a recursive method with three `int` parameters overflowed the default stack after about 7,400 nested calls when interpreted and about 11,400 once compiled by the JIT. A depth of 5000 stays below both figures, but not by a wide margin; beyond about 10⁴, use a table, or run the recursion on a thread with a large stack (the template is in the plan's Java exam kit).

A bottom-up table avoids both costs and is easy to get right once you apply @lem-14-order. Prefer it in Java when the whole table is needed anyway, as in every problem of this chapter.

### What the limits allow

Table: {#tbl-14-limits} Interval and game DPs under typical limits
| Shape | Work | *n* ≤ 500 | *n* ≤ 5000 |
|---|---|---|---|
| split DP, O(*n*³) | (*n* + 1)*n*(*n* − 1)/6 triples | 2.1 · 10⁷: fine | 2.1 · 10¹⁰: too slow |
| game or end-removal DP, O(*n*²) | *n*(*n* + 1)/2 states | 1.3 · 10⁵: trivial | 1.25 · 10⁷: fine |
| `long[n][n]` table | 8*n*² bytes | 2 MB | 200 MB: too much for most limits |
| `int[n][n]` table | 4*n*² bytes | 1 MB | 100 MB: risky |
| rolling `long[n]` (below) | 8*n* bytes | 4 KB | 40 KB |

For *n* ≤ 5000 a split DP needs a better idea (Knuth's optimisation or a different model) and is outside this plan. An end-removal game, though, only ever reads the previous length, so one array of the current length's values is enough.

```java {#lst-14-rolling} The same game DP in O(n) memory
// d[l] holds dp[l][l + len - 1] for the current length only.
static long bestScoreDifferenceRolling(int[] a) {
    int n = a.length;
    long[] d = new long[n];
    for (int i = 0; i < n; i++) d[i] = a[i];               // length 1
    for (int len = 2; len <= n; len++)
        for (int l = 0; l + len - 1 < n; l++) {
            int r = l + len - 1;
            // before this line: d[l] = dp[l][r - 1] (old length), d[l + 1] = dp[l + 1][r] (old length)
            d[l] = Math.max(a[l] - d[l + 1], a[r] - d[l]);
        }
    return n == 0 ? 0 : d[0];
}
```

The comment is the proof. In the pass for length len, `d[l]` still holds the value for [*l*, *r* − 1] from the previous pass, and `d[l + 1]` holds [*l* + 1, *r*] because the pass moves left to right and has not reached *l* + 1 yet. Overwriting `d[l]` loses nothing that a later step of this pass needs. The rolling version matched @lst-14-game on random rows of up to 400 elements, and both matched an exhaustive minimax on 4,000 small rows.

:::tip
Before writing an interval DP, write three things on paper: the meaning of dp[*l*][*r*] in one sentence, the base case (length 1 or 2), and which single operation, first or last, splits the segment. If you cannot say what is independent after that operation, the recurrence is probably wrong.
:::

## Summary

- Sorted, a set in which every pair divides is a divisor chain, so the largest divisible subset is an LIS with "divides" in place of "smaller": O(*n*²) with parent pointers.
- To visit all divisor pairs up to *N*, push from each value to its multiples. The total is Σ ⌊*N*/*v*⌋ ≤ *N*(⌊log *N*⌋ + 1), about 1.4 · 10⁷ for *N* = 10⁶.
- A chain of distinct values in 1..*N* has at most ⌊log *N*⌋ + 1 elements. Arrays in which each element divides the next are chains with repeats: Σ chains(*s*) · C(*K* − 1, *s* − 1) by stars and bars. With a non-prime modulus, build binomials with Pascal's rule.
- Interval DP stores dp[*l*][*r*] and must be filled by increasing length (or *l* descending, *r* ascending); "*l* ascending, *r* ascending" reads unfilled entries.
- Split recurrences come from the first or the last operation, whichever leaves independent pieces: the first cut for a stick, the last multiplication for matrices, the last balloon for Burst Balloons.
- In a game, a position is winning exactly when some move leads to a losing position. With scores, store the mover's best "my total minus yours": *D*(*l*, *r*) = max(*a*[*l*] − *D*(*l* + 1, *r*), *a*[*r*] − *D*(*l*, *r* − 1)). When the total is fixed, this is the same as each player maximising their own score.
- O(*n*³) fits *n* ≤ 500; for *n* ≤ 5000 only O(*n*²) time fits, and a `long[n][n]` table does not fit in memory, so roll the array by length.

## Review questions

1. Why must the values be sorted before the divisibility DP? Run the unsorted DP on [4, 2, 8] and compare with the true answer.
2. Compute Σ ⌊12/*v*⌋ for *v* = 1..12 and compare it with the bound of @thm-14-harmonic.
3. Using the chain counts of @ex-14-stars, how many arrays of length 4 with values in 1..6 have each element dividing the next?
4. In the matrix-chain template, the loops are changed to "for *l* from 0 up, for *r* from *l* + 1 up". Which entry is read before it is written when computing dp[0][2]?
5. Why is the cost of the first cut on a piece the same whichever cut is chosen, and why does that make the stick recurrence possible? Why is the DP over cut indices and not over positions 0..*L*?
6. Explain in two sentences why "choose the first balloon to burst" does not split Burst Balloons into independent subproblems.
7. Prove that in the take-from-either-end game with an even number of elements, the first player can always score at least half of the total.
8. For the take-away game with moves {1, 3, 4}, list the losing positions up to 14. Prove that *s* = 7 is losing directly from @thm-14-winlose.
9. A game DP has *n* = 5000. How much memory does `long[n][n]` need, and how much does @lst-14-rolling need? Why can the rolling version not be used for the matrix-chain DP?

:::answers
1. A chain can only be read in increasing order, because a positive integer is never divisible by a larger one. Without sorting, the DP only links *j* < *i* in the given order. On [4, 2, 8] it links 4 → 8 and 2 → 8 but never 2 → 4, and returns 2; the true answer is 3, the set {2, 4, 8}.
2. 12 + 6 + 4 + 3 + 2 + 2 + 1 + 1 + 1 + 1 + 1 + 1 = 35. The bound is 12 · (⌊log 12⌋ + 1) = 12 · 4 = 48.
3. Chains: 6 with one value, 8 with two, 3 with three. For *K* = 4: 6 · C(3, 0) + 8 · C(3, 1) + 3 · C(3, 2) = 6 + 24 + 9 = 39, which matches a brute force.
4. dp[0][2] tries *k* = 0, whose candidate dp[0][0] + dp[1][2] + *d*[0] · *d*[1] · *d*[3] needs dp[1][2]. Row 1 is filled in the next pass of the outer loop, so dp[1][2] is still 0 and that candidate, and possibly the minimum, comes out too small.
5. The first cut on a piece always cuts the whole piece, so it costs the piece's length *p*[*j*] − *p*[*i*] regardless of *k*. That fixed cost can be taken outside the minimum, and after it the two sub-pieces are independent, which is exactly what a split recurrence needs. Positions go up to 10⁶ while there are at most 100 cuts; every piece that can occur runs between two cut points (or ends), so indices into the sorted points describe all states with only (*m* + 2)² of them.
6. After bursting balloon *k* first, its two neighbours become adjacent, so the coins earned later on the left side depend on balloons from the right side and vice versa. Choosing the last balloon instead keeps it standing as a fixed wall between the two sides until both are finished.
7. Colour the positions 0, 1, …, *n* − 1 alternately even and odd. With *n* even, the two ends have different colours. If the first player always takes the end of the colour they chose, the two remaining ends after their move are both of the other colour, so the opponent must take that colour, and the first player's colour is again exposed at one end. So the first player can take every element of either colour. Choosing the colour with the larger sum gives at least half the total, so *D*(0, *n* − 1) ≥ 0.
8. The losing positions up to 14 are 0, 2, 7, 9 and 14. From 7 the moves lead to 6, 4 and 3. Each of those is winning: 6 → 2 (remove 4), 4 → 0 (remove 4), 3 → 2 (remove 1), each reaching a losing position. So every move from 7 leads to a winning position, and 7 is losing.
9. `long[5000][5000]` needs 8 · 25 · 10⁶ = 2 · 10⁸ bytes, about 200 MB, which exceeds a typical 256 MB limit once the JVM's own memory is counted. The rolling array needs 8 · 5000 = 40,000 bytes. The matrix-chain DP reads dp[*l*][*k*] and dp[*k* + 1][*r*] for **all** shorter lengths, not only the previous one, so the whole table must be kept.
:::
