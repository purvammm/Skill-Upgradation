Every later chapter of this book assumes that you can turn an idea into correct Java quickly. That skill has three parts. You must know what a solution will cost before you write it, so that you do not spend forty minutes on code that is too slow. You must know the standard library well enough that "count the values", "find the nearest booking" or "always take the largest" is one call you type without thinking. And you must know the handful of places where Java behaves differently from school arithmetic: integers that wrap around, remainders that come out negative, objects that look equal but are not `==`.

This chapter covers those three parts. It starts with the assessment itself and the routine that the two volumes follow, then sets up the language for talking about running time. The middle of the chapter is a tour of the primitive types, the collections and the string classes, with four of the day's problems as worked examples. The last three sections cover reading input in an exam that gives you only standard input, linked lists, and the call stack.

Much of this material is reference. Read it once today, and come back to @tbl-1-cost and @tbl-1-traps whenever a later chapter uses a structure you are unsure of.

## The assessment and how these two books work {#sec-1-exam}

### What the paper looks like

The Infosys Specialist Programmer (SP) and Digital Specialist Engineer (DSE) roles share one coding assessment. The reports collected in the plan agree on the following points.

- **Three problems in three hours**, in increasing difficulty. A 2026 off-campus candidate described an in-person, proctored lab round with about four DSA problems, and the official sample paper has a fourth "Complex" problem as well.
- **Marks**: the first problem is worth 20, the second 30 and the third 50.
- **Partial credit**: marks come from the test cases you pass, so a correct but slow solution still scores on the small tests. Sectional and overall cut-offs are reported. Negative marking applies only to plagiarism.
- **Languages**: C, C++, Java, Python and JavaScript.
- **Problem style**: long, story-style statements. Input arrives **one value per line**. You usually implement a function such as `get_ans(...)` that returns the answer. Typical limits are *n* ≤ 10⁵, with answers taken modulo 10⁹ + 7.
- **Conditions**: strict invigilation; phones, calculators and smartwatches were not allowed at past in-person rounds.

The official sample paper is harder than its labels suggest. Its "Easy" problem combines a number-theory trick (the square-free part of a number) with a tree technique (small-to-large merging) and a traversal without recursion; the plan estimates it at about Codeforces 1800. That gap is why the plan reaches LeetCode Hards and Codeforces 1600–2200 problems by the third week.

:::infosys
Partial marks are real marks. A brute force that is correct for small inputs passes the small test files, and on the sample paper's Hard problem trying every subsequence already works up to *N* ≈ 20. Never leave a problem blank. Chapter 9 teaches you to write the brute force first and to use it to test your fast solution.
:::

### Function stub or full program

Two kinds of question appear, and they need different code.

1. **A function stub.** The platform shows a method such as `get_ans(int n, int m, int[] a)` and reads the input for you. Keep the stub's name, parameters and return type exactly as given and fill in the body. Changing the signature can make every test fail.
2. **A full program.** You write `main` yourself and read every number from standard input. Then you need the `FastScanner` of @sec-1-io and a `PrintWriter` for output.

On LeetCode you write only the method, inside a class named `Solution`, and LeetCode passes you the input as arguments. On Codeforces you always write the full program. Practising both forms is part of the plan.

## Measuring cost: big-O notation {#sec-1-bigo}

Before you write a solution you should know, within a factor of ten, how long it will run. The limits in the statement tell you how fast the solution must be; big-O notation tells you how fast your idea is. Matching the two is the first thing to do with every problem.

### Counting steps

Count the **basic steps** an algorithm performs: an arithmetic operation, a comparison, an array access, an assignment. Each takes a small, fixed amount of time, so the total time is roughly proportional to the number of steps. We count the steps for the worst input of each size *n* and write the count as a function *f*(*n*).

Consider the brute force for "is there a pair *i* < *j* with *a*[*i*] + *a*[*j*] = *t*?":

```java
static boolean hasPairBrute(int[] a, int t) {
    for (int i = 0; i < a.length; i++)
        for (int j = i + 1; j < a.length; j++)
            if (a[i] + a[j] == t) return true;
    return false;
}
```

For a fixed *i* the inner loop runs *n* − 1 − *i* times. Over all *i* that is (*n* − 1) + (*n* − 2) + ⋯ + 0 = *n*(*n* − 1)/2 comparisons when no pair exists. For *n* = 10⁴ this is 49,995,000 comparisons, which runs in well under a second. For *n* = 10⁵ it is 4,999,950,000, which at the speeds measured below takes between 5 and 50 seconds. The exact count is less important than its shape: it grows like *n*².

### The definition

:::definition{#def-1-bigo} Big-O, big-Omega and big-Theta
Let *f* and *g* be functions from positive integers to non-negative numbers. In [[big-O notation]], *f*(*n*) = O(*g*(*n*)) means there are constants *c* > 0 and *n*₀ such that *f*(*n*) ≤ *c* · *g*(*n*) for every *n* ≥ *n*₀. Similarly *f*(*n*) = Ω(*g*(*n*)) means *f*(*n*) ≥ *c* · *g*(*n*) for all *n* ≥ *n*₀ and some *c* > 0, and *f*(*n*) = Θ(*g*(*n*)) means both hold.
:::

O is an upper bound, Ω a lower bound and Θ an exact order of growth. In practice people write O when they mean Θ, and this book follows the custom when the bound is tight.

:::example{#ex-1-bigo} A bound with explicit constants
Take *f*(*n*) = 3*n*² + 5*n* + 2. To show *f*(*n*) = O(*n*²), choose *c* = 4. The inequality 3*n*² + 5*n* + 2 ≤ 4*n*² is equivalent to *n*² − 5*n* − 2 ≥ 0, which first holds at *n* = 6 (at *n* = 5 the left side is −2). So *c* = 4 and *n*₀ = 6 work. The same *f* is also O(*n*³), because O is only an upper bound, but it is not O(*n*): for any *c*, 3*n*² > *c* · *n* as soon as *n* > *c*/3.
:::

Three rules follow directly from the definition and cover almost every analysis in this book.

1. **Constants and lower-order terms disappear.** 3*n*² + 5*n* + 2 = Θ(*n*²), and log₂ *n* and log₁₀ *n* differ only by a constant factor, so the base of a logarithm is never written.
2. **Sequential parts add, and the larger wins.** If one phase costs O(*n* log *n*) and the next O(*n*), the total is O(*n* log *n*).
3. **Nested parts multiply.** A loop of *n* iterations whose body costs O(log *n*) costs O(*n* log *n*).

:::lemma{#lem-1-sum} The sum rule
If *f*₁(*n*) = O(*g*₁(*n*)) and *f*₂(*n*) = O(*g*₂(*n*)), then *f*₁(*n*) + *f*₂(*n*) = O(max(*g*₁(*n*), *g*₂(*n*))).
:::

:::proof
There are constants with *f*₁(*n*) ≤ *c*₁*g*₁(*n*) for *n* ≥ *n*₁ and *f*₂(*n*) ≤ *c*₂*g*₂(*n*) for *n* ≥ *n*₂. For *n* ≥ max(*n*₁, *n*₂), *f*₁(*n*) + *f*₂(*n*) ≤ *c*₁*g*₁(*n*) + *c*₂*g*₂(*n*) ≤ (*c*₁ + *c*₂) · max(*g*₁(*n*), *g*₂(*n*)). So *c* = *c*₁ + *c*₂ and *n*₀ = max(*n*₁, *n*₂) satisfy the definition.
:::

Logarithms appear whenever a quantity is halved each step, which is the heart of binary search (Chapter 6), heaps (Chapter 5) and balanced trees.

:::claim{#thm-1-halving} Halving loops
For *n* ≥ 1 the loop `for (int x = n; x > 0; x /= 2)` runs exactly ⌊log₂ *n*⌋ + 1 times.
:::

:::proof
After *k* iterations, *x* = ⌊*n*/2ᵏ⌋, because integer division by 2 repeated *k* times equals one division by 2ᵏ, rounded down. The loop runs iteration *k* + 1 exactly when ⌊*n*/2ᵏ⌋ ≥ 1, that is when 2ᵏ ≤ *n*, that is when *k* ≤ log₂ *n*. So iterations *k* + 1 = 1, 2, …, ⌊log₂ *n*⌋ + 1 run and no more. For *n* = 10⁶ that is 20 iterations.
:::

### How fast is Java?

A useful planning figure is **10⁸ to 3 · 10⁸ basic steps per second** for typical contest Java. The range is wide because "a step" hides very different costs. These measurements were taken for this book with OpenJDK 25 (middle of three runs):

- a loop of 10⁹ iterations doing one XOR, one shift and one addition: 0.98 s;
- 10⁶ increments of random cells of an `int[]` of size 10⁶: 32 ms;
- 10⁶ `HashMap.merge` calls on random keys: 170 ms;
- 10⁶ `TreeMap.merge` calls on random keys: 630 ms;
- `Arrays.sort` on 10⁶ random `int` values: 95 ms.

So a trivial loop runs at 10⁹ steps per second, while a `TreeMap` operation costs about twenty times as much as an array access. When an estimate lands near the limit, count collection calls separately from array steps.

### From limits to a target

Reverse the reasoning: the largest *n* in the statement tells you which complexities can fit in about a second. @tbl-1-limits is the short version. The full table, with memory and more cases, is in Theory Appendix A.

Table: {#tbl-1-limits} Rough limits for a 1–2 second time limit
| Largest *n* | Fits | Typical technique |
|---|---|---|
| ≤ 10 | O(*n*!) | try every order |
| ≤ 20 | O(2ⁿ · *n*) | every subset, bitmask DP |
| ≤ 500 | O(*n*³) | three nested loops, interval DP |
| ≤ 5 000 | O(*n*²) | all pairs, two-dimensional DP |
| ≤ 10⁶ | O(*n* log *n*) | sorting, heaps, binary search, balanced trees |
| ≤ 10⁷–10⁸ | O(*n*) | one pass, prefix sums, two pointers |
| larger | O(log *n*) or O(1) | a formula, or binary search on the answer |

Memory is estimated the same way: cells times bytes per cell. An `int` takes 4 bytes and a `long` 8, so `new long[100000][100000]` asks for 10¹⁰ × 8 = 8 · 10¹⁰ bytes, about 80 GB. An array of 10⁶ `long` values is 8 MB and is always fine.

:::tip
Write the target complexity on paper before you write code. The workbook's problem worksheets have a box for it. If your idea does not meet the target, it is a partial-marks fallback, not the solution.
:::

## Primitive types and overflow {#sec-1-overflow}

### The integer types

Table: {#tbl-1-types} Java's numeric types
| Type | Bits | Range | Use it for |
|---|---|---|---|
| `int` | 32 | −2,147,483,648 to 2,147,483,647 (about ±2.1 · 10⁹) | indices, counts, values ≤ 10⁹ |
| `long` | 64 | −9,223,372,036,854,775,808 to 9,223,372,036,854,775,807 (about ±9.2 · 10¹⁸) | sums, products, anything modulo 10⁹ + 7 |
| `char` | 16 | 0 to 65,535 (unsigned) | characters; it is a number |
| `double` | 64 | about ±1.8 · 10³⁰⁸, 53 bits of precision | real numbers; integers are exact only up to 2⁵³ ≈ 9 · 10¹⁵ |

The default rule for this book is **`long` for every sum and product, `int` for indices and counts**. A `long` holds the product of two values below 3 · 10⁹, which covers every product of two numbers below the modulus 10⁹ + 7.

### Two's complement and wrap-around

:::definition{#def-1-twos} Two's complement
A Java `int` is stored as 32 bits *b*₃₁ … *b*₀ in [[two's complement]]: the pattern represents the value −*b*₃₁ · 2³¹ + *b*₃₀ · 2³⁰ + ⋯ + *b*₀ · 2⁰. The top bit counts as −2³¹ instead of +2³¹, so patterns with the top bit set are the negative numbers. A `long` works the same way with 64 bits.
:::

With this representation the processor adds and multiplies bit patterns exactly as it would for unsigned numbers and keeps the low 32 bits. The consequence is the rule you must remember:

:::keyidea
Every `int` addition, subtraction and multiplication returns the true result **modulo 2³²**, moved into the range [−2³¹, 2³¹). Java never throws an exception on integer overflow; you get a wrong number silently.
:::

These lines were run to produce the values in the comments:

```java {.fragment}
int big = 2_000_000_000;
int s = big + big;                       // -294967296  (4e9 - 2^32)
int a = 100_000, b = 100_000;
int p = a * b;                           // 1410065408  (1e10 - 2 * 2^32)
long ok = (long) a * b;                  // 10000000000 (a becomes long before *)
long late = (long) (a * b);              // 1410065408  (overflow happened first)
int wrap = Integer.MAX_VALUE + 1;        // -2147483648
int abs = Math.abs(Integer.MIN_VALUE);   // -2147483648 (there is no +2^31 in int)
```

The fourth line is the trap that catches people who know about overflow. In `(long) (a * b)` the multiplication happens in `int`, overflows, and only the wrong result is converted. In `(long) a * b` the cast applies to `a` alone, so `b` is promoted and the multiplication happens in `long`.

:::pitfall
Write `(long) a * b`, never `(long) (a * b)`. And in modular code, reduce after **every** multiplication: with *x*, *y* < 10⁹ + 7, `x * y % MOD` fits in a `long` (the product is at most about 1.0 · 10¹⁸, far below 9.2 · 10¹⁸), but `x * y * z % MOD` does not.
:::

### Division and remainders

Java's integer division rounds **towards zero**, and `%` is defined so that `a == (a / b) * b + a % b`. So the remainder takes the sign of the left operand: `-7 / 2` is −3, `-7 % 3` is −1 and `-3 % 5` is −3. Mathematics, and every hash-map key of Chapter 2, wants the remainder in [0, *m*). Use `Math.floorMod(-7, 3)`, which is 2, and `Math.floorDiv(-7, 2)`, which is −4 (rounding down).

A comparator written as subtraction fails for the same reason as any other `int` arithmetic. For *p* = 2 · 10⁹ and *q* = −2 · 10⁹, `p - q` is −294,967,296, which claims *p* < *q*. `Integer.compare(p, q)` returns 1, the right answer. Chapter 4 returns to comparators.

### Boxing and the Integer cache

Collections hold objects, not primitives, so `List<Integer>` and `Map<Integer, Integer>` store `Integer` objects. Converting an `int` to an `Integer` is called [[autoboxing]], and the reverse is unboxing; the compiler inserts both for you. Boxing calls `Integer.valueOf`, which by the Java Language Specification returns a **shared, cached object** for every value from −128 to 127 and may create a new object for any other value.

The operator `==` on two objects asks "are these the same object?", not "do they hold the same number?". Together, these two facts give the following results, all checked by running them:

```java {.fragment}
Integer i1 = 127, i2 = 127;
boolean x1 = i1 == i2;                  // true: both are the cached object for 127
Integer i3 = 128, i4 = 128;
boolean x2 = i3 == i4;                  // false: two different objects
boolean x3 = i3.equals(i4);             // true: same value
boolean x4 = i3.intValue() == i4;       // true: one side is int, so both are unboxed
Integer i5 = -129, i6 = -129;
boolean x5 = i5 == i6;                  // false; -128 == -128 would be true
```

`Long.valueOf` caches the same range. The upper end of the `Integer` cache can be raised with a JVM option, so code that happens to pass with `==` on your machine may fail elsewhere. The bug shows up in practice as `map.get(a) == map.get(b)` for two counts: it is correct while the counts are small and fails once both reach 128.

:::pitfall
Compare boxed values with `.equals()`, or unbox one side first (`int ca = map.get(a);`). And never unbox a value that may be `null`: `int c = map.get(k);` throws a `NullPointerException` when `k` is missing. Use `map.getOrDefault(k, 0)`.
:::

## The collections toolkit {#sec-1-collections}

### Pick the structure by the question

Each collection answers a few questions in one fast step. Decide which question your algorithm asks most often, then pick the structure that answers it.

Table: {#tbl-1-choose} Which structure answers which question
| The question | Structure | The call |
|---|---|---|
| Have I seen *x*? | `HashSet<Integer>` | `add`, `contains` |
| How many times did *x* appear? Where was *x*? | `HashMap<Integer, Integer>`, or `int[26]` for letters | `merge`, `getOrDefault` |
| What was added most recently? | `ArrayDeque` as a [[stack]] | `push`, `pop`, `peek` |
| What was added earliest? | `ArrayDeque` as a [[queue]] | `offer`, `poll`, `peek` |
| What is the smallest (or largest) item so far? | `PriorityQueue` | `add`, `poll`, `peek` |
| What is the nearest key below or above *x*? | `TreeMap` / `TreeSet` | `floorKey`, `ceilingKey`, `lower`, `higher` |
| What is element *i*? | array or `ArrayList` | `a[i]`, `get(i)` |

### Arrays and ArrayList

An `ArrayList` is an array that grows: when it is full, it allocates an array about 1.5 times larger and copies the elements across. One copy costs O(*n*), but it happens so rarely that *n* additions cost O(*n*) in total, which is what "O(1) amortised" means. Inserting or removing in the middle shifts every later element and costs O(*n*).

:::pitfall
`List<Integer>` has two `remove` methods. `list.remove(3)` removes the element at **index** 3; `list.remove(Integer.valueOf(3))` removes the first element equal to 3. The compiler picks the index version whenever you pass an `int`.
:::

Arrays of primitives sort in ascending order with `Arrays.sort(a)`. A custom order needs objects, so it works on `Integer[]` or on arrays of arrays such as `int[][]`, never on `int[]`. These lines are from the handbook's toolkit card:

```java {.fragment}
int[][] pairs = {{2, 5}, {1, 9}, {2, 1}};
Arrays.sort(pairs, (x, y) -> x[0] != y[0] ? Integer.compare(x[0], y[0]) : Integer.compare(x[1], y[1]));
// pairs is now {1,9}, {2,1}, {2,5}
Integer[] boxed = {5, 2, 8};
Arrays.sort(boxed, Collections.reverseOrder());    // 8, 5, 2
List<String> words = new ArrayList<>(Arrays.asList("bbb", "a", "cc"));
words.sort((x, y) -> Integer.compare(x.length(), y.length()));   // a, cc, bbb
```

Chapter 4 explains which algorithm each sort uses and why that matters.

### HashMap and HashSet

A hash map stores key–value pairs and finds a key in O(1) expected time; Chapter 2 explains how. Four calls do most of the work:

```java {.fragment}
int[] a = {3, 1, 3, 2, 3};
Map<Integer, Integer> freq = new HashMap<>();
for (int x : a) freq.merge(x, 1, Integer::sum);   // same as put(x, getOrDefault(x, 0) + 1)
int threes = freq.getOrDefault(3, 0);              // 3
int nines = freq.getOrDefault(9, 0);               // 0 (missing key, no exception)
Map<String, List<String>> groups = new HashMap<>();
groups.computeIfAbsent("eilnst", k -> new ArrayList<>()).add("listen");   // build groups
```

Iteration order over a `HashMap` is unspecified. If the output must be sorted, sort the keys or use a `TreeMap`.

### ArrayDeque as a stack and as a queue

A **stack** returns the most recently added item first (last in, first out); a **queue** returns the earliest (first in, first out). `ArrayDeque` is both, with O(1) operations at either end. Use it instead of `Stack`, which is an old synchronised class built on `Vector` and pays for locking on every call. `ArrayDeque` does not accept `null`.

```java {.fragment}
ArrayDeque<Integer> stack = new ArrayDeque<>();
stack.push(1);
stack.push(2);
int top = stack.pop();                             // 2 (last in, first out)
ArrayDeque<Integer> queue = new ArrayDeque<>();
queue.offer(1);
queue.offer(2);
int front = queue.poll();                          // 1 (first in, first out)
```

Do not mix the two families on one deque by accident: `push` and `pop` work at the front, `offer` adds at the back and `poll` removes from the front.

### PriorityQueue

A [[priority queue]] returns the smallest item first, whatever the order of insertion. Java's `PriorityQueue` is a binary heap (Chapter 5 builds one from scratch). The default is a min-heap; pass a comparator for anything else.

```java {.fragment}
PriorityQueue<Integer> minHeap = new PriorityQueue<>();                          // poll() = smallest
PriorityQueue<Integer> maxHeap = new PriorityQueue<>(Collections.reverseOrder()); // poll() = largest
PriorityQueue<long[]> byFirst = new PriorityQueue<>((x, y) -> Long.compare(x[0], y[0]));
```

Only the top is ordered. Printing a heap holding 5, 1, 4, 2, 3 gives `[1, 2, 4, 5, 3]`, the internal array, not a sorted list. To get the items in order, `poll` them one by one.

### TreeMap and TreeSet

:::definition{#def-1-ordered} Ordered map
An [[ordered map]] keeps its keys sorted and answers, for any value *x*, "which key is nearest to *x* from below or above?". Java's `TreeMap` (and `TreeSet` for keys alone) is a balanced binary search tree, so every such query and every update costs O(log *n*).
:::

The four neighbour queries differ only in whether *x* itself counts. For the set {10, 20, 30}, running the calls gives:

Table: {#tbl-1-tree} Neighbour queries on the set {10, 20, 30}
| Call | Meaning | Result for 20 | Result for 5 |
|---|---|---|---|
| `floor(x)` | largest key ≤ *x* | 20 | `null` |
| `lower(x)` | largest key < *x* | 10 | `null` |
| `ceiling(x)` | smallest key ≥ *x* | 20 | 10 |
| `higher(x)` | smallest key > *x* | 30 | 10 |

On a `TreeMap` the same queries are `floorKey`, `lowerKey`, `ceilingKey` and `higherKey`, and `floorEntry` and friends return the key with its value. `first()`, `last()`, `pollFirst()`, `headSet(x)` (keys < *x*) and `tailSet(x)` (keys ≥ *x*) complete the toolkit. Every result can be `null`, so test before you unbox.

### Worked example: Two Sum in one pass

LeetCode 1 (Two Sum) gives an array and a target and asks for the indices of two different elements that add up to the target; exactly one answer exists. The brute force of @sec-1-bigo checks every pair in O(*n*²). The one-pass method asks a hash map, at each index *j*, whether the partner value *t* − *a*[*j*] appeared earlier.

```java {#lst-1-twosum} Two Sum in one pass (LeetCode 1)
class Solution {
    public int[] twoSum(int[] nums, int target) {
        Map<Integer, Integer> seen = new HashMap<>();      // value -> index where it was seen
        for (int j = 0; j < nums.length; j++) {
            Integer i = seen.get(target - nums[j]);        // a partner seen earlier?
            if (i != null) return new int[]{i, j};
            seen.put(nums[j], j);                          // store after the look-up
        }
        return null;                                       // no pair (LeetCode promises one)
    }
}
```

:::theorem{#thm-1-twosum} Correctness of the one-pass Two Sum
If some pair *i* < *j* has *a*[*i*] + *a*[*j*] = *t*, @lst-1-twosum returns such a pair; otherwise it returns `null`. Every pair it returns is valid.
:::

:::proof
Invariant: when the loop starts index *j*, `seen` contains exactly the values *a*[0], …, *a*[*j* − 1], each mapped to an index where it occurs. It holds for *j* = 0 (empty map) and the `put` at the end of each iteration maintains it. *Validity*: a returned pair (*i*, *j*) has *a*[*i*] = *t* − *a*[*j*] by the look-up and *i* < *j* by the invariant. *Completeness*: let *j*\* be the smallest index that is the right end of some valid pair (*i*, *j*\*). The loop does not return before *j*\*, because a return at *j* < *j*\* would be a valid pair ending at *j*. At *j*\* the value *a*[*i*] = *t* − *a*[*j*\*] is in `seen` by the invariant, so the method returns.
:::

Storing after the look-up matters. If `put` came first, an element could pair with itself: for *a* = [3, 5] and *t* = 6, the element 3 would find itself at index 0 and return [0, 0].

:::example{#ex-1-twosum} Tracing Two Sum
Take *a* = [4, 11, 7, 2, 8, 5] and *t* = 13. The table shows the map at the start of each step.

```trace
j  a[j]  need = t - a[j]   map before this step       found
0    4         9            {}                          -
1   11         2            {4:0}                       -
2    7         6            {4:0, 11:1}                 -
3    2        11            {4:0, 7:2, 11:1}            11 at index 1  -> return [1, 3]
```
:::

The loop does at most *n* map look-ups and *n* insertions, so it runs in O(*n*) expected time and O(*n*) memory, against O(*n*²) time and O(1) memory for the brute force.

### Worked example: Valid Parentheses with a stack

LeetCode 20 (Valid Parentheses) asks whether a string of the characters `()[]{}` is balanced: every opener is closed by the matching closer, in the right order. The last opener that is still open must be closed first, which is exactly the question a stack answers. The listing pushes the closer it expects; a closer in the input must then equal the top of the stack.

```java {#lst-1-parens} Valid Parentheses with an ArrayDeque (LeetCode 20)
static boolean isValid(String s) {
    ArrayDeque<Character> expect = new ArrayDeque<>();   // closers we still owe, top = most recent
    for (char c : s.toCharArray()) {
        if (c == '(') expect.push(')');
        else if (c == '[') expect.push(']');
        else if (c == '{') expect.push('}');
        else if (expect.isEmpty() || expect.pop() != c) return false;  // wrong or unexpected closer
    }
    return expect.isEmpty();                             // every opener must be closed
}
```

Call a string *balanced* if it can be reduced to the empty string by repeatedly deleting an adjacent matching pair `()`, `[]` or `{}`. This is equivalent to the usual definition by nesting, and it is also the brute force the listing was tested against on 70,000 random strings.

:::lemma{#lem-1-pairdel} Deleting a matched pair does not change the result
If *s* = *u* *x* *y* *v*, where *x* is an opener and *y* its matching closer, then `isValid(s)` = `isValid(uv)`.
:::

:::proof
On *s* the method processes *u* exactly as on *uv*. If it returns `false` inside *u*, both runs return `false`. Otherwise, at *x* it pushes *y*; at the next character, *y*, it pops *y* and the comparison succeeds. The stack is now exactly as it was after *u*, so the rest of the run on *s* processes *v* from the same state as the run on *uv* and ends the same way.
:::

:::theorem{#thm-1-parens} Correctness of the stack check
`isValid(s)` returns `true` exactly when *s* is balanced.
:::

:::proof
*Balanced ⇒ true.* A balanced string reaches the empty string by some sequence of pair deletions. By @lem-1-pairdel no deletion changes the method's result, and `isValid("")` is `true`. *True ⇒ balanced*, by induction on the length of *s*. The empty string is balanced. Let *s* be non-empty and accepted. Its first character is an opener, because a closer on an empty stack returns `false`, and *s* contains a closer, because otherwise the stack would be non-empty at the end. Let *y* be the first closer and *x* the character just before it, which is an opener. At *y* the method pops the closer pushed for *x*, and since it does not return `false`, *y* matches *x*. Deleting *xy* gives a shorter string that is accepted by @lem-1-pairdel, hence balanced by induction; so *s* is balanced too.
:::

Each character causes one push or one pop, so the method runs in O(*n*) time and O(*n*) memory. The stack also has a direct meaning at every moment: it holds, from bottom to top, the closers still owed for the openers that have not yet been matched.

The stack is written from bottom to top.

```trace
{  push }   }         (  push )   )             (  push )   )
[  push ]   }]        [  push ]   )]            (  push )   ))
(  push )   }])       )  pop ] != ) -> false    )  pop )    )
)  pop )    }]                                  end: stack not empty -> false
]  pop ]    }
(  push )   })
)  pop )    }
}  pop }    (empty)  -> true
```
:::

### Worked example: the k largest values with a size-k heap

Many problems end with "report the *k* best". Sorting everything costs O(*n* log *n*). A min-heap that never holds more than *k* items costs O(*n* log *k*), and it also works when the items arrive one at a time.

```java {#lst-1-klargest} The k largest values with a size-k min-heap
static int[] kLargest(int[] a, int k) {
    PriorityQueue<Integer> heap = new PriorityQueue<>();   // min-heap: smallest of the kept k on top
    for (int x : a) {
        heap.add(x);
        if (heap.size() > k) heap.poll();                  // drop the smallest of k + 1
    }
    int[] res = new int[heap.size()];
    for (int i = res.length - 1; i >= 0; i--) res[i] = heap.poll();   // largest first
    return res;
}
```

:::claim{#thm-1-klargest} The heap keeps the k largest
After the loop has processed *a*[0..*j*], the heap holds a multiset of min(*k*, *j* + 1) values that are the largest among *a*[0..*j*] (ties broken arbitrarily).
:::

:::proof
By induction on *j*. Suppose the heap holds the *k* largest of the first *j* values and *x* arrives. The *k* largest of the first *j* + 1 values are among the heap's *k* values and *x*, because any value outside the heap was already beaten by *k* others. Of these *k* + 1 candidates the smallest is the one to drop, and `poll` removes exactly the smallest. While fewer than *k* values have arrived, nothing is dropped.
:::

:::example{#ex-1-klargest} Tracing the size-k heap
Take *a* = [5, 1, 9, 3, 7, 9, 2, 8] and *k* = 3. The heap contents are listed in sorted order for readability.

```trace
x   dropped   heap after the step
5      -      [5]
1      -      [1, 5]
9      -      [1, 5, 9]
3      1      [3, 5, 9]
7      3      [5, 7, 9]
9      5      [7, 9, 9]
2      2      [7, 9, 9]
8      7      [8, 9, 9]
```

The result is [9, 9, 8].
:::

Each of the *n* additions and at most *n* polls works on a heap of at most *k* + 1 items, so the time is O(*n* log *k*) and the memory O(*k*).

LeetCode 347 (Top K Frequent Elements) applies this to counts: first count each value with a `HashMap`, then run the size-*k* heap over the map's entries, ordered by count instead of by value. There is also an O(*n*) alternative. Every count lies between 1 and *n*, so you can put each value into a bucket indexed by its count, `List<Integer>[] bucket = new List[n + 1]`, and read the buckets from *n* down to 1 until *k* values are collected. Writing both versions is a good exercise.

### Worked example: My Calendar with TreeMap neighbours

LeetCode 729 (My Calendar I) receives bookings [*start*, *end*) one at a time and must accept a booking only if it overlaps no accepted booking. Two half-open intervals [*s*, *e*) and [*s*′, *e*′) overlap exactly when *s*′ < *e* and *s* < *e*′. Checking every accepted booking costs O(*n*) per request. An ordered map from start to end needs only two neighbours.

```java {#lst-1-calendar} My Calendar I with floorKey and ceilingKey (LeetCode 729)
class MyCalendar {
    private final TreeMap<Integer, Integer> booked = new TreeMap<>();   // start -> end, [start, end)

    public boolean book(int start, int end) {
        Integer before = booked.floorKey(start);        // latest booking starting at or before start
        if (before != null && booked.get(before) > start) return false;
        Integer after = booked.ceilingKey(start);       // earliest booking starting at or after start
        if (after != null && after < end) return false;
        booked.put(start, end);
        return true;
    }
}
```

:::theorem{#thm-1-calendar} Two neighbours suffice
Let the accepted bookings be pairwise disjoint and let [*s*, *e*) be a request. If [*s*, *e*) overlaps any accepted booking, it overlaps the booking with the largest start ≤ *s* or the booking with the smallest start ≥ *s*.
:::

:::proof
Let [*s*′, *e*′) be an accepted booking that overlaps [*s*, *e*), so *s*′ < *e* and *s* < *e*′. *Case s*′ ≤ *s*. Let *f* be the largest start ≤ *s*, so *s*′ ≤ *f* ≤ *s*. If *s*′ < *f*, the booking starting at *f* begins after [*s*′, *e*′) and is disjoint from it, so *e*′ ≤ *f* ≤ *s*, contradicting *s* < *e*′. Hence *s*′ = *f*: the floor booking is the overlapping one. *Case s*′ > *s*. Let *c* be the smallest start ≥ *s*, so *s* ≤ *c* ≤ *s*′ < *e*. Call that booking [*c*, *d*). It satisfies *c* < *e* and *s* ≤ *c* < *d*, so it overlaps the request.
:::

The listing tests exactly these two bookings. The floor booking overlaps when its end is greater than *s*; the ceiling booking overlaps when its start is less than *e*. Each request costs two O(log *n*) queries and one insertion, so *n* requests cost O(*n* log *n*) in total, against O(*n*²) for checking every booking.

:::example{#ex-1-calendar} Tracing seven requests
Requests arrive in this order. "floor" and "ceiling" are the neighbours found for the request's start, shown as start (end).

```trace

[0,6)     null       5 (10)       reject: [5,10) starts before 6
[30,31)   25 (30)    null         accept
```

The final map is {5: 10, 10: 20, 20: 25, 25: 30, 30: 31}.
:::

## Strings and characters {#sec-1-strings}

### Immutable strings and the cost of +=

:::definition{#def-1-immutable} Immutable object
An object is [[immutable]] if its contents can never change after it is created. Java's `String` is immutable: every method that seems to change a string, such as `concat`, `replace` or `+`, returns a new string and leaves the old one untouched.
:::

Immutability makes strings safe to share and to use as hash-map keys. It also makes one common loop quadratic.

:::claim{#thm-1-concat} Repeated += is quadratic
Building a string of length *n* with `s += c` for one character at a time copies 1 + 2 + ⋯ + *n* = *n*(*n* + 1)/2 characters.
:::

:::proof
The *i*-th `+=` cannot extend `s` in place, because `s` is immutable. It allocates a new string of length *i* and copies the *i* − 1 old characters and the new one. Summing *i* from 1 to *n* gives *n*(*n* + 1)/2.
:::

`StringBuilder` keeps a mutable buffer with spare capacity and roughly doubles it when it fills, so *n* appends copy fewer than 2*n* characters in total: O(1) amortised per append. The measured difference on this book's machine:

| Characters appended one at a time | `s += c` | `StringBuilder.append` |
|---|---|---|
| 25,000 | 0.33 s | under 1 ms |
| 50,000 | 0.92 s | under 1 ms |
| 100,000 | 3.1 s | under 1 ms |
| 200,000 | 6.5 s | 6 ms |

```java {.fragment}
StringBuilder sb = new StringBuilder();
sb.append("ab").append(3).reverse();
String s = sb.toString();                          // "3ba"
boolean same = s.equals("3ba");                    // true (== compares references, not text)
char[] chars = s.toCharArray();
Arrays.sort(chars);
String sorted = new String(chars);                 // "3ab"
```

The same reasoning applies to output: build one large `StringBuilder` or use one `PrintWriter` (@sec-1-io), never thousands of separate `System.out.println` calls.

### equals versus ==

Because strings are objects, `==` compares references. String **literals** with the same text are shared (the compiler and JVM keep one copy), so `"abc" == "abc"` is `true`, which hides the bug in small tests. A string built at run time is a new object: with `s4 = "ab"; s4 = s4 + "c";` the test `"abc" == s4` is `false` while `"abc".equals(s4)` is `true`. Always use `equals`, and `compareTo` for alphabetical order (it returns a negative number, zero or a positive number).

`s.charAt(i)` costs O(1). `s.substring(l, r)` (characters *l*..*r* − 1) **copies** them, so it costs O(*r* − *l*); calling it inside a loop over all positions makes the loop quadratic.

### Characters are numbers

A `char` is an unsigned 16-bit number, the character's code. Arithmetic on `char` happens in `int`, which gives three idioms you will use daily:

```java {.fragment}
char c = 'd';
int idx = c - 'a';                 // 3: position in the alphabet, an index into int[26]
char back = (char) ('a' + 3);      // 'd': the cast is needed, 'a' + 3 is an int
int digit = '7' - '0';             // 7: the digit's value
int code = 'a' + 1;                // 98, not 'b': the result of + is an int
```

`Character.isDigit`, `Character.isLetter`, `Character.toLowerCase` and `Character.isUpperCase` cover the rest.

### Counting letters with int[26]

When the keys are lowercase letters, an `int[26]` indexed by `c - 'a'` replaces a `HashMap<Character, Integer>`. It needs no boxing, no hashing and no `null` checks.

```java {#lst-1-count26} Counting letters with an int[26]
static int[] letterCounts(String s) {          // s contains only 'a'..'z'
    int[] cnt = new int[26];
    for (char c : s.toCharArray()) cnt[c - 'a']++;
    return cnt;                                // for "banana": cnt[0] = 3, cnt[1] = 1, cnt[13] = 2
}
```

Two strings are anagrams of each other when one is a rearrangement of the other, that is when every letter occurs equally often in both. So two strings are anagrams exactly when their count arrays are equal. LeetCode 242 (Valid Anagram) needs only this fact. The neat version uses one array: add 1 for each letter of the first string, subtract 1 for each letter of the second, and check that every entry is 0. It runs in O(*n* + 26) time with 26 integers of memory.

Counting is also the way to build a key for a group of anagrams. Sorting the letters gives the same key to every anagram ("listen" and "silent" both become "eilnst"), and `computeIfAbsent(key, k -> new ArrayList<>()).add(word)` collects each group.

## Reading input fast {#sec-1-io}

On LeetCode the input arrives as method arguments. In a full-program question you read it from standard input, and for 10⁵ or 10⁶ numbers the choice of reader decides whether the program finishes in time.

### Why Scanner is slow

`java.util.Scanner` is convenient but does a lot of work per token. It matches every token against a regular expression, converts numbers in a locale-aware way, and reads the input through a small buffer of 1024 characters. `BufferedReader` instead reads standard input in large chunks and returns a whole line at a time, and `StringTokenizer` splits a line on spaces with no regular expressions at all. The plan's author timed three readers on input written one number per line, as the Infosys input is (OpenJDK 25, middle of three runs, reading time only):

Table: {#tbl-1-readers} Time to read numbers written one per line
| Reader | 10⁵ numbers | 10⁶ numbers | When to use it |
|---|---|---|---|
| `Scanner` | 182 ms | 818 ms | small inputs only; risky above about 10⁵ numbers with a 1–2 s limit |
| `FastScanner` (`BufferedReader` + `StringTokenizer`) | 46 ms | 144 ms | the default: memorise it |
| `FastReader` (byte buffer) | 10 ms | 33 ms | only when reading millions of numbers |

Output matters as much. Printing 10⁶ lines with `System.out.println` took 2.0 s; the same output through one `PrintWriter` took 0.15 s.

### FastScanner: the version to memorise

```java {#lst-1-fastscanner} FastScanner and PrintWriter: a complete program that sums n numbers
import java.io.*;
import java.util.*;

public class Main {
    public static void main(String[] args) throws IOException {
        FastScanner fs = new FastScanner(System.in);
        PrintWriter out = new PrintWriter(new BufferedWriter(new OutputStreamWriter(System.out)));

        int n = fs.nextInt();                    // one value per line or all on one line: both work
        long[] a = new long[n];
        for (int i = 0; i < n; i++) a[i] = fs.nextLong();

        long sum = 0;
        for (long x : a) sum += x;
        out.println(sum);
        out.flush();                             // without this you print nothing
    }

    /** BufferedReader reads big chunks; StringTokenizer splits a line on spaces. */
    static final class FastScanner {
        private final BufferedReader br;
        private StringTokenizer st;

        FastScanner(InputStream in) {
            br = new BufferedReader(new InputStreamReader(in));
        }

        String next() throws IOException {
            while (st == null || !st.hasMoreTokens()) {   // current line used up: read another
                String line = br.readLine();
                if (line == null) return null;           // end of input
                st = new StringTokenizer(line);
            }
            return st.nextToken();
        }

        int nextInt() throws IOException { return Integer.parseInt(next()); }

        long nextLong() throws IOException { return Long.parseLong(next()); }

        double nextDouble() throws IOException { return Double.parseDouble(next()); }

        String nextLine() throws IOException {           // the next whole line, spaces included
            st = null;                                   // (drops anything left on the current line)
            return br.readLine();
        }
    }
}
```

Run on the input `3 10 20 30`, and again on the same four numbers written one per line, the program prints 60 both times. Line by line:

- `new BufferedReader(new InputStreamReader(System.in))` reads standard input in large blocks instead of a few characters at a time.
- `next()` returns one word. If the current line has no words left, it reads the next line and wraps it in a new `StringTokenizer`. That loop is why it does not matter whether the numbers come one per line or all on one line, and why blank lines are skipped.
- `nextInt()`, `nextLong()` and `nextDouble()` convert the next word.
- `nextLine()` returns the next whole line, spaces included. Use it only for text such as a sentence; it discards anything left on the current line.
- `PrintWriter` collects output in memory. `out.flush()` at the end sends it all at once. Forget it and nothing is printed, which scores zero.
- `main` declares `throws IOException` because `readLine` can throw it.

:::keyidea
`next()` keeps reading lines until it finds a word. That single loop makes `FastScanner` independent of how the values are spread over lines, which is exactly what one-value-per-line input needs.
:::

Table: {#tbl-1-scanner} Moving from Scanner to FastScanner
| With `Scanner` you wrote | With `FastScanner` you write |
|---|---|
| `Scanner sc = new Scanner(System.in);` | `FastScanner fs = new FastScanner(System.in);` |
| `sc.nextInt()`, `sc.nextLong()` | `fs.nextInt()`, `fs.nextLong()` |
| `sc.next()` (one word) | `fs.next()` |
| `sc.nextLine()` | `fs.nextLine()`; there is no trap where `nextLine()` right after `nextInt()` returns an empty string |
| `System.out.println(x)` in a loop | `out.println(x)`, then one `out.flush()` at the end |
| `main(String[] args)` | `main(String[] args) throws IOException` |

When the number of values is not given, read until `next()` returns `null`: `for (String w = fs.next(); w != null; w = fs.next()) { ... }`.

### One value per line

The official sample paper's Hard problem gives *N*, then *M*, then *N* values, each on its own line. With `FastScanner` the reading code is just the order of the statement: `int n = fs.nextInt(); int m = fs.nextInt();` and a loop of `fs.nextInt()`. If you are sure that every line holds exactly one value, `BufferedReader.readLine` alone is enough:

```java {.fragment}
BufferedReader br = new BufferedReader(new InputStreamReader(System.in));
int n = Integer.parseInt(br.readLine().trim());       // line 1: N
int m = Integer.parseInt(br.readLine().trim());       // line 2: M
int[] a = new int[n];
for (int i = 0; i < n; i++) a[i] = Integer.parseInt(br.readLine().trim());   // next N lines
```

This version fails on a blank line or on two values sharing a line, which `FastScanner` handles. Prefer `FastScanner` unless you are already sure of the layout.

:::infosys
Trust the samples, not the format text. In the sample paper's Medium problem the written input format puts *p* after the array, but all three samples only work if *p* comes right after *n*: the written order gives 1, 0, 0 against the expected 2, 3, 1. Run your reading code on every sample before you write the logic.
:::

### FastReader: the byte version

`FastReader` reads raw bytes 64 KB at a time and builds each number digit by digit (`r = r * 10 + digit`), without creating any `String`. It is about four times faster than `FastScanner` in @tbl-1-readers and harder to type from memory, so treat it as optional.

```java {#lst-1-fastreader} FastReader: optional byte-buffer reader
import java.io.*;
import java.util.*;

public class Main {
    static final long MOD = 1_000_000_007L;

    public static void main(String[] args) throws IOException {
        FastReader in = new FastReader(System.in);
        PrintWriter out = new PrintWriter(new BufferedWriter(new OutputStreamWriter(System.out)));

        int n = in.nextInt();              // one value per line or all on one line
        long[] a = new long[n];
        for (int i = 0; i < n; i++) a[i] = in.nextLong();

        long sum = 0;
        for (long x : a) sum += x;
        out.println(sum);

        out.flush();                        // forgetting this = empty output = 0 marks
    }

    /** Token reader: skips spaces AND newlines, so "one value per line" input is handled. */
    static final class FastReader {
        private final DataInputStream in;
        private final byte[] buf = new byte[1 << 16];
        private int len = 0, ptr = 0;

        FastReader(InputStream is) { in = new DataInputStream(is); }

        private int read() throws IOException {
            if (ptr == len) {
                len = in.read(buf, 0, buf.length);
                ptr = 0;
                if (len <= 0) return -1;
            }
            return buf[ptr++];
        }

        long nextLong() throws IOException {
            int c = read();
            while (c != '-' && (c < '0' || c > '9')) {
                if (c == -1) throw new EOFException();
                c = read();
            }
            boolean neg = c == '-';
            if (neg) c = read();
            long r = 0;
            while (c >= '0' && c <= '9') { r = r * 10 + (c - '0'); c = read(); }
            return neg ? -r : r;
        }

        int nextInt() throws IOException { return (int) nextLong(); }

        String next() throws IOException {
            int c = read();
            while (c != -1 && c <= ' ') c = read();
            if (c == -1) throw new EOFException();
            StringBuilder sb = new StringBuilder();
            while (c > ' ') { sb.append((char) c); c = read(); }
            return sb.toString();
        }
    }
}
```

`read()` refills the buffer whenever it runs out. `nextLong()` skips every byte that is not a digit or a minus sign, then accumulates digits. Run on `3 10 20 30` it prints 60; on 3, 10, 20, −30 one per line it prints 0.

:::pitfall
Three input bugs cost full problems: forgetting `out.flush()`, calling `nextLine()` in the middle of a line (it drops the rest of that line), and leaving `throws IOException` off `main` (a compile error).
:::

## Linked lists {#sec-1-lists}

### Nodes and references

:::definition{#def-1-list} Singly linked list
A [[linked list]] is a chain of nodes in which each node holds a value and a reference `next` to the following node; the last node's `next` is `null`. The list is known only through a reference to its first node, the *head*.
:::

A linked list gives up O(1) access by index (reaching node *i* takes *i* steps) in exchange for O(1) insertion and deletion at any node you already hold. Contest code rarely builds its own lists, but LeetCode list problems and interviews test the pointer manipulation directly, and the same moves reappear on trees.

The one skill these problems test is changing references without losing part of the list. Draw the boxes, and before each assignment ask: after this line, can I still reach every node I need? @lst-1-lists is the handbook's tested template, with LeetCode's node class and the four moves this section proves correct. Every method runs in O(*n*) time and O(1) extra memory.

```java {#lst-1-lists} Linked list moves: reverse, middle, cycle check, merge
static final class ListNode {                       // LeetCode's list node
    int val;
    ListNode next;

    ListNode(int val) { this.val = val; }
}

static ListNode reverse(ListNode head) {
    ListNode prev = null;
    while (head != null) {
        ListNode nxt = head.next;                        // save, point back, move on
        head.next = prev;
        prev = head;
        head = nxt;
    }
    return prev;
}

static ListNode middle(ListNode head) {                  // second middle for even length
    ListNode slow = head, fast = head;
    while (fast != null && fast.next != null) {
        slow = slow.next;
        fast = fast.next.next;
    }
    return slow;
}

static boolean hasCycle(ListNode head) {                 // Floyd: fast catches slow inside a cycle
    ListNode slow = head, fast = head;
    while (fast != null && fast.next != null) {
        slow = slow.next;
        fast = fast.next.next;
        if (slow == fast) return true;
    }
    return false;
}

static ListNode mergeSorted(ListNode a, ListNode b) {
    ListNode dummy = new ListNode(0), tail = dummy;      // a dummy head removes special cases
    while (a != null && b != null) {
        if (a.val <= b.val) {
            tail.next = a;
            a = a.next;
        } else {
            tail.next = b;
            b = b.next;
        }
        tail = tail.next;
    }
    tail.next = (a != null) ? a : b;
    return dummy.next;
}
```

### Reversing a list

`reverse` (lines 8–17) walks the list once and turns each `next` reference around. Three references are alive at every moment: `prev`, the node before; `head`, the node being processed; and `nxt`, saved so that the rest of the list is not lost.

:::lemma{#lem-1-reverse} Reversal invariant
Let the original list be *v*₁ → *v*₂ → ⋯ → *v*ₙ. At the start of each iteration, after *k* iterations, `prev` is the head of the list *v*ₖ → *v*ₖ₋₁ → ⋯ → *v*₁ → `null`, and `head` is the head of the untouched list *v*ₖ₊₁ → ⋯ → *v*ₙ → `null`.
:::

:::proof
Before the first iteration (*k* = 0), `prev` is the empty list and `head` is the whole list. In an iteration, `nxt` saves *v*ₖ₊₂ before the only reference to it, `head.next`, is overwritten. Then *v*ₖ₊₁.`next` is set to `prev`, which makes *v*ₖ₊₁ → *v*ₖ → ⋯ → *v*₁ the new reversed part, and `prev` and `head` move to *v*ₖ₊₁ and *v*ₖ₊₂. The loop ends when `head` is `null`, that is when *k* = *n*, and `prev` is then the head of the fully reversed list.
:::

The order of the four lines in the loop matters. Overwriting `head.next` before saving it loses the rest of the list, which is the classic bug.

### Fast and slow pointers: the middle

`middle` (lines 19–26) moves `slow` one node and `fast` two nodes per iteration. When `fast` runs off the end, `slow` has covered half the distance.

:::claim{#thm-1-middle} The slow pointer stops at index ⌊n/2⌋
For a list of *n* ≥ 1 nodes indexed 0..*n* − 1, `middle` returns node ⌊*n*/2⌋: the middle node for odd *n*, the second of the two middle nodes for even *n*.
:::

:::proof
After *t* iterations, `slow` is at index *t* and `fast` at index 2*t* (with index *n* meaning `null`). The loop continues while indices 2*t* and 2*t* + 1 both exist, that is while 2*t* + 1 ≤ *n* − 1. It therefore stops at the first *t* with 2*t* ≥ *n* − 1, which is *t* = ⌈(*n* − 1)/2⌉ = ⌊*n*/2⌋. For *n* = 5 it returns index 2; for *n* = 4, index 2.
:::

The condition `fast != null && fast.next != null` must be written in that order: Java evaluates `&&` from left to right and skips the second test when the first is false, so `fast.next` is never read on a `null`.

### Floyd's cycle detection

A list has a *cycle* if some node's `next` points back to an earlier node, so following `next` never reaches `null`. Remembering every visited node in a `HashSet` detects this with O(*n*) memory. Floyd's method, `hasCycle` (lines 28–36), uses the same two pointers and O(1) memory: if there is a cycle, the fast pointer enters it and eventually laps the slow one.

:::theorem{#thm-1-floyd} Floyd's method is correct and fast
If the list has no cycle, `hasCycle` returns `false`. If the list has a tail of μ nodes followed by a cycle of λ nodes, the pointers meet after exactly *t* steps, where *t* is the smallest multiple of λ that is at least max(μ, 1). In particular *t* ≤ μ + λ.
:::

:::proof
Number the nodes by their distance from the head: node *i* is reached after *i* steps. After *t* steps `slow` is at node *t* and `fast` at node 2*t*. *No cycle*: `fast` is always strictly ahead of `slow` (2*t* > *t* for *t* ≥ 1) on a path that ends, so the two never coincide, and the loop stops when `fast` reaches the end. *Cycle*: the nodes from index μ onwards repeat with period λ, so for positions *x*, *y* ≥ μ the nodes are the same exactly when *x* ≡ *y* (mod λ). The pointers coincide after *t* ≥ 1 steps exactly when *t* ≥ μ (so that `slow` is on the cycle) and 2*t* ≡ *t* (mod λ), that is when λ divides *t*. The smallest such *t* is the smallest multiple of λ that is ≥ max(μ, 1). It is at most μ + λ, because among the λ consecutive integers max(μ, 1), …, max(μ, 1) + λ − 1 one is a multiple of λ, and max(μ, 1) + λ − 1 ≤ μ + λ.
:::

The formula was checked by running the method on every list with 0 ≤ μ ≤ 12 and 1 ≤ λ ≤ 12: the meeting step always equalled it.

### Merging with a dummy head

`mergeSorted` (lines 38–52) builds a new chain by repeatedly attaching the smaller front node of the two lists. The first attachment would be a special case, because there is no tail yet, so the method starts from a *dummy* node whose `next` becomes the answer.

The invariant is that `dummy.next` … `tail` is the sorted merge of the nodes already taken, and every node still in `a` or `b` is at least `tail.val`. Taking the smaller front node keeps both halves true. When one list runs out, the other is already sorted and not smaller than `tail`, so it is attached whole. Each node is attached once: O(*n* + *m*) time and O(1) extra memory. Using `<=` takes from `a` on ties, which keeps the merge stable.

All four methods were tested on 20,000 random lists of up to 10 nodes against array-based versions (reverse an array, take index ⌊*n*/2⌋, add a random back edge, sort the concatenation).

:::pitfall
Before every `fast.next.next` check `fast != null && fast.next != null`. And reach for a dummy head whenever the first node of the result might change; it removes the special case for an empty result.
:::

## Recursion and the call stack {#sec-1-recursion}

### Frames

:::definition{#def-1-callstack} Call stack
Each method call that has started and not yet returned owns a *frame* holding its parameters, local variables and the place to return to. The frames form the [[call stack]]: a call pushes a frame and a return pops it. The *depth* of a recursion is the largest number of its frames alive at once.
:::

A Java thread's stack has a fixed size, set when the thread starts. When a recursion goes deeper than the stack allows, the JVM throws `StackOverflowError` and the program dies. The limit depends on the frame size and the JVM. On this book's machine, with default settings, a recursion with one `int` parameter succeeded at depth 10⁴ and failed at 2 · 10⁴; a parameterless method reached about 20,000 frames. Plan for **trouble somewhere between 10⁴ and 10⁵**.

Trees in the Infosys paper arrive as **parent arrays**: `parent[v]` is the parent of node *v*, and the root has parent −1. The depth of a node, its number of edges to the root, has a one-line recursive definition and an equally short loop.

```java {#lst-1-depth} The depth of one node: recursive and iterative
static int depthRec(int[] parent, int v) {
    return parent[v] == -1 ? 0 : 1 + depthRec(parent, parent[v]);   // one frame per ancestor
}

static int depthIter(int[] parent, int v) {
    int d = 0;
    for (int u = v; parent[u] != -1; u = parent[u]) d++;           // one frame in total
    return d;
}
```

Both methods take time proportional to the depth. The recursive one also needs one frame per ancestor. On a chain of 10⁵ nodes, run for this book, `depthIter` returned 99999 and `depthRec` threw `StackOverflowError`. Random trees are shallow, so a recursive solution can pass every small test and crash on the one test that is a long chain. That is how the official sample paper's trees, with up to 10⁵ nodes, catch recursive solutions.

### Rewriting recursion as a loop

There are two standard rewrites.

1. **The recursive call is the last thing that happens** (or can be made so with an accumulator, as `d` in `depthIter`). Then the method is a loop in disguise: replace the call by updating the variables and going round again.
2. **Work remains after the call returns.** Then keep the pending calls on an explicit `ArrayDeque` used as a stack. The deque lives on the heap, which is limited only by the memory limit, not by the thread stack.

@lst-1-alldepths computes the depth of every node, remembering the depths already known. In the recursive version the assignment to `depth[v]` must wait until the depth of the parent is known, so it is work that remains after the call. The iterative version walks up from *v*, pushing the nodes whose calls would be pending, until it reaches a node of known depth or the root; then it pops them, deepest call first, and does the remaining work in the order the calls would return.

```java {#lst-1-alldepths} The depth of every node: recursion with memory, and an explicit stack
static void allDepthsRec(int[] parent, int[] depth, int v) {        // depth[] starts filled with -1
    if (depth[v] != -1) return;
    if (parent[v] == -1) { depth[v] = 0; return; }
    allDepthsRec(parent, depth, parent[v]);
    depth[v] = depth[parent[v]] + 1;                                // runs after the call returns
}

static int[] allDepthsIter(int[] parent) {
    int n = parent.length;
    int[] depth = new int[n];
    Arrays.fill(depth, -1);
    ArrayDeque<Integer> pending = new ArrayDeque<>();
    for (int v = 0; v < n; v++) {
        int u = v;
        while (depth[u] == -1 && parent[u] != -1) {                 // the calls that would be made
            pending.push(u);
            u = parent[u];
        }
        if (depth[u] == -1) depth[u] = 0;                           // u is the root
        while (!pending.isEmpty()) {                                // the returns, deepest call first
            int w = pending.pop();
            depth[w] = depth[parent[w]] + 1;
        }
    }
    return depth;
}
```

Every node is pushed at most once over the whole run, because its depth is known from the moment it is popped, so `allDepthsIter` costs O(*n*) time and O(*n*) memory whatever the shape of the tree. For `parent` = [−1, 0, 1, 1, 3, 0] it returns [0, 1, 2, 2, 3, 1]. Both versions were compared on 5,000 random trees of up to 30 nodes, a quarter of them chains. Chapter 15 and Chapter 18 use the same idea for depth-first search and tree traversal without recursion.

### The big-stack thread

When rewriting would take too long in an exam, run the whole solution on a new thread with a large stack. The fourth argument of the `Thread` constructor is the requested stack size in bytes.

```java {#lst-1-bigstack} Deep recursion on a thread with a 128 MB stack (fallback)
import java.io.*;
import java.util.*;

public class Main {
    public static void main(String[] args) {
        // Run the real work on a thread with a 128 MB stack so deep recursion doesn't crash.
        Thread t = new Thread(null, () -> {
            try { solve(); } catch (IOException e) { throw new UncheckedIOException(e); }
        }, "solver", 1 << 27);
        t.start();
    }

    static void solve() throws IOException {
        int n = 1_000_000;                                  // a path of 1e6 nodes
        System.out.println(depth(n));
    }

    static int depth(int k) { return k == 0 ? 0 : 1 + depth(k - 1); }
}
```

This program recurses to depth 10⁶ and prints 1000000. The JVM treats the stack size as a request, so prefer the iterative rewrite when you have the time, and keep this as the fallback.

### Java 8 compatibility and the traps table

You do not know which Java version the exam's compiler uses, so write Java 8: no `var`, no records, no `List.of` or `Map.of`, no switch expressions, no text blocks. Every listing in this book compiles with `javac --release 8`. @tbl-1-traps collects the traps from the whole chapter.

Table: {#tbl-1-traps} Java traps that cost marks
| Trap | What happens | Fix |
|---|---|---|
| `int` products and sums | silent overflow, wrong answers (10⁹ × 10⁹) | `long` by default; cast before multiplying: `(long) a * b` |
| `%` on negative numbers | `-3 % 5 == -3` | `Math.floorMod(x, m)` |
| comparator `(x, y) -> x[0] - y[0]` | overflows for large values | `Integer.compare(x[0], y[0])` |
| `==` on `Integer` / `Long` objects | `false` for values outside −128..127 | `.equals()`, or unbox to `int` |
| recursive DFS on 10⁵ nodes | `StackOverflowError` | an explicit stack, or the big-stack thread |
| `Stack` / `Vector` | synchronised, so slower | `ArrayDeque` |
| `new long[100000][100000]` | out of memory | estimate first: cells × 8 bytes |
| newer syntax (`var`, records, `List.of`) | compile error on an old JDK | write Java 8 style |
| `s += c` in a loop | quadratic time | `StringBuilder` |
| `System.out.println` 10⁶ times | about 2 s of output alone | one `PrintWriter`, one `flush()` |

## Summary

- The Infosys paper has three (sometimes four) problems worth 20, 30 and 50 marks, scored by test cases passed. Input comes one value per line; some questions give a function stub whose signature you must keep.
- *f*(*n*) = O(*g*(*n*)) means *f* ≤ *c* · *g* from some *n*₀ on. Plan with about 10⁸–3 · 10⁸ basic steps per second, and turn the largest *n* into a target complexity before coding.
- `int` arithmetic wraps modulo 2³² without warning. Use `long` for sums and products, cast before multiplying, and use `Math.floorMod` for remainders.
- `==` compares references: it fails on `Integer` values outside −128..127 and on strings built at run time. Use `equals`.
- Choose the collection by its question: `HashMap` for counts, `ArrayDeque` for last-in or first-in, `PriorityQueue` for the smallest so far, `TreeMap` for the nearest key. A size-*k* heap finds the *k* largest in O(*n* log *k*).
- Strings are immutable, so `+=` in a loop is quadratic; use `StringBuilder`. Count letters in an `int[26]`.
- `FastScanner` reads tokens regardless of line layout and is about five times faster than `Scanner`; print through one `PrintWriter` and flush it.
- Linked-list code is correct when it never loses a reference: save `next` before overwriting it, check `fast` and `fast.next` before stepping twice, and use a dummy head.
- Recursion deeper than about 10⁴–10⁵ frames crashes; rewrite it with a loop or an explicit stack, or run on a big-stack thread.

## Review questions

1. Show that *n*² + 100*n* = O(*n*²) by giving explicit constants *c* and *n*₀. Is *n*² + 100*n* = O(*n*)? Prove your answer.
2. A solution sorts *n* = 2 · 10⁵ numbers and then, for each number, does a binary search. Estimate the number of basic steps and say whether it fits in one second.
3. What does `int x = 50_000 * 50_000;` store, and why? Write the line correctly for a `long` result.
4. `Integer a = 100, b = 100, c = 1000, d = 1000;` What are `a == b`, `c == d` and `c.equals(d)`, and why does the first differ from the second?
5. In @lst-1-twosum, what goes wrong if `seen.put(nums[j], j)` is moved before the look-up? Give a failing input.
6. Why does @thm-1-calendar need the accepted bookings to be pairwise disjoint? Give three bookings, two of which overlap, for which checking only the floor and ceiling neighbours misses an overlap with the request [5, 6).
7. You must report the 10 largest of 10⁶ numbers arriving one at a time. Compare sorting with a size-10 heap in time and memory.
8. Why is `FastScanner` indifferent to whether the input has one value per line or all values on one line, while the `readLine` fragment of @sec-1-io is not?
9. Using @thm-1-floyd, after how many steps do slow and fast meet on a list with μ = 7 and λ = 3? With μ = 0 and λ = 4?
10. A recursive function on a tree with 10⁵ nodes works on random trees but crashes on some tests. What is the likely shape of the failing trees, and what are two ways to fix the program?

:::answers
1. Take *c* = 2 and *n*₀ = 100: for *n* ≥ 100, 100*n* ≤ *n*², so *n*² + 100*n* ≤ 2*n*². It is not O(*n*): if *n*² + 100*n* ≤ *c* · *n* for all large *n*, then *n* + 100 ≤ *c* for all large *n*, which fails for *n* > *c*.
2. Sorting costs about *n* log₂ *n* ≈ 2 · 10⁵ × 18 = 3.6 · 10⁶ comparisons, and 2 · 10⁵ binary searches of about 18 steps each cost another 3.6 · 10⁶. About 7 · 10⁶ steps in total, far below 10⁸: it fits easily.
3. The true product 2.5 · 10⁹ exceeds 2³¹ − 1 ≈ 2.147 · 10⁹, so the result wraps: it stores 2,500,000,000 − 2³² = −1,794,967,296. Write `long x = 50_000L * 50_000;` (or `(long) a * b` for variables), so the multiplication happens in `long`.
4. `a == b` is `true` because 100 lies in the cached range −128..127, so both names refer to the same `Integer` object. `c == d` is `false` because 1000 is outside the cache and boxing creates two objects. `c.equals(d)` is `true` because it compares values.
5. An element can then pair with itself. For *nums* = [3, 5] and *target* = 6, index 0 stores 3 and immediately finds 6 − 3 = 3 at index 0, returning [0, 0], which uses one element twice.
6. The proof's first case uses disjointness to conclude that a booking starting before the floor ends before the floor starts. Without it, take bookings [0, 10), [2, 3) and [7, 8) and the request [5, 6). The floor of 5 is the booking starting at 2, which ends at 3 ≤ 5; the ceiling of 5 is the booking starting at 7, which starts at 7 ≥ 6. Neither overlaps, yet [0, 10) does. (My Calendar never stores overlapping bookings, so the case cannot arise there.)
7. Sorting needs all 10⁶ numbers in memory and about 10⁶ × 20 = 2 · 10⁷ comparisons. The size-10 heap keeps 11 numbers at most and costs about 10⁶ × log₂ 11 ≈ 3.5 · 10⁶ comparisons, and it can process the numbers as they arrive.
8. `FastScanner.next()` keeps reading lines until the current tokenizer has a word, so line breaks are just separators like spaces, and blank lines are skipped. The `readLine` fragment assumes each line holds exactly one value: two values on one line make `parseInt` fail, and a blank line makes it parse an empty string.
9. For μ = 7, λ = 3 the meeting step is the smallest multiple of 3 that is ≥ 7, which is 9. For μ = 0, λ = 4 it is the smallest multiple of 4 that is ≥ 1, which is 4.
10. The failing trees are long chains (or nearly so), where the recursion depth approaches 10⁵ and exceeds the thread stack. Fix it by replacing the recursion with an explicit `ArrayDeque` stack (or a parent-array order without recursion, Chapter 18), or by running the solution on a thread with a large stack as in @lst-1-bigstack.
:::
