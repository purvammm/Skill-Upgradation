A graph is the most general way to say "these things are connected". Cities and roads, cells of a grid and the moves between them, courses and their prerequisites, people and friendships: each is a set of objects with pairwise links, and many questions about them are the same few questions in disguise. How few steps from here to there? Which objects are connected at all? In what order can tasks be done if some must precede others?

This chapter answers those questions with three traversals. Breadth-first search explores in rings of increasing distance and so finds shortest paths when every step costs the same. Depth-first search, written with an explicit stack so that Java's call stack never overflows, finds connected components and two-colourings. Kahn's algorithm peels a directed graph from its sources and either produces an order in which every edge points forward or proves that a cycle exists. A small change to breadth-first search, a deque instead of a queue, then handles edges that cost 0 or 1. Every algorithm here runs in time proportional to the size of the graph, and the last section explains why, and what single line of code destroys that bound.

## Graphs and how to store them {#sec-15-repr}

:::definition{#def-15-graph} Graph
A [[graph]] *G* = (*V*, *E*) is a set *V* of **vertices** (also called nodes) and a set *E* of **edges**, each joining two vertices. In an **undirected** graph an edge {*u*, *v*} can be used both ways; in a **directed** graph an edge (*u*, *v*) goes from *u* to *v* only. We write *n* = |*V*| and *m* = |*E*|, and usually number the vertices 0..*n* − 1.
:::

Some words recur constantly. Two vertices joined by an edge are **neighbours**. The **degree** deg(*v*) of a vertex in an undirected graph is its number of incident edges; in a directed graph, the **indegree** counts edges coming in and the **outdegree** edges going out. A **path** is a sequence of vertices *v*₀, *v*₁, …, *v*ₖ in which consecutive vertices are joined by an edge; its **length** is the number of edges, *k*. A **cycle** is a path of length at least 1 that returns to its start without repeating an edge (in undirected graphs, of length at least 3, unless there are self-loops or parallel edges).

:::definition{#def-15-component} Connected component
In an undirected graph, *u* and *v* are **connected** if some path joins them. Being connected is an equivalence relation, and its classes are the [[connected components|connected component]]: maximal sets of vertices in which every two are connected.
:::

One counting fact underlies every running time in this chapter.

:::lemma{#lem-15-handshake} Handshake lemma
In an undirected graph, the degrees add up to twice the number of edges: Σ deg(*v*) = 2*m*. In a directed graph, the indegrees add up to *m*, and so do the outdegrees.
:::

:::proof
Count pairs (vertex, incident edge). Each undirected edge {*u*, *v*} contributes exactly two such pairs, one at *u* and one at *v*, so the number of pairs is 2*m*. Counting the same pairs vertex by vertex gives Σ deg(*v*). A directed edge (*u*, *v*) contributes one to the outdegree of *u* and one to the indegree of *v*.
:::

### Adjacency lists

An adjacency matrix, an *n* × *n* table of booleans, is simple but needs *n*² entries: 10¹⁰ for *n* = 10⁵, far beyond any memory limit. Contest graphs are stored as [[adjacency lists|adjacency list]]: for each vertex, the list of its neighbours. The handbook's builder takes an edge list, the form in which LeetCode and most exam statements give graphs.

```java {#lst-15-build} Adjacency lists from an edge list
@SuppressWarnings("unchecked")
static List<Integer>[] buildGraph(int n, int[][] edges, boolean directed) {
    List<Integer>[] g = new List[n];
    for (int i = 0; i < n; i++) g[i] = new ArrayList<>();
    for (int[] e : edges) {
        g[e[0]].add(e[1]);
        if (!directed) g[e[1]].add(e[0]);
    }
    return g;
}
```

:::java
Java does not allow `new List<Integer>[n]`, because arrays of generic types cannot be created. `new List[n]` creates an array of raw lists, and assigning it to `List<Integer>[]` gives an "unchecked" warning, which `@SuppressWarnings("unchecked")` silences. The code is safe as long as you only put `Integer`s in the lists.
:::

Each list entry is a reference to an `Integer` object. Java caches the objects for −128..127, but larger vertex numbers each get their own 16-byte object, plus a 4-byte slot in the list's array and the spare capacity that `ArrayList` keeps for growth. Measured on the machine used for this book (OpenJDK 25, *n* = 10⁵ vertices and *m* = 10⁶ directed edges), the lists took about 26 MB, roughly **26 bytes per edge**. That is fine for 10⁶ edges and uncomfortable for 10⁷.

### Three int arrays

When memory or speed matters, store the edges in plain `int` arrays. Edge number *e* goes to `to[e]`; the edges leaving *u* form a linked list that starts at `head[u]` and continues through `nxt[e]` until −1. This layout, sometimes called a *forward star*, is what the sample-paper walkthroughs use for trees.

```java {#lst-15-star} Adjacency in three int arrays, and BFS over them
// Edge e goes to to[e]; the edges leaving u form a linked list head[u], nxt[head[u]], ..., -1.
static int[] head, nxt, to;
static int edgeCount;

static void initGraph(int n, int maxEdges) {
    head = new int[n];
    Arrays.fill(head, -1);
    nxt = new int[maxEdges];
    to = new int[maxEdges];
    edgeCount = 0;
}

static void addEdge(int u, int v) {             // directed u -> v; add both ways if undirected
    to[edgeCount] = v;
    nxt[edgeCount] = head[u];                   // the new edge goes in front of u's list
    head[u] = edgeCount++;
}

static int[] bfsArrays(int n, int src) {        // the same BFS as Listing 15.3
    int[] dist = new int[n], queue = new int[n];
    Arrays.fill(dist, -1);
    int qh = 0, qt = 0;
    dist[src] = 0;
    queue[qt++] = src;
    while (qh < qt) {
        int u = queue[qh++];
        for (int e = head[u]; e != -1; e = nxt[e]) {
            int v = to[e];
            if (dist[v] != -1) continue;
            dist[v] = dist[u] + 1;
            queue[qt++] = v;
        }
    }
    return dist;
}
```

The same graph took about 8.7 MB this way: 8 bytes per edge for `nxt` and `to`, and 4 bytes per vertex for `head`. Remember that an undirected edge is stored twice, so `maxEdges` must be 2*m*. The neighbours come out in reverse order of insertion, which never matters for the algorithms in this chapter.

### Grids are graphs

A grid of *R* rows and *C* columns is a graph whose vertices are the cells and whose edges join cells that share a side. Nothing needs to be stored: the neighbours of (*r*, *c*) are found with two **direction arrays**.

```java {.fragment}
int[] DR = {1, -1, 0, 0}, DC = {0, 0, 1, -1};      // down, up, right, left
int rows = 3, cols = 4, r = 0, c = 2;
for (int d = 0; d < 4; d++) {
    int nr = r + DR[d], nc = c + DC[d];
    if (nr < 0 || nr >= rows || nc < 0 || nc >= cols) continue;   // bounds first
    int id = nr * cols + nc;                       // a single int id when you need one
}
```

For eight directions (diagonals too), use the eight pairs (*dr*, *dc*) with *dr*, *dc* ∈ {−1, 0, 1}, not both zero. Check the bounds before you read the cell; reading first throws `ArrayIndexOutOfBoundsException` at the border.

## Breadth-first search {#sec-15-bfs}

:::definition{#def-15-dist} Distance
In a graph where every edge has length 1, the **distance** δ(*s*, *v*) from *s* to *v* is the fewest edges on a path from *s* to *v*, or ∞ if there is no path.
:::

[[Breadth-first search]] (BFS) visits the vertices in order of distance from the source: first *s*, then all its neighbours, then everything two steps away, and so on. A first-in first-out queue produces exactly this order. When a vertex is discovered for the first time, it gets a distance one more than the vertex that discovered it and joins the back of the queue.

```java {#lst-15-bfs} Breadth-first search: fewest edges from one source
// Fewest edges from src to every node (-1 = unreachable)
static int[] bfs(List<Integer>[] g, int src) {
    int[] dist = new int[g.length];
    Arrays.fill(dist, -1);
    ArrayDeque<Integer> q = new ArrayDeque<>();
    dist[src] = 0;
    q.add(src);
    while (!q.isEmpty()) {
        int u = q.poll();
        for (int v : g[u]) {
            if (dist[v] != -1) continue;       // mark when you PUSH, not when you pop
            dist[v] = dist[u] + 1;
            q.add(v);
        }
    }
    return dist;
}
```

The `dist` array plays two roles: it stores the answer, and −1 means "not yet discovered", so no separate `visited` array is needed.

Take the undirected edges 0–1, 0–2, 1–3, 2–3, 3–4 and start at 0.

```

When 2 is popped, its neighbour 3 already has a distance, set when 1 was popped, so it is not queued again.
:::

### Why BFS finds shortest paths

:::lemma{#lem-15-queue} The queue holds at most two consecutive distances
At every moment, if the queue holds *v*₁, …, *v*ₖ from front to back, then dist[*v*₁] ≤ dist[*v*₂] ≤ ⋯ ≤ dist[*v*ₖ] ≤ dist[*v*₁] + 1. Consequently vertices leave the queue in non-decreasing order of dist.
:::

:::proof
Initially the queue holds only *s*. Suppose the statement holds and *v*₁ is popped with dist[*v*₁] = *d*. Every vertex then pushed gets *d* + 1, which is at least every value in the queue (all are *d* or *d* + 1) and at most (new front) + 1, because the new front has value at least *d*. So the sequence stays sorted with a spread of at most 1. Since the queue is always sorted and pops come from the front, the popped values never decrease.
:::

:::theorem{#thm-15-bfs} BFS computes distances
After @lst-15-bfs finishes, dist[*v*] = δ(*s*, *v*) for every *v* reachable from *s*, and dist[*v*] = −1 for every other vertex.
:::

:::proof
First, dist[*v*] ≥ δ(*s*, *v*) whenever dist[*v*] is set. It holds for *s*; when *v* gets dist[*u*] + 1 through the edge *u*–*v*, a path to *u* with dist[*u*] edges plus that edge is a path to *v* with dist[*u*] + 1 edges. The same argument shows that only reachable vertices are ever discovered.

Now suppose some reachable *v* ends with a wrong value, and choose one with the smallest δ(*s*, *v*) = *k*. Then *k* ≥ 1, since dist[*s*] = 0 is right. Let *u* be the vertex before *v* on a shortest path, so δ(*s*, *u*) = *k* − 1 and, by the choice of *v*, dist[*u*] = *k* − 1. Every discovered vertex is pushed and later popped, so *u* is popped at some point. At that moment either *v* is undiscovered, and it receives dist[*u*] + 1 = *k*; or *v* was discovered earlier by some *w* popped no later than *u*, and by @lem-15-queue dist[*w*] ≤ dist[*u*], so dist[*v*] = dist[*w*] + 1 ≤ *k*. Combined with dist[*v*] ≥ *k*, either way dist[*v*] = *k*, a contradiction.
:::

Each vertex is pushed at most once, because it is marked when pushed. Each adjacency list is scanned once, when its vertex is popped. By @lem-15-handshake the total scanning is 2*m* steps (undirected) or *m* (directed), so BFS runs in O(*n* + *m*) time and O(*n*) extra memory.

### Many sources at once

Sometimes the question is the distance to the **nearest** of several sources: the nearest exit, the nearest hospital, the first minute at which a spreading process reaches each cell.

:::theorem{#thm-15-multi} Multi-source BFS
If all sources are pushed with distance 0 before the loop starts, the loop computes, for every vertex, the distance to the nearest source.
:::

:::proof
Add an imaginary vertex *s*\* joined to every source. A BFS from *s*\* would pop *s*\* first and push all sources with distance 1; from then on it is the same loop, with every distance one larger. By @thm-15-bfs it computes δ(*s*\*, *v*) = 1 + min over sources *t* of δ(*t*, *v*), because every path from *s*\* enters the original graph through some source. Subtracting the 1 gives the claim.
:::

On a grid the template becomes the following, again verbatim from the handbook.

```java {#lst-15-grid} Grid BFS from several sources at once
static final int[] DR = {1, -1, 0, 0}, DC = {0, 0, 1, -1};

// Grid BFS from several sources at once ('#' = wall): steps to the nearest source, -1 if none
static int[][] gridBfs(char[][] grid, int[][] sources) {
    int rows = grid.length, cols = grid[0].length;
    int[][] dist = new int[rows][cols];
    for (int[] row : dist) Arrays.fill(row, -1);
    ArrayDeque<int[]> q = new ArrayDeque<>();
    for (int[] s : sources) {
        dist[s[0]][s[1]] = 0;
        q.add(s);
    }
    while (!q.isEmpty()) {
        int[] cur = q.poll();
        for (int d = 0; d < 4; d++) {
            int r = cur[0] + DR[d], c = cur[1] + DC[d];
            if (r < 0 || r >= rows || c < 0 || c >= cols) continue;
            if (grid[r][c] == '#' || dist[r][c] != -1) continue;
            dist[r][c] = dist[cur[0]][cur[1]] + 1;
            q.add(new int[]{r, c});
        }
    }
    return dist;
}
```

## Depth-first search without recursion {#sec-15-dfs}

[[Depth-first search]] (DFS) follows one path as far as it can before backing up. Written recursively it is three lines long: mark *u*, then for each unmarked neighbour, recurse. In Java that recursion is a trap. Each call uses a stack frame, and the default thread stack holds only some thousands to tens of thousands of frames. A path graph with 10⁵ vertices, which is a perfectly legal tree, crashes a recursive DFS with `StackOverflowError`.

:::infosys
The official sample paper gives trees as parent arrays with up to 10⁵ nodes, and its Easy problem needs a traversal of the whole tree. The plan's analysis of the paper names the trap directly: a recursive DFS on a chain overflows the stack in Java. Every traversal in this chapter is therefore written with an explicit `ArrayDeque`, whose size is limited only by the heap.
:::

For connected components the visiting order is irrelevant; what matters is that every vertex is visited exactly once. Replacing the BFS queue with a stack gives the handbook's component labelling.

```java {#lst-15-components} Connected components with an explicit stack
// Iterative DFS (no stack overflow): comp[v] = component number. Returns how many components.
static int components(List<Integer>[] g, int[] comp) {
    Arrays.fill(comp, -1);
    int count = 0;
    ArrayDeque<Integer> stack = new ArrayDeque<>();
    for (int s = 0; s < g.length; s++) {
        if (comp[s] != -1) continue;
        comp[s] = count;
        stack.push(s);
        while (!stack.isEmpty()) {
            int u = stack.pop();
            for (int v : g[u]) {
                if (comp[v] != -1) continue;
                comp[v] = count;
                stack.push(v);
            }
        }
        count++;
    }
    return count;
}
```

:::theorem{#thm-15-components} The labelling is the component structure
After @lst-15-components, comp[*u*] = comp[*v*] if and only if *u* and *v* are connected, and the return value is the number of components.
:::

:::proof
Consider the round started at *s*. Every vertex labelled in it was pushed from a labelled neighbour, so by induction it is connected to *s*. Conversely, let *v* be connected to *s* and suppose *v* is not labelled in this round. On a path from *s* to *v*, take the first vertex *w* that is not labelled in this round, and its predecessor *x* on the path, which is. Being labelled, *x* was pushed and therefore popped before the round ended, and at that pop its neighbour *w* was examined: either *w* was unlabelled and got labelled now, or it already had a label. That label is from this round, because a vertex labelled in an earlier round would have dragged its whole component, including *s*, into that round. Either way *w* is labelled in this round, a contradiction. So each round labels exactly the component of its start vertex, and a new round starts once per component.
:::

The cost is O(*n* + *m*) for the same reason as BFS. Note that this stack-based DFS does not visit vertices in the same order as the recursive one, and does not know when a vertex is "finished". For components and colourings that does not matter. For topological order, use Kahn's algorithm of @sec-15-topo rather than finishing times.

### Two colours: bipartite graphs

:::definition{#def-15-bipartite} Bipartite graph
An undirected graph is [[bipartite|bipartite graph]] if its vertices can be coloured with two colours so that every edge joins vertices of different colours.
:::

Bipartite graphs model "two kinds of things, links only across": jobs and workers, two teams that must be separated. Whether a graph is bipartite has a clean characterisation.

:::lemma{#lem-15-oddwalk} Odd closed walks contain odd cycles
If a graph has a closed walk (a path that may repeat vertices, ending where it starts) of odd length, it has a cycle of odd length.
:::

:::proof
By strong induction on the length *L* of the walk. If no vertex repeats except the start and end, the walk is itself a cycle of odd length. Otherwise some vertex *x* occurs twice at different positions inside it. Cutting the walk at those two occurrences splits it into two closed walks whose lengths add up to *L*. Since *L* is odd, one of them has odd length, and it is shorter than *L*, so by induction it contains an odd cycle.
:::

:::theorem{#thm-15-odd} The odd-cycle theorem
An undirected graph is bipartite if and only if it has no cycle of odd length.
:::

:::proof
If the graph is bipartite, colours alternate along every cycle, so a cycle returns to its starting colour only after an even number of steps. Conversely, suppose there is no odd cycle, and treat each component separately. Pick a root *r*, run BFS, and colour each vertex by the parity of its distance from *r*. If some edge *u*–*v* joined two vertices of the same parity, then a shortest path from *r* to *u*, the edge, and a shortest path from *v* back to *r* would form a closed walk of length δ(*r*, *u*) + δ(*r*, *v*) + 1, which is odd. By @lem-15-oddwalk the graph would contain an odd cycle, a contradiction. So the parity colouring is a valid two-colouring.
:::

The proof is also the algorithm: BFS (or the stack-based DFS) from every uncoloured vertex, give each newly discovered vertex the opposite colour of the vertex that found it, and report "not bipartite" as soon as an edge joins two vertices of the same colour. On the 4-cycle 0–1–2–3–0 the colours alternate 0, 1, 0, 1 and every edge is fine. On the 5-cycle 0–1–2–3–4–0, BFS from 0 gives distances [0, 1, 2, 2, 1], so vertices 2 and 3 both get colour 0 and the edge 2–3 is a conflict, as the theorem predicts for an odd cycle. This is the whole idea of the bonus problem LeetCode 785 (Is Graph Bipartite?); remember that its graph may be disconnected.

## Directed acyclic graphs and topological order {#sec-15-topo}

:::definition{#def-15-dag} DAG and topological order
A [[directed acyclic graph]] (DAG) is a directed graph with no directed cycle. A [[topological order]] of a directed graph is an ordering of all its vertices in which every edge (*u*, *v*) has *u* before *v*.
:::

If a graph has a cycle, no topological order exists: the vertices of the cycle would each have to come before the next one, all the way round. The converse is the content of Kahn's algorithm, and it rests on one small fact.

:::lemma{#lem-15-source} Every DAG has a source
Every non-empty DAG has a vertex with indegree 0.
:::

:::proof
Start anywhere and repeatedly step backwards along an incoming edge. If every vertex had an incoming edge, this walk could continue for ever; with only *n* vertices, some vertex would be visited twice, and the part of the walk between the two visits, read forwards, would be a directed cycle.
:::

**Kahn's algorithm** removes a source, which may create new sources, and repeats. In code, an indegree counter replaces the actual removal: removing *u* decrements the counter of each of its out-neighbours.

```java {#lst-15-kahn} Kahn's algorithm: a topological order, or null on a cycle
// Kahn's algorithm on a directed graph. Returns a topological order, or null if there is a cycle.
static int[] topoOrder(List<Integer>[] g) {
    int n = g.length;
    int[] indeg = new int[n];
    for (int u = 0; u < n; u++) for (int v : g[u]) indeg[v]++;
    int[] order = new int[n];
    int head = 0, tail = 0;
    for (int u = 0; u < n; u++) if (indeg[u] == 0) order[tail++] = u;
    while (head < tail) {
        int u = order[head++];
        for (int v : g[u]) if (--indeg[v] == 0) order[tail++] = v;
    }
    return tail == n ? order : null;          // some node never reached indegree 0 -> cycle
}
```

The `order` array doubles as the queue: positions `head..tail − 1` are waiting, positions before `head` are done.

:::theorem{#thm-15-kahn} Correctness of Kahn's algorithm
@lst-15-kahn outputs all *n* vertices if and only if the graph is acyclic, and when it does, the output is a topological order.
:::

:::proof
At any moment, indeg[*v*] equals the number of edges into *v* from vertices not yet taken out of the queue, because each such removal decrements it once per edge (duplicate edges included). A vertex enters the queue exactly when that number drops to 0.

*The output is ordered.* For an edge (*u*, *v*), *v* is appended only after its counter reaches 0, which requires *u* to have been taken out already, and *u* was appended before it was taken out. So *u* precedes *v*.

*Acyclic ⇒ everything is output.* Suppose the loop ends with some vertices never appended, and let *W* be that set. The subgraph on *W* is a DAG, so by @lem-15-source some *w* ∈ *W* has no incoming edge from *W*. All its in-neighbours are outside *W*, hence were appended and processed, so its counter reached 0 and it was appended: a contradiction.

*Cycle ⇒ not everything is output.* On a directed cycle, the first vertex of the cycle to be appended would need its predecessor on the cycle to have been processed before it, which is impossible.
:::

LeetCode 207 (Course Schedule) is this algorithm with one trap in the input: a pair [*a*, *b*] means "to take *a* you must first take *b*", so the edge goes **from *b* to *a***. ### DP over a DAG

A topological order is exactly the evaluation order a DP needs: when a vertex is processed, every vertex with an edge into it has already been processed.

:::theorem{#thm-15-dagdp} DP in topological order
Let *F*(*v*) be defined from the values *F*(*u*) of the in-neighbours *u* of *v* (and a base value for sources). Processing the vertices in topological order and, for each *u*, pushing *F*(*u*) along every edge (*u*, *v*) computes every *F*(*v*) correctly.
:::

:::proof
By induction along the order. When *u* is processed, all its in-neighbours come earlier, so all their pushes into *u* have already happened and *F*(*u*) is final. Its own pushes then use the final value.
:::

```java {#lst-15-dagdp} DP on a DAG in topological order
// DP on a DAG in topological order: longest path (in edges) ending at each node
static int[] longestPathEndingAt(List<Integer>[] g, int[] order) {
    int[] best = new int[g.length];
    for (int u : order) for (int v : g[u]) best[v] = Math.max(best[v], best[u] + 1);
    return best;
}

// Number of paths from src to every node, modulo 1e9+7, in the same order
static long[] countPaths(List<Integer>[] g, int[] order, int src) {
    final long MOD = 1_000_000_007L;
    long[] ways = new long[g.length];
    ways[src] = 1;
    for (int u : order) for (int v : g[u]) ways[v] = (ways[v] + ways[u]) % MOD;
    return ways;
}
```

On @fig-15-dag the longest paths ending at each vertex are [0, 0, 1, 1, 2, 3], and the numbers of paths starting at vertex 1 are [0, 1, 1, 1, 2, 3]: vertex 5 is reached by 1→3→5, 1→3→4→5 and 1→2→4→5. In a general graph, longest paths are a hard problem; in a DAG they cost O(*n* + *m*), because the order removes every cycle from consideration.

The same scheme handles weights on vertices. If each vertex is a task with a duration and an edge means "must finish before", the earliest finishing time of a task is its own duration plus the largest finishing time among its prerequisites. With durations [3, 2, 4, 1, 2, 5] on @fig-15-dag the finishing times are [3, 2, 7, 3, 9, 14], so everything is done at time 14. That one sentence is the key observation of the bonus problem LeetCode 2050 (Parallel Courses III).

## 0-1 BFS {#sec-15-01bfs}

Plain BFS assumes every edge has the same cost. If some moves are free and others cost 1, it gives wrong answers. In the directed graph with edges 0→1 (cost 1), 0→2 (0), 2→1 (0), 1→3 (1), 2→4 (1) and 3→4 (0), plain BFS reports [0, 1, 1, 2, 2] (it counts edges), while the cheapest costs are [0, 0, 0, 1, 1].

Dijkstra's algorithm (Chapter 17) handles any non-negative costs with a priority queue in O((*n* + *m*) log *n*). When the costs are only 0 and 1 there is a cheaper way: a deque in which a vertex reached by a free edge goes to the **front** and one reached by a paid edge goes to the **back**. This is [[0-1 BFS]].

```java {#lst-15-01bfs} 0-1 BFS with a deque
// Weights are only 0 or 1: a deque replaces the heap. Weight 0 -> front, weight 1 -> back.
static int[] zeroOneBfs(List<int[]>[] g, int src) {
    int[] d = new int[g.length];
    Arrays.fill(d, Integer.MAX_VALUE);
    d[src] = 0;
    ArrayDeque<Integer> dq = new ArrayDeque<>();
    dq.add(src);
    while (!dq.isEmpty()) {
        int u = dq.pollFirst();
        for (int[] e : g[u]) {
            int v = e[0], nd = d[u] + e[1];
            if (nd >= d[v]) continue;
            d[v] = nd;
            if (e[1] == 0) dq.addFirst(v);
            else dq.addLast(v);
        }
    }
    return d;
}
```

Here `g[u]` holds pairs {*v*, cost}. Unlike plain BFS, a vertex can be improved after it was pushed, so the test is "is the new distance smaller?", made every time, and a vertex can sit in the deque twice.

:::example{#ex-15-01} The deque at work
On the graph above, starting at 0 (each entry is a vertex; its current *d* is in the last column):

```trace
pop   d[u]   relaxations                  deque after    d[0..4]
 0     0     1 back (1), 2 front (0)      [2, 1]         [0, 1, 0, -, -]
 2     0     1 front (0), 4 back (1)      [1, 1, 4]      [0, 0, 0, -, 1]
 1     0     3 back (1)                   [1, 4, 3]      [0, 0, 0, 1, 1]
 1     0     -  (an old entry: nothing improves)   [4, 3]
 4     1     -                            [3]
 3     1     4: 1 + 0 is not < 1          []             [0, 0, 0, 1, 1]
```

Vertex 1 was pushed at the back with cost 1, then improved to 0 through the free edge from 2 and pushed again at the front. The second entry for 1 is popped later and changes nothing.
:::

:::theorem{#thm-15-01} Correctness and cost of 0-1 BFS
Give each deque entry the key *d*[*v*] that *v* had when the entry was pushed. Then (a) the keys are non-decreasing from front to back and differ by at most 1; (b) when @lst-15-01bfs ends, *d*[*v*] is the cheapest cost from the source; (c) each vertex is pushed at most twice, so the running time is O(*n* + *m*).
:::

:::proof
(a) An entry whose key is larger than the current *d*[*u*] is outdated: *u* was improved later and the newer entry, with a smaller key, was popped first. When *u* was popped with its newer key, all its edges were relaxed with that value, and *d* values only go down, so popping the outdated entry relaxes nothing. Now suppose (a) holds and the front entry, with key *K* = *d*[*u*], is popped. All keys in the deque lie in [*K*, *K* + 1]. A free edge pushes key *K* at the front, which is ≤ every key; a paid edge pushes *K* + 1 at the back, which is ≥ every key and at most front + 1. So (a) still holds.

(b) By (a), entries leave in non-decreasing key order, so the deque acts as a priority queue. Suppose some vertex *u* is popped with key *K* = *d*[*u*] while the true cost δ(*u*) is smaller. On a cheapest path from the source to *u*, let *x* be the last vertex that has already been popped with *d*[*x*] = δ(*x*) (the source qualifies), and *y* the next vertex on the path. When *x* was popped, the edge to *y* was relaxed, so *d*[*y*] ≤ δ(*x*) + cost(*x*, *y*) = δ(*y*) ≤ δ(*u*) < *K*, the middle step because costs are non-negative. The entry pushed for *y* with that key has not been popped, otherwise *y* would qualify instead of *x*. So the deque holds a key below *K* while *K* is at the front, contradicting (a). Hence every vertex's first real pop has *d* = δ, and later relaxations cannot lower it further.

(c) When *v* first gets a finite *d*, it is *K* or *K* + 1, where *K* is the key being popped. Later keys are at least *K* by (a), so *d*[*v*] can later drop at most once, from *K* + 1 to *K*. Each drop causes one push, so *v* is pushed at most twice and its edge list is scanned at most twice: O(*n* + *m*) in total.
:::

On 4,000 random graphs with costs 0 and 1 the listing matched a Bellman–Ford brute force, and no vertex was ever pushed more than twice.

### On a grid

Grids are where 0-1 BFS appears most. Suppose each cell has a colour, stepping onto a cell of the same colour is free, and stepping onto a different colour costs 1. The fewest colour changes from the top-left to the bottom-right cell is a 0-1 shortest path.

```java {#lst-15-01grid} 0-1 BFS on a grid: fewest colour changes
// Walk from the top-left to the bottom-right cell. Stepping onto a cell with the same letter
// costs 0; stepping onto a different letter costs 1. Cell (r, c) has the id r * C + c.
static int fewestColourChanges(char[][] g) {
    int R = g.length, C = g[0].length;
    int[] dist = new int[R * C];
    Arrays.fill(dist, Integer.MAX_VALUE);
    int[] dr = {1, -1, 0, 0}, dc = {0, 0, 1, -1};
    ArrayDeque<Integer> dq = new ArrayDeque<>();
    dist[0] = 0;
    dq.add(0);
    while (!dq.isEmpty()) {
        int id = dq.pollFirst(), r = id / C, c = id % C;
        for (int k = 0; k < 4; k++) {
            int nr = r + dr[k], nc = c + dc[k];
            if (nr < 0 || nr >= R || nc < 0 || nc >= C) continue;
            int w = g[nr][nc] == g[r][c] ? 0 : 1, nid = nr * C + nc;
            if (dist[id] + w >= dist[nid]) continue;
            dist[nid] = dist[id] + w;
            if (w == 0) dq.addFirst(nid);
            else dq.addLast(nid);
        }
    }
    return dist[R * C - 1];
}
```

:::tip
Use 0-1 BFS when every cost is 0 or 1, or more generally 0 or one fixed value *c* (divide by *c*). Use Dijkstra for any other non-negative costs, and plain BFS when all costs are equal. If an edge can have a negative cost, none of the three works.
:::

## Cost, and a checklist for traversals {#sec-15-checklist}

:::theorem{#thm-15-cost} Linear time
BFS, the stack-based component search, the bipartite check and Kahn's algorithm each run in O(*n* + *m*) time on adjacency lists; 0-1 BFS too, by @thm-15-01. On an *R* × *C* grid with four directions this is O(*RC*).
:::

:::proof
In each algorithm a vertex enters the queue or stack at most once, because it is marked (given a distance, a label, a colour, or a zero counter) at the moment it is pushed, and marked vertices are never pushed again. Each adjacency list is scanned once, when its vertex is removed. So the work is O(*n*) for pushes and pops plus the total length of the adjacency lists, which is 2*m* or *m* by @lem-15-handshake. A grid has *n* = *RC* vertices and at most 4*RC* directed adjacencies.
:::

The proof leans on one line of every template: **mark a vertex when you push it, not when you pop it**. Here is the version that marks on pop.

```java
// WRONG: marks a node when it is popped, and overwrites dist on every push
static int[] bfsMarkOnPop(List<Integer>[] g, int src) {
    int[] dist = new int[g.length];
    boolean[] done = new boolean[g.length];
    ArrayDeque<Integer> q = new ArrayDeque<>();
    q.add(src);
    while (!q.isEmpty()) {
        int u = q.poll();
        done[u] = true;                         // marked only now
        for (int v : g[u]) {
            if (done[v]) continue;
            dist[v] = dist[u] + 1;              // may overwrite a shorter distance
            q.add(v);                           // v may already be in the queue
        }
    }
    return dist;
}
```

It is wrong twice over. **Wrong answers:** on the triangle 0–1, 0–2, 1–2 it returns [0, 1, 2], because when 1 is popped, 2 is still waiting in the queue and not yet marked, so its distance 1 is overwritten with 2. On 2,000 random small graphs it gave a wrong distance on 663. **Exploding time:** a vertex can be pushed once by every neighbour that is popped before it, and each copy, when popped, pushes its own neighbours again. On an open 10 × 10 grid this version made 184,755 queue insertions instead of 100, and on a 20 × 20 grid it ran out of memory. A "lazy" repair that skips a popped vertex already marked (`if (done[u]) continue;` right after `poll`) is correct, but still makes up to one insertion per edge: 181 on the 10 × 10 grid. Marking on push keeps it to one per vertex.

:::checklist Before you submit a traversal
- Every vertex is marked when it is **pushed**, and marked vertices are never pushed again (except in 0-1 BFS, where the test is "strictly better").
- Grid moves check the bounds **before** reading the cell; walls and already-visited cells are skipped in the same `if`.
- Unreachable vertices keep a sentinel (−1 or `Integer.MAX_VALUE`) and the answer handles it (LeetCode 994 wants −1 if a fresh orange is never reached).
- Edge directions match the statement: "[*a*, *b*] means *b* before *a*" gives the edge *b* → *a*.
- The graph may be disconnected: loop over every vertex as a possible start (components, bipartite check).
- Distances counted in **cells** start at 1, distances in **edges** at 0.
- Vertices numbered 1..*n* in the input: either allocate *n* + 1 or subtract 1 when reading.
- No recursion deeper than a few thousand calls in Java; use an explicit stack or queue.
:::

## Summary

- A graph is vertices and edges, directed or undirected. Store it as `List<Integer>[]` (about 26 bytes per edge) or as head/next/to `int` arrays (8 bytes per edge). Grids are implicit graphs with direction arrays.
- The handshake lemma, Σ deg = 2*m*, is why every traversal costs O(*n* + *m*).
- BFS pops vertices in non-decreasing distance and finds the fewest-edge distance to every vertex. Pushing several sources with distance 0 gives the distance to the nearest source.
- DFS with an explicit `ArrayDeque` labels connected components without the risk of `StackOverflowError`.
- A graph is bipartite exactly when it has no odd cycle; colouring by BFS parity either succeeds or finds an edge between equal colours.
- Kahn's algorithm outputs every vertex exactly when the graph is acyclic, and the output is a topological order. DP over a DAG in that order computes longest paths, path counts and finishing times in O(*n* + *m*).
- 0-1 BFS puts free moves at the front of a deque and paid moves at the back; the deque stays sorted, each vertex is pushed at most twice, and the cost is O(*n* + *m*).
- Mark when you push, not when you pop: marking on pop gives wrong distances and can blow the queue up exponentially.

## Review questions

1. A simple undirected graph has 7 vertices with degrees 3, 3, 2, 2, 2, 1 and 1. How many edges does it have? Could a graph have degrees 3, 3, 3, 2, 2?
2. Estimate the memory of adjacency lists for *n* = 10⁵ and *m* = 2 · 10⁶ undirected edges, both as `List<Integer>[]` and as head/next/to arrays.
3. In the proof of @thm-15-bfs, where is @lem-15-queue used? What would go wrong if the queue were replaced by a stack?
4. Explain why multi-source BFS is not the same as running BFS from each source and taking the minimum, in cost though not in result. What is the cost of each for *k* sources?
5. Why is a graph containing a self-loop never bipartite? How does the BFS colouring detect it?
6. Kahn's algorithm is run on a graph with a cycle and returns `null`. Which vertices did it output before stopping? Characterise them.
7. In LeetCode 207, what happens to the answer if every edge is drawn in the wrong direction? Would the same be true for a problem that asks for the order of courses?
8. Why can't plain BFS be used when edge costs are 0 or 1? Give a three-vertex example where it fails.
9. Show that in 0-1 BFS a vertex can be pushed twice, with a concrete graph, and explain why it is never pushed three times.

:::answers
1. By the handshake lemma the degrees add to 2*m*: 3 + 3 + 2 + 2 + 2 + 1 + 1 = 14, so *m* = 7. Degrees 3, 3, 3, 2, 2 add to 13, which is odd, so no graph has them.
2. An undirected edge is stored twice, so there are 4 · 10⁶ list entries. At about 26 bytes per entry (the measurement in @sec-15-repr) that is roughly 100 MB as `List<Integer>[]`. As arrays: `nxt` and `to` with 4 · 10⁶ entries each is 32 MB, plus 0.4 MB for `head`. These are estimates; the exact figure depends on the JVM.
3. It is used for "*w* was popped no later than *u*, so dist[*w*] ≤ dist[*u*]": the queue pops in non-decreasing distance. With a stack, vertices are popped in a different order, a vertex can be discovered first along a long path, and its distance is then too large and never corrected (marking on push prevents a second discovery).
4. Both give the same distances. Multi-source BFS is one traversal, O(*n* + *m*) in total. Running BFS from each of *k* sources costs O(*k*(*n* + *m*)), which for *k* = *n* (every cell a source) is quadratic.
5. A self-loop joins a vertex to itself, so its two endpoints always have the same colour; it is a cycle of length 1, which is odd. In the BFS colouring, when *u* is popped its neighbour *u* already has a colour, equal to its own, and the conflict is reported.
6. It outputs exactly the vertices that cannot be reached from any vertex on a cycle. A vertex on a cycle never reaches indegree 0, and by induction along a path neither does any vertex reachable from it; every other vertex has only such "clean" vertices behind it and is output. With the edge 5 → 1 added to @fig-15-dag, every vertex except 0 is reachable from the cycle 1 → 3 → 5 → 1, and only 0 is output.
7. Reversing every edge maps each cycle to a cycle and each acyclic graph to an acyclic graph, so the yes/no answer is unchanged. A topological order of the reversed graph is the reverse of an order of the original, so an answer that prints the order would be wrong.
8. BFS counts edges, not costs. With edges 0→1 of cost 1, 0→2 of cost 0 and 2→1 of cost 0, BFS gives vertex 1 distance 1 (one edge), but the path 0→2→1 costs 0.
9. The graph of @ex-15-01 does it: vertex 1 is pushed at the back with *d* = 1 when 0 is popped, then improved to 0 through 2 and pushed at the front. By @thm-15-01, when a vertex first gets a value it is *K* or *K* + 1 for the key *K* being popped, and no later key is below *K*, so it can improve at most once.
:::
