Chapter 15 found shortest paths by breadth-first search, which counts edges. Most real questions put a number on each edge instead: the minutes a signal needs to cross a cable, the price of a flight, the height difference between two cells. Counting edges then gives the wrong answer, because a route with more edges can be cheaper. This chapter develops the algorithms that handle weights.

The chapter has two halves that meet at the end. The first half is about **shortest paths**: Dijkstra's algorithm, a proof of why its greedy choice is safe, the variants that change what "cost" means, and graphs whose vertices carry extra state. The second half is about **connecting things cheaply**: the union-find structure, which tracks groups that merge, and the minimum spanning tree, which connects every vertex at the least total cost. The last section uses union-find to answer questions of the form "using only values up to *T*" by processing everything in sorted order.

Throughout, a graph has *V* vertices numbered 0..*V* − 1 and *E* edges, and an edge (*u*, *v*) has a weight *w*(*u*, *v*). Directed edges go from *u* to *v*; undirected edges are stored as two directed ones.

## Weighted shortest paths and Dijkstra's algorithm {#sec-17-dijkstra}

:::definition{#def-17-dist} Path weight and distance
The weight of a path is the sum of the weights of its edges; the empty path from *s* to itself has weight 0. The [[distance|shortest-path distance]] dist(*s*, *v*) is the smallest weight of any path from *s* to *v*, or ∞ if *v* cannot be reached. A path that achieves it is a *shortest path*.
:::

A shortest path with non-negative weights can always be taken to be simple (no repeated vertex): removing a cycle from a path never increases its weight. So there are finitely many candidates, but far too many to enumerate. All the algorithms in this chapter work instead with a tentative distance *d*[*v*] for every vertex and improve it step by step.

:::definition{#def-17-relax} Relaxation
To [[relax|relaxation]] the edge (*u*, *v*) means: if *d*[*u*] + *w*(*u*, *v*) < *d*[*v*], set *d*[*v*] = *d*[*u*] + *w*(*u*, *v*). Initially *d*[*s*] = 0 and *d*[*v*] = ∞ for every other vertex.
:::

Relaxation is safe in one direction: it never makes *d*[*v*] smaller than the truth.

:::lemma{#lem-17-upper} Tentative distances are upper bounds
With non-negative weights, at every moment and for every vertex *v*, either *d*[*v*] = ∞ or *d*[*v*] is the weight of some walk from *s* to *v*. In particular *d*[*v*] ≥ dist(*s*, *v*).
:::

:::proof
At the start only *d*[*s*] = 0 is finite, and it is the weight of the empty walk. A relaxation sets *d*[*v*] to *d*[*u*] + *w*(*u*, *v*), where *d*[*u*] is the weight of a walk to *u*; appending the edge (*u*, *v*) gives a walk to *v* of exactly that weight. Finally, a walk that repeats a vertex contains a cycle, and cutting the cycle out leaves a walk between the same ends that is no heavier, because the cycle's weight is ≥ 0. Repeating this gives a simple path no heavier than the walk, so every walk weighs at least dist(*s*, *v*).
:::

The question is which edges to relax, and in what order, so that each tentative distance becomes exact quickly. Breadth-first search answers it for unit weights: process vertices in order of distance. Dijkstra's algorithm does the same for arbitrary non-negative weights, using a priority queue to find the closest unfinished vertex.

### The algorithm

Keep a min-heap of pairs (*d*, *u*). Repeatedly take the pair with the smallest *d*. If *d* still equals the current *d*[*u*], vertex *u* is now **settled**: its distance is final, and you relax all of its outgoing edges, pushing a new pair for every vertex whose tentative distance drops. If *d* is larger than *d*[*u*], the pair is out of date and you throw it away.

The second rule exists because Java's `PriorityQueue` cannot lower the key of an element that is already inside it. (`remove(Object)` exists but scans the whole heap, which costs O(size).) Instead of updating the old pair (9, 5) when *d*[5] falls to 7, the algorithm pushes a new pair (7, 5) and leaves the old one in the heap. The old pair is now a [[stale entry]]. It is recognised when it surfaces, because 9 ≠ *d*[5], and skipped. This technique is called **lazy deletion**.

```java {#lst-17-graph} Weighted adjacency lists
@SuppressWarnings("unchecked")
static List<int[]>[] weightedGraph(int n, int[][] edges, boolean directed) {   // edges[i] = {u, v, w}
    List<int[]>[] g = new List[n];
    for (int i = 0; i < n; i++) g[i] = new ArrayList<>();
    for (int[] e : edges) {
        g[e[0]].add(new int[]{e[1], e[2]});              // g[u] holds {to, weight}
        if (!directed) g[e[1]].add(new int[]{e[0], e[2]});
    }
    return g;
}
```

```java {#lst-17-dijkstra} Dijkstra's algorithm with lazy deletion (handbook template)
// Non-negative weights. g[u] holds {to, weight}. Returns Long.MAX_VALUE for unreachable nodes.
static long[] dijkstra(List<int[]>[] g, int src) {
    long[] d = new long[g.length];
    Arrays.fill(d, Long.MAX_VALUE);
    d[src] = 0;
    PriorityQueue<long[]> pq = new PriorityQueue<>((x, y) -> Long.compare(x[0], y[0]));
    pq.add(new long[]{0, src});
    while (!pq.isEmpty()) {
        long[] cur = pq.poll();
        int u = (int) cur[1];
        if (cur[0] != d[u]) continue;           // stale entry: u was already finalised
        for (int[] e : g[u]) {
            long nd = d[u] + e[1];
            if (nd < d[e[0]]) {
                d[e[0]] = nd;
                pq.add(new long[]{nd, e[0]});
            }
        }
    }
    return d;
}
```

:::java
Three details in @lst-17-dijkstra matter in Java. Distances are `long`: a path of 10⁵ edges of weight 10⁹ weighs 10¹⁴. The comparator is `Long.compare(x[0], y[0])`, never `(int) (x[0] - y[0])`, which overflows and silently breaks the heap order. And `Long.MAX_VALUE` is safe as "infinity" because the code only ever adds to `d[u]` after `u` has been taken from the heap, which means `d[u]` is finite.
:::

### Why the greedy choice is safe

Dijkstra's algorithm never reconsiders a settled vertex. That is only correct if the distance of a vertex is already exact at the moment it is settled. The proof below is written so that it uses just two facts about path weights, marked (P1) and (P2). @sec-17-variants reuses it for other costs.

* (P1) **Extending a path never makes it cheaper**: the weight of a path followed by one more edge is ≥ the weight of the path. For sums this is exactly *w* ≥ 0.
* (P2) **Extension respects order**: if *x* ≤ *y*, then *x* + *w* ≤ *y* + *w*.

:::theorem{#thm-17-dijkstra} Correctness of Dijkstra's algorithm
With non-negative weights, whenever @lst-17-dijkstra settles a vertex *u* (takes a pair (*d*[*u*], *u*) that is not stale), *d*[*u*] = dist(*s*, *u*), and *d*[*u*] never changes afterwards. When the loop ends, every vertex reachable from *s* has been settled, so *d* holds all distances.
:::

:::proof
Suppose the first claim fails, and let *u* be the **first** vertex settled with *d*[*u*] > dist(*s*, *u*). Let *S* be the set of vertices settled before *u*; by the choice of *u*, every *x* ∈ *S* has *d*[*x*] = dist(*s*, *x*). The source is in *S*: it is settled first, with *d*[*s*] = 0 = dist(*s*, *s*). Take a shortest path *P* from *s* to *u*, let *y* be the first vertex of *P* outside *S*, and let *x* be the vertex just before *y* on *P*, so *x* ∈ *S*.

When *x* was settled, the edge (*x*, *y*) was relaxed, so afterwards *d*[*y*] ≤ dist(*s*, *x*) + *w*(*x*, *y*). The part of *P* from *s* to *x* weighs at least dist(*s*, *x*), so by (P2) the part of *P* from *s* to *y* weighs at least dist(*s*, *x*) + *w*(*x*, *y*) ≥ *d*[*y*]. By (P1), the rest of *P* only adds weight, so *d*[*y*] ≤ weight(*P*) = dist(*s*, *u*) < *d*[*u*]. In particular *y* ≠ *u*.

Every time *d*[*y*] receives a value, a pair with that value is pushed. The pair carrying the current value of *d*[*y*] cannot have been taken out yet, because taking it out would have settled *y*, and *y* ∉ *S*. So at the moment *u* is settled, the heap contains a pair with key *d*[*y*] < *d*[*u*]. A min-heap returns its smallest key, so it could not have returned (*d*[*u*], *u*). This contradiction proves the first claim.

After *u* is settled, relaxations can only lower *d*[*u*], but by @lem-17-upper it cannot go below dist(*s*, *u*) = *d*[*u*]. So it never changes. Finally, if some reachable vertex were never settled, apply the same argument to a path from *s* to it, with *S* the set of all settled vertices: the first unsettled vertex *y* on that path received a pair when its predecessor was settled, and that pair would have been taken out and settled *y* before the heap emptied.
:::

### Cost

Each vertex is settled at most once, and settling it scans its outgoing edges once, so the algorithm performs at most *E* relaxations in total. A pair is pushed only after a successful relaxation, so the heap receives at most *E* + 1 pairs, and at most *E* + 1 pairs are taken out (most of them may be stale). Each heap operation costs O(log(*E* + 1)). A simple graph has *E* < *V*², so log *E* < 2 log *V*, and the total is

> O((*V* + *E*) log *V*) time and O(*V* + *E*) memory.

The *V* term pays for initialising the arrays. For *V* = *E* = 2 · 10⁵ this is a few million heap operations, comfortably under a second in Java.

Two shortcuts break the algorithm. Marking a vertex as visited when it is **pushed**, as BFS does, freezes the first tentative distance: in @ex-17-delay, node 2 would keep the value 4. And forgetting the stale check does not give wrong answers, but every stale pair rescans its vertex's edges, which can multiply the running time by the vertex degree.

### Why negative weights break it

The proof used (P1): extending a path never makes it cheaper. A negative edge breaks exactly that step, because a path through an unsettled vertex *y* can end up cheaper than *d*[*y*].

```fig {#fig-17-neg} A negative edge. True distances from A are in the notes. A version of Dijkstra that settles each vertex once settles B at 2 before it sees the cheaper route A → C → B of weight 1, and then reports d[D] = 3.
{"type": "graph", "unit": 80, "directed": true,
 "nodes": [{"id": "A", "x": 0, "y": 1.2, "note": "dist 0", "color": "green"},
           {"id": "B", "x": 2, "y": 1.2, "note": "dist 1", "color": "red"},
           {"id": "C", "x": 1, "y": 0, "note": "dist 3"},
           {"id": "D", "x": 3.2, "y": 1.2, "note": "dist 2", "color": "red"}],
 "edges": [["A", "B", "2"], ["A", "C", "3"], ["C", "B", "−2"], ["B", "D", "1"]]}
```

In @fig-17-neg a textbook version that settles every vertex exactly once returns *d* = [0, 2, 3, 3] for A, B, C, D, while the true distances are [0, 1, 3, 2]. The lazy template in @lst-17-dijkstra happens to return the right answer here: when C lowers *d*[B] to 1, it pushes (1, B), and B is settled a second time. But @thm-17-dijkstra no longer holds. A vertex can be settled again and again (on graphs built for the purpose, exponentially often), and if the graph has a cycle of negative total weight the loop never ends. For negative weights use the Bellman–Ford algorithm of @sec-17-state, which costs O(*VE*).

## Changing the cost of a path {#sec-17-variants}

The proof of @thm-17-dijkstra never used the fact that path weights are *sums*. It used only (P1) and (P2). Any cost that is built edge by edge and satisfies both can be minimised by the same loop, with `d[u] + e[1]` replaced by the new way of extending a cost.

### Minimax paths

In LeetCode 1631 (Path With Minimum Effort) you walk through a grid of heights, and the effort of a route is the **largest** absolute height difference between consecutive cells. You want the route of least effort. This is a [[minimax path|minimax path]]: minimise, over all paths, the maximum edge weight on the path.

:::theorem{#thm-17-minimax} Dijkstra for minimax paths
If all weights are ≥ 0 and the cost of a path is its largest edge weight (0 for the empty path), the loop of @lst-17-dijkstra with `d[u] + e[1]` replaced by `Math.max(d[u], e[1])` computes the minimax cost from *s* to every vertex.
:::

:::proof
Extending a cost *c* by an edge of weight *w* gives max(*c*, *w*). (P1) holds because max(*c*, *w*) ≥ *c*. (P2) holds because if *x* ≤ *y* then max(*x*, *w*) ≤ max(*y*, *w*). @lem-17-upper also carries over: every finite *d*[*v*] is the cost of a walk, and cutting a cycle out of a walk removes edges, which cannot raise the maximum. The proof of @thm-17-dijkstra then goes through word for word.
:::

```java {#lst-17-minimax} Minimax paths: Dijkstra with max in place of +
// The cost of a path is its LARGEST edge weight (weights >= 0). Same loop as Dijkstra.
static long[] minimaxPaths(List<int[]>[] g, int src) {
    long[] d = new long[g.length];
    Arrays.fill(d, Long.MAX_VALUE);
    d[src] = 0;                                      // the empty path has no edges
    PriorityQueue<long[]> pq = new PriorityQueue<>((x, y) -> Long.compare(x[0], y[0]));
    pq.add(new long[]{0, src});
    while (!pq.isEmpty()) {
        long[] cur = pq.poll();
        int u = (int) cur[1];
        if (cur[0] != d[u]) continue;
        for (int[] e : g[u]) {
            long nd = Math.max(d[u], e[1]);          // the only changed line
            if (nd < d[e[0]]) {
                d[e[0]] = nd;
                pq.add(new long[]{nd, e[0]});
            }
        }
    }
    return d;
}
```

Notice what the proof did *not* need: that every part of an optimal path is itself optimal. For sums this is true, but for maxima it is false. In @fig-17-effort the best route has effort 2; its first step already has difference 2, so every cell on it has minimax cost 2 from the corner, and many other routes to those middle cells are just as good. The proof only needs (P1) and (P2), which is why it survives.

For a grid, the vertices are the cells and each cell has up to four neighbours, so you do not need adjacency lists at all: give cell (*r*, *c*) the id *r* · *C* + *c* and compute the neighbours and step costs inside the loop. LeetCode 1631 is left for you to write in that form.

:::note
Two other methods solve minimax problems, and both are worth knowing. **Binary search on the answer** (Chapter 6): "is there a route whose every step is ≤ *T*?" is a plain BFS that ignores larger steps, and the answer is monotone in *T*, so about 20 BFS runs find the least *T* for heights up to 10⁶. **Kruskal's order** (@sec-17-mst): add the steps in increasing order of cost with union-find, and stop as soon as the two corners are connected; the cost of the last step added is the answer. @thm-17-mstminimax proves that this works.
:::

### Counting shortest paths

LeetCode 1976 (Number of Ways to Arrive at Destination) asks how many different shortest paths lead from vertex 0 to vertex *n* − 1, modulo 10⁹ + 7. Counting paths directly is hopeless; a grid-like graph can have exponentially many. The count can instead be carried along with the distance.

Call an edge (*u*, *v*) **tight** if dist(*s*, *u*) + *w*(*u*, *v*) = dist(*s*, *v*). A path from *s* is a shortest path exactly when every edge on it is tight, and the last edge of a shortest path to *v* is a tight edge (*u*, *v*) preceded by a shortest path to *u*. So, writing ways(*v*) for the number of shortest paths to *v*,

> ways(*s*) = 1, and ways(*v*) = Σ ways(*u*) over all tight edges (*u*, *v*).

With **positive** weights every tight edge goes from a smaller distance to a strictly larger one, so the tight edges form a directed acyclic graph, and Dijkstra settles its vertices in increasing distance, which is a topological order of that graph. The sum can therefore be accumulated during Dijkstra: this is the DAG counting of Chapter 15, with Dijkstra supplying the order.

```java {#lst-17-count} Counting shortest paths modulo a prime (positive weights)
static long[] countShortestPaths(List<int[]>[] g, int src, long mod) {
    int n = g.length;
    long[] d = new long[n], ways = new long[n];
    Arrays.fill(d, Long.MAX_VALUE);
    d[src] = 0;
    ways[src] = 1;
    PriorityQueue<long[]> pq = new PriorityQueue<>((x, y) -> Long.compare(x[0], y[0]));
    pq.add(new long[]{0, src});
    while (!pq.isEmpty()) {
        long[] cur = pq.poll();
        int u = (int) cur[1];
        if (cur[0] != d[u]) continue;                // u is settled, so ways[u] is final
        for (int[] e : g[u]) {
            int v = e[0];
            long nd = d[u] + e[1];
            if (nd < d[v]) {                         // strictly shorter: the old ways are useless
                d[v] = nd;
                ways[v] = ways[u];
                pq.add(new long[]{nd, v});
            } else if (nd == d[v]) {                 // a tie: add the shortest paths through u
                ways[v] = (ways[v] + ways[u]) % mod;
            }
        }
    }
    return ways;
}
```

:::theorem{#thm-17-count} Correctness of the counting rule
If every weight is positive, then when @lst-17-count settles a vertex *u*, ways[*u*] equals the number of shortest paths from *s* to *u* (modulo *mod*).
:::

:::proof
By induction in the order of settling. The source is settled first with ways[*s*] = 1, the empty path. Now consider a vertex *v* ≠ *s* being settled. Every tight edge (*u*, *v*) has dist(*s*, *u*) = dist(*s*, *v*) − *w*(*u*, *v*) < dist(*s*, *v*), so by @thm-17-dijkstra *u* was settled earlier, and by the induction hypothesis ways[*u*] was already correct when *u* relaxed (*u*, *v*). At that moment *nd* = dist(*s*, *v*).

Follow ways[*v*] over time. Before the first tight edge into *v* is relaxed, *d*[*v*] > dist(*s*, *v*), and any value stored in ways[*v*] belongs to a longer route. The first tight relaxation finds *nd* < *d*[*v*], so it **overwrites** ways[*v*] with ways[*u*]; every later tight relaxation finds *nd* = *d*[*v*] and **adds** ways[*u*]. Non-tight edges relaxed after that find *nd* > *d*[*v*] and change nothing. So when *v* is settled, ways[*v*] is the sum of ways[*u*] over all tight edges into *v*, which is the number of shortest paths to *v* by the recurrence above.
:::

:::example{#ex-17-count} Counting with ties
Take the undirected graph with edges 0–1 (1), 0–2 (1), 1–3 (1), 2–3 (1), 3–4 (2), 1–4 (3), 2–4 (5) and *s* = 0. Each row is one settled vertex; a dash in *d* means ∞.

  1      1      1      3: set d=2, ways=1;  4: set d=4, ways=1        [0,1,1,2,4] [1,1,1,1,1]

Vertex 4 has three shortest paths of length 4: 0–1–4, 0–1–3–4 and 0–2–3–4. The row for vertex 1 shows why the tie rule must wait for settling: at that moment ways[4] = 1 counts only the route through 1–4, and the two routes through vertex 3 arrive later.
:::

:::pitfall
The counting rule needs **positive** weights. With a zero-weight edge, two vertices at the same distance can be connected by a tight edge, and the heap may settle the later one first. For the edges *s*→*a* (1), *s*→*b* (1), *a*→*b* (0), *b*→*t* (1) there are two shortest paths to *t*, but if the input lists *s*→*b* before *s*→*a*, @lst-17-count settles *b* before *a* and returns 1. LeetCode 1976 guarantees positive travel times. Its distances need `long`: a shortest route can pass up to 199 roads, each taking up to 10⁹ minutes.
:::

:::infosys
In the official Infosys sample paper, typical limits are *n* ≤ 10⁵ with answers modulo 10⁹ + 7. The exam rules in the plan say: default to `long`, and take the modulus after every operation that can grow a count. In @lst-17-count the only such operation is the addition in the tie branch.
:::

## State-expanded graphs {#sec-17-state}

Many problems add a condition to the path: at most *K* stops, one discount coupon, a limited number of walls you may break. The vertex alone no longer tells you everything that matters about a partial route. Two routes that reach city *v*, one having used the coupon and one not, have different futures, so they must not be compared as if they were the same.

:::definition{#def-17-state} State-expanded graph
A [[state-expanded graph]] has one vertex for every pair (*v*, *x*), where *v* is a vertex of the original graph and *x* is the extra information a route carries (stops used, coupon used or not, walls broken). There is an edge (*u*, *x*) → (*v*, *y*) when the original edge (*u*, *v*) can be taken by a route in state *x* and leaves it in state *y*.
:::

If the extra information has *X* possible values, the new graph has *V* · *X* vertices and at most *E* · *X* edges per kind of move, and any shortest-path algorithm runs on it unchanged. The work is in choosing the state so that it captures *everything* the future depends on, and nothing more.

### One coupon

Suppose you may halve the price of one flight on your route (rounding down). The state is "coupon unused" (0) or "coupon used" (1). Every flight *u* → *v* of price *w* gives three edges: (*u*, 0) → (*v*, 0) and (*u*, 1) → (*v*, 1) at price *w*, and (*u*, 0) → (*v*, 1) at price ⌊*w*/2⌋, the moment the coupon is spent. There is no edge from layer 1 back to layer 0.

```java {#lst-17-coupon} A state-expanded graph: one edge at half price
// Vertex v "coupon unused" keeps the id v; v "coupon used" gets the id v + n.
// Run Dijkstra on the result from s; the answer for t is min(d[t], d[t + n]).
@SuppressWarnings("unchecked")
static List<int[]>[] couponGraph(int n, int[][] edges) {    // directed edges {u, v, w}
    List<int[]>[] h = new List[2 * n];
    for (int i = 0; i < 2 * n; i++) h[i] = new ArrayList<>();
    for (int[] e : edges) {
        int u = e[0], v = e[1], w = e[2];
        h[u].add(new int[]{v, w});                   // unused -> unused: pay in full
        h[u + n].add(new int[]{v + n, w});           // used -> used: pay in full
        h[u].add(new int[]{v + n, w / 2});           // unused -> used: spend the coupon on this edge
    }
    return h;
}
```

### At most K stops

LeetCode 787 (Cheapest Flights Within K Stops) limits the number of intermediate cities: at most *K* stops, so at most *K* + 1 flights. Plain Dijkstra on the cities is wrong here, because the cheapest way to reach a city may use too many flights, and Dijkstra then discards a dearer route that would have stayed within the limit. In @fig-17-stops the cheapest route from 0 to 3 is 0 → 1 → 2 → 3 with price 3, but it uses three flights. With *K* = 1 the answer is 6, and Dijkstra on cities never keeps that route, because it reaches 2 more cheaply through 1.

```fig {#fig-17-stops} Flights with prices. The cheapest route 0 → 1 → 2 → 3 costs 3 but uses three flights; with at most two flights (one stop) the best is 0 → 2 → 3 at 6.
{"type": "graph", "unit": 85, "directed": true,
 "nodes": [{"id": "0", "x": 0, "y": 1, "color": "green"}, {"id": "1", "x": 1, "y": 0}, {"id": "2", "x": 2, "y": 1}, {"id": "3", "x": 3, "y": 0, "color": "green"}],
 "edges": [["0", "1", "1"], ["1", "2", "1"], ["0", "2", "5"], ["2", "3", "1"], ["1", "3", "6"]]}
```

There are two correct ways to respect the limit. The first is a state-expanded graph whose state is the number of flights used: vertices (*v*, *j*) for 0 ≤ *j* ≤ *K* + 1, edges (*u*, *j*) → (*v*, *j* + 1), and the answer is the smallest *d*[(*t*, *j*)] over all *j*. The second needs no new graph at all. It computes, round by round, the cheapest price using at most *i* flights.

:::theorem{#thm-17-rounds} Bellman–Ford rounds
Let *b*ᵢ[*v*] be the least weight of a walk from *s* to *v* with at most *i* edges (∞ if there is none). Then *b*₀[*s*] = 0, *b*₀[*v*] = ∞ for *v* ≠ *s*, and for *i* ≥ 1

*b*ᵢ[*v*] = min( *b*ᵢ₋₁[*v*], min over edges (*u*, *v*) of *b*ᵢ₋₁[*u*] + *w*(*u*, *v*) ).
:::

:::proof
A walk with at most *i* edges either has at most *i* − 1 edges, and is counted by *b*ᵢ₋₁[*v*], or has exactly *i* edges; then it is a walk with *i* − 1 edges to some *u* followed by the edge (*u*, *v*), and the cheapest such choice for a fixed last edge costs *b*ᵢ₋₁[*u*] + *w*(*u*, *v*). Conversely, each term on the right is the weight of a walk with at most *i* edges. So both sides are the same minimum.
:::

The recurrence reads **only** row *i* − 1. Computing row *i* in a copy of the array and relaxing every edge from the old values gives exactly *b*ᵢ, at a cost of O(*E*) per round. For @fig-17-stops, relaxing the edges in the order 0→1, 1→2, 0→2, 2→3, 1→3:

```trace
round i   b_i[0..3]            meaning
   0      [0, inf, inf, inf]   no flights yet
   1      [0, 1, 5, inf]       one flight
   2      [0, 1, 2, 6]         two flights: K = 1 gives 6
   3      [0, 1, 2, 3]         three flights: K = 2 gives 3
```

If instead you update the array **in place**, a value improved earlier in the same round is used again later in that round. With the edge order above, the in-place round 1 already produces [0, 1, 2, 3]: the route 0 → 1 → 2 → 3 slips through in a single "round". That is harmless for ordinary shortest paths but wrong for a limit on the number of edges, which is why the copy matters.

:::note
Without a limit, *V* − 1 rounds always suffice when there is no negative cycle, because a shortest path is simple and has at most *V* − 1 edges. This is the **Bellman–Ford algorithm**: O(*VE*) time, correct with negative edges, and a *V*-th round that still improves something proves that a negative cycle is reachable. It is the right tool when Dijkstra's (P1) fails.
:::

### Free and paid moves: 0-1 BFS

When every edge costs 0 or 1, the heap can be replaced by a deque: Chapter 15's [[0-1 BFS]] pushes a vertex to the front after a 0-edge and to the back after a 1-edge. It is Dijkstra in disguise. Label each deque entry with the distance it was pushed with. Front to back, the labels never decrease and the last is at most the first plus 1: removing the front (label *x*) keeps this true, a 0-edge pushes label *x* at the front, and a 1-edge pushes *x* + 1 at the back, which is at most one more than any label left. So the deque always hands out a smallest label, just like the heap, and the proof of @thm-17-dijkstra applies. Each push follows a successful relaxation, so the cost is O(*V* + *E*) with no logarithm.

LeetCode 2290 (Minimum Obstacle Removal to Reach Corner) is this situation: stepping into an empty cell costs 0, stepping into an obstacle costs 1 (you remove it), and the distance to the far corner is the number of obstacles removed. The state is still just the cell; the weights carry the information.

Table: {#tbl-17-sp} Which shortest-path algorithm?
| Weights | Extra condition | Algorithm | Time |
|---|---|---|---|
| all equal | none | BFS (Chapter 15) | O(*V* + *E*) |
| 0 or 1 | none | 0-1 BFS | O(*V* + *E*) |
| ≥ 0 | none, or a cost satisfying (P1) and (P2) | Dijkstra | O((*V* + *E*) log *V*) |
| ≥ 0 | a small state (coupon, keys) | Dijkstra on (*v*, state) | O(*X*(*V* + *E*) log(*XV*)) |

## Union-find {#sec-17-dsu}

The second half of the chapter needs a different kind of structure. Imagine the edges of a graph arriving one at a time, and after each one you are asked "are *a* and *b* connected now?" or "how many components are there?". Running a BFS after every edge costs O(*V* + *E*) per question. A structure that only ever *merges* groups can do much better.

:::definition{#def-17-dsu} Disjoint-set union
A [[union-find|disjoint-set union (union-find)]] structure maintains a partition of the elements 0..*n* − 1 into disjoint groups, starting with every element alone. It supports two operations: find(*x*) returns a representative of *x*'s group, the same element for every member, and union(*a*, *b*) merges the groups of *a* and *b*.
:::

Each group is stored as a rooted tree in an array `parent`: the root is the representative and has `parent[r] == r`, and every other element points to some element of its group nearer the root. find(*x*) follows `parent` pointers up to the root. union(*a*, *b*) finds both roots and, if they differ, makes one root the child of the other. Two elements are in the same group exactly when their finds return the same root.

How quickly find runs depends on the height of the trees, and two rules keep them low.

**Union by size.** Store at each root the number of elements in its tree, and always hang the root of the *smaller* tree under the root of the larger one.

**Path halving.** During find, make every second node on the path point to its grandparent: `parent[x] = parent[parent[x]]`, then step to that grandparent. A node's parent is only ever replaced by one of its own ancestors, so the groups do not change, but the path to the root roughly halves every time it is walked. (Full *path compression*, which points every node on the path straight at the root, needs a second pass or recursion; halving gets the same bound in one loop.)

```java {#lst-17-dsu} Union-find with union by size and path halving, and Kruskal's algorithm (handbook template)
static final class DSU {
    final int[] parent, size;

    DSU(int n) {
        parent = new int[n];
        size = new int[n];
        for (int i = 0; i < n; i++) {
            parent[i] = i;
            size[i] = 1;
        }
    }

    int find(int x) {
        while (parent[x] != x) {
            parent[x] = parent[parent[x]];          // path halving: keeps trees flat
            x = parent[x];
        }
        return x;
    }

    boolean union(int a, int b) {                    // false if already connected
        a = find(a);
        b = find(b);
        if (a == b) return false;
        if (size[a] < size[b]) {
            int t = a;
            a = b;
            b = t;
        }
        parent[b] = a;                               // attach the smaller tree
        size[a] += size[b];
        return true;
    }
}

// Kruskal: minimum spanning tree weight, -1 if the graph is not connected. edges = {u, v, w}
static long mst(int n, int[][] edges) {
    Arrays.sort(edges, (x, y) -> Integer.compare(x[2], y[2]));
    DSU dsu = new DSU(n);
    long total = 0;
    int used = 0;
    for (int[] e : edges) {
        if (dsu.union(e[0], e[1])) {
            total += e[2];
            used++;
        }
    }
    return used == n - 1 ? total : -1;
}
```

The function `mst` at the bottom is Kruskal's algorithm, the subject of @sec-17-mst; it is printed here because the handbook keeps the two together. Note that `size[x]` is meaningful only when *x* is a root.

### Why the trees stay flat

:::lemma{#lem-17-logn} Union by size gives logarithmic height
With union by size, with or without path halving, every element is at depth at most log₂ *n* in its tree. Hence find costs O(log *n*).
:::

:::proof
Path halving only replaces a parent by an ancestor, which never increases any depth. So depths grow only through union. The depth of an element *x* grows (by exactly 1) only when the root of *x*'s tree is hung under another root. Union by size does that only when *x*'s tree is no larger than the other tree, so the merged tree containing *x* is at least twice as large as *x*'s old tree. Starting from size 1, a size that at least doubles at every step exceeds *n* after more than log₂ *n* steps, and no tree has more than *n* elements. So the depth of *x* is at most log₂ *n*.
:::

With path halving on top, the bound becomes far better on average. The following result is the reason union-find is described as "almost O(1)".

:::theorem{#thm-17-ackermann} Tarjan's bound (stated without proof)
With union by size (or by rank) and path compression or path halving, any sequence of *m* operations on *n* elements takes O(*m* · α(*n*)) time, where α is the inverse of the Ackermann function. α grows so slowly that α(*n*) ≤ 4 for every *n* that could ever be stored in a computer.
:::

The proof is long and not needed in practice. What you should remember is the consequence: for 10⁵ or 10⁶ operations, union-find behaves like an array access with a small constant, and the bound holds for every input, not just on average.

### Two direct applications

**Counting components.** Start with *n* groups. Each union that returns `true` merges two groups into one, so after processing all edges the number of components is *n* minus the number of successful unions. This is the same answer as Chapter 15's BFS, but it works when edges arrive over time and you need the count after each one.

**Detecting a cycle in an undirected graph.** Process the edges one by one.

:::claim{#thm-17-cycle} Union-find detects the first cycle
When the edges of an undirected graph are added one by one, union(*u*, *v*) returns `false` exactly when the edge (*u*, *v*) closes a cycle with edges added before it.
:::

:::proof
The groups are always the connected components of the edges added so far, since every edge merges the components of its two ends. union(*u*, *v*) returns `false` exactly when *u* and *v* are already in one component, that is, when the earlier edges already contain a path from *u* to *v*. That path together with the new edge is a cycle. Conversely, if the new edge lies on a cycle of the graph with it added, the rest of that cycle is a path from *u* to *v* made of earlier edges, so *u* and *v* were already connected.
:::

:::pitfall
Two elements are connected when `find(a) == find(b)`, not when `parent[a] == parent[b]`: the parents are just some nodes on the way to the root. Also, keep `find` iterative as in @lst-17-dsu. A recursive find is fine with union by size (depth at most 16 for 10⁵ elements, by @lem-17-logn) but overflows the stack if you ever drop the size rule and a chain of 10⁵ forms.
:::

:::tip
Information about a whole group belongs at its root: its size, its sum, its minimum, the number of special vertices it contains. In `union`, after `parent[b] = a`, combine `b`'s fields into `a`'s, exactly as `size[a] += size[b]` does.
:::

## Minimum spanning trees {#sec-17-mst}

"Connect all the cities with roads of least total length" asks for a set of edges that links every vertex, at minimum total weight. The cheapest such set never contains a cycle (dropping any edge of a cycle keeps everything connected and does not increase the weight when weights are non-negative), so it is a tree.

:::definition{#def-17-mst} Spanning tree and cuts
A *spanning tree* of a connected undirected graph is a subset of its edges that forms a tree containing every vertex; it has *V* − 1 edges. A [[minimum spanning tree]] (MST) is a spanning tree of least total weight. A [[cut]] is a split of the vertices into a non-empty set *S* and its non-empty complement *V* ∖ *S*. An edge *crosses* the cut if it has one end in each part. A cut *respects* a set of edges *A* if no edge of *A* crosses it. A *light* edge of a cut is a crossing edge of least weight.
:::

Both classical MST algorithms are greedy, and both are justified by one exchange argument.

:::theorem{#thm-17-cut} The cut property
Let *A* be a set of edges contained in some MST, let (*S*, *V* ∖ *S*) be a cut that respects *A*, and let *e* be a light edge of that cut. Then *A* ∪ {*e*} is also contained in some MST.
:::

:::proof
Let *T* be an MST that contains *A*. If *e* ∈ *T* there is nothing to prove. Otherwise write *e* = (*u*, *v*) with *u* ∈ *S* and *v* ∉ *S*. The tree *T* contains a unique path from *u* to *v*; it starts in *S* and ends outside *S*, so some edge *f* on it crosses the cut. Because the cut respects *A*, *f* ∉ *A*. Removing *f* from *T* splits it into two trees, one containing *u* and the other *v* (they were joined only through the path, which used *f*). Adding *e* joins them again, so *T*′ = *T* − *f* + *e* is a spanning tree. Since *e* is light and *f* crosses the cut, *w*(*e*) ≤ *w*(*f*), so *w*(*T*′) ≤ *w*(*T*). Hence *T*′ is also an MST, and it contains *A* ∪ {*e*}.
:::

### Kruskal's algorithm

[[Kruskal's algorithm]] sorts the edges by weight and scans them once, keeping an edge whenever its ends are in different components of the edges kept so far. Union-find answers that question and performs the merge in one call: `mst` in @lst-17-dsu keeps exactly the edges for which `union` returns `true`.

:::theorem{#thm-17-kruskal} Correctness of Kruskal's algorithm
For a connected undirected graph, the edges kept by Kruskal's algorithm form a minimum spanning tree. If the graph is not connected, fewer than *V* − 1 edges are kept, and `mst` returns −1.
:::

:::proof
We show that the set *A* of kept edges is always contained in some MST. This holds at the start, when *A* is empty. Suppose Kruskal keeps *e* = (*u*, *v*). At that moment *u* and *v* are in different groups; let *S* be the group of *u*. The groups are the components of *A*, so no edge of *A* crosses the cut (*S*, *V* ∖ *S*). Now take any edge *f* that crosses this cut. If *f* came before *e* in the sorted order, it was examined earlier; groups only ever merge, so its ends, which are in different groups now, were in different groups then, and *f* would have been kept and its ends merged. That contradicts *f* crossing the cut. So every crossing edge comes after *e* in sorted order, *w*(*e*) ≤ *w*(*f*), and *e* is light. By the cut property, *A* ∪ {*e*} is contained in some MST.

The kept edges never form a cycle (@thm-17-cycle). If the graph is connected and two groups remained at the end, some edge would join them; it was examined, its ends were in different groups then as well, and it would have been kept. So at the end *A* is a spanning tree contained in an MST, hence an MST. If the graph is disconnected, no forest can join its components, fewer than *V* − 1 edges are kept, and `used == n - 1` fails.
:::

Sorting costs O(*E* log *E*) and the *E* union calls cost O(*E* α(*V*)), so Kruskal runs in O(*E* log *E*) time and O(*V* + *E*) memory.

A useful by-product connects back to minimax paths.

:::theorem{#thm-17-mstminimax} Kruskal's tree contains minimax paths
In a connected undirected graph, for any two vertices *a* and *b*, the path from *a* to *b* in the tree built by Kruskal's algorithm is a minimax path between them.
:::

:::proof
Let *M* be the minimax cost between *a* and *b*, achieved by a path *P* whose edges all weigh ≤ *M*. Look at the moment when Kruskal has examined every edge of weight ≤ *M*. Each edge of *P* has been examined, and after an edge is examined its two ends are in the same group (it was either kept, or skipped because they already were). So all vertices of *P*, in particular *a* and *b*, are in one group, joined by kept edges of weight ≤ *M*. That group is a subtree of the final tree, and a tree has only one path between two vertices, so the tree path from *a* to *b* uses only edges of weight ≤ *M*. No path can do better than *M*, so this one is minimax.
:::

### Prim's algorithm and dense graphs

[[Prim's algorithm]] grows a single tree. Start with *S* = {0}. Repeatedly add the cheapest edge with exactly one end in *S*, and put its other end into *S*. Each chosen edge is a light edge of the cut (*S*, *V* ∖ *S*), which respects the tree edges chosen so far, so by the cut property the edges always stay inside some MST, and after *V* − 1 steps they form one.

With a heap, Prim's algorithm looks like Dijkstra and costs O((*V* + *E*) log *V*). The version worth memorising is the one that uses no heap at all. Keep `best[v]`, the cheapest edge from *v* to the current tree. Each of the *V* steps scans all vertices to find the smallest `best` outside the tree, adds it, and scans its edges to lower the other `best` values.

```java {#lst-17-prim} Prim's algorithm for a dense graph in O(V²)
// Complete graph given by a weight function; here a matrix w[u][v] = w[v][u].
// best[v] = the cheapest edge from v to the tree built so far.
static long primDense(int[][] w) {
    int n = w.length;
    long[] best = new long[n];
    boolean[] inTree = new boolean[n];
    Arrays.fill(best, Long.MAX_VALUE);
    best[0] = 0;
    long total = 0;
    for (int step = 0; step < n; step++) {
        int u = -1;
        for (int v = 0; v < n; v++)                  // the cheapest vertex outside the tree
            if (!inTree[v] && (u == -1 || best[v] < best[u])) u = v;
        inTree[u] = true;
        total += best[u];
        for (int v = 0; v < n; v++)                  // u's edges may connect others more cheaply
            if (!inTree[v] && w[u][v] < best[v]) best[v] = w[u][v];
    }
    return total;
}
```

Both inner loops run *V* times per step, so the time is O(*V*²) whatever the number of edges, and the extra memory is O(*V*). This is optimal for a **complete** graph, where *E* = *V*(*V* − 1)/2 and merely reading the edges costs Θ(*V*²).

LeetCode 1584 (Min Cost to Connect All Points) is that case: up to 1000 points, and every pair is an edge whose weight is the Manhattan distance. Kruskal must first build all 499,500 edges as `int[3]` objects (roughly 18 MB) and sort them, about 10⁷ comparisons. @lst-17-prim needs no edge list: replace `w[u][v]` by the distance between points *u* and *v*, computed when needed, and the memory is three arrays of length 1000. On the machine used to test this book, Kruskal took about 200–480 ms on 1000 random points and Prim with a precomputed matrix 5–30 ms, with identical answers.

| Graph | Choose | Time | Memory |
|---|---|---|---|

| complete or nearly complete, weights computed from coordinates | Prim, array version | O(*V*²) | O(*V*) |

## Offline processing in sorted order {#sec-17-offline}

Union-find cannot split a group once it is formed. That sounds like a limitation, but it suggests a strategy: if the questions only ever need groups to grow, arrange to ask them in an order in which the groups do only grow.

A typical question is "can *a* reach *b* using only vertices whose value is at most *T*?". For a single *T* this is one BFS on the allowed vertices. For 10⁵ queries with different thresholds, one BFS each is too slow. But the allowed vertex set for *T* contains the allowed set for any smaller *T*. So sort the queries by *T*, sort the vertices by value, and sweep: before answering a query with threshold *T*, **activate** every vertex of value ≤ *T* that is not yet active, and union each newly active vertex with its already active neighbours. A method that reads all the queries first and answers them in an order of its own choosing is called [[offline|offline algorithm]].

:::lemma{#lem-17-activate} Activation keeps the components exact
After every vertex of value ≤ *T* has been activated (and no other vertex), the union-find groups of the active vertices are exactly the connected components of the graph formed by the vertices of value ≤ *T* and the edges between them.
:::

:::proof
Every union joins two active vertices that share an edge, so each group lies inside one component. Conversely, take any edge whose two ends both have value ≤ *T*. When the later of its two ends was activated, the other end was already active and is a neighbour, so the edge was unioned then. All edges of the component have therefore been unioned, and the whole component is one group.
:::

:::example{#ex-17-activate} Switching vertices on by value
The tree in @fig-17-activate has values 4, 2, 3, 1, 2, 1, 3 on vertices 0..6. Activating in increasing value (ties in index order) gives:

```trace
value  activate  unions with active neighbours  groups of active vertices
  1       3      -                              {3}
  1       5      -                              {3} {5}
  2       1      1-3                            {1,3} {5}
  2       4      4-1                            {1,3,4} {5}
  3       2      2-5                            {1,3,4} {2,5}
  3       6      6-2                            {1,3,4} {2,5,6}
  4       0      0-1, 0-2                       {0,1,2,3,4,5,6}
```

So "can 3 reach 4 with every value ≤ 2?" is answered after row 4: yes, both are in {1, 3, 4}. "Can 3 reach 5 with every value ≤ 3?" is answered after row 6: no, they are in different groups, because the only route passes through vertex 0, whose value is 4.
:::

Sorting the vertices and the *Q* queries costs O(*V* log *V* + *Q* log *Q*), and the sweep performs O(*V* + *E* + *Q*) union-find operations, so the whole method is nearly linear after sorting. The same sweep works with edges instead of vertices ("using only edges of weight ≤ *T*"): sort the edges and union each one when the threshold passes its weight. That is Kruskal's loop with queries interleaved, and @thm-17-mstminimax is its special case for a single pair.

LeetCode 2421 (Number of Good Paths) uses this activation order. A good path's ends have the same value *x* and no vertex on it is larger, so its key observation is: two vertices of value *x* are the ends of a good path exactly when they lie in the same group right after every vertex of value ≤ *x* has been activated. What to count at that moment is the part left for you.

## Summary

- Dijkstra's algorithm settles vertices in increasing distance using a min-heap. With non-negative weights a settled distance is final; the proof needs only that extending a path never makes it cheaper (P1) and that extension respects order (P2).
- Java's `PriorityQueue` has no decrease-key, so push a new pair on every improvement and skip pairs whose distance differs from `d[u]`. The heap holds at most *E* + 1 pairs; the cost is O((*V* + *E*) log *V*). Use `long` distances and `Long.compare`.
- Negative edges violate (P1). Use Bellman–Ford, O(*VE*), or *K* rounds of it with a copied array when the number of edges is limited.
- Replacing + by max gives minimax paths with the same loop. Counting shortest paths adds `ways[u]` on ties and resets it on strict improvements; it needs positive weights.
- Extra conditions become extra state: vertices (*v*, *x*) in a state-expanded graph. 0/1 weights need only a deque (0-1 BFS, O(*V* + *E*)).
- Union-find with union by size has depth ≤ log₂ *n*; with path halving as well, operations cost O(α(*n*)), effectively constant. A `false` from `union` means the edge closes a cycle.
- The cut property (a light crossing edge belongs to some MST) justifies both Kruskal (sort + union-find, O(*E* log *E*)) and Prim (grow one tree). For complete graphs, Prim's array version runs in O(*V*²) with O(*V*) memory.
- Questions with a threshold can be answered offline: sort them, activate vertices or edges in increasing order, and let union-find grow the groups.

## Review questions

1. The heap in @lst-17-dijkstra can hold up to *E* + 1 pairs. Why is each heap operation still O(log *V*) on a simple graph?
2. What happens to correctness, and to the running time, if the line `if (cur[0] != d[u]) continue;` is deleted from @lst-17-dijkstra?
3. Give a directed graph with three vertices on which the route with the fewest edges from vertex 0 to vertex 1 is not the shortest one, and give both answers.
4. Why does @lst-17-minimax start with `d[src] = 0`? Give an example with a negative weight where this start value produces a wrong answer, and say what start value would fix it.
5. In @ex-17-count, ways[4] equals 1 when vertex 1 is settled but 3 at the end. Explain why the final value can only be trusted once vertex 4 itself is settled.
6. For the flights of @fig-17-stops with *K* = 1, what does a Bellman–Ford loop that updates the array in place return after *K* + 1 = 2 rounds (edges relaxed in the order 0→1, 1→2, 0→2, 2→3, 1→3), and why is it wrong?
7. Give a sequence of unions on 8 elements that makes some element reach depth 3 under union by size. Why can no sequence reach depth 4?
8. Prove that if all edge weights are different, the minimum spanning tree is unique.
9. For LeetCode 1584 with 1000 points, compare the work and memory of Kruskal's algorithm and @lst-17-prim.
10. Why must the offline method of @sec-17-offline answer the queries in increasing order of *T*? What could go wrong if it answered them in input order?

:::answers
1. Every pair pushed follows a successful relaxation, so there are at most *E* + 1 pairs and each operation costs O(log(*E* + 1)). A simple graph has *E* < *V*², so log(*E* + 1) ≤ 2 log *V* = O(log *V*).
2. The answers stay correct. A stale pair is processed with the current `d[u]` (the code uses `d[u]`, not `cur[0]`), which is the value already used when *u* was settled, so every relaxation from it fails. But each stale pair now rescans all of *u*'s edges, so the running time can grow by a factor of the largest degree.
3. Edges 0→1 (10), 0→2 (1), 2→1 (1). The fewest-edges route is 0→1, one edge of weight 10. Dijkstra finds dist(0, 1) = 2 through vertex 2.
4. The empty path from the source has no edges, and with non-negative weights its cost 0 is the smallest possible, so max(0, *w*) = *w* for the first edge. With an edge *s*→*v* of weight −3, the true minimax cost of *v* is −3 but the code computes max(0, −3) = 0. Starting from `Long.MIN_VALUE` (the maximum of an empty set) fixes it: (P1) and (P2) hold for max with any weights.
5. A tight edge into 4 can be relaxed by any vertex settled before 4. When vertex 1 is settled, vertex 3 (distance 2) is not, and the two shortest paths through the edge 3–4 have not been added yet. By @thm-17-count, ways[4] is final when 4 is settled, because by then every tight predecessor (distance < 4) has been settled.
6. The in-place round 1 already gives [0, 1, 2, 3], and round 2 changes nothing, so it returns 3. That price uses three flights (0→1→2→3), more than the two allowed; the correct answer is 6 (0→2→3). Values improved earlier in a round are reused later in the same round, so a round can add more than one edge.
7. union(0,1), union(2,3), union(4,5), union(6,7), union(0,2), union(4,6), union(0,4) gives `parent` = [0, 0, 0, 2, 0, 4, 4, 6], and element 7 has the path 7 → 6 → 4 → 0, depth 3. By @lem-17-logn the depth is at most log₂ 8 = 3.
8. Suppose *T*₁ ≠ *T*₂ are both minimum spanning trees, and let *e* be the lightest edge that is in exactly one of them, say *e* ∈ *T*₁. Adding *e* to *T*₂ creates a cycle. Not all of that cycle's edges are in *T*₁ (a tree has no cycle), so some edge *f* ≠ *e* on it is in *T*₂ but not in *T*₁. Then *f* is also in exactly one tree, so *w*(*f*) > *w*(*e*), as the weights are distinct and *e* is the lightest such edge. Now *T*₂ + *e* − *f* is a spanning tree lighter than *T*₂, a contradiction.
9. Kruskal builds 499,500 edges (about 18 MB as `int[3]` objects) and sorts them, about 10⁷ comparisons, then runs 499,500 unions. Prim performs 1000 steps, each with two scans of 1000 vertices, about 2 · 10⁶ simple operations, and needs three arrays of length 1000 if distances are computed on demand. In the book's test run Prim was about 10–40 times faster.
10. Union-find can only merge. The groups for a threshold *T* must contain no vertex of value > *T*. If a query with a large *T* were answered first, its activated vertices could join *a* and *b* through a vertex that a later query with a small *T* must not use, and that union cannot be undone.
:::
