A tree is the simplest connected graph: no cycles, one route between any two vertices. That simplicity is what makes tree problems feel easy on paper and fail in Java. The recursive function you would write for a tree is short and correct, but on a tree that is a long chain of 10⁵ vertices it calls itself 10⁵ times deep, and the Java call stack runs out.

This chapter has three parts. Sections @sec-18-trees and @sec-18-binary cover the definitions and the recursion you use on LeetCode's binary trees, where it is safe. @sec-18-iterative shows how to do the same work on a general tree given as a parent array, which is how the Infosys sample paper delivers its trees, without any recursion at all. Sections @sec-18-lifting to @sec-18-sizes then answer questions about ancestors and paths: the lowest common ancestor by binary lifting, path counts from root prefixes, and answers built from subtree sizes. Chapter 19 builds dynamic programming on top of all of this.

## Trees and how they are stored {#sec-18-trees}

:::definition{#def-18-tree} Tree
A [[tree]] is a connected undirected graph with no cycle. A *leaf* is a vertex of degree 1 (in a tree with at least two vertices).
:::

Three facts about trees are used constantly: a tree with *n* vertices has *n* − 1 edges, any two vertices are joined by exactly one path, and either property, together with connectivity, identifies a tree. All three follow from one small lemma.

:::lemma{#lem-18-leaf} Two leaves
Every tree with *n* ≥ 2 vertices has at least two leaves.
:::

:::proof
Take a longest simple path *v*₀, *v*₁, …, *v*ₖ in the tree; *k* ≥ 1 because the tree is connected and has an edge. Suppose *v*₀ had a neighbour *x* other than *v*₁. If *x* is not on the path, then *x*, *v*₀, …, *v*ₖ is a longer simple path. If *x* = *v*ᵢ with *i* ≥ 2, then *v*₀, *v*₁, …, *v*ᵢ, *v*₀ is a cycle. Both are impossible, so *v*₀ has degree 1. The same argument applies to *v*ₖ, and *v*₀ ≠ *v*ₖ.
:::

:::theorem{#thm-18-edges} Trees have n − 1 edges
A tree with *n* vertices has exactly *n* − 1 edges.
:::

:::proof
By induction on *n*. A tree with one vertex has no edges. For *n* ≥ 2, remove a leaf ℓ and its only edge. The rest has no cycle, and it is still connected: a simple path between two other vertices never passes through ℓ, because passing through a vertex uses two of its neighbours and ℓ has only one. So the rest is a tree with *n* − 1 vertices and, by induction, *n* − 2 edges. Adding ℓ back gives *n* − 1.
:::

:::theorem{#thm-18-unique} Unique paths
In a tree there is exactly one simple path between any two vertices *a* and *b*. Conversely, a connected graph with *n* vertices and *n* − 1 edges is a tree.
:::

:::proof
A path exists because the tree is connected. Suppose *P* and *Q* are different simple paths from *a* to *b*. Follow both from *a*; let *x* be the last vertex before they first differ. From *x*, follow *P* until it first reaches a vertex *y* that lies on *Q* after *x*; such a *y* exists because both paths end at *b*. The piece of *P* from *x* to *y* meets *Q* only at *x* and *y*, and it is not the same as *Q*'s piece from *x* to *y*, because the two paths leave *x* along different edges. Together the two pieces form a cycle, which a tree does not have.

For the converse, suppose a connected graph has *n* vertices, *n* − 1 edges and a cycle. Deleting one edge of the cycle keeps the graph connected (the rest of the cycle replaces it). Repeat until no cycle is left. The result is a tree with *n* vertices and fewer than *n* − 1 edges, contradicting @thm-18-edges.
:::

These facts are practical. An edge list with *n* − 1 edges that connects all *n* vertices is guaranteed to be a tree, so "the path from *u* to *v*" is well defined and every algorithm in this chapter applies.

### Rooted trees

Most tree algorithms first pick a vertex as the **root**. Then every other vertex *v* has a **parent**: the next vertex on the unique path from *v* to the root.

:::definition{#def-18-rooted} Rooted-tree vocabulary
In a tree rooted at *r*: the [[ancestors|ancestor]] of *v* are the vertices on the path from *v* to *r*, including *v* itself; *v* is a *descendant* of each of them. The *children* of *v* are the vertices whose parent is *v*. The [[depth]] of *v* is the number of edges from *v* to the root. The [[subtree]] of *v* consists of *v* and all its descendants. The *height* of *v* is the number of edges on the longest downward path from *v* to a leaf of its subtree.
:::

### Four ways a tree arrives

Table: {#tbl-18-repr} Tree representations and where you meet them
| Representation | What you are given | Typical source | Children of *v* |
|---|---|---|---|
| `TreeNode` objects | a root with `left` and `right` pointers | LeetCode binary-tree problems | `node.left`, `node.right` |
| parent array | `par[v]` for every *v*, −1 (or 0 when 1-indexed) at the root | Infosys sample paper, LeetCode 2246 | build children lists first |
| children lists | `List<Integer>[] kids` or `head`/`next` arrays | built by you from a parent array | iterate the list |
| edge list | *n* − 1 pairs {*u*, *v*} with no direction | LeetCode 834, 1519, 2477 | root it by BFS first |

A parent array is compact (one `int` per vertex) but answers only "who is above me?". Almost every algorithm needs to go down as well, so the first step is to build children lists. `List<Integer>[]` is easy to write; two `int` arrays, `head[u]` (first child of *u*) and `next[c]` (next sibling of *c*), do the same job without creating 10⁵ list objects and boxed integers. An edge list does not say which end is the parent, so you choose a root and run a BFS, recording where each vertex was reached from. @sec-18-iterative gives the code for all of these.

## Recursion on binary trees {#sec-18-binary}

On LeetCode a binary tree arrives as `TreeNode` objects, and recursion is the natural tool. A recursive function on a tree is correct by **structural induction**: if it returns the right value for the empty tree (`null`), and it returns the right value for a node whenever the recursive calls returned the right values for its two subtrees, then it is right for every tree. So designing the function comes down to one question.

:::keyidea
What single fact does a node's parent need to know about the node's subtree? That fact is the return value. Everything else the problem asks for goes into a separate holder that every call can update.
:::

### Height and diameter

For the height, the answer to the question is the height itself: a node's height is one more than the larger of its children's heights. The handbook template counts **nodes** on the longest downward path, so that `null` returns 0 and a leaf returns 1; in edges this is one more than the height of @def-18-rooted.

The [[diameter]] of a tree, asked for in LeetCode 543 (Diameter of Binary Tree), is the number of edges on its longest path. A parent cannot compute the diameter of its subtree from the children's diameters alone, because the longest path may pass through the parent. The fix is to notice where a path can bend.

:::theorem{#thm-18-diameter} Every path bends at one node
Let *h*(*x*) be the number of nodes on the longest downward path from *x*, with *h*(`null`) = 0. Every simple path in a rooted tree has a unique highest node *v*, and the path consists of a downward path from *v* into the left subtree and one into the right subtree, either possibly empty. Consequently the diameter is the maximum over all nodes *v* of *h*(*v*.left) + *h*(*v*.right).
:::

:::proof
Along a path, consecutive vertices are parent and child, so the depth changes by exactly 1 at each step. A simple path cannot go down from *x* to a child *c* and then up again, because the only vertex above *c* is *x*. So the path first goes up and then only goes down, and the turning point is its unique highest node *v*. From *v* it can enter each child's subtree at most once, since entering a subtree twice would pass through that child twice. A binary node has two children, so the path is a downward chain into the left subtree joined at *v* to a downward chain into the right subtree. The left chain has at most *h*(*v*.left) edges (one edge from *v* to each of its nodes below *v*), and similarly on the right, with equality for the longest chains. So the longest path with highest node *v* has *h*(*v*.left) + *h*(*v*.right) edges, and the diameter is the largest of these over all *v*.
:::

The function therefore returns the height, which the parent needs, and records *l* + *r* at every node in a holder `best`, which the parent does not need. A one-element array is the shortest way to give every recursive call write access to the same variable.

```java {#lst-18-diameter} LeetCode's TreeNode; diameter and maximum path sum (handbook template)
static final class TreeNode {                       // LeetCode's binary tree node
    int val;
    TreeNode left, right;

    TreeNode(int val) { this.val = val; }
}

// Pattern: a function returns one fact about a subtree; a holder array collects the answer.
// Diameter (LeetCode 543): longest path in edges between any two nodes.
static int diameter(TreeNode root) {
    int[] best = {0};
    height(root, best);
    return best[0];
}

static int height(TreeNode node, int[] best) {     // nodes on the longest downward path
    if (node == null) return 0;
    int l = height(node.left, best), r = height(node.right, best);
    best[0] = Math.max(best[0], l + r);              // the path that bends at this node
    return 1 + Math.max(l, r);
}

// Maximum path sum (LeetCode 124): same shape, negative branches are dropped
static int maxPathSum(TreeNode root) {
    int[] best = {Integer.MIN_VALUE};
    gain(root, best);
    return best[0];
}

static int gain(TreeNode node, int[] best) {
    if (node == null) return 0;
    int l = Math.max(0, gain(node.left, best)), r = Math.max(0, gain(node.right, best));
    best[0] = Math.max(best[0], node.val + l + r);
    return node.val + Math.max(l, r);                 // a parent can use only one branch
}
```

### Maximum path sum with negative values

LeetCode 124 (Binary Tree Maximum Path Sum) asks for the largest sum of node values on any non-empty path, and values may be negative. @thm-18-diameter still says where a path bends, but now a chain into a child's subtree is optional: taking it is worth it only if its best sum is positive.

Let *g*(*x*), the **gain** of *x*, be the largest sum of a downward path that starts at *x* and contains at least *x*.

:::theorem{#thm-18-gain} Gains and the best path
*g*(*x*) = *x*.val + max(0, *g*(*x*.left), *g*(*x*.right)), where a missing child contributes 0. The best path whose highest node is *v* has sum *v*.val + max(0, *g*(*v*.left)) + max(0, *g*(*v*.right)), and `maxPathSum` returns the largest of these over all *v*.
:::

:::proof
A downward path from *x* is *x* alone, or *x* followed by a downward path from one child. The best continuation through a child *c* is worth *g*(*c*), and it should be taken only if it adds something, which gives the formula for *g*(*x*) (by induction on the height of *x*, the recursive calls return the correct gains). By @thm-18-diameter, a path with highest node *v* is *v* plus an optional downward chain starting at each child, and the two choices are independent, so each child's chain is added exactly when its gain is positive. Every non-empty path has a highest node, so the maximum over *v* is the answer.
:::

The listing computes `l` and `r` as `Math.max(0, gain(...))`, updates `best` with the bend `node.val + l + r`, and returns `node.val + Math.max(l, r)`: the parent may continue into only one of the two branches.

:::example{#ex-18-gain} Dropping negative branches
For the tree of @fig-18-gain the calls return:

  6        5          -2        5  0      11              11              11

The answer is 11, the path 5–6. Node 6 drops its −2 child; node 7 drops its −1 child; and the bend at the root, −20 + 11 + 10 = 1, loses to the bend at 6.
:::

:::pitfall
`best` must start at `Integer.MIN_VALUE`, not 0. If every value is negative, the answer is the largest single value (a path must contain at least one node). For the tree with root −3 and one child −1, `maxPathSum` returns −1; starting `best` at 0 would return 0, a path that does not exist.
:::

### Lowest common ancestor

:::definition{#def-18-lca} Lowest common ancestor
The [[lowest common ancestor]] (LCA) of *p* and *q* in a rooted tree is the deepest vertex that is an ancestor of both. Because a vertex is its own ancestor, if *q* lies in the subtree of *p*, the LCA is *p*.
:::

LeetCode 236 (Lowest Common Ancestor of a Binary Tree) gives two nodes of a binary tree and asks for their LCA. The recursive rule is three lines, and its correctness rests on describing precisely what a call returns for *every* subtree, not only for the whole tree.

```java {#lst-18-lca} Lowest common ancestor and level order on TreeNode (handbook template)
static final class TreeNode { int val; TreeNode left, right; TreeNode(int val) { this.val = val; } }

// Lowest common ancestor (LeetCode 236)
static TreeNode lca(TreeNode root, TreeNode p, TreeNode q) {
    if (root == null || root == p || root == q) return root;
    TreeNode l = lca(root.left, p, q), r = lca(root.right, p, q);
    if (l != null && r != null) return root;          // p and q are on different sides
    return l != null ? l : r;
}

// Level-order traversal (LeetCode 102): BFS, one level per outer loop
static List<List<Integer>> levelOrder(TreeNode root) {
    List<List<Integer>> levels = new ArrayList<>();
    if (root == null) return levels;
    ArrayDeque<TreeNode> q = new ArrayDeque<>();
    q.add(root);
    while (!q.isEmpty()) {
        List<Integer> level = new ArrayList<>();
        for (int k = q.size(); k > 0; k--) {          // exactly the nodes of this level
            TreeNode node = q.poll();
            level.add(node.val);
            if (node.left != null) q.add(node.left);
            if (node.right != null) q.add(node.right);
        }
        levels.add(level);
    }
    return levels;
}
```

:::theorem{#thm-18-lcarec} What the recursive LCA returns
For every node *x* (or `null`), `lca(x, p, q)` returns the LCA of *p* and *q* if both lie in the subtree of *x*; returns whichever of *p*, *q* lies in the subtree of *x* if exactly one does; and returns `null` if neither does. In particular, called on the root of a tree containing both, it returns their LCA.
:::

:::proof
By induction on the height of *x*. For `null` the subtree is empty and the call returns `null`. If *x* is *p* (the case *q* is symmetric), the call returns *p*. That is correct in both possible cases: if *q* is in the subtree of *p*, the LCA is *p*; if not, exactly one of them, *p*, is in the subtree.

Otherwise *x* is neither, and by induction the calls on the children return values described by the theorem. If *p* and *q* are in different children's subtrees, each side returns the one it contains, both are non-null, and *x* is returned; *x* is a common ancestor, and no child of *x* is, so *x* is the LCA. If both are in the same child's subtree, that side returns their LCA and the other side returns `null`, so the LCA is passed up. If exactly one is in the subtree of *x*, its side returns it and the other side `null`, so it is passed up. If neither is, both sides return `null`, and so does *x*.
:::

On the tree of @fig-18-diameter with *p* = 8 and *q* = 7, the call at 8 returns 8, which 6 and 4 pass up unchanged; on the other side 7 returns itself and 5 passes it up; node 2 receives 8 from the left and 7 from the right and returns itself; node 3 returns `null`; and the root passes 2 up. The LCA is 2.

### Level order

The `levelOrder` function in @lst-18-lca is BFS from the root with one extra idea: the size of the queue, read *before* the inner loop starts, is the number of nodes in the current level.

:::claim{#thm-18-levels} One level per outer iteration
At the start of the *d*-th iteration of the outer loop (counting from 0), the queue holds exactly the nodes of depth *d*, from left to right.
:::

:::proof
For *d* = 0 the queue holds only the root. If it holds the depth-*d* nodes from left to right, the inner loop removes exactly `q.size()` of them, that is, all of them and nothing else, and appends each one's left child and then right child. The nodes of depth *d* + 1 are exactly the children of the depth-*d* nodes, and listing the children of a left-to-right row in order lists them from left to right.
:::

For the tree of @fig-18-diameter (values equal to the labels) the result is [[1], [2, 3], [4, 5], [6, 7], [8, 9]].

:::java
Recursion depth is the height of the tree. LeetCode's tests for these problems pass with the recursive templates. A general tree from a parent array is different: it can be a chain. On the JDK used to test this book, the recursive `height` above, run on a chain built from `TreeNode`s with default JVM settings, worked at depth 2 · 10⁴ and threw `StackOverflowError` at depth 5 · 10⁴. The exact limit depends on the JVM and the frame size, so never rely on it for 10⁵ nodes.
:::

## General trees without recursion {#sec-18-iterative}

:::infosys
In the official sample paper the trees arrive as parent arrays with up to 10⁵ nodes, and the plan's Lesson 4 is blunt: a recursive DFS on a chain of that length crashes with `StackOverflowError`. The test data only has to contain one long chain for a recursive solution to score nothing on that file. Everything in this section runs in loops over arrays, so the depth of the tree does not matter.
:::

The replacement for recursion is an **order** in which to visit the vertices. Recursion does two kinds of work: on the way down it passes information from a parent to its children (depths, prefix sums), and on the way back up it combines the children's results into the parent's (sizes, heights, DP values). The breadth-first order supports both.

:::definition{#def-18-bfsorder} BFS order
The [[BFS order]] of a rooted tree lists the root, then all vertices of depth 1, then all of depth 2, and so on, as produced by a breadth-first search from the root that appends each vertex's children when the vertex is removed from the queue.
:::

:::theorem{#thm-18-order} Parents first, children first backwards
In the BFS order, every vertex other than the root appears after its parent. Consequently, a loop that walks the order **backwards** reaches every vertex after all of its descendants, and a loop that walks it **forwards** reaches every vertex after all of its ancestors.
:::

:::proof
A vertex *c* is appended to the order only while its parent *u* is being processed, and *u* is processed only after it was itself appended, so *u* occupies an earlier position. Every vertex is appended: by induction on depth, a vertex of depth *d* + 1 is appended when its parent, of depth *d*, is processed. For the consequences, apply the first statement repeatedly along the path from a descendant up to the vertex: positions strictly decrease going up, so every ancestor of *v* is before *v* and every descendant after it.
:::

The handbook template builds children lists from the parent array, produces the BFS order with an array used as a queue, and computes subtree sizes with one backward loop.

```java {#lst-18-bfs} Children lists, BFS order and subtree sizes from a parent array (handbook template)
// General tree: nodes 0..n-1, par[root] = -1 (LeetCode style).
// Infosys input is often 1-indexed with par[root] = 0: subtract 1 from every value first.
@SuppressWarnings("unchecked")
static List<Integer>[] childrenOf(int[] par) {
    List<Integer>[] kids = new List[par.length];
    for (int v = 0; v < par.length; v++) kids[v] = new ArrayList<>();
    for (int v = 0; v < par.length; v++) if (par[v] != -1) kids[par[v]].add(v);
    return kids;
}

// BFS order: every parent comes before its children. No recursion, so no stack overflow.
static int[] bfsOrder(int[] par) {
    List<Integer>[] kids = childrenOf(par);
    int n = par.length;
    int[] order = new int[n];
    int head = 0, tail = 0;
    for (int v = 0; v < n; v++) if (par[v] == -1) order[tail++] = v;   // the root
    while (head < tail) {
        int u = order[head++];
        for (int c : kids[u]) order[tail++] = c;
    }
    return order;
}

// "Post-order" without recursion: walk the BFS order BACKWARDS (children before parents)
static int[] subtreeSizes(int[] par) {
    int[] order = bfsOrder(par), size = new int[par.length];
    Arrays.fill(size, 1);
    for (int i = order.length - 1; i > 0; i--) {         // order[0] is the root
        int v = order[i];
        size[par[v]] += size[v];
    }
    return size;
}
```

The size loop is correct because of @thm-18-order: when vertex *v* is reached and adds `size[v]` to its parent, all of *v*'s children were reached earlier and have already added their sizes to `size[v]`, so `size[v]` = 1 + Σ size[*c*] is final. The order array doubles as the BFS queue: `head` is the front and `tail` the back, and since each vertex is appended exactly once, an array of length *n* is enough. Everything costs O(*n*) time and memory.

:::pitfall
Walking the vertex numbers *n* − 1, …, 1, 0 instead of the BFS order is correct only if every parent has a smaller number than its children. Some inputs happen to have that property, but nothing in a parent array guarantees it. If vertex 2 is the parent of vertex 1, the index loop reaches 2 first and adds `size[2]` to its parent before vertex 1 has added its own size to `size[2]`. Use the BFS order every time and the question never arises.
:::

### Arrays instead of lists, and pushing values down

For 10⁵ vertices, `List<Integer>[]` creates 10⁵ list objects and up to 10⁵ boxed integers. Two `int` arrays describe the same children lists: `head[u]` is the first child of *u* (−1 if none) and `next[c]` is the next sibling of *c*. Inserting the children in decreasing order of number makes each list come out in increasing order, so the BFS order below is identical to the template's.

```java {#lst-18-arrays} BFS order with head/next arrays, and depths in one forward pass
// Children without List objects: head[u] = first child of u, next[c] = the next sibling of c.
static int[] bfsOrderArrays(int[] par) {
    int n = par.length, root = -1;
    int[] head = new int[n], next = new int[n], order = new int[n];
    Arrays.fill(head, -1);
    for (int v = n - 1; v >= 0; v--) {                   // backwards: siblings in increasing order
        if (par[v] == -1) root = v;
        else {
            next[v] = head[par[v]];
            head[par[v]] = v;
        }
    }
    int qh = 0, qt = 0;
    order[qt++] = root;
    while (qh < qt) {
        int u = order[qh++];
        for (int c = head[u]; c != -1; c = next[c]) order[qt++] = c;
    }
    return order;
}

// Walking the order FORWARDS pushes information from parents to children.
static int[] depths(int[] par, int[] order) {
    int[] depth = new int[par.length];
    for (int v : order) depth[v] = par[v] == -1 ? 0 : depth[par[v]] + 1;
    return depth;
}
```

The `depths` loop is the forward half of @thm-18-order: when *v* is reached, its parent's depth is already final. Any quantity defined from the parent's value (depth, the sum of values on the root path, the binary-lifting rows of @sec-18-lifting) is computed the same way.

### Rooting an edge list

When the tree arrives as an undirected edge list, choose a root and let a BFS discover the parents. The value −2 marks "not reached yet", so the root's −1 is never mistaken for a missing parent.

```java {#lst-18-edges} Rooting an edge list: a parent array by BFS
// Edge list (LeetCode style) -> parent array rooted at `root`; par[root] = -1.
@SuppressWarnings("unchecked")
static int[] parentsFromEdges(int n, int[][] edges, int root) {
    List<Integer>[] g = new List[n];
    for (int i = 0; i < n; i++) g[i] = new ArrayList<>();
    for (int[] e : edges) {
        g[e[0]].add(e[1]);
        g[e[1]].add(e[0]);
    }
    int[] par = new int[n];
    Arrays.fill(par, -2);                                // -2 = not visited yet
    par[root] = -1;
    ArrayDeque<Integer> q = new ArrayDeque<>();
    q.add(root);
    while (!q.isEmpty()) {
        int u = q.poll();
        for (int v : g[u]) {
            if (par[v] != -2) continue;
            par[v] = u;
            q.add(v);
        }
    }
    return par;
}
```

Each vertex receives as parent the neighbour from which BFS first reached it, which is the neighbour one step closer to the root, exactly the parent of @def-18-rooted.

### Entry and exit times

Some questions need a depth-first order instead: "is *u* an ancestor of *v*?" for many pairs, or, in Chapter 20, "sum over the subtree of *v*" while values change. An explicit stack replaces the call stack. Each stack entry is a vertex, and `cur[v]` remembers which child of *v* to visit next, which is exactly the information a recursive call keeps in its local variables.

:::definition{#def-18-euler} Entry and exit times
In a depth-first traversal from the root, the [[entry time]] tin[*v*] is the number of vertices visited before *v*, and tout[*v*] is the largest entry time of any vertex in the subtree of *v*.
:::

```java {#lst-18-euler} Iterative DFS with entry and exit times
// tin[v] = time v is first visited; tout[v] = the largest tin inside v's subtree.
// u is an ancestor of v (or v itself) exactly when tin[u] <= tin[v] <= tout[u].
static int[][] entryExitTimes(int[] par) {
    int n = par.length, root = -1, timer = 0, top = 0;
    int[] head = new int[n], next = new int[n];
    Arrays.fill(head, -1);
    for (int v = n - 1; v >= 0; v--) {
        if (par[v] == -1) root = v;
        else {
            next[v] = head[par[v]];
            head[par[v]] = v;
        }
    }
    int[] tin = new int[n], tout = new int[n], stack = new int[n];
    int[] cur = head.clone();                            // cur[v] = the next child of v to visit
    stack[top++] = root;
    tin[root] = timer++;
    while (top > 0) {
        int v = stack[top - 1];
        if (cur[v] != -1) {                              // go down to the next child
            int c = cur[v];
            cur[v] = next[c];
            tin[c] = timer++;
            stack[top++] = c;
        } else {                                         // every child is finished
            tout[v] = timer - 1;
            top--;
        }
    }
    return new int[][]{tin, tout};
}
```

:::theorem{#thm-18-interval} A subtree is an interval of entry times
For every vertex *v*, the vertices of the subtree of *v* receive exactly the entry times tin[*v*], tin[*v*] + 1, …, tout[*v*]. Hence *u* is an ancestor of *w* exactly when tin[*u*] ≤ tin[*w*] ≤ tout[*u*].
:::

:::proof
The stack always holds the path from the root to its top vertex, because every push puts a child of the current top. Consider the time between the push of *v* and its pop. Every vertex pushed in that time is pushed while *v* is still on the stack, so it is a child of a vertex on the stack at or above *v*: a descendant of *v*. Conversely, *v* is popped only when `cur[v]` = −1, that is, after all its children have been pushed, and each child *c* is popped (above *v*) only after all of *c*'s children were pushed; by induction on height, every descendant of *v* is pushed before *v* is popped. Each vertex is pushed once, and the timer advances by one per push. So the subtree of *v* receives consecutive entry times starting at tin[*v*], and the last one is `timer - 1` at the moment *v* is popped, which the code stores in tout[*v*]. The ancestor test follows: *w* is in the subtree of *u* exactly when its entry time lies in *u*'s interval.
:::

### Worked example: the longest path in a general tree

@thm-18-diameter carries over to vertices with any number of children: a path still has a unique highest vertex *v*, and from *v* it can enter at most two children's subtrees. So the longest path with highest vertex *v* uses the **two longest chains** that start at different children. Writing down[*v*] for the number of edges on the longest downward path from *v*, a child *c* offers a chain of length down[*c*] + 1 measured from *v*, and the best bend at *v* is the sum of the two largest offers (0 for each missing one).

```java {#lst-18-longest} Longest path in a general tree: the two longest child chains
// down[v] = edges on the longest downward path from v. The longest path bends at its
// highest node v and uses v's two longest child chains. Children are finished first.
static int longestPath(int[] par, int[] order) {
    int n = par.length, best = 0;
    int[] down = new int[n], top1 = new int[n], top2 = new int[n];   // two best (down[c] + 1)
    for (int i = n - 1; i >= 0; i--) {
        int v = order[i];
        down[v] = top1[v];
        best = Math.max(best, top1[v] + top2[v]);         // the path that bends at v
        int p = par[v];
        if (p == -1) continue;
        int chain = down[v] + 1;                          // v's chain extended to p
        if (chain > top1[p]) {
            top2[p] = top1[p];
            top1[p] = chain;
        } else if (chain > top2[p]) {
            top2[p] = chain;
        }
    }
    return best;
}
```

Keeping only the two largest offers instead of sorting all of them makes each vertex O(1) work, so the whole loop is O(*n*), and it never recurses.

## Lowest common ancestors by binary lifting {#sec-18-lifting}

The recursive LCA of @lst-18-lca answers one query in O(*n*). With a parent array and depths there is an equally simple method: lift the deeper vertex until both have the same depth, then lift both one step at a time until they meet. That costs O(depth) per query, which on a chain of 10⁵ vertices with 10⁵ queries is 10¹⁰ steps. Binary lifting makes each step a jump of a power of two.

:::definition{#def-18-lifting} Binary-lifting table
For a rooted tree, [[binary lifting]] stores up[*k*][*v*], the 2ᵏ-th ancestor of *v*, for 0 ≤ *k* < LOG, where LOG is chosen so that 2<sup>LOG</sup> ≥ *n*. Jumps that would pass the root stop at the root: the root's parent is taken to be the root itself.
:::

Write anc(*v*, *j*) for the vertex *j* steps above *v*, stopping at the root if *v* has fewer than *j* ancestors above it. Going up *a* steps and then *b* more is the same as going up *a* + *b* steps (stopping at the root in both cases), so anc(anc(*v*, *a*), *b*) = anc(*v*, *a* + *b*).

:::lemma{#lem-18-doubling} The doubling rule
up[0][*v*] is the parent of *v* (the root for the root), and for *k* ≥ 1, up[*k*][*v*] = up[*k* − 1][ up[*k* − 1][*v*] ].
:::

:::proof
up[*k*][*v*] = anc(*v*, 2ᵏ) = anc(anc(*v*, 2ᵏ⁻¹), 2ᵏ⁻¹) by the composition rule with *a* = *b* = 2ᵏ⁻¹, and the right-hand side is up[*k* − 1] applied twice.
:::

The rule reads row *k* − 1 at the vertex *x* = up[*k* − 1][*v*], an ancestor of *v*. If the vertices are processed in BFS order, every ancestor of *v* comes earlier (@thm-18-order), so all rows of *x* are already filled when *v* needs them. That is why the constructor below loops over `order`, filling all LOG rows of each vertex at once.

```java {#lst-18-lifting} Binary lifting: k-th ancestor, LCA and distance (handbook template)
// Binary lifting: up[k][v] = the 2^k-th ancestor of v. O(n log n) build, O(log n) per query.
static final class LCA {
    final int LOG;
    final int[][] up;
    final int[] depth;

    LCA(int[] par, int[] order) {                        // par[root] = -1, order = BFS order
        int n = par.length, lg = 1;
        while ((1 << lg) < n) lg++;
        LOG = lg;
        up = new int[LOG][n];
        depth = new int[n];
        for (int v : order) {                            // parents are filled in first
            up[0][v] = par[v] == -1 ? v : par[v];        // the root points to itself
            depth[v] = par[v] == -1 ? 0 : depth[par[v]] + 1;
            for (int k = 1; k < LOG; k++) up[k][v] = up[k - 1][up[k - 1][v]];
        }
    }

    int kthAncestor(int v, int k) {                      // -1 if v has fewer than k ancestors
        if (k > depth[v]) return -1;
        for (int b = 0; b < LOG; b++) if (((k >> b) & 1) == 1) v = up[b][v];
        return v;
    }

    int lca(int a, int b) {
        if (depth[a] < depth[b]) {
            int t = a;
            a = b;
            b = t;
        }
        a = kthAncestor(a, depth[a] - depth[b]);          // same depth first
        if (a == b) return a;
        for (int k = LOG - 1; k >= 0; k--) {
            if (up[k][a] != up[k][b]) {                  // jump while still below the LCA
                a = up[k][a];
                b = up[k][b];
            }
        }
        return up[0][a];
    }

    int dist(int a, int b) {
        return depth[a] + depth[b] - 2 * depth[lca(a, b)];
    }
}
```

The only change from the handbook card is that the constructor receives the BFS order as a parameter (from @lst-18-bfs or @lst-18-arrays) instead of computing it.

:::theorem{#thm-18-kth} The k-th ancestor from binary digits
If *k* ≤ depth[*v*], `kthAncestor(v, k)` returns the vertex exactly *k* steps above *v*.
:::

:::proof
Write *k* as a sum of distinct powers of two, one for each set bit *b*. The loop jumps up 2ᵇ steps for each set bit, using up[*b*]. The jumps together cover *k* ≤ depth[*v*] steps, so no jump reaches past the root and none of them is cut short. By the composition rule, the consecutive jumps add up to a single climb of *k* steps.
:::

:::theorem{#thm-18-lifting} Correctness of the LCA query
`lca(a, b)` returns the lowest common ancestor of *a* and *b*.
:::

:::proof
Let *a* be the deeper vertex. The LCA *L* of *a* and *b* has depth at most depth[*b*], so it is an ancestor of the vertex depth[*a*] − depth[*b*] steps above *a*; replacing *a* by that vertex does not change the LCA. Now *a* and *b* have the same depth *D*. If they are equal, that vertex is the LCA.

Otherwise, at any moment of the loop, let *t* ≥ 1 be the current distance from *a* (and from *b*, which has the same depth) up to *L*. For *j* < *t*, the vertices *j* steps above *a* and above *b* are different (otherwise they would be a common ancestor deeper than *L*); for *j* ≥ *t* they are equal, since both are *j* − *t* steps above *L* (or both the root). So the test `up[k][a] != up[k][b]` holds exactly when 2ᵏ < *t*, that is, 2ᵏ ≤ *t* − 1, and a jump keeps *a* ≠ *b* and lowers *t* − 1 by 2ᵏ. The loop tries *k* = LOG − 1 down to 0 and jumps whenever 2ᵏ fits into the current *t* − 1, so it subtracts the binary digits of the initial *t* − 1 from largest to smallest (that value is below *n* ≤ 2<sup>LOG</sup>, so every digit is available). After the loop *t* − 1 = 0: *a* and *b* are distinct children of *L*, and `up[0][a]` is *L*.
:::

:::theorem{#thm-18-dist} Distance through the LCA
For vertices *a*, *b* with lowest common ancestor *L*, the path between them has depth[*a*] + depth[*b*] − 2 · depth[*L*] edges.
:::

:::proof
Going up from *a* to *L* takes depth[*a*] − depth[*L*] edges, and going down from *L* to *b* takes depth[*b*] − depth[*L*]. The two pieces share only *L*: below *L*, *a* and *b* lie in different children's subtrees (or one of the pieces is empty). So their union is a simple path, which by @thm-18-unique is *the* path from *a* to *b*.
:::

### Cost and memory

Building fills LOG entries for each of *n* vertices: O(*n* log *n*) time. A *k*-th ancestor query makes at most LOG jumps, and an LCA query at most 2 · LOG, so each is O(log *n*). For *n* = 10⁵ the loop `while ((1 << lg) < n)` gives LOG = 17, and the table holds 17 · 10⁵ = 1.7 · 10⁶ `int`s, about 6.8 MB.

:::java
The table is `int[LOG][n]`, not `int[n][LOG]`. Java stores a 2-D array as an array of row objects, each with its own header of about 16 bytes. Seventeen rows of length 10⁵ cost almost nothing extra; 10⁵ rows of length 17 add about 1.6 MB of headers, 10⁵ allocations and an extra pointer step on every access. Put the short dimension first.
:::

LeetCode 1483 (Kth Ancestor of a Tree Node) asks exactly for `kthAncestor` on a fixed tree with many queries, which is what the table is built for.

## Path queries from root prefixes {#sec-18-paths}

Binary lifting finds the LCA; combined with values accumulated along root paths, it answers questions about whole paths. The idea is the prefix sum of Chapter 2, laid along every root-to-vertex path at once.

Let every edge (*v*, par[*v*]) have a weight *w*[*v*], and define the [[root prefix]] *F*[*v*] as the sum of the weights on the path from the root to *v* (*F*[root] = 0). It is computed in one forward pass over the BFS order: *F*[*v*] = *F*[par[*v*]] + *w*[*v*].

:::theorem{#thm-18-prefix} Path values from root prefixes
For vertices *u*, *v* with lowest common ancestor *L*, the sum of the edge weights on the path between *u* and *v* is *F*[*u*] + *F*[*v*] − 2 · *F*[*L*]. If the values sit on vertices instead, with *S*[*v*] the sum of the values from the root to *v* inclusive, the path sum is *S*[*u*] + *S*[*v*] − 2 · *S*[*L*] + val[*L*].
:::

:::proof
*L* is an ancestor of *u*, so the root-to-*u* path is the root-to-*L* path followed by the *L*-to-*u* path, and *F*[*u*] = *F*[*L*] + (weights from *L* down to *u*). Likewise for *v*. By the proof of @thm-18-dist the path between *u* and *v* is the union of the *L*-to-*u* and *L*-to-*v* pieces, so its weight is (*F*[*u*] − *F*[*L*]) + (*F*[*v*] − *F*[*L*]). With vertex values, *S*[*u*] − *S*[*L*] and *S*[*v*] − *S*[*L*] both exclude *L*'s own value, which belongs to the path once, so it is added back.
:::

The same works for **counts**. If each edge has one of a few colours or weights 1..*W*, keep one prefix per colour, *C*[*v*][*c*] = the number of edges of colour *c* on the root path; applying the theorem to the indicator "this edge has colour *c*" gives the count of colour *c* on any path as *C*[*u*][*c*] + *C*[*v*][*c*] − 2 · *C*[*L*][*c*]. The memory is *W* · *n* integers, which for *W* = 26 and *n* = 10⁴ is 2.6 · 10⁵.

:::example{#ex-18-paths} Counting edge weights on a path

C[0] = [0, 0, 0]   C[8] = [0, 1, 1]
```

For the path 9–6, *L* = 3: weight 1 appears 3 + 3 − 2 · 2 = 2 times, weight 2 appears 2 + 0 − 0 = 2 times and weight 3 never. Directly: the path 9–7–5–3–6 has edges of weights 2, 1, 2, 1. For the path 8–6, *L* = 0 and the counts are simply *C*[8] + *C*[6] = [3, 1, 1], the five edges 8–2–0–1–3–6.
:::

## Subtree sizes as answers {#sec-18-sizes}

Many tree questions that look global are sums over edges, and the contribution of an edge depends only on how many vertices lie on each side of it. Removing the edge (*v*, par[*v*]) splits the tree into the subtree of *v*, with size[*v*] vertices, and the rest, with *n* − size[*v*].

:::theorem{#thm-18-pairs} The sum of all distances
The sum of dist(*a*, *b*) over all unordered pairs {*a*, *b*} of vertices equals Σ size[*v*] · (*n* − size[*v*]) over all non-root vertices *v*.
:::

:::proof
dist(*a*, *b*) is the number of edges on the path between them, so the total counts pairs (pair, edge) with the edge on the pair's path. The edge (*v*, par[*v*]) lies on the path between *a* and *b* exactly when one of them is in the subtree of *v* and the other is not: if both are inside, their path stays inside the subtree (it goes through their LCA, which is in the subtree), and if both are outside it never enters the subtree. There are size[*v*] · (*n* − size[*v*]) such pairs. Summing over edges counts every (pair, edge) once.
:::

```java {#lst-18-pairs} Sum of all pairwise distances from subtree sizes
// Edge (v, par[v]) lies on the path between a and b exactly when one of them is inside
// v's subtree, so it is used by size[v] * (n - size[v]) pairs.
static long sumOfAllDistances(int[] par, int[] order) {
    int n = par.length;
    int[] size = new int[n];
    Arrays.fill(size, 1);
    long total = 0;
    for (int i = n - 1; i > 0; i--) {                    // children before parents
        int v = order[i];
        total += (long) size[v] * (n - size[v]);
        size[par[v]] += size[v];
    }
    return total;
}
```

For the tree of @fig-18-rooted the five edges contribute 3 · 3 = 9 (edge 1–0), 2 · 4 = 8 (edge 2–0) and 1 · 5 = 5 for each of the three leaf edges, 32 in total. The cast to `long` matters: for *n* = 10⁵ a single product can reach 2.5 · 10⁹, and the total reaches about 1.7 · 10¹⁴ on a chain.

The same edge-by-edge view solves LeetCode 2477 (Minimum Fuel Cost to Report to the Capital). Every representative in the subtree of *v* must cross the edge from *v* to its parent, and a car carries at most *seats* people, so at least ⌈size[*v*] / *seats*⌉ cars cross that edge. That is the key observation; showing that the bound can be met at every edge simultaneously, and summing it, is the rest of the problem.

## Summary

- A tree with *n* vertices has *n* − 1 edges and exactly one path between any two vertices; a connected graph with *n* − 1 edges is a tree.
- For recursion on `TreeNode`, decide what one node returns to its parent (height, gain, "p or q is below me") and record paths that bend at the node in a separate holder. Every path has a unique highest node.
- In the maximum path sum, a branch is used only if its gain is positive, and `best` starts at `Integer.MIN_VALUE`.
- The recursive LCA is correct because of a precise statement of what it returns for every subtree, including the case where one node is an ancestor of the other.
- On parent arrays with up to 10⁵ vertices, never recurse. Build the BFS order: walking it backwards finishes children before parents (sizes, heights, DP), forwards finishes parents first (depths, prefixes, lifting rows).
- An explicit-stack DFS gives entry and exit times; a subtree is the interval tin[*v*]..tout[*v*].
- Binary lifting stores up[*k*][*v*] = up[*k* − 1][up[*k* − 1][*v*]], built in BFS order: O(*n* log *n*) build, O(log *n*) for *k*-th ancestor, LCA and distance = depth[*a*] + depth[*b*] − 2 · depth[LCA].
- Path sums and counts are root prefixes combined at the LCA; many global sums are per-edge contributions that depend only on size[*v*] and *n* − size[*v*].

## Review questions

1. A parent array of length *n* has exactly one entry −1, and every other entry is a valid vertex number. Must it describe a tree? Use @thm-18-unique to say exactly what must be checked, and give a counterexample with *n* = 3.
2. In @lst-18-diameter, why does `gain` return `node.val + Math.max(l, r)` while it records `node.val + l + r` in `best`?
3. In the recursive LCA, suppose *q* lies in the subtree of *p*. What does the call at *p* return, and why is it correct that the subtree of *p* is never searched?
4. Would walking the entry-time order of @lst-18-euler backwards also compute subtree sizes correctly? Why?
5. For *n* = 10⁵, what value of LOG does the `LCA` constructor choose, and how much memory does the table use? Why is LOG = 17 enough for every query?
6. Why must the rows of `up` be filled in BFS order? Give a parent array for which filling them in index order 0, 1, …, *n* − 1 gives a wrong entry.
7. In the second query of @ex-18-lifting, which jumps does the final loop of `lca` make, and how does that match the proof of @thm-18-lifting?
8. For a chain of *n* vertices (par[*v*] = *v* − 1), give a formula for the sum of all pairwise distances using @thm-18-pairs, and evaluate it for *n* = 4.
9. In @thm-18-prefix, why is val[*L*] added back for vertex values but nothing is added back for edge weights?

:::answers
1. Not necessarily. Each non-root vertex contributes one edge to its parent, so there are *n* − 1 edges, and by @thm-18-unique the graph is a tree exactly when it is connected, which you check by a BFS from the root that must reach all *n* vertices. Counterexample: par = [−1, 2, 1]. Vertices 1 and 2 point at each other, forming a cycle, and vertex 0 is cut off; the BFS from 0 reaches only one vertex.
2. A path can bend only at its highest node. The value returned to the parent describes a path that continues upwards through the parent, so it may use at most one of the node's two branches. The value recorded in `best` describes a path whose highest node is this node, which may use both.
3. It returns *p* immediately, without looking below it. By @def-18-lca the LCA of *p* and a descendant *q* is *p* itself, so nothing below *p* can change the answer; @thm-18-lcarec covers this case.
4. Yes. In a depth-first order every vertex also comes after its parent (a child is pushed while its parent is on the stack, after the parent's entry), so the backward walk again reaches children before parents. The proof of the size loop needs only that property.
5. LOG = 17, because 2¹⁶ = 65,536 < 10⁵ ≤ 131,072 = 2¹⁷. The table has 17 · 10⁵ `int`s, about 6.8 MB. A jump distance is at most the depth, which is at most *n* − 1 < 2¹⁷, so its binary digits fit in bits 0..16.
6. up[*k*][*v*] reads row *k* − 1 at an ancestor of *v*, which must already be filled. With par = [1, −1, 1] the root is 1. In index order, vertex 0 is processed first, and up[1][0] = up[0][up[0][0]] = up[0][1] reads the root's row before it has been filled, so it reads 0 instead of 1. (`int` arrays start at 0.) The BFS order [1, 0, 2] fills vertex 1 first.
7. After lifting, *a* = 3 and *b* = 8 at depth 2, and the LCA 0 has depth 0, so *t* = 2 and *t* − 1 = 1 = 2⁰. The loop finds equal entries for *k* = 3, 2, 1 and different ones for *k* = 0, so it jumps once, to *a* = 1 and *b* = 2, and returns up[0][1] = 0. The jumps are the binary digits of *t* − 1, as in the proof.
8. Rooted at vertex 0, the subtree of vertex *v* is {*v*, …, *n* − 1}, of size *n* − *v*, so the sum is Σ (*n* − *v*) · *v* over *v* = 1..*n* − 1 = Σ *k*(*n* − *k*) for *k* = 1..*n* − 1. For *n* = 4: 1 · 3 + 2 · 2 + 3 · 1 = 10. Directly, the six pairs have distances 1, 2, 3, 1, 2, 1, which also sum to 10.
9. With edge weights, *F*[*u*] − *F*[*L*] and *F*[*v*] − *F*[*L*] are exactly the edges of the two pieces, and the pieces share no edge. With vertex values, both differences exclude the value of *L*, yet *L* is a vertex of the path, so its value must be counted once.
:::
