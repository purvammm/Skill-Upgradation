A greedy algorithm builds its answer one decision at a time and never takes a decision back. It is the fastest kind of algorithm to write and the easiest to get wrong: many natural greedy rules are false, and they often pass the samples. This chapter is about telling the two apart.

Almost every greedy algorithm in an exam starts with a sort, because the sort decides the order in which decisions are made. So the chapter starts with sorting in Java: what `Arrays.sort` does, how to write comparators that cannot overflow or contradict themselves, and what can go wrong on adversarial inputs. The second section gives the tool for proving a greedy correct, the **exchange argument**, and the habit that catches false greedies before they cost marks: checking against a brute force on small inputs.

The rest of the chapter applies both to the problems that appear most often in practice: intervals. Merging them, keeping as many disjoint ones as possible, and packing all of them into the fewest rooms are three different questions with three different sort keys. The chapter ends with a custom order (the Largest Number problem, an Infosys repeat) and with two greedy invariants that are not about intervals at all.

## Sorting in Java {#sec-4-sorting}

### Two algorithms behind one method name

`Arrays.sort` chooses its algorithm by the element type.

- **Primitive arrays** (`int[]`, `long[]`, `double[]`, `char[]`) are sorted with **dual-pivot quicksort**, a quicksort that splits the range around two pivots into three parts. Its average time is O(*n* log *n*) and it is very fast in practice: sorting 10⁶ random `int` values took between 11 and 91 ms over three runs on this book's machine.
- **Object arrays** (`Integer[]`, `String[]`, `int[][]`) and `List.sort` / `Collections.sort` use **TimSort**, a merge sort that first detects runs that are already sorted. It is O(*n* log *n*) in the worst case and O(*n*) on input that is already sorted. Boxing and comparator calls make it slower: 10⁶ `Integer` values took 410–570 ms, and 10⁶ `int[]` pairs sorted by a lambda comparator 470–700 ms.

:::definition{#def-4-stable} Stable sort
A sort is [[stable|stable sort]] if elements that compare equal keep their original relative order.
:::

TimSort is stable, and Java guarantees it for every object sort. Quicksort is not a stable algorithm, but for primitives it cannot matter: two equal `int` values are indistinguishable. Stability matters when you sort records by one field and want ties to stay in input order. Sorting (Asha, 70), (Ben, 85), (Chen, 70), (Dev, 85), (Esi, 60) by score gives Esi, Asha, Chen, Ben, Dev: Asha stays before Chen and Ben before Dev.

### The worst case of quicksort, and a precaution

Quicksort is fast because its pivots usually split the range into balanced parts. For every fixed pivot rule there are inputs on which the splits are badly unbalanced, and then quicksort takes Θ(*n*²) time. The dual-pivot quicksort of Java 8 has no defence against such inputs, and contest problems have used crafted "anti-quicksort" tests to make `Arrays.sort(int[])` time out. Since JDK 14 the implementation switches to heap sort when the partitioning becomes too deep, which caps the worst case at O(*n* log *n*). You do not know which JDK an exam uses, so when the input could be adversarial, shuffle first: a random order makes the bad case astronomically unlikely, whatever the pivot rule.

```java {#lst-4-shuffle} Shuffle before sorting primitives (a precaution against crafted inputs)
static void shuffleThenSort(int[] a) {
    Random rnd = new Random();
    for (int i = a.length - 1; i > 0; i--) {                         // Fisher-Yates shuffle
        int j = rnd.nextInt(i + 1);
        int t = a[i]; a[i] = a[j]; a[j] = t;
    }
    Arrays.sort(a);
}
```

The shuffle costs O(*n*) and is cheap insurance: shuffling and sorting 10⁶ values took 35–74 ms. The alternative, sorting an `Integer[]` so that TimSort's guarantee applies, costs about five times as much.

### Why O(n log n) is the best a comparison sort can do

Both algorithms compare elements and move them according to the results. No algorithm of that kind can beat *n* log *n* by more than a constant factor.

:::theorem{#thm-4-lower} Lower bound for comparison sorting
Any algorithm that sorts *n* distinct values using only comparisons needs at least log₂(*n*!) comparisons on some input, and log₂(*n*!) ≥ (*n*/2) log₂(*n*/2).
:::

:::proof
Run the algorithm on the *n*! orderings of *n* distinct values. Each comparison has two outcomes, so after *c* comparisons the algorithm can be in at most 2ᶜ different states. Two orderings that lead to the same sequence of outcomes are rearranged in the same way, so at most one of them ends sorted. Hence 2ᶜ ≥ *n*!, that is *c* ≥ log₂(*n*!). For the estimate, the product *n*! = 1 · 2 ⋯ *n* contains at least *n*/2 factors that are each at least *n*/2, so log₂(*n*!) is at least *n*/2 times log₂(*n*/2).
:::

Sorting is therefore Θ(*n* log *n*), and a greedy algorithm that sorts once and then makes one O(1) or O(log *n*) decision per element costs Θ(*n* log *n*) in total.

### Comparators

A comparator `(x, y) -> ...` must return a negative number when *x* goes first, a positive number when *y* goes first and 0 for a tie. It must also be **consistent**: if it says *x* before *y* and *y* before *z*, it must say *x* before *z*. Two rules prevent almost every comparator bug.

1. **Never subtract.** `(x, y) -> x[0] - y[0]` overflows when the values differ by more than 2³¹ − 1 (Chapter 1 showed 2 · 10⁹ − (−2 · 10⁹) = −294,967,296) and then reports the wrong order. Use `Integer.compare` and `Long.compare`.
2. **Break ties explicitly** when the order of ties matters, with a second key.

```java {.fragment}
int[][] iv = {{5, 9}, {1, 4}, {5, 6}};
Arrays.sort(iv, (x, y) -> Integer.compare(x[1], y[1]));             // by end: {1,4}, {5,6}, {5,9}
Arrays.sort(iv, (x, y) -> x[0] != y[0] ? Integer.compare(x[0], y[0])
                                       : Integer.compare(y[1], x[1])); // start up, then end down
Integer[] idx = {0, 1, 2};
int[] key = {30, 10, 20};
Arrays.sort(idx, (p, q) -> Integer.compare(key[p], key[q]));         // indices in key order: 1, 2, 0
```

The last two lines show the standard way to sort while remembering original positions: sort an array of indices by the values they point to.

:::pitfall
An inconsistent comparator can make TimSort throw `IllegalArgumentException: Comparison method violates its general contract!`, usually only on large inputs. The cause is a comparator that is not transitive or that returns different answers for the same pair, for example one that compares `double` values with subtraction and casts to `int`.
:::

## What makes a greedy algorithm correct {#sec-4-greedy}

:::definition{#def-4-greedy} Greedy algorithm
A [[greedy algorithm]] builds a solution by a sequence of choices, each made by a fixed local rule ("take the interval that ends first", "take the largest coin") and never revised.
:::

A greedy is correct when two properties hold.

- **[[Greedy-choice property]]**: some optimal solution contains the greedy's first choice.
- **Optimal substructure**: after the first choice, what remains is a smaller instance of the same problem, and an optimal solution of it, combined with the first choice, is optimal for the whole.

Given both, induction on the size of the instance proves the greedy optimal. The second property is usually obvious from the problem. The first is where the work is, and the standard tool for it is the exchange argument.

:::keyidea
**[[Exchange argument]].** Take any optimal solution *O*. If it does not agree with the greedy's choice, change *O* by exchanging one of its elements for the greedy's choice, and show that the result is still feasible and no worse. Then an optimal solution that agrees with the greedy exists.
:::

The same idea works for orderings: if an optimal order has two neighbours that the greedy would put the other way round, show that swapping them never makes the answer worse. Repeated swaps then turn any optimal order into the greedy's order without losing anything (@sec-4-largest uses exactly this).

### Testing a greedy before trusting it

A greedy rule that sounds right is often wrong. For "choose as many pairwise disjoint intervals as possible", three plausible rules are: take the interval that starts first, take the shortest, take the one that ends first. Only the third is correct, and a brute force over all subsets finds counterexamples to the others in seconds.

```java {#lst-4-brute} Brute force for interval scheduling: try every subset (n <= 20)
static int bruteMaxNonOverlap(int[][] iv) {          // touching ends allowed, as in [1,2] and [2,3]
    int n = iv.length, best = 0;
    for (int m = 0; m < (1 << n); m++) {              // m = the subset, one bit per interval
        boolean ok = true;
        for (int i = 0; i < n && ok; i++)
            for (int j = i + 1; j < n && ok; j++)
                if ((m >> i & 1) == 1 && (m >> j & 1) == 1
                        && iv[i][0] < iv[j][1] && iv[j][0] < iv[i][1]) ok = false;   // overlap
        if (ok) best = Math.max(best, Integer.bitCount(m));
    }
    return best;
}
```

Comparing a rule with this brute force exposes it at once. Two of the smallest counterexamples, both checked by running the greedy and the brute force:

- **Earliest start** on [1, 10], [2, 3], [4, 5]: it takes [1, 10] and then nothing else fits, so 1. The optimum is 2.
- **Shortest first** on [1, 5], [4, 7], [6, 10]: it takes [4, 7] (length 3), which overlaps both others, so 1. The optimum is 2.

:::tip
Before you submit a greedy, write the brute force (it takes five minutes) and compare the two on a few thousand random inputs of size 5–10. If they disagree, the brute force hands you a small counterexample. Chapter 9 turns this into a reusable stress tester. A brute force that is correct also scores the small tests on its own.
:::

## Merging intervals {#sec-4-merge}

LeetCode 56 (Merge Intervals) asks to merge all overlapping intervals and return the disjoint blocks that remain. Here intervals are closed and touching ones merge: [1, 3] and [3, 5] become [1, 5]. The key is to sort by **start**.

```java {#lst-4-merge} Merging overlapping intervals (LeetCode 56)
// Merge overlapping intervals {start, end}
static int[][] merge(int[][] iv) {
    Arrays.sort(iv, (x, y) -> Integer.compare(x[0], y[0]));    // sort by start
    List<int[]> out = new ArrayList<>();
    for (int[] cur : iv) {
        int[] last = out.isEmpty() ? null : out.get(out.size() - 1);
        if (last != null && cur[0] <= last[1]) last[1] = Math.max(last[1], cur[1]);
        else out.add(new int[]{cur[0], cur[1]});
    }
    return out.toArray(new int[0][]);
}
```

:::theorem{#thm-4-merge} Correctness of the merge
After processing the first *i* intervals in order of start, `out` is the list of maximal merged blocks of those intervals, sorted by start, and the last block has the largest start.
:::

:::proof
By induction on *i*; for *i* = 0 the list is empty. Let the next interval be *c* = [*s*, *e*]. Every interval processed so far has start ≤ *s*. Every block except the last ends before the last block starts (they are disjoint and sorted), and the last block starts at a value ≤ *s*, so every earlier block ends before *s*: none of them can touch *c*. So *c* either overlaps the last block, when *s* ≤ last end, and the two merge into one block whose end is the larger of the two ends; or it overlaps nothing processed so far and starts a new block, which has the largest start. Either way the list again consists of the maximal blocks in order.
:::

The sort costs O(*n* log *n*) and the loop O(*n*), so the total is O(*n* log *n*) with O(*n*) memory for the output.

:::example{#ex-4-merge} Tracing the merge
Take [5, 7], [1, 3], [2, 4], [6, 8], [10, 12], [12, 13]. After sorting by start:

```trace

[1, 3]     new block    [1,3]
[2, 4]     extend       [1,4]
[5, 7]     new block    [1,4] [5,7]
[6, 8]     extend       [1,4] [5,8]
[10, 12]   new block    [1,4] [5,8] [10,12]
[12, 13]   extend       [1,4] [5,8] [10,13]      (touching ends merge)
```
:::

If the statement says that touching intervals do **not** merge, the test becomes `cur[0] < last[1]`. That one character is the most common difference between interval problems, so read the statement for it every time.

## Interval scheduling: keep the most {#sec-4-schedule}

Given *n* intervals, choose as many as possible so that no two overlap. With half-open intervals [*s*, *e*), or with closed ones where touching ends are allowed, [1, 2] and [2, 3] can both be chosen. The correct greedy is "always take the interval that **ends** first among those that still fit".

```java {#lst-4-schedule} The most non-overlapping intervals: sort by end
// Most intervals you can keep with no overlap (touching ends allowed): sort by END
static int maxNonOverlapping(int[][] iv) {
    Arrays.sort(iv, (x, y) -> Integer.compare(x[1], y[1]));
    int count = 0;
    long end = Long.MIN_VALUE;
    for (int[] cur : iv) {
        if (cur[0] >= end) {
            count++;
            end = cur[1];
        }
    }
    return count;
}
```

:::theorem{#thm-4-schedule} Earliest end is optimal
@lst-4-schedule returns the largest number of pairwise non-overlapping intervals.
:::

:::proof
Let the greedy choose *g*₁, *g*₂, …, *g*ₖ in this order, and let *O* = *o*₁, *o*₂, …, *o*ₘ be any optimal solution sorted by end, so its intervals are disjoint and *o*₁ ends before *o*₂ starts, and so on. *Exchange step.* *g*₁ is an interval with the smallest end overall, so end(*g*₁) ≤ end(*o*₁). Replace *o*₁ by *g*₁ in *O*. The result is still feasible: *o*₂ starts at or after end(*o*₁) ≥ end(*g*₁), so *g*₁ does not overlap *o*₂ or anything later. It still has *m* intervals, so it is optimal and agrees with the greedy's first choice. *Induction.* Remove *g*₁ and every interval that starts before end(*g*₁). The remaining intervals are exactly those compatible with *g*₁, the greedy's later choices *g*₂, …, *g*ₖ are its run on them, and *o*₂, …, *o*ₘ is a feasible choice among them. By induction on the number of intervals, the greedy chooses at least *m* − 1 of them, so *k* ≥ *m*. Since *O* is optimal, *k* = *m*.
:::

The sort is O(*n* log *n*), the scan O(*n*). The variable `end` is a `long` starting at `Long.MIN_VALUE`, so the first interval is always accepted even if its start is `Integer.MIN_VALUE`.

### Removing the fewest, and the closed-endpoint variant

LeetCode 435 (Non-overlapping Intervals) asks for the fewest intervals to **remove** so that the rest do not overlap. Removing a set *R* leaves a non-overlapping set exactly when the kept set *n* − |*R*| is non-overlapping, so the fewest removals is *n* minus the most you can keep. For the eleven intervals above that is 11 − 4 = 7.

When touching endpoints count as overlapping (closed intervals that must not share even a point), the same greedy works with the test changed from `cur[0] >= end` to `cur[0] > end`. This is the key observation for LeetCode 452 (Minimum Number of Arrows to Burst Balloons): one arrow at the end of the earliest-ending balloon bursts every balloon that contains that point, and touching balloons share an arrow.

## Partitioning into the fewest groups {#sec-4-groups}

Now every interval must be kept, and the question is how many groups (meeting rooms, railway platforms) are needed so that the intervals in each group do not overlap. LeetCode 2406 (Divide Intervals Into Minimum Number of Groups) is this question for closed intervals.

:::definition{#def-4-depth} Depth of a set of intervals
The [[depth|depth of intervals]] of a set of intervals is the largest number of them that contain one common point.
:::

:::theorem{#thm-4-depth} Fewest groups equals depth
The fewest groups into which a set of intervals can be split, with no two overlapping intervals in the same group, equals its depth.
:::

:::proof
*Lower bound.* If *d* intervals contain a common point, every two of them overlap, so they need *d* different groups. *Upper bound.* Process the intervals in order of start, and put each into any group whose last interval does not overlap it, opening a new group only when every group's last interval overlaps it. Suppose interval *c* = [*s*, *e*] opens group number *g*. Then each of the *g* − 1 existing groups has a last interval that overlaps *c*; since those intervals started at or before *s*, overlapping *c* means they end at or after *s*, so they all contain the point *s*. Together with *c*, that is *g* intervals containing *s*, so *g* ≤ depth. Every group was opened this way, so the greedy uses at most depth groups.
:::

The proof gives two algorithms: compute the depth directly (only the number is needed), or run the greedy with a heap when the actual assignment is needed.

### Sweeping sorted starts and ends

The depth is reached at some start point, because coverage only increases at starts. The handbook's template sorts the starts and the ends separately and walks through the starts, retiring every interval that ended before the current start.

```java {#lst-4-sweep} Maximum overlap by sweeping sorted starts and ends
// Most intervals covering one point = minimum platforms / meeting rooms.
// Closed intervals: a train that arrives at the minute another leaves needs its own platform.
static int maxOverlap(int[][] iv) {
    int n = iv.length;
    int[] starts = new int[n], ends = new int[n];
    for (int i = 0; i < n; i++) {
        starts[i] = iv[i][0];
        ends[i] = iv[i][1];
    }
    Arrays.sort(starts);
    Arrays.sort(ends);
    int best = 0, busy = 0;
    for (int i = 0, j = 0; i < n; i++) {
        while (j < n && ends[j] < starts[i]) {   // use <= if touching intervals can share
            j++;
            busy--;
        }
        busy++;
        best = Math.max(best, busy);
    }
    return best;
}
```

At the moment interval *i* (in start order) is counted, `busy` is (*i* + 1) minus the number of ends strictly before *s*ᵢ, which is the number of intervals with start ≤ *s*ᵢ, among the first *i* + 1, that are still open at *s*ᵢ. At the last of several equal starts this is exactly the coverage of the point *s*ᵢ, so the maximum over *i* is the depth. Two sorts and one pass: O(*n* log *n*).

### Events and tie-breaking

An equivalent and more flexible [[sweep line]] turns every interval into two **events**, (*s*, +1) and (*e*, −1), sorts them by time and adds them up. The only subtlety is two events at the same time. For closed intervals a start at time *t* overlaps an interval ending at *t*, so **starts must come before ends** at equal times; for half-open intervals (or "a platform freed at minute *t* can be used at minute *t*") ends come first.

```java {#lst-4-events} Maximum overlap with events and an explicit tie-break
static int maxOverlapEvents(int[][] iv) {                           // closed intervals [s, e]
    int n = iv.length;
    int[][] ev = new int[2 * n][];
    for (int i = 0; i < n; i++) {
        ev[2 * i] = new int[]{iv[i][0], +1};                           // start
        ev[2 * i + 1] = new int[]{iv[i][1], -1};                       // end
    }
    Arrays.sort(ev, (x, y) -> x[0] != y[0] ? Integer.compare(x[0], y[0])
                                           : Integer.compare(y[1], x[1]));   // ties: starts first
    int busy = 0, best = 0;
    for (int[] e : ev) {
        busy += e[1];
        best = Math.max(best, busy);
    }
    return best;
}
```

### A heap of end times

To produce the groups themselves, run the greedy of @thm-4-depth with a min-heap holding the last end time of every group. For the next interval in start order, the group whose last interval ended first is the best candidate to reuse: if even that one overlaps, they all do.

```java {#lst-4-heap} Fewest groups with a min-heap of end times (closed intervals)
static int minGroups(int[][] iv) {
    int[][] s = iv.clone();
    Arrays.sort(s, (x, y) -> Integer.compare(x[0], y[0]));          // by start
    PriorityQueue<Integer> ends = new PriorityQueue<>();              // last end of each group
    for (int[] cur : s) {
        if (!ends.isEmpty() && ends.peek() < cur[0]) ends.poll();  // reuse the earliest-freed group
        ends.add(cur[1]);
    }
    return ends.size();
}
```

Each interval costs at most one `poll` and one `add` on a heap of at most depth elements, so the total is O(*n* log *n*). All three methods (sorted starts and ends, events, heap) were compared with a brute force over every assignment of up to 7 intervals to groups, and with direct counting at every integer point, on 20,000 random sets.

## Custom orders: the Largest Number {#sec-4-largest}

LeetCode 179 (Largest Number) gives non-negative integers and asks for the largest number that can be formed by concatenating all of them in some order, returned as a string. Sorting by numeric value fails: for 9 and 90 the larger value 90 should go second, because 990 > 909. Sorting the strings alphabetically in reverse fails too: "121" > "12" alphabetically, but 12121 > 12112, so "12" should go first.

The right comparison looks at the two possible concatenations: put *x* before *y* when *x* + *y* > *y* + *x* as strings. Both concatenations have the same length, so comparing them as strings compares them as numbers.

```java {.fragment}
String[] s = {"12", "121", "9", "90", "0"};
Arrays.sort(s, (x, y) -> (y + x).compareTo(x + y));   // x first when x + y is larger
// s is now 9, 90, 12, 121, 0, which concatenates to "990121210"
```

Is this a legitimate order? A comparator defined by "which concatenation is larger" is not obviously transitive, and TimSort may throw or return garbage if it is not. The following theorem settles it by giving each string a number that the comparator really compares.

:::theorem{#thm-4-order} The concatenation order is a valid order
For a non-empty digit string *x* with numeric value *X*, let *t*(*x*) be 10 to the power of the length of *x* (so *t*("121") = 1000), and let *v*(*x*) = *X* / (*t*(*x*) − 1). Then *x* + *y* > *y* + *x* exactly when *v*(*x*) > *v*(*y*), and *x* + *y* = *y* + *x* exactly when *v*(*x*) = *v*(*y*). Hence the comparator orders strings by decreasing *v*, which is transitive.
:::

:::proof
Appending *y* to *x* shifts *x* left by the length of *y*, so the numeric value of the concatenation *x* + *y* is *X* · *t*(*y*) + *Y*. So *x* + *y* > *y* + *x* as numbers exactly when *X* · *t*(*y*) + *Y* > *Y* · *t*(*x*) + *X*, that is when *X*(*t*(*y*) − 1) > *Y*(*t*(*x*) − 1). Both brackets are positive, so dividing by them gives *X* / (*t*(*x*) − 1) > *Y* / (*t*(*y*) − 1). The same steps with = in place of > give the second statement. Comparing real numbers is transitive, so the comparator is.
:::

The number *v*(*x*) is the value of 0.*xxx*…, the digits of *x* repeated for ever: *v*(9) = 1, *v*(90) = 0.909…, *v*(12) = 0.1212…, *v*(121) = 0.121121…, *v*(0) = 0. The order 9, 90, 12, 121, 0 is exactly decreasing *v*.

:::theorem{#thm-4-largest} Sorting by the concatenation order is optimal
Concatenating the strings in order of decreasing *v* gives the largest possible number.
:::

:::proof
Take any arrangement with two neighbours *x*, *y* in that order and *v*(*x*) < *v*(*y*). Swapping them changes the string *P* + *x* + *y* + *S* into *P* + *y* + *x* + *S*: same length, same prefix and suffix, and the middle part grows because *y* + *x* > *x* + *y* by @thm-4-order. So an optimal arrangement never has such a pair: its *v* values are non-increasing. Any two arrangements with non-increasing *v* differ only in the order inside groups of equal *v*, and swapping two neighbours with equal *v* does not change the string, because then *x* + *y* = *y* + *x*. So every arrangement with non-increasing *v*, including the sorted one, gives the same, optimal, string.
:::

One case remains. If every number is 0, the concatenation is "000…0", but the answer must be "0". Check the first string after sorting: if it is "0", every string is "0". The sort makes O(*n* log *n*) comparisons, each building two strings of length up to twice the longest number. The sort with this comparator matched a brute force over all orders on 5,000 random inputs of up to 6 numbers; writing the rest of LeetCode 179 is left for the problem worksheet.

:::infosys
"Arrange numbers to form the largest number" is an Infosys repeat problem (four reports in the plan's question bank). It is LeetCode 179, with the same comparator and the same all-zeros case.
:::

## Greedy invariants beyond sorting {#sec-4-reach}

Two more greedy patterns are worth knowing because their correctness rests on an invariant that is easy to state and to check.

### Reachability: all values 0..x

Suppose you have coins with positive values and ask which totals can be paid with a subset of them. Process the coins in increasing order and keep *x*, the largest value such that **every** total 0, 1, …, *x* can be paid with the coins used so far.

:::lemma{#lem-4-reach} Extending the reachable range
If every total 0..*x* can be paid with some set of coins and a new coin *c* satisfies *c* ≤ *x* + 1, then every total 0..*x* + *c* can be paid. If instead every remaining coin is larger than *x* + 1 and the coins used so far sum to *x*, the total *x* + 1 can never be paid.
:::

:::proof
For a total *t* ≤ *x*, use the old way. For *x* < *t* ≤ *x* + *c*, the total *t* − *c* lies in 0..*x* because *t* − *c* ≥ *x* + 1 − *c* ≥ 0, so pay *t* − *c* the old way and add *c*. For the second part: any subset paying *x* + 1 cannot use a remaining coin (each is larger than *x* + 1), and the used coins sum to only *x*.
:::

Starting from *x* = 0 and adding the coins in increasing order while *c* ≤ *x* + 1 keeps *x* equal to the sum of the coins used, so the lemma applies at every step. The scan stops at the first coin that is larger than *x* + 1: by the second half of the lemma, *x* + 1 is then the smallest total that cannot be paid, even though the remaining coins can pay many larger totals. Sorting is what makes this work: a coin processed out of order could be larger than *x* + 1 only because a smaller coin had not been added yet.

:::example{#ex-4-reach} Which totals can coins pay?
Coins 1, 2, 5 and 13, in increasing order:

```trace
coin   test           x
 1     1 <= 0 + 1     0 -> 1
 2     2 <= 1 + 1     1 -> 3
 5     5 >  3 + 1     stop: every total 0..3 can be paid, 4 cannot
```

With one more coin of value 4 the scan continues: 1, 2, 4, 5, 13 give *x* = 1, 3, 7, 12, 25, so every total 0..25 can be paid. Adding the single coin *x* + 1 = 4 at the point where the scan stopped extended the range from 3 to 25.
:::

The scan costs O(*n* log *n*) for the sort and O(*n*) after it. This invariant is the key observation of LeetCode 1798 (Maximum Number of Consecutive Values You Can Make). Workbook Chapter 4 uses it for a design exercise: the fewest coins to add so that every total 1..*n* can be paid.

### Constraints from both sides: two passes

Some problems put a constraint between each element and **both** of its neighbours. A single left-to-right pass can only see the left neighbour. The trick is two passes, one per direction, and a proof that the second pass does not break what the first one achieved.

Here is a new example. Given caps *h*[0..*n* − 1] ≥ 0, find the array *b* with 0 ≤ *b*[*i*] ≤ *h*[*i*] and |*b*[*i*] − *b*[*i* + 1]| ≤ 1 that is as large as possible in every position. (Think of terrain that must be levelled so that neighbouring columns differ by at most one, without ever adding material.)

```java {#lst-4-twopass} Two passes: the largest array under caps with neighbours differing by at most 1
static int[] capHeights(int[] h) {                    // largest b <= h with |b[i] - b[i+1]| <= 1
    int n = h.length;
    int[] b = h.clone();
    for (int i = 1; i < n; i++) b[i] = Math.min(b[i], b[i - 1] + 1);       // pass 1: left neighbours
    for (int i = n - 2; i >= 0; i--) b[i] = Math.min(b[i], b[i + 1] + 1);  // pass 2: right neighbours
    return b;
}
```

:::theorem{#thm-4-twopass} The two passes give the pointwise largest feasible array
The array *b* returned by @lst-4-twopass is feasible, and every feasible array *c* satisfies *c*[*i*] ≤ *b*[*i*] for every *i*.
:::

:::proof
Write *L* for the array after pass 1 and *b* for the result. *Feasible.* Pass 2 makes *b*[*i*] ≤ *b*[*i* + 1] + 1 directly. For the other direction, *b*[*i*] = min(*L*[*i*], *b*[*i* + 1] + 1). If the minimum is *b*[*i* + 1] + 1, then *b*[*i* + 1] ≤ *b*[*i*] + 1 trivially. Otherwise *b*[*i*] = *L*[*i*], and *b*[*i* + 1] ≤ *L*[*i* + 1] ≤ *L*[*i*] + 1 = *b*[*i*] + 1, using that pass 2 only lowers values and pass 1 made *L*[*i* + 1] ≤ *L*[*i*] + 1. Values never rise above *h* and never fall below 0, because each is a minimum of non-negative quantities. *Largest.* Let *c* be feasible. By induction from the left, *c*[*i*] ≤ *L*[*i*]: *c*[0] ≤ *h*[0] = *L*[0], and *c*[*i*] ≤ min(*h*[*i*], *c*[*i* − 1] + 1) ≤ min(*h*[*i*], *L*[*i* − 1] + 1) = *L*[*i*]. Then by induction from the right, *c*[*i*] ≤ min(*L*[*i*], *c*[*i* + 1] + 1) ≤ min(*L*[*i*], *b*[*i* + 1] + 1) = *b*[*i*].
:::

For *h* = [3, 0, 4, 6, 5, 1, 3], pass 1 gives [3, 0, 1, 2, 3, 1, 2] and pass 2 gives [1, 0, 1, 2, 2, 1, 2]. Feasibility and maximality were checked against an enumeration of every feasible array on 20,000 random inputs of up to six positions. Both passes are O(*n*).

LeetCode 135 (Candy) is the mirror image: the constraints are lower bounds ("a child with a higher rating than a neighbour gets more candies"), and the smallest feasible array comes from two passes that each take a maximum instead of a minimum.

## Summary

- `Arrays.sort` uses dual-pivot quicksort for primitives (fast, average O(*n* log *n*); quadratic on crafted inputs in Java 8, so shuffle first when that matters) and stable TimSort for objects (O(*n* log *n*) worst case, slower because of boxing).
- No comparison sort beats log₂(*n*!) ≈ *n* log₂ *n* comparisons. Write comparators with `Integer.compare`, never subtraction, and make them consistent.
- A greedy is correct when an exchange argument shows that some optimal solution agrees with its first choice. Test every greedy against a brute force on small inputs; false rules fail within seconds.
- Merge intervals by sorting by start; only the last block can overlap the next interval.
- Keep the most non-overlapping intervals by sorting by **end**; fewest removals = *n* − most kept. Whether touching ends overlap changes `>=` into `>`.
- The fewest groups (rooms, platforms) equals the maximum overlap: a lower bound from one crowded point and a greedy that achieves it. Sweep sorted events with the right tie-break, or keep a min-heap of end times.
- Largest Number sorts by *x* + *y* versus *y* + *x*; it is a valid order because it compares *v*(*x*) = *X*/(*t*(*x*) − 1) with *t*(*x*) = 10 to the length of *x*, and sorting by it is optimal by adjacent exchanges. Handle the all-zeros case.
- "Every total 0..*x* can be paid" extends to 0..*x* + *c* with any coin *c* ≤ *x* + 1; scanning sorted coins finds the smallest total that cannot be paid. Constraints from both neighbours are handled by two passes and a proof that the second keeps the first.

## Review questions

1. Why does stability not matter when sorting an `int[]`, but matter when sorting `int[][]` rows by their first column?
2. A comparator for `long` values is written `(x, y) -> (int) (x - y)`. Give two different reasons why it can sort incorrectly.
3. For interval scheduling, give a counterexample to the rule "take the interval that overlaps the fewest others", or explain why you could not find one quickly. What does this tell you about testing greedies?
4. In the exchange step of @thm-4-schedule, why is the modified solution still feasible after replacing *o*₁ by *g*₁?
5. LeetCode 435 counts [1, 2] and [2, 3] as non-overlapping. What single change to @lst-4-schedule would treat them as overlapping, and what would the fewest removals then be for [1, 2], [2, 3], [3, 4]?
6. Explain why the depth of a set of intervals is a lower bound on the number of rooms, and why the greedy never exceeds it.
7. In @lst-4-events, what goes wrong if equal-time events are sorted with ends first for closed intervals? Give the trains of @ex-4-trains as an example.
8. Using *v*(*x*) from @thm-4-order, order the strings "4", "40", "45" and "7", and write the largest number they form.
9. Coins are [1, 1, 3, 9]. Using @lem-4-reach, what is the largest *x* such that every total 0..*x* can be paid? Which total is the first that cannot?

:::answers
1. Two equal `int` values are indistinguishable, so no output can reveal whether they were swapped. Rows of an `int[][]` with the same first column can differ in other columns, so their relative order is visible; Java's object sort (TimSort) keeps it.
2. The subtraction `x - y` can overflow `long` when the values have opposite signs and large magnitudes, giving the wrong sign. And the cast to `int` keeps only the low 32 bits, so a difference such as 2³² becomes 0 (a false tie) and 2³¹ becomes negative. Use `Long.compare(x, y)`.
3. The rule is wrong, but its counterexamples are larger than the ones in @sec-4-greedy. Take the four disjoint intervals [0, 3], [4, 7], [8, 11], [12, 15], the bridge [6, 9], three copies of [2, 5] and three copies of [10, 13] (11 intervals, touching ends allowed). The bridge overlaps only two others, fewer than any other interval, so the rule takes it first; that removes [4, 7] and [8, 11], and at most one interval from each side can still be added, for 3 in total. The optimum is 4 (the top row). A random comparison with the brute force also found a counterexample with 9 intervals, but none with fewer than 9 within 300,000 tries. The lesson: a rule that survives tiny tests can still be wrong, so prove it with an exchange argument or stress-test it on inputs of size 8–10 as well.
4. *g*₁ has the smallest end of all intervals, so end(*g*₁) ≤ end(*o*₁). Every later interval of *O* starts at or after end(*o*₁), hence at or after end(*g*₁), so none of them overlaps *g*₁. The other intervals of *O* were already pairwise disjoint.
5. Change `cur[0] >= end` to `cur[0] > end`. Then [1, 2] and [2, 3] conflict, and so do [2, 3] and [3, 4]. The greedy keeps [1, 2] and [3, 4], so the fewest removals is 3 − 2 = 1.
6. Intervals containing a common point pairwise overlap, so each needs its own room: rooms ≥ depth. When the greedy opens room *g* for interval [*s*, *e*], each of the other *g* − 1 rooms has a last interval that started no later than *s* and still overlaps [*s*, *e*], so it contains *s*; with the new interval, *g* intervals contain *s*, so *g* ≤ depth.
7. At time 700 the departure of B = [610, 700] would be processed before the arrival of D = [700, 730], so the count would go 2 → 1 → 2 and never reach 3. The method would answer 2, which is wrong for closed intervals: at minute 700 trains B, C and D are all present.
8. *v*(7) = 7/9 ≈ 0.778, *v*(45) = 45/99 ≈ 0.455, *v*(4) = 4/9 ≈ 0.444, *v*(40) = 40/99 ≈ 0.404. Decreasing order: 7, 45, 4, 40, giving 745440.
9. Start with *x* = 0. Coin 1 ≤ 1: *x* = 1. Coin 1 ≤ 2: *x* = 2. Coin 3 ≤ 3: *x* = 5. Coin 9 > 6: stop. So every total 0..5 can be paid and 6 is the first that cannot.
:::
