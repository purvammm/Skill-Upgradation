  - find the next and previous greater or smaller element of every index in O(n) with a stack, and prove the bound by counting pushes and pops;
  - handle circular arrays by scanning the array twice;
  - find the largest rectangle in a histogram by treating each bar as the lowest bar of its rectangle;

A large family of array questions has the same core: for every position, find the nearest position to its right (or left) whose value is larger (or smaller). "How many days until a warmer day?" "How far can this bar extend before a lower bar stops it?" "Where does this element stop being the minimum?" A double loop answers each in O(*n*²). A stack that keeps its values in sorted order answers all of them in O(*n*), and the proof that it does so is one of the cleanest examples of amortised analysis.

The chapter develops the stack once, carefully, and then applies it four ways: to next-greater queries, to the largest rectangle in a histogram, to sums over all subarrays (the contribution technique, which is where most of the subtle bugs live), and to greedy problems that build the smallest possible string. It ends by connecting the stack to the monotonic deque of Chapter 3 and to a tree that the stack builds without trying.

## Next greater element {#sec-7-nge}

:::definition{#def-7-nge} Next and previous greater or smaller element
For an array *a*[0..*n* − 1] and an index *i*, the [[next greater element]] of *i* is the smallest *j* > *i* with *a*[*j*] > *a*[*i*], or "none" (written −1) if no such *j* exists. The previous greater element is the largest *j* < *i* with *a*[*j*] > *a*[*i*]. Next and previous *smaller* elements are defined the same way with <. Each has a non-strict version with ≥ or ≤.
:::

The brute force scans right from each *i* until it finds a larger value: O(*n*²) in the worst case, for example on a decreasing array. The fast method rests on one observation about which indices are still "waiting" for their answer.

Scan from left to right. After reading *a*[0..*i* − 1], call an index *j* < *i* **waiting** if no index between *j* and *i* holds a value greater than *a*[*j*]: its next greater element, if any, is at *i* or later. Take two waiting indices *j* < *k*. Since *k* lies between *j* and *i* and *j* is waiting, *a*[*k*] ≤ *a*[*j*]. So the values of the waiting indices, read from left to right, never increase. When *a*[*i*] arrives, the waiting indices it answers are those with *a*[*j*] < *a*[*i*], and because the values are sorted, these are exactly the most recent waiting indices. A stack holds the waiting indices with the most recent on top.

:::definition{#def-7-stack} Monotonic stack
A [[monotonic stack]] is a stack of array indices whose values are sorted from bottom to top (non-increasing for next-greater queries, non-decreasing for next-smaller queries). Before an index is pushed, every index on top that would break the order is popped, and each pop is the moment that index's answer becomes known.
:::

```java {#lst-7-nge} Next strictly greater element of every index (handbook template)
// Index of the next strictly greater element to the right (-1 if none). O(n).
static int[] nextGreater(int[] a) {
    int n = a.length;
    int[] res = new int[n];
    Arrays.fill(res, -1);
    int[] st = new int[n];          // indices whose answer is still unknown; values decrease
    int top = 0;
    for (int i = 0; i < n; i++) {
        while (top > 0 && a[st[top - 1]] < a[i]) res[st[--top]] = i;   // a[i] answers them
        st[top++] = i;
    }
    return res;
}
```

The stack is an `int[]` with a `top` counter: `st[top - 1]` is the top, `st[--top]` pops it, `st[top++] = i` pushes. This is faster than `ArrayDeque<Integer>`, which boxes every index, and much faster than `java.util.Stack`, which synchronises every call.

:::theorem{#thm-7-nge} Correctness of the next-greater stack
After the iteration for index *i* of @lst-7-nge: (a) the stack holds, in increasing order of index from bottom to top, exactly the waiting indices *j* ≤ *i*, those with no value greater than *a*[*j*] in positions *j* + 1..*i*; (b) their values are non-increasing from bottom to top; (c) every index not on the stack has `res` equal to its next greater element. Consequently the method returns the next greater element of every index.
:::

:::proof
By induction on *i*. Before the loop the stack is empty and nothing has been decided, so (a)–(c) hold. Assume they hold after index *i* − 1 and read *a*[*i*].

The indices whose next greater element is *i* are the waiting indices *j* < *i* with *a*[*j*] < *a*[*i*]: such a *j* has no greater value before *i*, by (a), and *a*[*i*] is greater. By (b) these indices form a block at the top of the stack, so the `while` loop pops exactly them and records *i* for each, which keeps (c). Every index that stays has *a*[*j*] ≥ *a*[*i*], so it is still waiting after *i*, and pushing *i* (which is trivially waiting) keeps (a). Since every remaining value is ≥ *a*[*i*], the new top *i* keeps the order (b). After the last index, the indices still on the stack have no greater value anywhere to their right, and their `res` is the initial −1, which is correct.
:::

### Why the stack costs O(n)

The `while` loop can pop many indices in one iteration. On [10, 9, 8, 7, 6, 5, 4, 3, 2, 100] the final 100 pops nine indices at once. A bound of "*n* iterations × up to *n* pops" would suggest O(*n*²). The true cost is much smaller, and the argument is worth knowing by name.

:::definition{#def-7-amortised} Amortised analysis
[[Amortised analysis]] bounds the *total* cost of a sequence of operations, even when single operations can be expensive. The average cost per operation, the total divided by the number of operations, is the amortised cost.
:::

:::lemma{#lem-7-cost} Each index is pushed once and popped at most once
@lst-7-nge performs exactly *n* pushes and at most *n* pops, so its running time is O(*n*) and it uses O(*n*) extra memory.
:::

:::proof
Each iteration of the `for` loop pushes one index, so there are *n* pushes. A pop removes an index that was pushed earlier and is never pushed again, so the number of pops cannot exceed the number of pushes. Every iteration of the `while` loop performs one pop, so the `while` loop runs at most *n* times in total over the whole scan. Everything else is O(1) per index.
:::

In the example above, the nine pops at the end are paid for by the nine pushes before them: the scan as a whole does 10 pushes and 9 pops.

### The four variants

Changing the comparison and the moment you read the answer gives every nearest-element query. Indices are popped when they can no longer be the answer for anyone; what remains under the new index is its answer on the left, and the index that pops an element is that element's answer on the right.

Table: {#tbl-7-variants} One scan from left to right answers each query
| Query | Pop while | Answer is recorded | Stack values, bottom to top |
|---|---|---|---|
| next greater (>) | `a[top] < a[i]` | for each popped index: *i* | non-increasing |
| next smaller (<) | `a[top] > a[i]` | for each popped index: *i* | non-decreasing |
| previous greater (>) | `a[top] <= a[i]` | for *i*: the top after popping | strictly decreasing |
| previous smaller (<) | `a[top] >= a[i]` | for *i*: the top after popping | strictly increasing |

Swapping `<` and `<=` switches between the strict and non-strict versions: popping on `a[top] <= a[i]` gives "next greater or equal" to the popped indices. Scanning from right to left swaps "next" and "previous".

```java {#lst-7-prev} Previous strictly smaller element of every index
// Index of the previous strictly smaller element to the left (-1 if none). O(n).
static int[] prevSmaller(int[] a) {
    int n = a.length;
    int[] res = new int[n];
    int[] st = new int[n];          // values strictly increase from bottom to top
    int top = 0;
    for (int i = 0; i < n; i++) {
        while (top > 0 && a[st[top - 1]] >= a[i]) top--;    // can never answer i or anyone later
        res[i] = top == 0 ? -1 : st[top - 1];
        st[top++] = i;
    }
    return res;
}
```

Why may the popped indices be thrown away? An index *j* with *a*[*j*] ≥ *a*[*i*] lies left of *i*, so for any later index *k*, *i* is closer to *k* than *j* and at least as small. If *j* would answer *k* (*a*[*j*] < *a*[*k*]), so does *i*, and *i* is nearer. So *j* can never again be the *previous* smaller element of anyone.

:::tip
One scan can give two answers at once. In @lst-7-prev, the index *i* that pops *j* is *j*'s next smaller-or-equal element, because *j* was popped exactly when a value ≤ *a*[*j*] arrived. @sec-7-contrib needs precisely this pair: previous strictly smaller on one side, next smaller-or-equal on the other.
:::

### Circular arrays

In a circular array the element after *a*[*n* − 1] is *a*[0], and LeetCode 503 (Next Greater Element II) asks for the next greater *value* in that circular order. The fix is to scan the array twice: let *i* run from 0 to 2*n* − 1 and read *a*[*i* mod *n*].

:::claim{#thm-7-circular} Two laps are enough
If index *j* has a next greater element in circular order, it lies within the next *n* − 1 positions after *j*, all of which are visited after *j* is pushed during the first lap.
:::

:::proof
The circular successors of *j* are *j* + 1, …, *j* + *n* − 1 (taken mod *n*), which are the scan positions *j* + 1..*j* + *n* − 1 ≤ 2*n* − 2. Index *j* is pushed at scan position *j* < *n*, and the argument of @thm-7-nge applies to the doubled sequence, so *j* is popped by the first of those positions with a greater value.
:::

Push only during the first lap (*i* < *n*); in the second lap the indices only answer waiting ones. For *a* = [5, 3, 4, 1, 2] the circular next greater values are [−1, 4, 5, 2, 5]: the 4 answers the 2 only by wrapping round, and 5, the maximum, has no answer. Turning @lst-7-nge into this version takes three small edits, which are left for the problem itself.

## Worked example: daily temperatures {#sec-7-daily}

LeetCode 739 (Daily Temperatures) gives daily temperatures and asks, for each day, how many days you must wait for a warmer one (0 if none). That is the next strictly greater element, reported as a distance: answer[*j*] = nge(*j*) − *j*, or 0. The only change to @lst-7-nge is what is stored when *j* is popped by *i*.

## Largest rectangle in a histogram {#sec-7-hist}

A histogram is a row of bars of width 1 and heights *h*[0..*n* − 1]. LeetCode 84 (Largest Rectangle in Histogram) asks for the largest area of an axis-parallel rectangle that fits inside the bars. A rectangle over the bars *l*..*r* can be as tall as the lowest bar in that range, so the task is

  max over 0 ≤ *l* ≤ *r* < *n* of (*r* − *l* + 1) · min(*h*[*l*..*r*]).

There are *n*(*n* + 1)/2 ranges; carrying a running minimum while extending *r* gives an O(*n*²) brute force. The stack does better by changing the question: instead of asking "how tall can this range be?", ask "if bar *i* is the lowest bar of the rectangle, how wide can the rectangle be?".

:::theorem{#thm-7-hist} Each bar as the lowest bar
Let *L*ᵢ be the index of the previous bar strictly lower than *h*[*i*] (−1 if none) and *R*ᵢ the index of the next bar strictly lower than *h*[*i*] (*n* if none). Then the largest rectangle has area

  max over *i* of *h*[*i*] · (*R*ᵢ − *L*ᵢ − 1).
:::

:::proof
*Every candidate is a real rectangle.* All bars strictly between *L*ᵢ and *R*ᵢ are at least *h*[*i*] tall, by the definition of *L*ᵢ and *R*ᵢ, so a rectangle of height *h*[*i*] over the *R*ᵢ − *L*ᵢ − 1 bars *L*ᵢ + 1..*R*ᵢ − 1 fits. So the maximum of the candidates is at most the optimum.

*The optimum is among the candidates.* Take an optimal rectangle over bars *l*..*r*, with height *H* = min(*h*[*l*..*r*]) (a lower height would only lose area). Choose *i* in *l*..*r* with *h*[*i*] = *H*. No bar in *l*..*r* is lower than *H*, so the previous strictly lower bar is left of *l* and the next strictly lower bar is right of *r*: *L*ᵢ < *l* and *R*ᵢ > *r*. Hence the candidate for *i* has width *R*ᵢ − *L*ᵢ − 1 ≥ *r* − *l* + 1 and height *H*, so its area is at least the optimum.
:::

Both boundary arrays come from @tbl-7-variants, one scan from each side.

```java {#lst-7-hist} Largest rectangle in a histogram, two passes
static long largestRectangle(int[] h) {
    int n = h.length;
    int[] left = new int[n], right = new int[n];   // previous / next strictly lower bar
    int[] st = new int[n];
    int top = 0;
    for (int i = 0; i < n; i++) {
        while (top > 0 && h[st[top - 1]] >= h[i]) top--;
        left[i] = top == 0 ? -1 : st[top - 1];
        st[top++] = i;
    }
    top = 0;
    for (int i = n - 1; i >= 0; i--) {
        while (top > 0 && h[st[top - 1]] >= h[i]) top--;
        right[i] = top == 0 ? n : st[top - 1];
        st[top++] = i;
    }
    long best = 0;
    for (int i = 0; i < n; i++) best = Math.max(best, (long) h[i] * (right[i] - left[i] - 1));
    return best;
}
```

### One pass

The usual exam version computes the areas while popping, in a single scan with a sentinel bar of height 0 after the end that empties the stack.

```java {#lst-7-hist1} Largest rectangle in one pass: a bar's rectangle is settled when it is popped
static long largestRectangleOnePass(int[] h) {
    int n = h.length;
    int[] st = new int[n + 1];
    int top = 0;
    long best = 0;
    for (int i = 0; i <= n; i++) {
        int cur = i == n ? 0 : h[i];              // height 0 after the end pops everything
        while (top > 0 && h[st[top - 1]] >= cur) {
            int j = st[--top];                    // h[j] is the lowest bar of left+1 .. i-1
            int left = top == 0 ? -1 : st[top - 1];
            best = Math.max(best, (long) h[j] * (i - left - 1));
        }
        st[top++] = i;
    }
    return best;
}
```

When *j* is popped by *i*, the bar under it on the stack is the previous strictly lower bar (the stack is strictly increasing), and *i* is the next bar with height **≤** *h*[*j*]. For a bar with an equal neighbour to its right, the width is therefore too short. The trace for the same histogram shows this at *i* = 4, where bar 2 is settled with width 2, while bar 4, of the same height, is settled one step later with the full width 3.

```trace

0   3                                               [0]
1   1   pop 0: h 3, width 1, area 3                 [1]
2   4                                               [1, 2]
3   5                                               [1, 2, 3]
4   4   pop 3: h 5, width 1, area 5
        pop 2: h 4, width 2, area 8                 [1, 4]
5   2   pop 4: h 4, width 3, area 12                [1, 5]

7   0   pop 6: area 3; pop 5: area 10; pop 1: area 7
```

:::claim{#thm-7-ties} Short widths for ties do not matter
@lst-7-hist1 returns the largest area.
:::

:::proof
Every computed area is a real rectangle, since the bars strictly between `left` and *i* are all ≥ *h*[*j*]. For the optimum over *l*..*r* with height *H*, let *i** be the **rightmost** bar in *l*..*r* with height *H*. Every bar in *i** + 1..*r* is strictly higher than *H*, so the bar that pops *i** (the next bar with height ≤ *H*) is right of *r*, and the bar below it on the stack (the previous strictly lower bar) is left of *l*. So the width computed for *i** is at least *r* − *l* + 1.
:::

:::java
Areas can exceed `int`: 10⁵ bars of height 10⁵ give 10¹⁰. Write `(long) h[j] * width`, with the cast on the first factor, so the multiplication itself is done in `long`. `(long) (h[j] * width)` casts after the overflow has already happened.
:::

The same idea solves "largest rectangle of 1s in a 0/1 grid": for each row, let *h*[*c*] be the number of consecutive 1s ending at that row in column *c*, and run the histogram algorithm on every row, in O(rows × columns) total.

## The contribution technique {#sec-7-contrib}

LeetCode 907 (Sum of Subarray Minimums) asks for the sum, over all *n*(*n* + 1)/2 subarrays, of the minimum of the subarray, modulo 10⁹ + 7. The brute force extends each subarray to the right while carrying the minimum, O(*n*²). The fast method turns the sum around.

:::definition{#def-7-contrib} Contribution technique
The [[contribution technique]] computes a sum over many objects (here, subarrays) by asking, for each element, how many objects it is responsible for. If every object has exactly one responsible element and element *i* is responsible for *c*ᵢ objects, each worth *a*[*i*], the sum is Σ *a*[*i*] · *c*ᵢ.
:::

For subarray minimums, the responsible element of a subarray is its minimum. The difficulty is **ties**: in [2, 1, 3, 1, 2] the subarray [1, 3, 1] has two minimum positions, and it must be counted once. The fix is a rule that picks exactly one of them, here the rightmost.

:::theorem{#thm-7-contrib} Counting the subarrays each element owns
Let left[*i*] be the previous index with a value strictly smaller than *a*[*i*] (−1 if none), and right[*i*] the next index with a value smaller than **or equal to** *a*[*i*] (*n* if none). Then *a*[*i*] is the rightmost minimum of exactly (*i* − left[*i*]) · (right[*i*] − *i*) subarrays, every subarray is counted for exactly one *i*, and

  Σ over subarrays of min = Σ over *i* of *a*[*i*] · (*i* − left[*i*]) · (right[*i*] − *i*).
:::

:::proof
Call position *i* the owner of the subarray *a*[*l*..*r*] if *a*[*i*] is its minimum and no position to the right of *i* inside the subarray holds the same value. Each subarray has exactly one owner, its rightmost minimum.

Fix *i*. A subarray *a*[*l*..*r*] with *l* ≤ *i* ≤ *r* is owned by *i* exactly when every value in *a*[*l*..*i* − 1] is ≥ *a*[*i*] and every value in *a*[*i* + 1..*r*] is > *a*[*i*]. The first condition says no index in *l*..*i* − 1 is strictly smaller, that is, *l* > left[*i*]; the second says no index in *i* + 1..*r* is smaller or equal, that is, *r* < right[*i*]. So *l* ranges over left[*i*] + 1..*i* (that is *i* − left[*i*] choices) and *r* independently over *i*..right[*i*] − 1 (right[*i*] − *i* choices), giving the product. Summing *a*[*i*] times this count over all *i* adds each subarray's minimum exactly once, by its owner.
:::

The handbook template computes both boundary arrays with the comparisons of the theorem: the left scan pops on `>=`, leaving the previous strictly smaller index; the right-to-left scan pops on `>`, leaving the next smaller-or-equal index.

```java {#lst-7-summin} Sum of the minimums of all subarrays (handbook template)
// Sum of min(subarray) over all subarrays: a[i] is the minimum of (i - left) * (right - i) of them
static long sumSubarrayMins(int[] a) {
    int n = a.length;
    int[] left = new int[n], right = new int[n];
    ArrayDeque<Integer> st = new ArrayDeque<>();
    for (int i = 0; i < n; i++) {            // left[i]: previous index with a smaller value
        while (!st.isEmpty() && a[st.peek()] >= a[i]) st.pop();
        left[i] = st.isEmpty() ? -1 : st.peek();
        st.push(i);
    }
    st.clear();
    for (int i = n - 1; i >= 0; i--) {       // right[i]: next index with a smaller-or-equal value
        while (!st.isEmpty() && a[st.peek()] > a[i]) st.pop();
        right[i] = st.isEmpty() ? n : st.peek();
        st.push(i);
    }
    long total = 0;
    for (int i = 0; i < n; i++) total += (long) a[i] * (i - left[i]) * (right[i] - i);
    return total;                            // LeetCode 907 wants this mod 1e9+7
}
```

### Why the tie-breaking matters

Use strict comparisons on both sides, and a subarray with two equal minima is owned by both; use non-strict on both, and it is owned by neither. On [2, 2] the true sum is 2 + 2 + 2 = 6. Strict on both sides gives 8 (the subarray [2, 2] is counted twice); non-strict on both gives 4 (it is not counted at all). The template's rule (strict on the left, non-strict on the right) gives 6. The opposite rule (non-strict on the left, strict on the right) is equally correct; it makes the *leftmost* minimum the owner.

:::pitfall
Getting one side wrong passes every test with distinct values and fails as soon as values repeat. Small hand-made examples usually have distinct values, so a wrong tie rule survives them. Always test the contribution formula on an array with ties, such as [2, 2] or [3, 1, 3, 1], against a brute force.
:::

### The modulus

LeetCode 907 keeps *n* and the values at 3 · 10⁴ or less, so the exact total is at most about 4.5 · 10⁸ subarrays × 3 · 10⁴ ≈ 1.4 · 10¹³ and fits in `long`; taking the remainder at the end is enough. With *n* = 10⁵ and values up to 10⁹, one count (*i* − left)(right − *i*) can reach (*n*/2)² = 2.5 · 10⁹ and the total can approach 10¹⁹, beyond `long`. Then reduce every term:

```java {#lst-7-mod} The contribution sum modulo 1e9+7, safe for large n and values
static final long MOD = 1_000_000_007L;

static long sumOfMinsMod(int[] a, int[] left, int[] right) {    // left, right as in sumSubarrayMins
    long total = 0;
    for (int i = 0; i < a.length; i++) {
        long count = (long) (i - left[i]) * (right[i] - i) % MOD;   // < 2.5e9 before the mod
        total = (total + a[i] % MOD * count) % MOD;                 // both factors < MOD: < 1.1e18
    }
    return total;
}
```

Both factors of the product are below 10⁹ + 7 after the reduction, so the product stays below about 1.0 · 10¹⁸ < 9.2 · 10¹⁸, the largest `long`.

:::infosys
The plan's decoding of the official sample paper reports typical limits of *n* ≤ 10⁵ with answers taken mod 10⁹ + 7. Sums over all subarrays or all pairs are the classic reason for that modulus, so reduce each term as above rather than hoping the total fits.
:::

### Maxima, ranges and other contributions

For the sum of subarray **maximums**, reverse every comparison: left[*i*] is the previous strictly *greater* index and right[*i*] the next greater-or-equal index. The proof is the same with "maximum" in place of "minimum".

The **range** of a subarray is its maximum minus its minimum. Because a sum of differences is the difference of the sums,

  Σ over subarrays of (max − min) = Σ over subarrays of max − Σ over subarrays of min,

so the sum of all ranges (LeetCode 2104, Sum of Subarray Ranges, a bonus problem today) is two contribution sums, one for maxima and one for minima. For [2, 1, 3, 1, 2] the maxima sum to 37, the minima to 19, and the ranges to 18.

The counts are useful on their own. The number of subarrays whose minimum is exactly *v* is the sum of the counts of the indices holding *v*; the number of subarrays in which *a*[*i*] is the minimum is its count. Any question of the form "sum over all subarrays of a function of the minimum" is answered the same way.

## Greedy stacks for the smallest result {#sec-7-greedy}

The last application looks different but uses the same stack. Delete exactly *k* characters of a string *s* so that the remaining string, read in order, is as small as possible in dictionary order.

:::definition{#def-7-lex} Lexicographic order
For two strings of the same length, *x* is lexicographically smaller than *y* if, at the first position where they differ, the character of *x* is smaller. This is [[lexicographic order]], the order of a dictionary. For two digit strings of the same length it is also the numeric order.
:::

All results have length *n* − *k*, so only the first difference matters. That makes the early positions far more important than the late ones, and suggests deleting a large character as early as possible. The right place to delete turns out to be the first **descent**: the first *i* with *s*[*i*] > *s*[*i* + 1].

:::lemma{#lem-7-one} The best single deletion
Let *i* be the first index with *s*[*i*] > *s*[*i* + 1], or *i* = *n* − 1 if *s* is non-decreasing. Deleting *s*[*i*] gives the lexicographically smallest of the *n* strings obtained by deleting one character.
:::

:::proof
Write *D*ⱼ for *s* with position *j* deleted. *D*ⱼ[*p*] = *s*[*p*] for *p* < *j* and *s*[*p* + 1] for *p* ≥ *j*.

*Deleting earlier, j < i.* For *p* < *j* the two strings agree. For *j* ≤ *p* < *i*, *D*ⱼ[*p*] = *s*[*p* + 1] ≥ *s*[*p*] = *D*ᵢ[*p*], because *s*[0..*i*] is non-decreasing. From *p* = *i* on they agree again. So *D*ᵢ ≤ *D*ⱼ.

*Deleting later, j > i.* The strings agree before position *i*, and at position *i*, *D*ᵢ[*i*] = *s*[*i* + 1] < *s*[*i*] = *D*ⱼ[*i*]. So *D*ᵢ < *D*ⱼ. (If *s* is non-decreasing, *i* = *n* − 1 and only the first case arises.)
:::

One good deletion is not yet *k* good deletions. The next result says that the greedy choice is never a mistake.

:::theorem{#thm-7-greedy} Greedy deletion is optimal
For 1 ≤ *k* ≤ *n*, deleting *k* characters one at a time, each time at the first descent of the current string (or its last character if there is none), gives the lexicographically smallest string obtainable by deleting *k* characters.
:::

:::proof
It is enough to show that some optimal set of *k* deleted positions contains the position *i* of @lem-7-one; then the rest is an optimal deletion of *k* − 1 characters from *D*ᵢ, and induction on *k* finishes the proof. Take an optimal set *S* of *k* positions with *i* ∉ *S*.

*Case 1: S contains a position j < i.* Replace *j* by *i*. The two results differ only in the characters kept from positions *j*..*i*. Let the kept positions in that block be *k*₁ < ⋯ < *k*ₜ = *i* for *S*; for the new set they are *j*, *k*₁, …, *k*ₜ₋₁, each shifted one place to the left in the list. Since *s*[*j*..*i*] is non-decreasing, each character of the new list is ≤ the character in the same place of the old list. So the new result is no larger.

*Case 2: every position of S is after i.* Let *j* = min *S* and replace it by *i*. The results agree before position *i*. At position *i*, the old result has *s*[*i*] and the new one has *s*[*i* + 1] (position *i* + 1 is kept in the new set, since the only change was to delete *i* instead of *j*), and *s*[*i* + 1] < *s*[*i*]. So the new result is smaller, contradicting optimality; this case cannot happen.

In both cases there is an optimal set containing *i*.
:::

Doing *k* deletions one by one and rescanning from the start each time costs O(*nk*). A stack removes the rescanning. After deleting position *i*, the prefix *s*[0..*i* − 1] is still non-decreasing, so the next descent is at *i* − 1 (if *s*[*i* − 1] is larger than the character that moved next to it) or later, never earlier. Keep the non-decreasing prefix on a stack; when the next character is smaller than the top, the top is the first descent, so pop it and spend one deletion.

```java {#lst-7-greedy} The smallest string after deleting exactly k characters
static String smallestAfterDeleting(String s, int k) {      // 0 <= k <= s.length()
    StringBuilder st = new StringBuilder();                  // the stack: kept characters, non-decreasing
    for (char c : s.toCharArray()) {
        while (k > 0 && st.length() > 0 && st.charAt(st.length() - 1) > c) {
            st.setLength(st.length() - 1);                   // the top is the first descent: delete it
            k--;
        }
        st.append(c);
    }
    st.setLength(st.length() - k);                           // non-decreasing now: delete from the end
    return st.toString();
}
```

Each character is appended once and removed at most once, so the method runs in O(*n*). When the scan ends with deletions left over, the stack is non-decreasing, its first descent is "none", and @lem-7-one says to delete the last character, *k* times.

:::example{#ex-7-greedy} Deleting three letters of "becadfa"
```trace
char  popped  stack   k left
b     -       b       3
e     -       be      3
c     e       bc      2
a     c, b    a       0
d     -       ad      0
f     -       adf     0
a     -       adfa    0
result: adfa
```

A brute force over all 35 ways to keep four of the seven letters agrees. Note the last letter: the `a` after `f` would like to pop `f`, but the deletions are used up.
:::

### Digits, and letters used once

For digits the same greedy gives the smallest number: equal-length digit strings compare numerically exactly as they compare lexicographically. On "52814" with two deletions, the first descent is the 5 (giving "2814") and then the 8 (giving "214"). LeetCode 402 (Remove K Digits), a bonus problem today, adds two details that are part of the problem rather than the idea: leading zeros of the result must be removed, and an empty result is written "0".

LeetCode 316 (Remove Duplicate Letters), the other bonus stack problem, keeps each distinct letter exactly once instead of deleting a fixed number. The stack changes in two ways: a letter already on the stack is skipped, and the top may be popped only if it is larger than the current letter **and** occurs again later in the string, so that it can be taken then. An array of last positions answers "occurs again later" in O(1).

## Relatives: the monotonic deque and the Cartesian tree {#sec-7-relatives}

### The monotonic deque

Chapter 3 found the maximum of every window of length *k* with a deque of indices whose values decrease from front to back. Its back end behaves exactly like the next-greater stack: a new value pops every smaller value, because those can never again be a window maximum. The only addition is at the front: when the index there falls out of the window, it is removed. Each index still enters once and leaves once, so the cost is O(*n*) by the argument of @lem-7-cost. A monotonic deque is a monotonic stack that also forgets old indices.

A different structure with a similar name, the *minimum stack*, stores with each pushed value the minimum of the stack so far, so that the current minimum is always on top. Two such stacks make a queue with O(1) amortised minimum. It answers "minimum of everything currently stored", not "nearest smaller element".

### The Cartesian tree

The stack also builds a tree, almost for free.

:::definition{#def-7-cartesian} Cartesian tree
The [[Cartesian tree]] of an array with distinct values is the binary tree whose root is the position of the minimum, whose left subtree is the Cartesian tree of the part to the left of the minimum, and whose right subtree is the Cartesian tree of the part to its right.
:::

Read in order (left subtree, node, right subtree), the tree lists the indices 0..*n* − 1; and every node's value is smaller than its children's. The subtree of node *i* covers exactly the indices strictly between its previous smaller and next smaller elements, the same range as in @thm-7-hist. So the largest rectangle in a histogram is the maximum over the nodes of value × subtree size.

```java {#lst-7-cartesian} Parents in the Cartesian tree (minimum at the root), built with a stack
static int[] cartesianParent(int[] a) {          // distinct values; parent -1 for the root
    int n = a.length;
    int[] par = new int[n];
    Arrays.fill(par, -1);
    int[] st = new int[n];                       // the right spine of the tree built so far
    int top = 0;
    for (int i = 0; i < n; i++) {
        int last = -1;
        while (top > 0 && a[st[top - 1]] > a[i]) last = st[--top];
        if (last != -1) par[last] = i;           // the popped chain hangs below i, on its left
        if (top > 0) par[i] = st[top - 1];       // i becomes the right child of the new top
        st[top++] = i;
    }
    return par;
}
```

For [5, 2, 6, 1, 4, 3] the parents are [1, 3, 1, −1, 5, 3]: the 1 at index 3 is the root, the 2 at index 1 heads the left part [5, 2, 6], and the 3 at index 5 heads the right part [4, 3].

Two facts make the tree worth knowing later. The minimum of any range *a*[*l*..*r*] is the value at the lowest common ancestor of *l* and *r*, which links range-minimum queries to the tree algorithms of Chapter 18. And the stack in @lst-7-cartesian is the right spine of the tree: each new value climbs the spine while it is smaller, which is the next-smaller scan of @tbl-7-variants with the pops recorded as edges.

## Summary

- A monotonic stack keeps the indices still waiting for an answer, with sorted values. A new value pops every index it answers; those are always on top.
- Each index is pushed once and popped at most once, so a scan costs O(*n*) in total, even though one step can pop many indices. This is amortised analysis.
- The comparison decides the query: pop on `<` for next greater, on `>` for next smaller; read the popped indices for "next", the top after popping for "previous". `<` versus `<=` decides strict versus non-strict.
- Circular arrays: scan 2*n* positions with `i % n` and push only in the first lap.
- Largest rectangle: every bar is tried as the lowest bar, spreading to its previous and next strictly lower bars; the optimum is among these *n* candidates.
- Contribution: Σ min over all subarrays = Σ *a*[*i*] · (*i* − left[*i*]) · (right[*i*] − *i*), with strict on one side and non-strict on the other so that each subarray has exactly one owner. Test with ties; use `long` and reduce mod 10⁹ + 7 per term for large inputs.
- Sums of maxima reverse the comparisons; sums of ranges are the sum of maxima minus the sum of minima.
- The smallest string after *k* deletions deletes at the first descent each time; a stack does all *k* deletions in O(*n*), and leftover deletions come off the end.
- Use `int[]` with a top pointer or `ArrayDeque`, never `Stack`.

## Review questions

1. In @lst-7-nge, why are the values on the stack non-increasing from bottom to top? Which step of the proof of @thm-7-nge would fail without this?
2. Give an array of length 6 on which one iteration of the `while` loop in @lst-7-nge pops five indices. How many pops does the whole scan make, and why is the method still O(*n*)?
3. Which pop condition and which reading of the stack give the previous greater-or-equal element of every index?
4. For a circular array, why does scanning 2*n* positions suffice? Does anything go wrong if indices are also pushed during the second lap?
5. Why is it enough, in the largest-rectangle problem, to consider rectangles whose height equals the height of one of the bars inside them?
6. Compute the sum of subarray minimums of [3, 3, 3] with the template's tie rule, and then with strict comparisons on both sides. Explain the difference.
7. Which comparisons do you use for left and right when summing subarray maximums? Write the sum of subarray ranges in terms of two contribution sums.
8. In @lst-7-greedy, why are the remaining *k* deletions taken from the end of the stack after the scan?
9. In the Cartesian tree of an array with distinct values, which indices does the subtree of node *i* contain? Use the answer to explain the link with @thm-7-hist.

:::answers
1. Just before *i* is pushed, the `while` loop has popped every index with a value smaller than *a*[*i*], so the new top below *i* holds a value ≥ *a*[*i*], and the order is kept. The proof uses the order to say that the indices answered by *a*[*i*] (those with smaller values) form one block at the top. Without it, a smaller value could sit under a larger one, the `while` loop would stop at the larger one, and the smaller value would miss its answer.
2. [6, 5, 4, 3, 2, 100]: the 100 pops the five indices 4, 3, 2, 1, 0 in one iteration. The whole scan makes 6 pushes and 5 pops. Each index is pushed once and popped at most once, so the `while` loop runs at most *n* times in total, and the method is O(*n*).
3. Scan left to right, pop while `a[top] < a[i]`, and after popping read the top (if any) as the answer for *i*: everything strictly smaller has been removed, so the top is the nearest earlier index with a value ≥ *a*[*i*].
4. The circular next greater element of *j* is among the *n* − 1 positions after it, and the doubled scan visits all of them after *j* was pushed in the first lap. Pushing during the second lap as well does not change any answer: a second-lap copy of *j* can only be popped by a value that appears after it, and the first greater value after it is the same one that answered (or will answer) the first-lap copy. It only costs extra pushes and pops, so the first-lap rule is a small saving, not a correctness fix.
5. An optimal rectangle can always be raised until it touches the top of its lowest bar, because the height is limited only by the lowest bar in its range; raising it increases the area. So its height is the height of that bar.
6. With the template's rule, index 0 owns 1 · 1 subarray, index 1 owns 2 · 1, index 2 owns 3 · 1, six in total, and the sum is 3 · 6 = 18, which is correct (six subarrays, each with minimum 3). With strict comparisons on both sides, every index extends over the whole array: counts 1 · 3, 2 · 2, 3 · 1 = 3 + 4 + 3 = 10, and the sum is 30. Subarrays containing several 3s are counted once for each 3 they contain.
7. left[*i*] = previous index with a strictly greater value, right[*i*] = next index with a greater-or-equal value (or the mirror rule). Σ ranges = Σ over *i* of *a*[*i*] · count_max(*i*) − Σ over *i* of *a*[*i*] · count_min(*i*).
8. After the scan the stack is non-decreasing, so the current string has no descent. By @lem-7-one the best single deletion is then the last character, and the same holds after each such deletion, so the remaining *k* deletions remove the last *k* characters.
9. The indices strictly between the previous smaller and the next smaller element of *i*, that is, left[*i*] + 1..right[*i*] − 1. In the histogram, that range is exactly the widest rectangle in which bar *i* is the lowest, so the largest rectangle is the maximum of *a*[*i*] × (size of the subtree of *i*).
:::
