## The repair session {#sec-26-repair}

The error log has been collecting entries since Day 1: the problem, its topic, one of the nine causes (misread, wrong idea, overflow or mod, off-by-one, time limit, input reading, edge case, stack overflow, ran out of time), the rule that would have prevented the mistake, and the date for a re-solve three days later. The pattern recall tracker at the front of the workbook holds the other half of the evidence: a rating of A (again), S (shaky) or G (solid) for every pattern at its reviews 1, 3, 7 and 14 days after it was taught. The tracker's own instruction is that any pattern still at A on Day 26 goes into the repair session.

:::definition{#def-26-repair} Repair session
A [[repair session]] is a timed block in which you choose your weakest patterns from the error log and the pattern tracker, re-derive each one from memory, re-solve the logged problems without notes, and replace each vague rule by one that you can check against code in ten seconds.
:::

Re-reading a solution feels like progress and changes little. A re-solve without notes tests the two things that fail under exam pressure, recall of the template and recognition of the trap, and a failed re-solve tells you exactly which of the two is missing.

### The method

1. **Collect** (10 minutes). List every error-log entry dated at least three days ago and every pattern with an A in the tracker.
2. **Choose** (5 minutes). Group the entries by cause and by pattern. Take the three weakest: a cause that appears twice, a pattern rated A, a problem that failed its first re-solve. Three done properly beat eight done halfway.
3. **Re-derive** (10 minutes per pattern). Cover the theory book. Write the template from memory, then one sentence that says why it is correct: the invariant, the exchange argument or the recurrence. Compare with the listing and mark every difference.
4. **Re-solve** (the plan's limits: Easy 20, Medium 40, Hard 60 minutes). Solve the logged problem again from a blank file, with a timer. Run the samples and two edge cases of your own.
5. **Rewrite the rule.** If the old rule was "be careful with overflow", the new one is "cast the first factor of every product of two `int`s to `long`". Write it in the log, and in the margin of the template if the cause appeared twice.

A re-solve that fails becomes a new error-log entry with a re-solve date three days later, which is Day 29. Stop after 90 minutes even if entries remain; the plan says to stop the day when the core is done.

## Why a size cap breaks the basis {#sec-26-cap}

The repeat problem, as the plan paraphrases it: *N* is even with *N* ≤ 120, the values satisfy *A*[*i*] ≤ 10⁶, and you choose at most *N*/2 of them, not necessarily adjacent, to make their XOR as large as possible. The samples are [1, 2] with answer 2 and [1, 2, 4, 7] with answer 7.

Chapter 8's XOR basis finds the largest XOR over *all* subsets. On [1, 2] it returns 1 ⊕ 2 = 3, which uses two elements while the cap allows one, so the answer is 2. The basis keeps, for each reachable value, no record of how many elements produce it. Two facts from Chapter 8 frame the rest of the problem:

* every subset XOR lies in the span of the basis, so no subset beats the basis maximum *M*;
* every value of the span is the XOR of at most *r* of the original numbers, where *r* is the number of basis elements (the rank), and *r* ≤ 20 because 10⁶ < 2²⁰ = 1,048,576.

So the cap can only matter when *N*/2 < *r*. For that case you need, for every reachable value, the *fewest* elements that reach it.

## The XOR knapsack {#sec-26-knap}

There are only 2²⁰ possible XOR values, so a table indexed by the value is affordable, in the same way as the capacity table of the 0/1 knapsack in Chapter 11.

:::definition{#def-26-knap} XOR knapsack
For values *a*[0..*n* − 1] below 2ᴮ, let *f*ᵢ[*x*] be the fewest elements among *a*[0..*i* − 1] whose XOR is *x*, or ∞ if no subset of them has XOR *x*. Computing *f*ₙ for all 2ᴮ values of *x* is the [[XOR knapsack]].
:::

:::theorem{#thm-26-knap} The XOR knapsack recurrence
*f*₀[0] = 0 and *f*₀[*x*] = ∞ for *x* ≠ 0. For 0 ≤ *i* < *n* and every *x*,
*f*ᵢ₊₁[*x*] = min(*f*ᵢ[*x*], *f*ᵢ[*x* ⊕ *a*[*i*]] + 1), with ∞ + 1 = ∞.
:::

:::proof
With no elements only the empty set exists, and its XOR is 0. For *i* ≥ 0, split the subsets *S* of *a*[0..*i*] with XOR *x* by whether they contain *a*[*i*]. Those without it are exactly the subsets of *a*[0..*i* − 1] with XOR *x*; the fewest elements among them is *f*ᵢ[*x*]. Those with it have the form *S* = *T* ∪ {*a*[*i*]} with *T* ⊆ *a*[0..*i* − 1], and XOR(*T*) ⊕ *a*[*i*] = *x* holds exactly when XOR(*T*) = *x* ⊕ *a*[*i*] (law 5 of Chapter 8). Then |*S*| = |*T*| + 1, which is smallest when *T* is a smallest set with XOR *x* ⊕ *a*[*i*], giving *f*ᵢ[*x* ⊕ *a*[*i*]] + 1. If no such *T* exists, this case contributes nothing, which ∞ + 1 = ∞ expresses. Every subset is in exactly one case, so *f*ᵢ₊₁[*x*] is the smaller of the two.
:::

The answer to the repeat is the largest *x* with *f*ₙ[*x*] ≤ ⌊*N*/2⌋; *x* = 0 always qualifies through the empty set.

```java {#lst-26-knap} The XOR knapsack: fewest elements for every XOR value
// f[x] = fewest elements of a whose XOR is x, or INF if no subset gives x. O(n * 2^B).
static final int INF = Integer.MAX_VALUE / 2;

static int[] fewestElements(int[] a, int B) {
    int size = 1 << B;
    int[] cur = new int[size], next = new int[size];
    Arrays.fill(cur, INF);
    cur[0] = 0;                                    // the empty set has XOR 0
    for (int v : a) {
        for (int x = 0; x < size; x++)
            next[x] = Math.min(cur[x], cur[x ^ v] + 1);   // skip v, or take it
        int[] t = cur; cur = next; next = t;       // the new row becomes the current one
    }
    return cur;
}
```

`INF` is half of `Integer.MAX_VALUE`, so `INF + 1` does not overflow, and every entry stays at most `INF` because it is the minimum with `cur[x]`. Each pass reads the whole old row and writes a fresh one, the safe method that Chapter 11 recommended for knapsacks whose transition can read on either side of *x*; *x* ⊕ *v* may be larger or smaller than *x*. The cost is O(*n* · 2ᴮ) time and two arrays of 2ᴮ `int`s, 8 MB for *B* = 20.

## Basis and knapsack together {#sec-26-combine}

:::theorem{#thm-26-basis} When the basis answer is right
Let *r* be the rank of the values and *c* = ⌊*N*/2⌋ the cap. If *r* ≤ *c*, the answer equals the maximum subset XOR *M* given by the basis. If *r* > *c*, then *N* < 2*r* ≤ 2*B*.
:::

:::proof
Every subset XOR lies in the span, so no subset with at most *c* elements exceeds *M*. Chapter 8 proved that every span value, *M* included, is the XOR of at most *r* of the original numbers; with *r* ≤ *c* that subset respects the cap, so the answer is *M*. For the second statement, *r* > *c* = ⌊*N*/2⌋ means *r* ≥ *c* + 1 > *N*/2, so *N* < 2*r*, and *r* ≤ *B* because the basis numbers have distinct highest bits below *B*.
:::

So the program builds the basis first. When *r* ≤ *c* it returns the greedy maximum in O(*N* · *B*). Otherwise the knapsack runs on fewer than 2*B* elements, at most (2*B* − 1) · 2ᴮ ≈ 4.1 · 10⁷ updates for *B* = 20. It chooses *B* from the values themselves: the bit length of the OR of all values, so small inputs get small tables. The input format is not given in the plan; the program assumes *N* and then the *N* values, which `FastScanner` reads whether they come one per line or on one line.

```java {#lst-26-halfxor} Maximum XOR of at most N/2 elements: a complete program
import java.io.*;
import java.util.*;

/** Infosys repeat: the largest XOR of at most n/2 of the n values (n even, values below 2^20). */
public class Main {
    public static void main(String[] args) throws IOException {
        FastScanner fs = new FastScanner(System.in);
        int n = fs.nextInt();                          // n, then n values, one per line
        int[] a = new int[n];
        for (int i = 0; i < n; i++) a[i] = fs.nextInt();
        System.out.println(solve(a));
    }

    static int solve(int[] a) {
        int cap = a.length / 2, all = 0;
        for (int v : a) all |= v;
        int B = 32 - Integer.numberOfLeadingZeros(all);   // every XOR of the values is below 2^B

        int[] basis = new int[Math.max(B, 1)];   // Chapter 8: basis[i] has top bit i, or is 0
        int rank = 0;
        for (int v : a) {
            for (int i = B - 1; i >= 0 && v != 0; i--) {
                if (((v >> i) & 1) == 0) continue;
                if (basis[i] == 0) { basis[i] = v; rank++; v = 0; }
                else v ^= basis[i];
            }
        }
        if (rank <= cap) {                             // the cap cannot bind: basis maximum
            int r = 0;
            for (int i = B - 1; i >= 0; i--) r = Math.max(r, r ^ basis[i]);
            return r;
        }
        int[] f = fewestElements(a, B);                // here n < 2 * rank <= 2 * B
        for (int x = (1 << B) - 1; x > 0; x--) if (f[x] <= cap) return x;
        return 0;
    }

    // f[x] = fewest elements of a whose XOR is x, or INF if no subset gives x. O(n * 2^B).
    static final int INF = Integer.MAX_VALUE / 2;

    static int[] fewestElements(int[] a, int B) {
        int size = 1 << B;
        int[] cur = new int[size], next = new int[size];
        Arrays.fill(cur, INF);
        cur[0] = 0;                                    // the empty set has XOR 0
        for (int v : a) {
            for (int x = 0; x < size; x++)
                next[x] = Math.min(cur[x], cur[x ^ v] + 1);   // skip v, or take it
            int[] t = cur; cur = next; next = t;       // the new row becomes the current one
        }
        return cur;
    }

    static final class FastScanner {
        private final BufferedReader br;
        private StringTokenizer st;

        FastScanner(InputStream in) { br = new BufferedReader(new InputStreamReader(in)); }

        String next() throws IOException {
            while (st == null || !st.hasMoreTokens()) {
                String line = br.readLine();
                if (line == null) return null;
                st = new StringTokenizer(line);
            }
            return st.nextToken();
        }

        int nextInt() throws IOException { return Integer.parseInt(next()); }
    }
}
```

Run on the two samples, one value per line (2, 1, 2 and 4, 1, 2, 4, 7), it prints 2 and 7. On 20,000 random inputs with even *N* from 2 to 14 and values below 2ᵇ for *b* from 1 to 6, `solve` agreed with a brute force over all subsets of at most *N*/2 elements, the knapsack branch ran in 6,078 of them, and `fewestElements` matched a brute-force table of fewest elements in every case. On 38 random values up to 10⁶ (rank 20 > 19, so the knapsack runs) the whole program took about 0.1 s; on 120 values it took the basis branch and finished in about 0.05 s.

:::pitfall
Two traps from the tests. `INF = Integer.MAX_VALUE` makes `cur[x ^ v] + 1` overflow to a negative number, after which every unreachable value looks reachable with a negative count and passes `f[x] <= cap`. And forgetting `cur[0] = 0` makes every entry ∞: the empty set is what starts every chain.
:::

## Pairs with a prime sum: the sieve tier {#sec-26-sieve}

The second repeat comes from an interview report quoted in the plan: count the pairs *i* < *j* with (*A*[*i*] ⊕ *A*[*j*]) < *K* and *A*[*i*] + *A*[*j*] prime. The candidate's nested loops tested each sum for primality by trial division and timed out. The report gives no limits and no samples, so the input format below (*n*, then *K*, then *n* values ≥ 0, one per line) and the examples are my own.

The trial-division version costs O(*n*² · √*V*) for sums up to *V*. The first fix removes the √*V*: every sum is at most 2 · max(*A*), so one sieve of Eratosthenes up to that bound (Chapter 10) turns each primality test into an array lookup.

```java {#lst-26-sieve} The sieve tier: every pair, with primality as a lookup
// composite[v] is true for v = 0, 1 and every composite v <= limit (Chapter 10's sieve)
static boolean[] sieve(int limit) {
    boolean[] composite = new boolean[Math.max(limit + 1, 2)];
    composite[0] = composite[1] = true;
    for (int p = 2; (long) p * p <= limit; p++)
        if (!composite[p])
            for (int q = p * p; q <= limit; q += p) composite[q] = true;
    return composite;
}

static long countPairsQuadratic(int[] a, int k) {            // O(n^2 + V log log V)
    int maxA = 0;
    for (int v : a) maxA = Math.max(maxA, v);
    boolean[] composite = sieve(2 * maxA);
    long count = 0;
    for (int i = 0; i < a.length; i++)
        for (int j = i + 1; j < a.length; j++)
            if ((a[i] ^ a[j]) < k && !composite[a[i] + a[j]]) count++;
    return count;
}
```

The sieve costs O(*V* log log *V*) time and *V* + 1 bytes for *V* = 2 · max(*A*): 2 MB for values up to 10⁶. The double loop is then O(*n*²) with a tiny constant, fine up to *n* of a few thousand. For *n* = 10⁵ it is 5 · 10⁹ pairs: on random values up to 10⁶ it took between 4.4 and 5.4 s in two runs. This tier is also the brute force for testing the next one.

## Listing the candidates with a trie {#sec-26-trie}

Chapter 8's trie counts the *y* with *x* ⊕ *y* < *K* in O(*B*) per query, by adding whole subtrees at the 1-bits of *K*. It cannot count the prime sums the same way. XOR works bit by bit, but addition carries, so whether *x* + *y* is prime depends on all bits of *y* at once, and no number stored in a subtree node can summarise it. The trie can still do the expensive part, which is skipping every *y* with *x* ⊕ *y* ≥ *K* without looking at it, provided it can *list* the members of a subtree cheaply. Sorting makes that possible.

:::lemma{#lem-26-range} Subtrees are ranges of the sorted values
Insert the values in sorted order *s*[0] ≤ *s*[1] ≤ ⋯ into a binary trie over *B* bits. After *s*[0..*j* − 1] are inserted, the values stored below any node are exactly *s*[lo..hi] for some lo ≤ hi.
:::

:::proof
A node at depth *d* stands for a prefix *P* of *d* bits, and a value passes through it exactly when its top *d* bits equal *P*, that is, when it lies in the interval [*P* · 2ᴮ⁻ᵈ, (*P* + 1) · 2ᴮ⁻ᵈ). In a sorted array the elements that lie in an interval occupy consecutive positions, and so do those among the first *j*.
:::

So each node needs only two numbers: lo, set when the node is created, and hi, set every time a value passes through it. The [[subtree range|trie subtree range]] replaces the count of Chapter 8's trie; the count is hi − lo + 1.

:::theorem{#thm-26-list} The walk lists exactly the pairs with XOR below K
In @lst-26-xorprime, the query for *x* = *s*[*j*] visits every *y* among *s*[0..*j* − 1] with *x* ⊕ *y* < *K* exactly once and no other *y*. Hence `count` ends as the number of pairs with XOR below *K* and a prime sum.
:::

:::proof
Chapter 8 proved that the walk of `countXorLess` collects disjoint subtrees whose union is exactly the set of stored *y* with *x* ⊕ *y* < *K*: at each 1-bit of *K* it takes the child that makes the XOR bit 0 and continues along the child that makes it 1. The query loop makes the same moves and takes the same subtrees. By @lem-26-range each of them is a range *s*[lo..hi] of indices below *j*, which the inner loop visits once each, testing the sum with the sieve. Each unordered pair of the input corresponds to exactly one pair of positions *i* < *j* in sorted order, and it is examined when the later position *j* is queried.
:::

```java {#lst-26-xorprime} Pairs with XOR below K and a prime sum: a complete program
import java.io.*;
import java.util.*;

/** Pairs i < j with (a[i] xor a[j]) < K and a[i] + a[j] prime. Input: n, K, n values >= 0. */
public class Main {
    public static void main(String[] args) throws IOException {
        FastScanner fs = new FastScanner(System.in);
        int n = fs.nextInt();
        int k = fs.nextInt();
        int[] a = new int[n];
        for (int i = 0; i < n; i++) a[i] = fs.nextInt();
        System.out.println(countPairs(a, k));
    }

    static long countPairs(int[] a, int k) {
        int n = a.length;
        if (n < 2 || k <= 0) return 0;
        int[] s = a.clone();
        Arrays.sort(s);                                   // insert in increasing order (lemma)
        int maxA = s[n - 1];
        boolean[] composite = sieve(2 * maxA);            // every sum is at most 2 * maxA
        int vb = 32 - Integer.numberOfLeadingZeros(maxA); // values, so XORs, are below 2^vb
        if (k > (1 << vb)) k = 1 << vb;                   // a larger K accepts every pair anyway
        int B = Math.max(1, 32 - Integer.numberOfLeadingZeros(maxA | k));   // values, K < 2^B

        int cap = n * B + 1;
        int[] next = new int[2 * cap];                    // children of v: next[2v], next[2v + 1]
        int[] lo = new int[cap], hi = new int[cap];       // the subtree of v is s[lo[v]..hi[v]]
        int size = 1;
        long count = 0;
        for (int j = 0; j < n; j++) {
            int x = s[j], node = 0;
            for (int b = B - 1; b >= 0; b--) {            // query: the y among s[0..j-1]
                int xb = (x >> b) & 1, kb = (k >> b) & 1;
                if (kb == 1) {
                    int c = next[2 * node + xb];          // XOR bit 0 here: every y below is < K
                    if (c != 0)
                        for (int i = lo[c]; i <= hi[c]; i++)
                            if (!composite[x + s[i]]) count++;
                    node = next[2 * node + (xb ^ 1)];     // XOR bit 1: still equal to K so far
                } else {
                    node = next[2 * node + xb];           // XOR bit must be 0
                }
                if (node == 0) break;                     // nobody continues this path
            }
            node = 0;                                     // insert x
            for (int b = B - 1; b >= 0; b--) {
                int slot = 2 * node + ((x >> b) & 1);
                if (next[slot] == 0) { next[slot] = size; lo[size] = j; size++; }
                node = next[slot];
                hi[node] = j;
            }
        }
        return count;
    }

    // composite[v] is true for v = 0, 1 and every composite v <= limit (Chapter 10's sieve)
    static boolean[] sieve(int limit) {
        boolean[] composite = new boolean[Math.max(limit + 1, 2)];
        composite[0] = composite[1] = true;
        for (int p = 2; (long) p * p <= limit; p++)
            if (!composite[p])
                for (int q = p * p; q <= limit; q += p) composite[q] = true;
        return composite;
    }

    static final class FastScanner {
        private final BufferedReader br;
        private StringTokenizer st;

        FastScanner(InputStream in) { br = new BufferedReader(new InputStreamReader(in)); }

        String next() throws IOException {
            while (st == null || !st.hasMoreTokens()) {
                String line = br.readLine();
                if (line == null) return null;
                st = new StringTokenizer(line);
            }
            return st.nextToken();
        }

        int nextInt() throws IOException { return Integer.parseInt(next()); }
    }
}
```

Two lines deal with large *K*. All values are below 2<sup>*vb*</sup>, so every XOR is too, and any *K* above 2<sup>*vb*</sup> accepts every pair; replacing it by 2<sup>*vb*</sup> keeps that meaning and keeps *B* at most *vb* + 1. Then *B* covers both the values and *K*, which the walk needs: a first version that took *B* from *K* alone ignored the high bits of large values, and the stress test found it at once.

### Cost, and when it pays

Sorting costs O(*n* log *n*), the walks O(*n* · *B*), the sieve O(*V* log log *V*), and the inner loops exactly *P*, the number of pairs with XOR below *K*. An algorithm whose running time depends on the size of what it finds, here *P*, is called [[output-sensitive|output-sensitive algorithm]]. The trie has at most *n* · *B* + 1 nodes with four `int`s each, about 32 MB for *n* = 10⁵ and *B* = 20.

On 30,000 random inputs (*n* ≤ 11, values up to 8, 64 or 2000, *K* from 0 to beyond every XOR), the program and the sieve tier both agreed with trial division. Timed on *n* = 10⁵ random values up to 10⁶:

Table: {#tbl-26-time} The trie program on n = 10⁵ random values up to 10⁶
| *K* | pairs with XOR < *K* (*P*) | time |
|---|---|---|
| 2¹⁰ | 5,118,482 | 0.05 s |
| 2¹⁴ | 81,863,835 | 0.14 s |
| 2¹⁷ | 635,758,347 | 0.8 s |

The sieve tier took about 5 s for *K* = 2¹⁴. When *K* exceeds every XOR, *P* = *n*(*n* − 1)/2 and the trie lists every pair, so it is no faster than the double loop. Without the problem's limits nobody can promise more. The plan's advice for this problem is to read the limits before choosing O(*n*²); if *n* is a few thousand, the sieve tier is the whole solution.

## Bonus: brute force over matchings {#sec-26-complex}

The Complex problem of the official sample paper flips a matching of tree edges and asks about patterns on root-to-leaf paths. The plan rates it 2400+ and notes that the paper's own explanations of it contradict each other, so the samples cannot fully pin down the rules; Chapter 25 covers the paper and gives a partial-marks program for its written statement. The plan aims only for partial marks there, with a brute force for *N* ≤ 15. That brute force has two parts, enumerating matchings and checking paths, and both are shown here on a different example.

:::lemma{#lem-26-matchings} Enumerating matchings edge by edge
The recursion of @lst-26-matchings, called with `e = 0` and empty masks, adds every matching of the graph to `out` exactly once and nothing else. With *m* edges and *M* matchings it makes at most (*m* + 1) · *M* calls.
:::

:::proof
The recursion decides the edges in order 0..*m* − 1, each either skipped or taken, and takes an edge only if neither end is already used. A finished sequence of decisions therefore describes a set of edges with no shared end, a matching. Conversely, a matching *T* is produced by the sequence "take *e* exactly when *e* ∈ *T*": every take is allowed because the edges of *T* share no ends. Different sequences give different sets, so no matching appears twice. Every call lies on the path from the first call to some finished sequence, each such path has *m* + 1 calls, and there are *M* finished sequences.
:::

```java {#lst-26-matchings} Every matching of a small tree, and a brute-force maximum-weight matching
// Every matching of a graph with edges (eu[e], ev[e]), as a bitmask of chosen edges.
// Edge e is skipped, or taken if neither end is used yet. Vertices 0..n-1 with n <= 31.
static void matchings(int e, int used, int chosen, int[] eu, int[] ev, List<Integer> out) {
    if (e == eu.length) { out.add(chosen); return; }
    matchings(e + 1, used, chosen, eu, ev, out);                         // skip edge e
    int ends = (1 << eu[e]) | (1 << ev[e]);
    if ((used & ends) == 0)                                              // take edge e
        matchings(e + 1, used | ends, chosen | (1 << e), eu, ev, out);
}

static long bestMatchingBrute(int[] eu, int[] ev, long[] w) {         // evaluate every matching
    List<Integer> all = new ArrayList<>();
    matchings(0, 0, 0, eu, ev, all);
    long best = 0;
    for (int mask : all) {
        long s = 0;
        for (int e = 0; e < eu.length; e++) if (((mask >> e) & 1) == 1) s += w[e];
        best = Math.max(best, s);
    }
    return best;
}
```

The example evaluation is Chapter 19's maximum-weight matching, which makes a good test: on 5,000 random trees with up to 12 vertices, `bestMatchingBrute` equalled the tree DP of Chapter 19, and the number of matchings equalled a check of all 2ᵐ edge subsets. The point of enumerating edge by edge rather than over all subsets is the count. A tree with 15 vertices has 14 edges and 2¹⁴ = 16,384 subsets, but a path of 15 vertices has only 987 matchings, a star has 15, and 10,000 random trees with 15 vertices had at most 923.

The second part lists the label strings of all root-to-leaf paths. A BFS order puts every parent before its children, so each path string is the parent's string plus one character, with no recursion.

```java {#lst-26-paths} The label string of every root-to-leaf path
// The label string of every root-to-leaf path (par[root] = -1), without recursion.
static List<String> rootToLeafStrings(int[] par, char[] label) {
    int n = par.length, root = -1;
    List<List<Integer>> kids = new ArrayList<>();
    for (int v = 0; v < n; v++) kids.add(new ArrayList<Integer>());
    for (int v = 0; v < n; v++) if (par[v] == -1) root = v; else kids.get(par[v]).add(v);
    int[] order = new int[n];
    int head = 0, tail = 0;
    order[tail++] = root;
    while (head < tail) for (int c : kids.get(order[head++])) order[tail++] = c;
    String[] path = new String[n];
    List<String> out = new ArrayList<>();
    for (int i = 0; i < n; i++) {                      // BFS order: parents before children
        int u = order[i];
        path[u] = (par[u] == -1 ? "" : path[par[u]]) + label[u];
        if (kids.get(u).isEmpty()) out.add(path[u]);
    }
    return out;
}
```

For par = [−1, 0, 0, 1, 1, 2] with labels `b a b b a a` it returns "bab", "baa" and "bba", and only the first contains "ab". It matched a recursive DFS on 5,000 random labelled trees. For *N* ≤ 15 the strings have total length at most 15², so `String.contains` on each is cheap.

The key observation for the Complex problem is the combination: for *N* ≤ 15, enumerate the matchings with @lst-26-matchings, apply each one's changes as the statement defines them, rebuild the root-to-leaf strings with @lst-26-paths and test each with `contains`. Under a thousand matchings times a few hundred characters per check is far inside the time limit. How the changes and the costs are defined is the part the PDF leaves unclear, so check your reading of the rules against every sample before trusting the brute force.

## Summary

- The repair session takes 90 minutes: collect the error-log entries at least three days old and the A-rated patterns, choose three, re-derive each template with its reason, re-solve without notes, and rewrite each rule so that it can be checked against code.
- A size cap breaks the XOR basis because the basis forgets how many elements make each value. Every span value needs at most *r* elements, so the basis maximum is the answer whenever *r* ≤ ⌊*N*/2⌋.
- The XOR knapsack keeps, for each of the 2ᴮ values, the fewest elements that reach it: *f*ᵢ₊₁[*x*] = min(*f*ᵢ[*x*], *f*ᵢ[*x* ⊕ *a*ᵢ] + 1). It costs O(*n* · 2ᴮ) time and two rows of memory.
- Basis first, knapsack only when *r* > ⌊*N*/2⌋, which forces *N* < 2*B*: at most about 4.1 · 10⁷ updates for *B* = 20.
- For pairs with a prime sum, sieve once up to 2 · max(*A*); the double loop with lookups is the first tier and the test oracle.
- A trie built from sorted values has subtrees that are ranges of the sorted array, so the walk of Chapter 8 can list the pairs with XOR below *K* in time proportional to their number, *P*.
- For a tree with *N* ≤ 15, enumerating matchings edge by edge visits at most a thousand sets, and BFS order builds every root-to-leaf string without recursion.

## Review questions

1. Why does the XOR basis return 3 on the sample [1, 2], and why is the answer 2?
2. In the proof of @thm-26-knap, which law of XOR turns "XOR(*T*) ⊕ *a*[*i*] = *x*" into a condition on *T* alone?
3. The knapsack of @lst-26-knap writes each pass into a fresh array. Suppose instead it updates one array in place, `f[x] = Math.min(f[x], f[x ^ v] + 1)` for *x* = 0, 1, 2, …. Show that for this minimum the result is still correct, even though Chapter 11 warned against in-place updates for this transition.
4. Prove that if the values are below 2²⁰ and *N* ≥ 40, @lst-26-halfxor never runs the knapsack.
5. Why can a trie node not store a number that answers "how many *y* below me make *x* + *y* prime"?
6. In @lem-26-range, why must the values be inserted in sorted order? Give a small example where inserting in input order makes some subtree a set of positions that is not a range.
7. A prime greater than 2 is odd. How could you use that to roughly halve the candidates the trie lists, and which pairs need separate treatment?
8. For which *K* does @lst-26-xorprime do about as much work as the double loop, and what then decides between them?
9. Why does @lst-26-matchings visit far fewer than 2¹⁴ sets for a tree with 15 vertices, and how many does it visit for a star?

:::answers
1. The basis spans {0, 1, 2, 3}, and its greedy maximum is 3 = 1 ⊕ 2, which uses two elements. With *N* = 2 the cap is one element, so the best is the larger single value, 2.
2. Law (5): *a* ⊕ *b* = *c* if and only if *a* = *b* ⊕ *c*. With *a* = XOR(*T*), *b* = *a*[*i*] and *c* = *x* it gives XOR(*T*) = *a*[*i*] ⊕ *x* = *x* ⊕ *a*[*i*].
3. Let *y* = *x* ⊕ *v*. If *y* > *x*, then *f*[*y*] has not been updated when *x* is processed, so *f*[*x*] gets min(old *f*[*x*], old *f*[*y*] + 1), the correct value. If *y* < *x*, then *f*[*y*] already holds min(old *f*[*y*], old *f*[*x*] + 1), so *f*[*x*] becomes min(old *f*[*x*], old *f*[*y*] + 1, old *f*[*x*] + 2), and the last term never wins. If *v* = 0, then *y* = *x* and *f*[*x*] = min(*f*[*x*], *f*[*x*] + 1) is unchanged, which is right. Using an element twice cancels it and costs two more, so it never helps a minimum. (For a count of subsets it would double-count, which is why the fresh array is the safe default.) A test of 3,000 random cases confirmed that the two versions agree.
4. The basis numbers have distinct highest bits below 20, so the rank is *r* ≤ 20. With *N* ≥ 40 the cap is at least 20 ≥ *r*, so the test `rank <= cap` succeeds and the method returns the basis maximum.
5. Primality of *x* + *y* depends on all bits of *y* together because addition carries, and it also depends on the query value *x*. A node would need a separate count for every possible *x*, which is no better than the pairs themselves.
6. A subtree holds the values with a given prefix, which form an interval of values; only in sorted order are they consecutive *positions*. With input order [1, 4, 0] and *B* = 3, the subtree of prefix 0 holds the values 1 and 0 at positions 0 and 2, but position 1 holds 4, so the positions {0, 2} are not a range.
7. A prime sum above 2 has one odd and one even term, so its XOR has bit 0 equal to 1. Keep two tries, one for even and one for odd values, and query each *x* only against the trie of the other parity. Two values of equal parity can only have the prime sum 2, from 1 + 1 or 0 + 2, so those pairs need a separate count: *c*(*c* − 1)/2 for *c* ones (their XOR is 0 < *K*), plus (number of 0s) × (number of 2s) when 0 ⊕ 2 = 2 < *K*.
8. When *K* is larger than almost every XOR, *P* is close to *n*(*n* − 1)/2 and the trie lists nearly every pair. Then the limits decide: if *n*² is affordable the simpler double loop is the solution, and if not, neither method is fast enough and the problem must have smaller *n* or a further idea.
9. It only extends sets in which no two edges share an end, so it visits matchings, not subsets, and its call count is at most (*m* + 1) times their number (@lem-26-matchings). In a star every edge uses the centre, so the matchings are the empty set and the 14 single edges: 15 in total.
:::
