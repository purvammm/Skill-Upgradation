A brute force over pairs or over subarrays looks at Θ(*n*²) candidates. For *n* = 10⁵ that is 5 · 10⁹, far too many. This chapter is about two ideas that look at only O(*n*) of them and still never miss the answer.

The first idea works on a **sorted** array. Two indices start at the two ends and move towards each other; at every step one comparison proves that one of the two elements cannot be part of any answer, so it is discarded for good. The second idea works on **contiguous** pieces of an array or string. A window [*l*, *r*] slides from left to right; the right end always advances, and the left end advances only when the window breaks a rule. Both pointers move at most *n* times, so the whole scan is linear.

Neither idea is correct for every problem, and the important part of the chapter is the condition that makes each one correct. For two pointers it is sortedness. For windows it is *monotonicity*: shrinking a valid window must keep it valid. Each section states the condition, proves the algorithm correct under it, and shows the counterexample when it fails. The chapter ends with the monotonic deque, which answers "maximum of every window of size *k*" in O(*n*), and with a guide to choosing between this chapter's tools and the prefix sums of Chapter 2.

## Two pointers on a sorted array {#sec-3-pairs}

### Is there a pair with a given sum?

Given a sorted array *a*[0..*n* − 1] and a target *t*, decide whether some *i* < *j* has *a*[*i*] + *a*[*j*] = *t*. The [[two pointers|two-pointer technique]] puts *l* at the first index and *r* at the last. If *a*[*l*] + *a*[*r*] is too small, the only way to increase the sum is to move *l* right; if it is too large, move *r* left.

```java {#lst-3-pairs} Two pointers on a sorted array: find a pair, count pairs
// Sorted array, pointers at both ends: does any pair add up to target?
static boolean hasPairWithSum(int[] sorted, long target) {
    int l = 0, r = sorted.length - 1;
    while (l < r) {
        long s = (long) sorted[l] + sorted[r];
        if (s == target) return true;
        if (s < target) l++;      // need a bigger sum
        else r--;                 // need a smaller sum
    }
    return false;
}

// Count pairs i < j with sorted[i] + sorted[j] <= target
static long countPairsAtMost(int[] sorted, long target) {
    long count = 0;
    int l = 0, r = sorted.length - 1;
    while (l < r) {
        if ((long) sorted[l] + sorted[r] <= target) {
            count += r - l;       // sorted[l] pairs with every index in (l, r]
            l++;
        } else {
            r--;
        }
    }
    return count;
}
```

The argument for correctness is an *elimination* argument: each move throws away one index, and we must show that the index thrown away is not part of any answer.

:::theorem{#thm-3-pairs} Two pointers discard no valid pair
In `hasPairWithSum`, the following holds at the start of every iteration: every pair *i* < *j* with *a*[*i*] + *a*[*j*] = *t* satisfies *l* ≤ *i* and *j* ≤ *r*. Consequently the method returns `true` exactly when such a pair exists.
:::

:::proof
Initially *l* = 0 and *r* = *n* − 1, so every pair satisfies the bounds. Suppose the invariant holds and *s* = *a*[*l*] + *a*[*r*] < *t*. Any valid pair that uses index *l* has the form (*l*, *j*) with *j* ≤ *r* by the invariant, and since the array is sorted, *a*[*l*] + *a*[*j*] ≤ *a*[*l*] + *a*[*r*] < *t*. So no valid pair uses *l*, and every valid pair has *i* ≥ *l* + 1: the invariant survives `l++`. The case *s* > *t* is symmetric: any valid pair (*i*, *r*) has *a*[*i*] + *a*[*r*] ≥ *a*[*l*] + *a*[*r*] > *t*, so `r--` discards nothing. If the method returns `true`, it has found a valid pair. If the loop ends with *l* ≥ *r*, the invariant says every valid pair has *l* ≤ *i* < *j* ≤ *r* ≤ *l*, which is impossible, so none exists.
:::

Each iteration moves one pointer one step towards the other, so there are at most *n* − 1 iterations: O(*n*) time and O(1) memory, after an O(*n* log *n*) sort if the input is not sorted already.

Take *a* = [1, 3, 4, 6, 8, 11] and *t* = 14.


### Counting pairs with sum at most X

`countPairsAtMost` uses the same picture to count instead of search. If *a*[*l*] + *a*[*r*] ≤ *X*, then *a*[*l*] + *a*[*j*] ≤ *X* for **every** *j* in (*l*, *r*], because those *a*[*j*] are no larger than *a*[*r*]. So *a*[*l*] forms *r* − *l* good pairs at once, and index *l* has nothing more to contribute. If the sum is greater than *X*, then *a*[*i*] + *a*[*r*] > *X* for every *i* in [*l*, *r*), so index *r* forms no good pair with anything left.

:::claim{#thm-3-count} Counting pairs
At the start of every iteration of `countPairsAtMost`, `count` equals the number of good pairs (*i*, *j*) with *i* < *l*, and no good pair has *l* ≤ *i* < *j* with *j* > *r*. At the end, `count` is the number of good pairs.
:::

:::proof
Both statements hold initially. In the first branch, the good pairs with *i* = *l* are exactly (*l*, *j*) for *l* < *j* ≤ *r* (pairs with *j* > *r* are excluded by the second statement), which is *r* − *l* pairs; adding them and moving *l* keeps the first statement. In the second branch, no good pair uses *r* together with an index in [*l*, *r*), so the second statement survives `r--`. When *l* ≥ *r*, every pair with *i* ≥ *l* has *j* > *i* ≥ *l* ≥ *r*, so it is not good, and all good pairs have been counted.
:::

For *a* = [1, 3, 4, 6, 8, 11] and *X* = 9 the scan adds 4 (index 0 with indices 1..4) and then 2 (index 1 with indices 2..3), for a total of 6, matching a brute force over all 15 pairs.

:::pitfall
Sorting changes indices. LeetCode 1 (Two Sum) asks for original indices, so either use the hash map of Chapter 1 or sort an array of indices by value. And cast before adding: `(long) a[l] + a[r]`, since two values near 2 · 10⁹ overflow `int`.
:::

## 3Sum: sorting plus two pointers {#sec-3-3sum}

LeetCode 15 (3Sum) asks for all *distinct* triples of values from the array that add up to 0. Checking every triple is Θ(*n*³). Fixing the smallest element of the triple turns the rest into a pair problem: after sorting, for each *i*, find all pairs in *a*[*i* + 1..*n* − 1] with sum −*a*[*i*]. Each pair search is the scan of @sec-3-pairs, so the total is O(*n*²).

The difficulty is **duplicates**. The array [−1, −1, 0, 1, 1] contains the triple of values (−1, 0, 1) four times over as index triples, but it must be reported once. Sorting puts equal values next to each other, which makes duplicates cheap to skip.

### Distinct pairs with a given sum

@lst-3-distinct is the inner loop: it reports every pair of *values* (*x*, *y*) with *x* ≤ *y* and *x* + *y* = *t* inside *a*[*from*..*n* − 1], each exactly once.

```java {#lst-3-distinct} All distinct value pairs with a given sum in a sorted range
static List<int[]> distinctPairs(int[] a, int from, long target) {   // a sorted; search a[from..]
    List<int[]> out = new ArrayList<>();
    int l = from, r = a.length - 1;
    while (l < r) {
        long s = (long) a[l] + a[r];
        if (s < target) l++;
        else if (s > target) r--;
        else {
            out.add(new int[]{a[l], a[r]});
            l++;
            r--;
            while (l < r && a[l] == a[l - 1]) l++;   // skip copies of the value just used
            while (l < r && a[r] == a[r + 1]) r--;
        }
    }
    return out;
}
```

:::claim{#thm-3-distinct} Each value pair is reported once
@lst-3-distinct reports every value pair (*x*, *y*) with *x* ≤ *y*, *x* + *y* = *t*, that occurs at two different positions of *a*[*from*..*n* − 1], and reports each such pair exactly once.
:::

:::proof
The two non-hit branches discard an index exactly as in @thm-3-pairs, so no pair that is still unreported is lost there. At a hit with *x* = *a*[*l*] and *y* = *a*[*r*], every other pair whose smaller value is *x* must have larger value *t* − *x* = *y*, and every pair whose larger value is *y* has smaller value *x*: both are the pair just reported. So moving *l* past every copy of *x* and *r* past every copy of *y* loses no new pair. Because *l* has moved past all copies of *x*, every later report has a strictly larger first value, so no value pair is reported twice.
:::

### Assembling 3Sum

The full method is now three steps, which you will write yourself for LeetCode 15:

1. Sort the array.
2. For each *i*, skip it if *a*[*i*] = *a*[*i* − 1]: every triple starting with that value was already found from the first copy, because that copy saw a superset of the remaining elements.
3. Otherwise collect the distinct pairs with sum −*a*[*i*] in *a*[*i* + 1..*n* − 1] and report each together with *a*[*i*].

A triple of values *x* ≤ *y* ≤ *z* is reported only from the first index *i* holding *x* (step 2), and only once there (@thm-3-distinct), so every distinct triple appears exactly once. For [−2, 0, 1, 1, 2, −1, −4, 2], sorted to [−4, −2, −1, 0, 1, 1, 2, 2], the method finds the four triples (−4, 2, 2), (−2, 0, 2), (−2, 1, 1) and (−1, 0, 1). An assembled version of these steps matched a brute force over all triples on 20,000 random arrays of up to 9 values in [−5, 5].

The outer loop runs *n* times and each inner scan is O(*n*), so the time is O(*n*²): about *n*²/2 = 4.5 · 10⁶ pointer moves for *n* = 3 000. Apart from the output and the sort, the memory is O(1).

### Why not hashing?

A hash set can also find pairs: for each *i*, scan *j* > *i* and ask whether −*a*[*i*] − *a*[*j*] was seen between them. That is O(*n*²) as well, but it is slower and messier. Every step is a hash operation instead of an array comparison (in Chapter 1's measurements, about five times slower per operation), and removing duplicate triples needs a set of sorted triples, with extra memory and boxing. Sorting makes duplicates adjacent, so a single comparison skips them.

:::tip
"Pairs or triples with a sum" plus "the order of the input does not matter" is the signal to sort first. The sort costs O(*n* log *n*), which never dominates an O(*n*²) search.
:::

## Variable-size sliding windows {#sec-3-window}

The second family asks about **contiguous** pieces: the longest substring without a repeated character, the longest run of 1s if you may flip *k* zeros, the shortest stretch whose sum reaches a target. A brute force tries every window [*l*, *r*]: Θ(*n*²) windows, and often more work per window.

### The template

:::definition{#def-3-window} Sliding window
A [[sliding window]] is a contiguous piece *a*[*l*..*r*] of an array or string, described by its two ends, together with a *state* that summarises its contents (a sum, a count of zeros, a table of counts). The window *slides* when *r* or *l* advances by one; the state is updated for the one element that enters or leaves, instead of being recomputed.
:::

```java {#lst-3-window} Sliding window template: longest subarray with at most k distinct values
// Longest subarray with at most k distinct values.
// Template: grow r, shrink l while the window is invalid, then record the answer.
static int longestAtMostKDistinct(int[] a, int k) {
    Map<Integer, Integer> cnt = new HashMap<>();
    int best = 0;
    for (int l = 0, r = 0; r < a.length; r++) {
        cnt.merge(a[r], 1, Integer::sum);                       // 1. add a[r]
        while (cnt.size() > k) {                                // 2. shrink while invalid
            if (cnt.merge(a[l], -1, Integer::sum) == 0) cnt.remove(a[l]);
            l++;
        }
        best = Math.max(best, r - l + 1);                       // 3. [l, r] is valid
    }
    return best;
}
```

The three numbered steps are the whole pattern. The *state* of the window (here the map of counts) must always describe exactly the elements of *a*[*l*..*r*]: step 1 adds *a*[*r*], and every `l++` in step 2 first removes *a*[*l*].

:::pitfall
Bringing a count down to 0 does not remove the key from a `HashMap`. Remove it yourself, as the template does, or `cnt.size()` counts values that are no longer in the window.
:::

### When is it correct?

The template never tries most windows. It is correct only because of a property of the rule.

:::definition{#def-3-monotone} Monotone window condition
A rule that decides whether a window *a*[*l*..*r*] is *valid* is [[monotone|monotone window condition]] if every contiguous sub-window of a valid window is valid, and the empty window is valid.
:::

"At most *k* distinct values", "no repeated character", "at most *k* zeros" and "sum ≤ *X* when all values are positive" are monotone: removing elements from either end cannot create a second distinct value, a repeat, a zero or a larger positive sum. "Sum exactly *k*" is not, and neither is "sum ≤ *X*" when negative values are allowed.

For each right end *r*, let *L*(*r*) be the smallest *l* ≤ *r* + 1 for which [*l*, *r*] is valid. (The empty window [*r* + 1, *r*] is valid, so *L*(*r*) exists.)

:::lemma{#lem-3-left} The left boundary only moves right
If the window condition is monotone, then [*l*, *r*] is valid exactly when *L*(*r*) ≤ *l* ≤ *r* + 1, and *L*(*r*) ≤ *L*(*r* + 1) for every *r*.
:::

:::proof
If *L*(*r*) ≤ *l*, then [*l*, *r*] is a sub-window of the valid window [*L*(*r*), *r*], so it is valid; if *l* < *L*(*r*), it is invalid by the minimality of *L*(*r*). For the second part, [*L*(*r* + 1), *r* + 1] is valid, so its sub-window [*L*(*r* + 1), *r*] is valid, and by minimality *L*(*r*) ≤ *L*(*r* + 1).
:::

:::theorem{#thm-3-window} Correctness of the template
If the window condition is monotone, then after step 2 of iteration *r* the template has *l* = *L*(*r*). Hence `r - l + 1` is the length of the longest valid window ending at *r*, and `best` is the length of the longest valid window overall.
:::

:::proof
By induction on *r*, with *L*(−1) = 0. Before iteration *r*, *l* = *L*(*r* − 1) ≤ *L*(*r*) by @lem-3-left. Step 2 increments *l* while [*l*, *r*] is invalid, which by the lemma means while *l* < *L*(*r*), and stops as soon as *l* = *L*(*r*), because that window is valid. The longest valid window ending at *r* starts at *L*(*r*), and every valid window ends at some *r*, so the maximum over *r* is the overall answer.
:::

:::theorem{#thm-3-linear} The template runs in O(n) steps
Over the whole run, step 2 executes at most *n* times in total, so the template performs O(*n*) additions and removals.
:::

:::proof
Each execution of the loop body in step 2 increases *l* by one, *l* never decreases, and *l* ≤ *r* + 1 ≤ *n* throughout. So the body runs at most *n* times over the whole run, not *n* times per iteration of *r*. Each index enters the window once (step 1) and leaves at most once (step 2).
:::

This is an [[amortised|amortised analysis]] bound: a single iteration of *r* may shrink the window by many steps, but the total over all iterations is at most *n*. With a `HashMap` state each step costs O(1) expected time; with an `int[]` of counts it costs O(1) worst case.

### Example: the longest substring without repeating characters

LeetCode 3 (Longest Substring Without Repeating Characters) is the standard first window problem. The rule "no character occurs twice" is monotone. The state is a count per character; LeetCode 3's strings are ASCII, so an `int[128]` replaces the map. When *a*[*r*] makes a count 2, only that character can be repeated, so step 2 shrinks until its count is 1 again.

```java {#lst-3-lc3} Longest substring without repeating characters (LeetCode 3)
static int lengthOfLongestSubstring(String s) {
    int[] cnt = new int[128];                    // LeetCode 3 uses ASCII characters only
    int best = 0;
    for (int l = 0, r = 0; r < s.length(); r++) {
        char c = s.charAt(r);
        cnt[c]++;
        while (cnt[c] > 1) cnt[s.charAt(l++)]--;  // shrink until c is unique again
        best = Math.max(best, r - l + 1);
    }
    return best;
}
```

:::example{#ex-3-lc3} Tracing on "abcbdab"

```trace

0   a         0 -> 0          a         1
1   b         0 -> 0          ab        2
2   c         0 -> 0          abc       3
3   b         0 -> 2          cb        3    (drop a, b)

```

The answer is 4 ("cbda").

A common variant stores the last index where each character was seen and jumps *l* straight to one past it: `l = Math.max(l, last[c] + 1)`. It is the same algorithm with step 2 done in one jump; the `Math.max` stops *l* from moving left when the previous copy is already outside the window.

### Example: at most k zeros

LeetCode 1004 (Max Consecutive Ones III) gives a 0/1 array and asks for the longest run of 1s if you may flip at most *k* zeros. Flipping zeros inside a window turns it into all 1s, so the question is "the longest window with at most *k* zeros", a monotone rule. The state is one integer.

```java {#lst-3-lc1004} Longest window with at most k zeros (LeetCode 1004)
static int longestOnes(int[] a, int k) {
    int zeros = 0, best = 0;
    for (int l = 0, r = 0; r < a.length; r++) {
        if (a[r] == 0) zeros++;
        while (zeros > k) if (a[l++] == 0) zeros--;   // shrink until at most k zeros
        best = Math.max(best, r - l + 1);
    }
    return best;
}
```

## Longest repeating character replacement {#sec-3-replace}

LeetCode 424 (Longest Repeating Character Replacement) gives a string of uppercase letters and an integer *k*: you may replace at most *k* characters, and you want the longest substring of one repeated letter. This section derives the window condition and then proves a shortcut that most published solutions use without explanation.

### The window condition

To make a window uniform, keep its most frequent letter and replace everything else. So a window of length *w* whose most frequent letter occurs *f* times needs exactly *w* − *f* replacements:

> [*l*, *r*] is valid ⇔ (*r* − *l* + 1) − maxCount(*l*, *r*) ≤ *k*,

where maxCount(*l*, *r*) is the largest count of a single letter in the window. The rule is monotone: removing an end character lowers *w* by 1 and *f* by at most 1, so *w* − *f* cannot grow. By @thm-3-window the template is correct if step 2 recomputes the maximum of the 26 counts each time. That costs 26 steps per check, and there are at most 2*n* checks (one that fails per *r*, one per `l++`), which is fast enough for any limit in this problem.

### The shortcut: never decrease maxCount

The well-known O(*n*) version keeps a variable *M* that is the largest count **ever** seen, never decreases it, and replaces the `while` by an `if`: when (*r* − *l* + 1) − *M* > *k*, it removes one character on the left. So the window never shrinks: each step it either grows by one or slides one place to the right. The window may even be invalid for a while. The answer is the largest length reached.

:::example{#ex-3-replace} The shortcut on "ABBACBBA" with k = 1
The table shows the state after each step. "true max" is the real maxCount of the window, for comparison.

```trace
r  ch   M   slide?  window  length  true max  best
0  A    1   no      A         1        1        1
1  B    1   no      AB        2        1        2
2  B    2   no      ABB       3        2        3
3  A    2   yes     BBA       3        2        3
4  C    2   yes     BAC       3        1        3   <- invalid window, length kept
5  B    2   yes     ACB       3        1        3
6  B    2   yes     CBB       3        2        3
7  A    2   yes     BBA       3        2        3
```

The answer is 3, which a brute force over all windows confirms. At *r* = 4 and 5 the window needs two replacements, more than *k*, yet nothing goes wrong: the algorithm keeps the length 3 that it has already proved achievable and only looks for something longer.
:::

Why is this correct? The intuition is that the length can only grow when *M* grows, and a stale *M* only describes a window that really existed. Write *w*ᵣ and *M*ᵣ for the window length and *M* after step *r*.

:::lemma{#lem-3-replace} Three facts about the shortcut
(a) *w*ᵣ − *M*ᵣ ≤ *k* after every step. (b) *M*ᵣ is at least the count of every letter in the window [*l*, *r*] just before the possible slide at step *r*. (c) At a step *t* where *M* increases, there is no slide, and the window after step *t* contains *M*ₜ copies of *s*[*t*].
:::

:::proof
(a) If there is no slide, the test (*r* − *l* + 1) − *M*ᵣ ≤ *k* is exactly the statement. If there is a slide, *w*ᵣ = *w*ᵣ₋₁ and *M*ᵣ ≥ *M*ᵣ₋₁, so *w*ᵣ − *M*ᵣ ≤ *w*ᵣ₋₁ − *M*ᵣ₋₁ ≤ *k* by induction. (b) Take a letter *x* in the window and let *t* ≤ *r* be its last position there. When *s*[*t*] was added, the window then in use started no later than the current one (the left end never moves left), so it contained at least as many copies of *x* as the current window, and *M* was raised to at least that count. *M* never decreases. (c) A count rises by one per step, so *M*ₜ = *M*ₜ₋₁ + 1. Before the possible slide the length is *w*ₜ₋₁ + 1, and (*w*ₜ₋₁ + 1) − *M*ₜ = *w*ₜ₋₁ − *M*ₜ₋₁ ≤ *k* by (a), so there is no slide. The count of *s*[*t*] in that window is the new maximum *M*ₜ.
:::

:::theorem{#thm-3-replace} The shortcut finds the optimum
Let *A* be the length of the longest substring that can be made uniform with at most *k* replacements. The window length after the last step equals *A*.
:::

:::proof
*No more than A.* Fix any step *r*, and let *t* ≤ *r* be the last step at which *M* increased, so *M*ᵣ = *M*ₜ. By (c) the window *W* after step *t* has *M*ᵣ copies of some letter *c*, and its length *w*ₜ ≤ *w*ᵣ because lengths never decrease. Any substring of length *w*ᵣ that contains *W* (one exists, since *w*ᵣ ≤ *r* + 1 ≤ *n*) has at least *M*ᵣ copies of *c*, so it needs at most *w*ᵣ − *M*ᵣ ≤ *k* replacements by (a). Hence *A* ≥ *w*ᵣ.
*At least A.* Let [*i*, *j*] be an optimal window. Suppose that at some step *r* ≤ *j* the window started at *i* and slid, so that (*r* − *i* + 1) − *M*ᵣ > *k*. The window [*i*, *r*] is a sub-window of [*i*, *j*], so it is valid: (*r* − *i* + 1) − maxCount(*i*, *r*) ≤ *k*. By (b), *M*ᵣ ≥ maxCount(*i*, *r*), which contradicts the slide. So the left end never passes *i* before step *j*, and *w*ⱼ ≥ *j* − *i* + 1 = *A*. Lengths never decrease, so the final length is at least *A*.
:::

Both versions, the exact one with 26 counts and the shortcut (with `if` or with `while`), matched a brute force on 20,000 random strings over {A, B, C}. Writing the code is left for the problem worksheet. In an exam, the exact version is the safer one to write first: its proof is @thm-3-window.

## Counting windows: exactly K {#sec-3-exact}

Some problems ask **how many** windows satisfy a rule. With a monotone rule, @lem-3-left says the valid windows ending at *r* are exactly [*l*, *r*] for *L*(*r*) ≤ *l* ≤ *r*, so there are *r* − *L*(*r*) + 1 of them. Replace step 3 of the template by `count += r - l + 1` and the scan counts every valid window in O(*n*).

"Exactly *K*" rules are not monotone: a window with exactly two odd numbers has sub-windows with one. The fix is to count two monotone rules and subtract.

:::theorem{#thm-3-exact} Exactly = at most minus at most
For any non-negative quantity *q* attached to windows (the number of odd values, of zeros, of distinct values), the number of windows with *q* = *K* equals atMost(*K*) − atMost(*K* − 1), where atMost(*m*) is the number of windows with *q* ≤ *m*, and atMost(−1) = 0.
:::

:::proof
The windows with *q* ≤ *K* split into two disjoint groups: those with *q* ≤ *K* − 1 and those with *q* = *K*. Counting both sides gives atMost(*K*) = atMost(*K* − 1) + exactly(*K*).
:::

When *q* only grows as a window is extended (counts of odd values, zeros or distinct values all do), "*q* ≤ *m*" is monotone and each atMost is one window scan. Here is the method on a new example: count the subarrays that contain exactly *k* odd numbers.

```java {#lst-3-exact} Subarrays with exactly k odd numbers
static long atMostOdd(int[] a, int k) {
    if (k < 0) return 0;                          // no window has fewer than 0 odd values
    long count = 0;
    int odd = 0;
    for (int l = 0, r = 0; r < a.length; r++) {
        if ((a[r] & 1) == 1) odd++;
        while (odd > k) if ((a[l++] & 1) == 1) odd--;
        count += r - l + 1;                       // windows [l..r], [l+1..r], ..., [r..r]
    }
    return count;
}

static long exactlyKOdd(int[] a, int k) {
    return atMostOdd(a, k) - atMostOdd(a, k - 1);
}
```

The test `(a[r] & 1) == 1` is used instead of `a[r] % 2 == 1` because, as Chapter 1 showed, `-3 % 2` is −1 in Java; the bit test is correct for negative values.

:::example{#ex-3-exact} Exactly two odd numbers in [2, 1, 1, 4, 1, 6]
The two scans, with the number of windows added at each *r*:

```trace

r  a[r]  odd  l  add  total              r  a[r]  odd  l  add  total
0   2     0   0   1     1                0   2     0   0   1     1
1   1     1   0   2     3                1   1     1   0   2     3
2   1     2   0   3     6                2   1     1   2   1     4
3   4     2   0   4    10                3   4     1   2   2     6
```

So exactly(2) = 17 − 11 = 6. Running the method for every *k* gives exactly(0) = 3, exactly(1) = 8, exactly(2) = 6 and exactly(3) = 4. These add up to 21 = 6 · 7/2, the number of non-empty subarrays, as they must.
:::

LeetCode 992 (Subarrays with K Different Integers) has the same shape with *q* = the number of distinct values, which also only grows as a window is extended.

## The shortest valid window {#sec-3-shortest}

"Shortest window that reaches a target" problems have the opposite monotonicity: making a valid window **longer** keeps it valid. A window whose positive values sum to at least *T* still does when extended; a window that contains every required value still does when extended. For such rules the template records the answer **inside** the loop: while the window is valid, record its length, then shrink.

```java {#lst-3-shortest} Shortest subarray with sum at least target (positive values)
// Shortest subarray with sum >= target (all values positive)
static int shortestSumAtLeast(int[] a, long target) {
    int best = Integer.MAX_VALUE;
    long sum = 0;
    for (int l = 0, r = 0; r < a.length; r++) {
        sum += a[r];
        while (sum >= target) {                                 // valid: record, then shrink
            best = Math.min(best, r - l + 1);
            sum -= a[l++];
        }
    }
    return best == Integer.MAX_VALUE ? 0 : best;
}
```

:::lemma{#lem-3-shortest} Correctness of the shrink-while-valid loop
Suppose every window that contains a valid window is valid. For each *r* let *G*(*r*) be the largest *l* such that [*l*, *r*] is valid (or −1 if none). Then *G* is non-decreasing, and after iteration *r* of @lst-3-shortest, *l* = *G*(*r*) + 1 and the shortest valid window ending at *r*, of length *r* − *G*(*r*) + 1, has been recorded.
:::

:::proof
[*G*(*r*), *r*] is valid, so the larger window [*G*(*r*), *r* + 1] is valid and *G*(*r* + 1) ≥ *G*(*r*). Also [*l*, *r*] is valid exactly when *l* ≤ *G*(*r*): windows with smaller *l* contain [*G*(*r*), *r*]. Assume that before iteration *r*, *l* = *G*(*r* − 1) + 1 ≤ *G*(*r*) + 1. The loop records and advances while [*l*, *r*] is valid, that is while *l* ≤ *G*(*r*), so its last recording is the window [*G*(*r*), *r*] and it stops at *l* = *G*(*r*) + 1. (For *r* = 0 start from *l* = 0 = *G*(−1) + 1 with *G*(−1) = −1.)
:::

The same O(*n*) amortised argument as @thm-3-linear applies: *l* advances at most *n* times in total.

### Need and have

When validity means "the window contains everything on a list", keep two numbers instead of comparing whole count tables. These [[need/have counters]] are *need*, how many requirements there are, and *have*, how many the window currently meets. A requirement becomes met when its count rises to the required level and stops being met when the count falls below it, so each add or remove updates *have* in O(1). The window is valid exactly when *have* = *need*.

Here is the pattern on a new problem: the shortest subarray that contains every distinct value of the array at least once. The requirements are "value *v* occurs at least once", one per distinct value.

```java {#lst-3-needhave} Shortest window containing every distinct value (need/have counters)
static int shortestWithAllValues(int[] a) {
    Map<Integer, Integer> cnt = new HashMap<>();
    Set<Integer> values = new HashSet<>();
    for (int x : a) values.add(x);
    int need = values.size();                                   // values the window must contain
    int have = 0, best = Integer.MAX_VALUE;
    for (int l = 0, r = 0; r < a.length; r++) {
        if (cnt.merge(a[r], 1, Integer::sum) == 1) have++;      // a value enters the window
        while (have == need) {                                  // valid: record, then shrink
            best = Math.min(best, r - l + 1);
            if (cnt.merge(a[l], -1, Integer::sum) == 0) have--; // a value leaves completely
            l++;
        }
    }
    return best == Integer.MAX_VALUE ? 0 : best;
}
```

:::example{#ex-3-needhave} Tracing on [2, 1, 2, 2, 3, 1, 3, 2]
There are three distinct values, so *need* = 3. The table shows, for each *r*, the windows recorded inside the loop and the state when the loop stops.

```trace
r  a[r]  windows recorded (length)          have after  l after  best
0   2    -                                      1          0       -
1   1    -                                      2          0       -
2   2    -                                      2          0       -
3   2    -                                      2          0       -
4   3    [2,1,2,2,3] (5), [1,2,2,3] (4)         2          2       4
5   1    [2,2,3,1] (4), [2,3,1] (3)             2          4       3
6   3    -                                      2          4       3
7   2    [3,1,3,2] (4), [1,3,2] (3)             2          6       3
```

The answer is 3, for example [2, 3, 1] at indices 3..5.
:::

For a requirement list with multiplicities, such as "at least two copies of *x* and one of *y*", store the required count per item and increase *have* when an item's count reaches its requirement exactly. That is the key observation behind LeetCode 76 (Minimum Window Substring).

## Fixed-size windows and the monotonic deque {#sec-3-deque}

Now the window has a fixed size *k*, and the question is the maximum of every window: for *a*[0..*n* − 1], output max(*a*[*i*..*i* + *k* − 1]) for *i* = 0..*n* − *k*. Sums of fixed windows are easy (add the new element, subtract the old one), but a maximum cannot be "subtracted": when the current maximum leaves the window, which element takes over? Rescanning the window costs O(*k*) per step and O(*nk*) in total; a `TreeMap` of counts gives O(*n* log *k*). A deque does it in O(*n*).

### The idea: dominated elements never matter

Suppose *j* < *i* and *a*[*j*] ≤ *a*[*i*]. Every window that contains *j* and is still to come also contains *i*, because *i* is later and windows move right. So *j* can never again be the unique maximum: *i* is at least as large and leaves the window later. Such a *j* can be deleted the moment *i* arrives. What remains after the deletions is a list of indices whose values strictly decrease from oldest to newest.

:::definition{#def-3-deque} Monotonic deque
A [[monotonic deque]] for window maxima is a double-ended queue of indices *j*₁ < *j*₂ < ⋯ < *j*ₘ from the current window whose values strictly decrease: *a*[*j*₁] > *a*[*j*₂] > ⋯ > *a*[*j*ₘ]. New indices enter at the back; indices leave at the back when dominated and at the front when they fall out of the window.
:::

```java {#lst-3-windowmax} Maximum of every window of size k with a monotonic deque
// Maximum of every window of size k, O(n). The deque holds indices; their values decrease.
static int[] windowMax(int[] a, int k) {
    int n = a.length;
    int[] res = new int[n - k + 1];
    ArrayDeque<Integer> dq = new ArrayDeque<>();
    for (int i = 0; i < n; i++) {
        while (!dq.isEmpty() && a[dq.peekLast()] <= a[i]) dq.pollLast();   // they can never win now
        dq.addLast(i);
        if (dq.peekFirst() <= i - k) dq.pollFirst();                       // front left the window
        if (i >= k - 1) res[i - k + 1] = a[dq.peekFirst()];
    }
    return res;
}
```

:::theorem{#thm-3-deque} The front of the deque is the window maximum
After iteration *i* of @lst-3-windowmax: (1) the deque holds indices of the window (*i* − *k*, *i*] in increasing order with strictly decreasing values, and its last index is *i*; (2) every index of the window that is not in the deque has a later index of the window with a value at least as large. Consequently *a*[front] is the maximum of the window.
:::

:::proof
By induction on *i*. Suppose (1) and (2) hold after iteration *i* − 1 for the window (*i* − 1 − *k*, *i* − 1]. The `while` loop removes from the back every index *j* with *a*[*j*] ≤ *a*[*i*]; each such *j* is dominated by the later index *i*, which is in the new window, so (2) holds for it. The back elements that stay have values greater than *a*[*i*], so appending *i* keeps the values strictly decreasing. All deque indices were > *i* − 1 − *k*, so the only one that can now lie outside the new window is *i* − *k*, and if present it is the smallest index, at the front; the `if` removes it. Indices outside the window do not matter for (2): an index *j* of the new window that was dominated by a later *j*′ is still dominated, since *j*′ > *j* is also in the new window. This proves (1) and (2). For the consequence, start from any window index and follow "a later index with a value at least as large" while the current index is not in the deque. Indices increase, so this stops at a deque index with a value at least the starting value. So the window maximum is attained in the deque, and the deque's largest value is at its front.
:::

:::theorem{#thm-3-dequecost} The deque method is linear
@lst-3-windowmax performs at most 2*n* deque insertions and removals in total, so it runs in O(*n*) time and uses O(*k*) memory.
:::

:::proof
Each index is added to the deque exactly once. Each index is removed at most once, either from the back or from the front, because a removed index is never added again. So there are at most *n* additions and *n* removals, and each `while` test that fails ends the loop for that iteration, adding at most *n* more comparisons. The deque never holds more than the *k* indices of one window.
:::

:::example{#ex-3-windowmax} Tracing with k = 3
Take *a* = [4, 2, 12, 3, 8, 7, 1, 5]. The deque is shown as index:value pairs from front to back.

```trace

1    2        -                 -            0:4 1:2

```

The output is [12, 12, 12, 8, 8, 7]. The run made 14 deque operations, within the bound 2*n* = 16.
:::

:::pitfall
Store indices, not values: the front check `dq.peekFirst() <= i - k` needs to know where the front element sits. For window minima, flip the comparison and remove from the back while `a[dq.peekLast()] >= a[i]`.
:::

The same deque appears in dynamic programming when *dp*[*i*] needs the best *dp*[*j*] over the last *k* positions *j*: the deque holds candidate indices *j*, and each *dp*[*i*] is computed in O(1) amortised instead of O(*k*).

## Choosing between windows, two pointers and prefix sums {#sec-3-choose}

The three techniques of Chapters 2 and 3 overlap, and the wrong choice produces code that passes the samples and fails hidden tests. The deciding questions are about structure, not about the story in the statement.

Table: {#tbl-3-choose} Which technique for which question
| The question | Condition you need | Technique | Cost |
|---|---|---|---|
| pair or triple with a target sum, order irrelevant | none (sort first) | two pointers from both ends | O(*n* log *n*) + O(*n*) per pair search |
| longest window with a rule | rule is monotone (sub-windows of valid windows are valid) | grow-and-shrink window | O(*n*) |
| shortest window with a rule | extending a valid window keeps it valid | shrink-while-valid window | O(*n*) |
| number of windows with *q* = *K* | *q* never decreases when a window is extended | atMost(*K*) − atMost(*K* − 1) | O(*n*) |
| max or min of every window of size *k* | fixed size | monotonic deque | O(*n*) |
| windows with sum exactly *k*, any signs | none | prefix sums + hash map (Chapter 2) | O(*n*) expected |

### Negative numbers break windows

Sum-based window rules are monotone only when every value is positive (or non-negative). With negatives, removing an element can **raise** the sum, and the template silently gives wrong answers. Two small inputs, both checked by running the code:

- *Longest subarray with sum ≤ 0* on [5, −10, 5]. The whole array has sum 0, so the answer is 3. The window template removes the 5 at index 0 as soon as it sees it (sum 5 > 0) and ends with 2.
- *Shortest subarray with sum ≥ 1* on [−3, 3]. The answer is 1, the subarray [3]. @lst-3-shortest never sees a valid window, because the sum of [−3, 3] is 0 and it never drops the −3, so it returns 0 ("none").

When negatives are allowed, go back to the prefix sums of Chapter 2. Sums of subarrays become differences *P*[*r* + 1] − *P*[*l*], and questions about them become questions about pairs of prefix values, which a hash map (exact sums), sorting or a monotonic deque over the prefix array (shortest sum ≥ *T*) can answer.

:::keyidea
Before you write a window, test the rule: "if [*l*, *r*] is valid, is [*l* + 1, *r*] valid?". If the answer depends on the signs of the values, the window is wrong for some input.
:::

## Summary

- On a sorted array, two pointers from both ends find or count pairs in O(*n*): each comparison proves that one end index belongs to no answer (@thm-3-pairs).
- 3Sum is "fix the smallest, then two pointers", O(*n*²). Sorting makes duplicate values adjacent, so skipping equal neighbours reports each triple once.
- A variable window is correct when its rule is monotone: sub-windows of valid windows are valid. Then the left end *L*(*r*) never moves left, and grow-and-shrink finds the longest valid window ending at every *r*.
- Both pointers move at most *n* times, so a window scan costs O(*n*) amortised, whatever happens in one iteration.
- For character replacement the rule is length − maxCount ≤ *k*. Recomputing maxCount from 26 counts is correct and simple; keeping a never-decreasing maxCount and sliding the window is also correct, by @thm-3-replace.
- Count valid windows by adding *r* − *l* + 1 per step; count "exactly *K*" as atMost(*K*) − atMost(*K* − 1).
- For "shortest valid window" rules that survive extension, record inside the loop and shrink while valid; need/have counters make the validity test O(1).
- The monotonic deque keeps only undominated indices, so its front is the window maximum and each index enters and leaves once: O(*n*).
- With negative values, sum-based windows fail; use prefix sums.

## Review questions

1. In @thm-3-pairs, why is it safe to discard index *l* when *a*[*l*] + *a*[*r*] < *t*, even though *a*[*l*] has not been tried with any index other than *r*?
2. `countPairsAtMost` adds *r* − *l* in one step. Which property of the array justifies counting all those pairs without looking at them?
3. In 3Sum, what goes wrong if the outer loop does not skip *i* when *a*[*i*] = *a*[*i* − 1]? Give an input and the duplicated output.
4. Which of these window rules are monotone? (a) at most 3 distinct values; (b) at least 3 distinct values; (c) sum ≤ 10 with values in [1, 100]; (d) sum ≤ 10 with values in [−5, 5]; (e) every character occurs an even number of times.
5. Explain in one paragraph why the window template is O(*n*) even though the inner `while` loop can run *n* times in a single iteration.
6. In the replacement shortcut of @sec-3-replace, the window can be invalid. Why does that not make the final answer too large?
7. Use @thm-3-exact to compute the number of subarrays of [1, 1, 1] with exactly one odd value, showing atMost(1) and atMost(0).
8. In @lst-3-windowmax the back is popped while `a[back] <= a[i]`. What changes if it pops only while `a[back] < a[i]`? Is the output still correct, and is the running time still O(*n*)?
9. Give an input on which the window template for "longest subarray with sum ≤ *X*" fails because of a negative value, and name the method you would use instead.

:::answers
1. By the invariant every valid pair lies inside [*l*, *r*], so the only possible partners of *l* are indices *j* ≤ *r*. Since the array is sorted, *a*[*j*] ≤ *a*[*r*] for all of them, so *a*[*l*] + *a*[*j*] ≤ *a*[*l*] + *a*[*r*] < *t*. Trying *r*, the largest partner, already tried them all.
2. Sortedness: for every *j* in (*l*, *r*], *a*[*j*] ≤ *a*[*r*], so *a*[*l*] + *a*[*j*] ≤ *a*[*l*] + *a*[*r*] ≤ *X*. All *r* − *l* pairs (*l*, *j*) are good.
3. A triple can then be reported once from each copy of its smallest value. For [−1, −1, 0, 1] the method reports (−1, 0, 1) twice: from the first −1 it finds the pair (0, 1) in [−1, 0, 1], and from the second −1 it finds (0, 1) again in [0, 1].
4. (a) Monotone. (b) Not monotone: a valid window can have invalid sub-windows; extending keeps it valid, so it suits the shortest-window loop instead. (c) Monotone, because all values are positive. (d) Not monotone: removing −5 from a window can raise its sum above 10. (e) Not monotone: "aa" is valid but its sub-window "a" is not.
5. Every iteration of the inner loop increases *l* by one, *l* never decreases, and *l* never exceeds *n*. So across the whole run the inner loop body executes at most *n* times in total. Adding the *n* iterations of the outer loop gives O(*n*) steps.
6. The length only increases at a step where (length − *M*) ≤ *k*, and *M* is the count of one letter inside a window that really occurred, of length at most the current length (@lem-3-replace (c)). Any window of the current length that contains that earlier window is valid, so every length the algorithm reports is achievable (first half of @thm-3-replace).
7. atMost(1): the windows with at most one odd value are the three single elements, so 3. atMost(0) = 0, since every element is odd. Exactly one odd value: 3 − 0 = 3.
8. Equal values then stay in the deque, so its values are non-increasing instead of strictly decreasing. The front is still a maximum, so the output stays correct, and each index is still added and removed at most once, so the time stays O(*n*). The deque may hold more elements.
9. [5, −10, 5] with *X* = 0: the answer is 3 (sum 0), but the template drops the first 5 immediately and returns 2. Use prefix sums: the subarray *a*[*l*..*r*] qualifies when *P*[*l*] ≥ *P*[*r* + 1] − *X*, so for each right end you need the smallest *l* with that property, which prefix maxima of *P* and a binary search (Chapter 6) find in O(log *n*).
:::
