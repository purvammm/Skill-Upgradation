## Why consolidate {#sec-28-why}

A topic you studied three weeks ago is not lost, but it is slow to retrieve. In a mock that looks like five minutes spent remembering whether the Fenwick loop adds `i & -i` or subtracts it, or an hour on a problem whose signal you would have seen at once in the week you learned it. Consolidation is practice at retrieving: cover the answer, produce it, check.

:::definition{#def-28-signal} Signal
A [[signal]] is a feature of a statement that points to a technique: a phrase in the question ("minimise the maximum"), an object (a parent array, a set of intervals) or a limit (*n* ≤ 20). A statement usually has several signals. The largest limit is the one to read first.
:::

:::definition{#def-28-map} Pattern-recognition map
A [[pattern-recognition map]] is a table from signals to techniques, with the chapter in which each technique is taught and proved. It is read in the direction statement → technique, the opposite of the order in which a textbook is written.
:::

Recognition and recall fail in different ways, so they are practised separately: recognition on statements without code (Workbook Exercise 28.3 has twelve new ones), recall on code without statements, in the handbook's recall mode (@sec-28-templates). The speed drill joins the two under a clock.

:::infosys
The plan's note for today says that writing templates quickly and without errors is what saves time on the real Q1. The official sample paper shows why: its "Easy" problem needs three techniques at once (the square-free kernel, small-to-large merging and a traversal without recursion), so every minute not spent typing a template is a minute for combining them.
:::

## From the largest limit to a technique family {#sec-28-limits}

The four tables have 59 rows, too many to scan under pressure. The limits shorten the list before you read the words: the largest *n* fixes the complexity that fits, the complexity fixes a small family of techniques, and only then do the signals choose.

:::definition{#def-28-family} Technique family
A [[technique family]] is the set of techniques whose cost fits one band of the largest limit. For *n* ≤ 20 it is the exponential searches of Chapters 9 and 22; for *n* ≤ 2 · 10⁵ it is sorting, heaps, binary search, Fenwick and segment trees, Dijkstra and the tree methods.
:::

The bands are those of the handbook's limits table, which Chapter 16 printed in full, taken at the lower end of each range. At each band's limit the number of steps is 10 · 10! ≈ 3.6 · 10⁷, 20 · 2²⁰ ≈ 2.1 · 10⁷, 500³ = 1.25 · 10⁸, 5000² = 2.5 · 10⁷, 2 · 10⁵ · log₂(2 · 10⁵) ≈ 3.5 · 10⁶ and 10⁷; for a single value, √10¹² = 10⁶ and log₂ 10¹⁸ ≈ 60. Each fits the 10⁸ to 3 · 10⁸ simple operations per second that the handbook assumes for Java, the cubic band only just.

Three corrections apply before you read the band.

* **Several inputs.** With *n* elements and *q* queries the budget is about (*n* + *q*) log *n*; the brute force costs *n* · *q*.
* **Many test cases.** When the statement bounds the sum of *n* over *t* test cases, the band applies to that sum, and each test case may only do work proportional to its own *n* (the pitfall of Chapter 9).
* **Values are not lengths.** A value up to 10⁹ cannot index an array, and searching over it costs only log₂ 10⁹ ≈ 30 checks (Chapter 6).

## The speed drill {#sec-28-drill}

:::definition{#def-28-drill} Speed drill
A [[speed drill]] is a short problem solved against a fixed limit, here 15 minutes, with the whole exam routine: read, model, limits, technique, code, samples, edge cases, checklist, submit. Its purpose is the routine, not the problem.
:::

The three drills are LeetCode 217 (Contains Duplicate), LeetCode 881 (Boats to Save People) and LeetCode 2300 (Successful Pairs of Spells and Potions). The plan's usual limits are 20 minutes for an Easy and 40 for a Medium, so today's 15 minutes come from not hesitating between steps more than from typing faster. A useful split: two minutes to read and model, two to write the limit, the technique and the edge cases, seven to code, three to run the samples and edge cases, and one for the checklist of Chapter 27. :::example{#ex-28-dup} LeetCode 217
"Does any value appear at least twice?" is the toolkit's "have I seen *x*?" (Chapter 1), and with up to 10⁵ values the target is O(*n*).

```java {#lst-28-dup} Contains Duplicate (LeetCode 217)
static boolean containsDuplicate(int[] nums) {
    Set<Integer> seen = new HashSet<>();
    for (int x : nums)
        if (!seen.add(x)) return true;      // add returns false when x is already in the set
    return false;
}
```

When the loop reaches index *i*, the set holds exactly the values of *nums*[0..*i* − 1], so `add` fails exactly when *nums*[*i*] repeats an earlier value; if it never fails, all values are distinct. The cost is *n* expected O(1) set operations and O(*n*) memory; sorting and comparing neighbours takes O(*n* log *n*) without a set. Edge cases: one value (false), all values equal (true at index 1). The listing agrees with a quadratic check on 10,000 random arrays.
:::

LeetCode 881 needs an argument. Each boat carries at most two people whose weights add up to at most *limit*, nobody weighs more than *limit*, and the question is the fewest boats. The signal "pairing people in boats" is written on the two-pointer card itself (@tbl-28-map1). The greedy rule: the heaviest person still waiting takes the next boat, and the lightest person still waiting joins if the two fit.

```java {#lst-28-boats} Boats to Save People (LeetCode 881)
static int numRescueBoats(int[] people, int limit) {
    Arrays.sort(people);                    // LeetCode lets you sort the input in place
    int i = 0, j = people.length - 1, boats = 0;
    while (i <= j) {
        if (people[i] + people[j] <= limit) i++;   // the lightest rides with the heaviest
        j--;                                       // the heaviest leaves in this boat either way
        boats++;
    }
    return boats;
}
```

:::theorem{#thm-28-boats} The heaviest person's boat
Let *p*[0] ≤ *p*[1] ≤ ⋯ ≤ *p*[*m* − 1] be the weights still waiting, *m* ≥ 2. If *p*[0] + *p*[*m* − 1] > *limit*, every valid assignment puts the heaviest person alone. Otherwise some assignment with the fewest boats puts the lightest and the heaviest person together. Consequently @lst-28-boats returns the fewest boats.
:::

:::proof
Write *l* for the lightest and *h* for the heaviest person. If *p*[*l*] + *p*[*h*] > *limit*, every other person weighs at least *p*[*l*], so nobody fits with *h*, and *h* is alone in every assignment.

Otherwise take any assignment with the fewest boats. If *l* and *h* already share a boat, there is nothing to do. If *h* is alone, move *l* into *h*'s boat; this is valid because *p*[*l*] + *p*[*h*] ≤ *limit*, and the boat *l* left either keeps one person or becomes empty, so the number of boats does not grow. If *h* shares a boat with someone *k* ≠ *l*, swap *k* and *l*. The boat {*l*, *h*} is valid as before. The other boat now holds *k*, alone or with *l*'s former partner *r*, and *p*[*k*] + *p*[*r*] ≤ *p*[*k*] + *p*[*h*] ≤ *limit* because *p*[*r*] ≤ *p*[*h*]. The number of boats is unchanged. In every case an assignment with the fewest boats puts *l* with *h*.

Now the loop. The people still waiting are always *p*[*i*..*j*], sorted, with *p*[*i*] the lightest and *p*[*j*] the heaviest. Argue by induction on their number *m* = *j* − *i* + 1. For *m* = 1 it uses one boat, which is optimal. For *m* ≥ 2 it makes the choice the first part allows (*h* alone, or *h* with *l*). Removing that boat from an optimal assignment leaves an optimal assignment of the others, since a cheaper one for them would give a cheaper one overall. By induction the loop places the others optimally too.
:::

Sorting costs O(*n* log *n*). Every pass of the loop decreases *j* by one, so it runs once per boat, at most *n* times, and the memory is the sorted array. LeetCode keeps every weight at most 3 · 10⁴, so a sum of two weights fits easily in an `int`.

## Choosing the error-log re-solves {#sec-28-resolve}

The plan asks for four re-solves today. Chapter 26 gave the method for one: a blank file, a timer, the samples and two edge cases of your own, and a new rule. The question here is which four, because after 27 days the log usually holds more entries than fit. Three rules choose them.

1. **Entries due on Day 29 come first.** A re-solve that failed on Day 26 is due again on Day 29 (Chapter 26), but Day 29's plan is one warm-up and rest. Doing it a day early keeps the rest day free.
2. **Then the highest scores.** Give each remaining entry 2 points if its cause appears at least twice in your log, since the log exists because mistakes repeat; 2 points if its topic is one the official sample paper needs (rooted trees and traversals without recursion, small-to-large merging, number theory, segment trees, Fenwick trees, DP with an extra dimension); and 1 point if it has not yet been re-solved cleanly.
3. **Ties go to the more recent entry**, which has had less review.

The weights are a judgement, not a theorem. Change them if your log suggests otherwise, but decide before you see which problems they pick.

## Summary

- Consolidation practises retrieval: recognition (statement to technique) on statements without code, recall (technique to code) on code without statements, and both together in the speed drill.
- The pattern-recognition map has one row per handbook card, from signal to technique to chapter, and a fourth table for the Infosys repeats. Use it only in the direction statement → chapter.
- Read the largest limit before the words. It fixes a band, a complexity and a small family of techniques; the signals then choose inside the family. Correct the band for several inputs, for a bound on the sum of *n*, and for values that are not lengths.
- Write the 15 weakest templates in one timed sitting, aiming for 40 minutes, and check the one detail per template that costs marks.
- A speed drill rehearses the whole routine in 15 minutes. In LeetCode 881 the heaviest person leaves in every boat, with the lightest one when the pair fits; an exchange argument proves it.
- Re-solve the entries due on Day 29 first, then the highest scores for a repeated cause, a sample-paper topic and no clean re-solve yet.
- Tonight, put the template details, the playbook card, the error-log rules and the map's signal columns on paper, so that Day 29 is reading only.

## Review questions

1. Why does the chapter read the largest limit before the words of the statement? What can go wrong with the opposite order?
2. A statement has *t* ≤ 10⁴ test cases with Σ *n* ≤ 2 · 10⁵. Which band of @fig-28-limits applies, and what must the code avoid?
3. Give two signals that both mention pairs but lead to different techniques, and say what decides between them.
4. Why is "160 seconds per template" a useful target, and what does a template that takes more than five minutes tell you?
5. In the proof of @thm-28-boats, why does swapping *k* and *l* leave the other boat valid?
6. The loop of @lst-28-boats is changed to `while (i < j)`. On which inputs does it give a wrong answer?
7. Why are entries due on Day 29 re-solved on Day 28, and why does a re-solve that fails today get no new date?

:::answers
1. The limit fixes the complexity that fits, and with it a family of a few techniques, so the words only have to choose among those. Reading the words first invites a familiar technique that is too slow (an O(*n*²) DP for *n* = 2 · 10⁵) or one far more complex than needed (a segment tree where *n* ≤ 20 allows enumeration).
2. The band of the sum, 2 · 10⁵, so O(*n* log *n*) per test case is fine. The code must avoid per-test work proportional to the maximum size, such as clearing a global array of 2 · 10⁵ entries in each of 10⁴ test cases: 2 · 10⁹ writes.
3. "Count pairs with sum ≤ *X*" leads to two pointers after sorting; "count pairs with XOR below *k*" leads to the binary trie; "count subarrays with sum *k*" counts pairs of prefixes and leads to prefix sums with a hash map. The objects (elements or prefixes) and the operation (sum or XOR) decide.
4. Fifteen templates in 40 minutes is 160 seconds each, about the time to type a short template you know without thinking. More than five minutes means you are re-deriving it, which works at home and costs too much time on the first problem of the exam.
5. The other boat now holds *k* and *l*'s former partner *r*. Since *h* is the heaviest, *p*[*r*] ≤ *p*[*h*], so *p*[*k*] + *p*[*r*] ≤ *p*[*k*] + *p*[*h*], which was at most *limit* because *k* and *h* shared a boat.
6. Whenever one person is left over in the middle, that is whenever the loop ends with *i* = *j*. The last person never gets a boat: [3] with *limit* 3 returns 0 instead of 1. Two of LeetCode's three samples already show the bug, which is a reason to run every sample.
7. Day 29 is a rest day with one warm-up, so work due then is moved one day earlier. A failure today cannot be re-solved three days later, since the exam comes first; its rule goes on the one-page sheet to be read instead.
:::
