## Exercises

Do these after the mock and its post-mortem, or the next morning if you are tired. They practise the habits of Theory Chapter 9 on small new problems: writing the slow, obviously correct version, enumerating by hand, shrinking a counterexample, naming the cause of a failure, and reading the limits. None of them uses or hints at a mock problem.

:::exercise{#exr-9-brute} Write a brute force
A new problem: there are *n* ≤ 16 players with skills *s*[0..*n* − 1] ≥ 1. A team is a set of at least two players, and it is *balanced* when its strongest skill is at most twice its weakest skill. Count the balanced teams, and give the size of the largest one. Write a brute force in the style of @T:lst-9-subsets. Keep it obviously correct; speed does not matter.

:::grid{rows=14}
:::

:::

:::exercise{#exr-9-shrink} Shrink a counterexample
A new problem: find the largest product of a non-empty subarray. A tempting fast idea copies Kadane's scan from @T:lst-9-stress, with products in place of sums. Both methods below compile.

```java
static long solve(int[] a) {                       // Kadane's scan, copied for products
    long best = a[0], cur = a[0];
    for (int i = 1; i < a.length; i++) {
        cur = Math.max(a[i], cur * a[i]);            // the best product ending at i?
        best = Math.max(best, cur);
    }
    return best;
}

static long brute(int[] a) {                       // every subarray
    long best = Long.MIN_VALUE;
    for (int l = 0; l < a.length; l++) {
        long p = 1;
        for (int r = l; r < a.length; r++) { p *= a[r]; best = Math.max(best, p); }
    }
    return best;
}
```

With these two methods, the stress tester of @T:lst-9-stress (same seed, same generator) stops at once with `Mismatch on iteration 1: [-6, -9, -10, 10, 3, 4]` and `fast=120  brute=10800`. Run the shrinker of @T:lst-9-shrink by hand. Remember its order: in each round it tries deleting one element, from the left, then two neighbours, then halving each value (rounding towards zero, as Java's `/` does), and it restarts the round after every accepted change. The first three accepted changes are done. Continue until no change keeps the disagreement.

**Exercise 9.1.** A brute force over all masks, as in @T:lst-9-subsets:

```java
static long[] balancedTeams(int[] s) {               // {count, size of the largest}; O(2^n * n)
    int n = s.length;
    long count = 0, largest = 0;
    for (int mask = 0; mask < (1 << n); mask++) {
        if (Integer.bitCount(mask) < 2) continue;
        int lo = Integer.MAX_VALUE, hi = Integer.MIN_VALUE;
        for (int i = 0; i < n; i++)
            if ((mask & (1 << i)) != 0) { lo = Math.min(lo, s[i]); hi = Math.max(hi, s[i]); }
        if (hi <= 2L * lo) {
            count++;
            largest = Math.max(largest, Integer.bitCount(mask));
        }
    }
    return new long[]{count, largest};
}
```

For [3, 5, 8, 4, 10], sort to 3, 4, 5, 8, 10 and count the teams by their weakest member. With 3 weakest, the others must be at most 6, so they come from {4, 5}: 2² − 1 = 3 teams. With 4 weakest: {5, 8}, 3 teams. With 5 weakest: {8, 10}, 3 teams. With 8 weakest: {10}, 1 team. With 10 weakest: none. That makes 10 balanced teams, and the largest has 3 players ({3, 4, 5}, {4, 5, 8} or {5, 8, 10}). The brute force returns {10, 3}. It costs O(2ⁿ · *n*): 2¹⁶ · 16 ≈ 10⁶ steps here, and 2²⁰ · 20 ≈ 2 · 10⁷ for *n* = 20, so with *n* ≤ 2 · 10⁵ it would pass the tests with *n* up to about 20. (The counting by weakest member, done with a sort and a pointer, gives an O(*n* log *n*) solution; it agreed with the brute force on 5000 random arrays.)

On [0, −1, −1] no deletion and no halving keeps the disagreement, so the shrinker stops; running @T:lst-9-shrink gives the same twelve steps. In step 1, deleting *a*[0] gives [−9, −10, 10, 3, 4], where both methods return 10800, so the change is rejected (and likewise for *a*[1] and *a*[2]). The final input shows the flaw: after the 0, `cur` is 0, and at the first −1 the scan keeps max(−1, 0) = 0 and throws away the product −1 ending there, which the next −1 would have turned into the answer 1. A negative product can become the largest one. The cause is a **wrong idea**. Repair: keep both the largest and the smallest product ending at *i*:

```java
static long solveFixed(int[] a) {                  // largest and smallest product ending at i
    long best = a[0], hi = a[0], lo = a[0];
    for (int i = 1; i < a.length; i++) {
        long x = a[i];
        long h = Math.max(x, Math.max(hi * x, lo * x));
        lo = Math.min(x, Math.min(hi * x, lo * x));
        hi = h;
        best = Math.max(best, hi);
    }
    return best;
}
```

It agreed with `brute` on 100 000 random arrays from the same generator.

**Exercise 9.4.** (1) Overflow / mod: `lo + hi` exceeds 2³¹ − 1. Rule: write `lo + (hi - lo) / 2`, or use `long` for every search bound. (2) Misread statement (output format). Rule: compare your output with the first sample character by character before submitting. (3) Stack overflow. Rule: any recursion that can be deeper than 10⁴ becomes a loop with an explicit stack. (4) Wrong idea: the earliest start can be a long meeting that blocks many short ones; the exchange argument works for the earliest *end* (Chapter 4). Rule: prove a greedy or stress-test it before submitting. (5) Input reading. Rule: after `nextInt()`, call `nextLine()` once to finish the line, or read every token with FastScanner. (6) Off-by-one: the search range must be half-open, [0, *n*), so that "not found" can return *n*. Rule: lower-bound searches start with `hi = n`. (7) TLE / complexity: 10⁴ · 2 · 10⁵ = 2 · 10⁹ cells allocated and zeroed. Rule: allocate once at the largest size and clear only the first *n* + 1 entries in each test case. (8) Edge case: all values equal. Rule: before submitting, run *n* = 1, all values equal and the extreme values. (9) Ran out of time. Rule: submit the brute force as soon as it passes the samples, and by minute 150 every problem has a submission.

**Exercise 9.5.** (1) O(*n*! · *n*): 8 · 8! = 322 560 steps; try all orders. (2) O(2ⁿ · *n*): 18 · 2¹⁸ ≈ 4.7 · 10⁶; all subsets or a bitmask DP. (3) O(*n*³): 400³ = 6.4 · 10⁷; triple loops or interval DP. (4) O(*n*²): 4000² = 1.6 · 10⁷; all pairs or a 2-D DP. O(*n*³) would need 6.4 · 10¹⁰ steps, hundreds of seconds, so no. (5) O(*n* log *n*) per test case, which sums to about 2 · 10⁵ · 18 ≈ 3.5 · 10⁶ steps; clearing 2 · 10⁵ entries in each of 10⁴ test cases costs 2 · 10⁹ writes, a time-limit failure on its own. (6) O(√*n*) = 10⁶ steps (trial division) or O(log *n*) (binary search, fast power). (7) 2.5 · 10⁷ states: as `long` that is 200 MB, too close to 256 MB once the JVM's own memory is counted; as `int` 100 MB, which fits; if each row reads only the previous one, two rows suffice. An O(*n*²) brute force does about 10⁸ simple steps per second, so it finishes up to *n* ≈ 10⁴.
