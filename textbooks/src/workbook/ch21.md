:::exercise{#exr-21-concept} Concept check
Answer true or false, and give a one-line reason.

1. After any operation of @T:lst-21-lazymax, `mx[x]` is the true maximum of node *x*'s range for every node *x*.
2. A query may skip `push`, because it does not change any value of the array.
3. One operation can call more than two nodes on the same level.
4. Arrays of size 2*n* are enough for a recursive segment tree on *n* elements.
5. In the K-parts DP, filling row *k* in any order of *i* is fine, as long as row *k* − 1 is complete.
6. If all values of *a* are different, the gift-box answer is *n* for every *K* ≤ *n*.
7. In @T:lst-21-bakery, `tree.add(last[x] + 1, i - 1, 1)` may be replaced by `tree.add(Math.max(0, last[x]), i - 1, 1)`, because one extra position does no harm.

:::exercise{#exr-21-design} Design before you code: values that occur once

:::exercise{#exr-21-bug} Find the bug
This version of the lazy max tree compiles, passes the sample below, and gives correct answers in every test that uses only point updates. Find an input with at most two operations on which it is wrong, say what it returns, and fix it.

```java
static final class LazyMaxBuggy {
    final int n;
    final long[] mx, lz;

    LazyMaxBuggy(int n) {
        this.n = n;
        mx = new long[4 * n];
        lz = new long[4 * n];
    }

    private void push(int x) {
        if (lz[x] == 0) return;
        for (int c = 2 * x; c <= 2 * x + 1; c++) {
            mx[c] += lz[x];
            lz[c] += lz[x];
        }
        lz[x] = 0;
    }

    void add(int l, int r, long v) { add(1, 0, n - 1, l, r, v); }

    private void add(int x, int lo, int hi, int l, int r, long v) {
        if (r < lo || hi < l) return;
        if (l <= lo && hi <= r) {
            mx[x] += v;
            lz[x] += v;
            return;
        }
        push(x);
        int mid = (lo + hi) >>> 1;
        add(2 * x, lo, mid, l, r, v);
        add(2 * x + 1, mid + 1, hi, l, r, v);
        mx[x] = Math.max(mx[2 * x], mx[2 * x + 1]);
    }

    long max(int l, int r) { return max(1, 0, n - 1, l, r); }

    private long max(int x, int lo, int hi, int l, int r) {   // "a query changes nothing"
        if (r < lo || hi < l) return Long.MIN_VALUE;
        if (l <= lo && hi <= r) return mx[x];
        int mid = (lo + hi) >>> 1;
        return Math.max(max(2 * x, lo, mid, l, r), max(2 * x + 1, mid + 1, hi, l, r));
    }
}
```

The sample, with `n = 6`: add(2, 2, 4), add(0, 0, 1), max(0, 5) → 4, add(1, 4, 3), max(0, 5) → 7, max(3, 4) → 3. The buggy tree prints all three answers correctly.

:::answers
**Exercise 21.1.** (1) `mx[c] += lz[x]`; (2) `lz[c] += lz[x]`; (3) `lz[x] = 0`; (4) `l <= lo && hi <= r`; (5) `push(x)`; (6) `mx[x] = Math.max(mx[2 * x], mx[2 * x + 1])`. Without the push, line (6) rebuilds `mx[x]` from children that do not yet include the pending tag of *x*, so the tag disappears from `mx[x]` while `lz[x]` still holds it: the stored value is then too small by `lz[x]`.

**Exercise 21.2.** From a run of an instrumented copy of the listing:

| node | after add(1, 6, 2) | after add(0, 3, 1) | after max(2, 5) |
|---|---|---|---|
| [0,7] | 2 / 0 | 3 / 0 | 3 / 0 |
| [0,3] | 2 / 0 | 3 / 1 | 3 / 0 |
| [4,7] | 2 / 0 | 2 / 0 | 2 / 0 |
| [0,1] | 2 / 0 | 2 / 0 | 3 / 1 |
| [2,3] | 2 / 2 | 2 / 2 | 3 / 3 |
| [4,5] | 2 / 2 | 2 / 2 | 2 / 2 |
| [6,7] | 2 / 0 | 2 / 0 | 2 / 0 |
| covered nodes | [1], [2,3], [4,5], [6] | [0,3] | [2,3] → 3, [4,5] → 2 |
| calls | 11 | 3 | 7 |

The query returns 3. The array is then [1, 3, 3, 3, 2, 2, 2, 0]. The first update also writes tags on the leaves [1] and [6]; they are never read. After the second update, [2,3] stores 2 because the +1 sits in the tag of its parent [0,3], which covers it; the query max(2, 5) finds [0,3] partial and pushes the +1 into [0,1] and [2,3] before reading [2,3].

**Exercise 21.3.** Rows 4–7, from a run of the method:

| i | a[i − 1] | +1 on j = | T[0..7] after the add | dp[2][i] |
|---|---|---|---|---|
| 4 | 3 | 0..3 | −∞, 4, 4, 3, 3, 3, 3, 3 | 4 |
| 5 | 1 | 2..4 | −∞, 4, 5, 4, 4, 3, 3, 3 | 5 |
| 6 | 3 | 4..5 | −∞, 4, 5, 4, 5, 4, 3, 3 | 5 |
| 7 | 1 | 5..6 | −∞, 4, 5, 4, 5, 5, 4, 3 | 5 |

The answer is 5. At *i* = 7, three split points reach 5: *j* = 2 gives [2, 1] + [2, 3, 1, 3, 1] = 2 + 3; *j* = 4 gives [2, 1, 2, 3] + [1, 3, 1] = 3 + 2; *j* = 5 gives [2, 1, 2, 3, 1] + [3, 1] = 3 + 2. Row 5 adds only on 2..4 because the previous 1 is at index 1.

**Exercise 21.4.** (1) False: a node misses the tags of its ancestors; in @T:fig-21-tags, [4,5] stores 3 but *a*[4..5] has maximum 5. (2) False: with `n = 2`, add(0, 1, 5) then max(0, 0) returns 0 without the push (Exercise 21.7). (3) True: up to four calls per level, two of them partial (@T:thm-21-visits); add(3, 12, 1) on 16 elements has four calls on each of the levels 2, 3 and 4. (4) False: *n* = 6 already uses index 13 ≥ 12. (5) True: dp[*k*][*i*] reads only row *k* − 1. (6) True: every box then has as many distinct values as elements, so every split totals *n* (confirmed on 2000 random permutations). (7) False: position `last[x]` already contains a copy of *x* and must not gain 1. In a random test this version disagreed with the baseline on 340 of 1000 cases; one failing case is [3, 1, 1, 1, 1, 2, 1, 3, 3, 3] with *K* = 1, where it returns 4 instead of 3.

**Exercise 21.5.** (1) "set 7" (add 2, then set 4; add 3 makes set 7; set 1; add 6 makes set 7); the maximum is 7. A run of the class gave tag 7 with `isSet` true and max 7. (2) 5 and 6: the two tags do not commute. (3) Tag +7 and sum 7 · 6 = 42. (4) "set 5": the root's tag is newer, and set overrides the older add 7; the query returns 5.

**Exercise 21.6.** For *j* ≤ *p*₂, *x* already occurred at least twice: Δ = 0. For *p*₂ < *j* ≤ *p*₁, *x* occurred exactly once and now twice: Δ = −1. For *p*₁ < *j* ≤ *i* − 1, *x* is new: Δ = +1. So each step is two range adds, +1 on [*p*₁ + 1, *i* − 1] and −1 on [*p*₂ + 1, *p*₁] (only when *p*₁ ≥ 0), followed by one range max. The tree stores dp[*k* − 1][*j*] + score(*a*[*j*..*i* − 1]); per value you keep the last two positions. Time O(*K* *n* log *n*), memory O(*n*). For *a* = [1, 2, 1, 1, 3, 2] at *i* = 4: *p*₁ = 2, *p*₂ = 0, so +1 on *j* = 3..3 and −1 on *j* = 1..2 (a direct count gives the changes 0, −1, −1, +1 for *j* = 0..3). The answer for *K* = 2 is 4, from [1, 2] + [1, 1, 3, 2] = 2 + 2 or [1, 2, 1] + [1, 3, 2] = 1 + 3. This design was checked against an exhaustive search on 4000 random arrays.

**Exercise 21.7.** `max` never pushes. With `n = 2`: add(0, 1, 5) covers the root, which stores 5 with tag 5; max(0, 0) finds the root partial, goes to leaf [0] without pushing and returns 0 instead of 5. Fix: call `push(x);` in `max` after the covered check, before computing `mid`. The bug hides when only leaves carry tags, as with the point updates of Chapter 20 (3000 of 3000 random runs correct), and when every query asks for the whole array (also 3000 of 3000). In the sample, the two whole-array queries stop at the root, and the query max(3, 4) passes only through nodes that hold no pending tag, so the missing push changes nothing.

**Exercise 21.8.** (1) Lazy tree per layer, @T:lst-21-bakery: at most 50 · (3 · 35 000 + 1) · 63 ≈ 3.3 · 10⁸ calls (about 0.6 s measured); the baseline would make about 3.06 · 10¹⁰ steps. (2) Baseline @T:lst-21-slow: 1 909 600 inner steps. (3) Difference array (Chapter 2): O(*n* + *m*) ≈ 2 · 10⁵ steps. (4) @T:lst-21-lazysum: at most 67 calls per operation for *n* = 10⁵, so about 1.34 · 10⁷ calls. (5) Lazy **min** tree per layer with the range add of @T:sec-21-recognise: at most 100 · (3 · 35 000 + 1) · 63 ≈ 6.6 · 10⁸ calls. (6) Try all 2¹⁹ = 524 288 ways to place the cuts, about 10⁷ steps with an O(*n*) cost per split, and use it as the brute force in a stress test.

**Exercise 21.9.** Compare with @T:lst-21-lazymax. `push` is called in exactly two places: in `add` and in `max`, after the covered check and before the recursive calls. The arrays have 4*n* entries.
