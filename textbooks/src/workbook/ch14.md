:::answers
**Exercise 14.1.** (1) `2`; (2) `l + len - 1`; (3) `Long.MAX_VALUE`; (4) `k < r`; (5) `dp[k + 1][r]`. The recurrence reads dp[*l*][*k*] and dp[*k* + 1][*r*], two shorter segments inside [*l*, *r*]. By @T:lem-14-order they are ready when every shorter segment has been filled first. With "*l* from 0 up" as the outer loop, dp[*k* + 1][*r*] lies in a row that is filled later, so it is still 0 when it is read. Without the cast the product is computed in `int`: 2000 · 2000 · 2000 = 8 · 10⁹ wraps around to −589 934 592, and the method returns that negative number. With the cast it returns 8 000 000 000.

**Exercise 14.2.** The positions 0 to 15 are L L W W L W W L L W W L W W L L. The losing positions are exactly those with *s* mod 7 equal to 0, 1 or 4, which a program confirmed up to 1000. Positions 0 and 1 have no move. From a losing position both moves lead to a winning one: from 7, the moves reach 5 and 2, both W. The pattern must repeat: each entry depends only on the five entries before it, and entries 7–11 (L L W W L) equal entries 0–4, so by induction every entry equals the one 7 places earlier. 100 = 14 · 7 + 2 is winning: remove 2 and leave 98 = 14 · 7, a losing position.

| D(l, r) | r = 0 | r = 1 | r = 2 | r = 3 | r = 4 |
|---|---|---|---|---|---|
| l = 0 | 4 | 4 | 0 | 1 | 2 |
| l = 1 | — | 8 | 4 | 5 | 6 |
| l = 2 | — | — | 4 | 3 | 2 |
| l = 3 | — | — | — | 1 | 2 |
| l = 4 | — | — | — | — | 3 |

At the corner, taking the 4 gives 4 − *D*(1, 4) = 4 − 6 = −2, and taking the 3 gives 3 − *D*(0, 3) = 3 − 1 = 2. So the first player takes the **smaller** end, the 3. The sum is 20 and *D* = 2, so the totals are (20 + 2)/2 = 11 and 9. One optimal line: 3, then the opponent takes 1 (since 1 − *D*(0, 2) = 1 is better than 4 − *D*(1, 3) = −1), then 4, 8, 4. If both players always take the larger end, the moves are 4, 8, 4, 3, 1 and the first player loses 9 to 11. An exhaustive minimax search agrees with the table; on 4000 random rows the table, the rolling version and the exhaustive search all agreed.

The least total cost is 25. The best candidate at the top is *k* = 3, so the first cut is at *p*[3] = 7. Following the best *k* in each piece gives the order 7, 3, 2, 9, costing 11 + 7 + 3 + 4 = 25 (the orders 7, 3, 9, 2 and 7, 9, 3, 2 also cost 25). Cutting from left to right costs 11 + 9 + 8 + 4 = 32. A search over all 24 orders confirms the minimum 25 (the worst order costs 34), and the DP matched that search on 3000 random sticks.

**Exercise 14.5.** (1) False: Σ ⌊*N*/*v*⌋ = 13 970 034 ≈ 1.4 · 10⁷ for *N* = 10⁶ (@T:tbl-14-harmonic). (2) True: each step at least doubles the value, so *k* values need 2ᵏ⁻¹ ≤ 10⁹, that is *k* ≤ 30; the chain 1, 2, 4, …, 2²⁹ = 536 870 912 has exactly 30. (3) False: 10000 is not prime, so the inverses do not all exist; use Pascal's rule. (4) True: dp[*i*][*j*] reads dp[*i*][*k*] (same *i*, smaller *j*, filled earlier in this pass) and dp[*k*][*j*] (larger *i*, an earlier pass), as in @T:lem-14-order. (5) False: in @exr-14-games the first player must take the 3, the smaller end; taking the 4 loses by 2. (6) True: the two totals add up to the fixed sum, so "own − other" is 2 · own − sum, and both goals pick the same moves (@T:thm-14-diff). (7) False: on [1, 5, 2] the difference is −2, so the first player gets 3 of 8. The colouring argument needs an even number of elements. (8) True: 22 mod 7 = 1. **Exercise 14.6.** dp[*l*][*r*] = the least cost of merging piles *l*..*r* into a single pile; dp[*l*][*l*] = 0. Split on the **last** merge: it joins a pile made from *l*..*k* with a pile made from *k* + 1..*r*, for some *l* ≤ *k* < *r*. Its cost is sum(*l*..*r*) whatever *k* is, because the final pile always contains all the stones; before it, the two sides were merged independently. So dp[*l*][*r*] = sum(*l*..*r*) + min over *k* of (dp[*l*][*k*] + dp[*k* + 1][*r*]), with the sum taken from a prefix-sum array (Chapter 2). Fill by increasing length. Time O(*n*³): (*n* + 1)*n*(*n* − 1)/6 = 10 666 600 triples for *n* = 400. Memory: a `long[400][400]`, 1.28 MB. Use `long`: the total is at most 399 merges of at most 4 · 10⁸ stones, about 1.6 · 10¹¹, which does not fit an `int`. For [7, 5, 4, 7] the prefix sums are 0, 7, 12, 16, 23. Then dp[0][1] = 12, dp[1][2] = 9, dp[2][3] = 11; dp[0][2] = 16 + min(0 + 9, 12 + 0) = 25; dp[1][3] = 16 + min(0 + 11, 9 + 0) = 25; dp[0][3] = 23 + min(0 + 25, 12 + 11, 25 + 0) = **46**: merge 7 + 5, then 4 + 7, then 12 + 11, for 12 + 11 + 23. The greedy rule merges the cheapest pair 5 + 4 first (cost 9), leaving [7, 9, 7]; both pairs now cost 16, and either choice leaves two piles that cost 23 to join, a total of 48. The DP matched a brute force over all merge orders on 3000 random rows.

**Exercise 14.7.** It fails on [2, 1, 3]: it returns 3, while the correct difference is 2 (exhaustive search agrees). In the pass for length 2, *l* = 1 comes first and overwrites `d[1]` with *D*(1, 2) = max(1 − 3, 3 − 1) = 2. Then *l* = 0 should compute *D*(0, 1) = max(2 − *D*(1, 1), 1 − *D*(0, 0)) = max(1, −1) = 1, but `d[1]` no longer holds *D*(1, 1) = 1, so it computes max(2 − 2, 1 − 2) = 0. The last pass then gives max(2 − 2, 3 − 0) = 3 instead of max(2 − 2, 3 − 1) = 2. Fix: run the pass from left to right, `for (int l = 0; l + len - 1 < n; l++)`, so that `d[l + 1]` still holds the previous length when `d[l]` is overwritten. Rows of one or two elements always pass, because each pass has at most one step. On 5000 random rows of up to 8 values the buggy method was wrong on 1493.

**Exercise 14.8.** (1) @T:lst-14-divisible: 1000 · 999/2 = 499 500 divisibility tests, instant. Values up to 2 · 10⁹ still fit an `int` (the largest is 2 147 483 647). (2) @T:lst-14-multiples: 13 970 034 steps. Trial division up to √*v* for every *v* would cost Σ ⌊√*v*⌋ = 666 167 500 steps, about 50 times more. (3) Split DP on the last balloon, O(*n*³). With the two padding balloons there are 502 positions, and the triples *l* < *k* < *r* number C(502, 3) = 20 958 500: time is fine, and the table has 502² ≈ 2.5 · 10⁵ entries. (4) The game DP has 12 502 500 states, so time is fine, but a `long[5000][5000]` needs 200 000 000 bytes: memory binds. Use @T:lst-14-rolling, 40 000 bytes. (5) 20 833 332 500 triples, about 2 · 10¹⁰: time binds, and the plan has no faster method for it. (6) Stars and bars. A chain has at most ⌊log 10⁴⌋ + 1 = 14 values, so 13 passes of the loop over multiples compute all chain counts, each at most 93 668 steps, about 1.2 · 10⁶ in all. The 14 binomials C(*K* − 1, *s* − 1) come from Pascal's rule with *r* < 14, about 10⁴ · 14 = 1.4 · 10⁵ additions. The direct DP would cost *K* · 93 668 ≈ 9.4 · 10⁸ steps. (7) A table of 10¹⁸ entries is impossible. Print the table up to 100, see the period 7 (losing exactly when *s* mod 7 is 0 or 2), prove it by induction, and answer in O(1): 10¹⁸ mod 7 = 1, a winning position.
