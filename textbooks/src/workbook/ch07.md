:::exercise{#exr-7-concept} Concept check
Answer true or false, and give a one-line reason.

1. One iteration of the `for` loop in @T:lst-7-nge can perform up to *n* − 1 pops, so the method is O(*n*²) in the worst case.
2. For the previous strictly smaller element, pop while `a[top] >= a[i]` and read the top after popping.
3. In the contribution formula, using strict comparisons on both sides over-counts subarrays whose minimum occurs more than once.
4. The sum of subarray ranges equals the sum of subarray maximums minus the sum of subarray minimums.
5. For a circular array, it is wrong to push indices during the second lap.
6. In @T:lst-7-greedy, if *k* deletions remain after the scan, they are taken from the front of the stack.

:::exercise{#exr-7-bug} Find the bug
This version of the contribution sum compiles and passes every test with distinct values. Find the smallest positive input on which it is wrong, give both answers, and fix it with one character.

```java
static long sumMinsBuggy(int[] a) {
    int n = a.length;
    long total = 0;
    for (int i = 0; i < n; i++) {
        int l = i - 1;
        while (l >= 0 && a[l] >= a[i]) l--;          // previous strictly smaller
        int r = i + 1;
        while (r < n && a[r] >= a[i]) r++;           // next strictly smaller
        total += (long) a[i] * (i - l) * (r - i);
    }
    return total;
}
```

:::answers
**Exercise 7.1.** (1) `Arrays.fill(res, -1)`; (2) `top > 0`; (3) `a[st[top - 1]] < a[i]`; (4) `res[st[--top]] = i`; (5) `st[top++] = i`. For next greater or equal, pop on `a[st[top - 1]] <= a[i]`; for next smaller, pop on `a[st[top - 1]] > a[i]`.

**Exercise 7.2.** Popped at each step: none, none, none, {2, 1}, {3, 0}, none, {5, 4}. Stacks after: [0], [0, 1], [0, 1, 2], [0, 3], [4], [4, 5], [6]. The result is [4, 3, 3, 4, 6, 6, −1] with 6 pops. Each index is pushed once and can be popped at most once, so 7 pushes allow at most 7 pops; the last index is never popped here.

**Exercise 7.3.** Rows 2–4: (left 1, right 3, count 1 · 1 = 1, contribution 2); (left 1, right 4, count 2 · 1 = 2, contribution 4); (left −1, right 5, count 5 · 1 = 5, contribution 5). The total is 3 + 6 + 2 + 4 + 5 = 20, and the counts 1 + 6 + 1 + 2 + 5 add to 15 = 5 · 6/2, the number of subarrays. A brute force also gives 20. Index 1 does not own any subarray that also contains index 4, for example [1, 2, 2, 1] or the whole array: the value 1 occurs again at index 4, and the rightmost minimum owns the subarray, so index 4 does.

**Exercise 7.4.** L = [−1, 0, 0, 2, −1, 4], R = [4, 2, 4, 4, 6, 6], widths [4, 1, 3, 1, 6, 1], areas [8, 4, 9, 5, 6, 3]. The largest rectangle has area 9: height 3 over bars 1..3.

**Exercise 7.5.** (1) False: each index is pushed once and popped at most once, so the total number of pops is at most *n* and the method is O(*n*). (2) True: everything ≥ *a*[*i*] is removed, so the top is strictly smaller. (3) True: such a subarray is owned by every position of its minimum. (4) True: the sum of differences is the difference of the sums. (5) False: it changes no answer, only adds work (Theory Chapter 7, review question 4). (6) False: the stack is non-decreasing, so the best deletion is the last character; they come off the end.

**Exercise 7.6.** The span needs the previous strictly greater price: pop while `p[top] <= p[i]`; then the span is *i* + 1 if the stack is empty and *i* − top otherwise; push *i*. O(*n*) time and memory, by the push–pop count. For [30, 25, 27, 27, 40, 22, 26] the spans are [1, 1, 2, 3, 5, 1, 2].

**Exercise 7.7.** Any array with a repeated minimum fails; the smallest positive one is [1, 1]. The true sum is 1 + 1 + 1 = 3; the buggy method gives 4, because the subarray [1, 1] is owned by both positions. On [3, 1, 2, 2, 1] it gives 24 instead of 20. Fix: make one side non-strict, for example `while (r < n && a[r] > a[i]) r++;` on the right.

**Exercise 7.8.** 3: push, stack 3, k 3. 1: pop 3, stack 1, k 2. 4: push, stack 14. 1: pop 4, stack 11, k 1. 5: push, stack 115. 9: push, stack 1159. 2: pop 9, stack 1152, k 0. The result is 1152. Spending the third deletion on the 9 gives 1152; spending it on the 5 would give 1192. The two first differ at the third digit, where 5 < 9, so 1152 is smaller. The greedy deletes the 9 because 9 > 2 is the first descent of 11592.

**Exercise 7.9.** Compare with @T:lst-7-summin. The left scan pops on `a[top] >= a[i]` (so left is strictly smaller) and the right-to-left scan pops on `a[top] > a[i]` (so right is smaller or equal); the opposite pairing (non-strict on the left, strict on the right) is also correct. The same strictness on both sides is never correct.
