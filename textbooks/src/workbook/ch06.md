:::exercise{#exr-6-concept} Concept check
Answer true or false, and give a one-line reason.

1. `Arrays.binarySearch` returns the first index holding the key when the key occurs several times.
2. `lowerBound(a, x)` can return `a.length`.
3. In a "maximise the minimum" search with the branches `lo = mid` and `hi = mid - 1`, the midpoint must be rounded down.
4. If ok(*x*) is monotone on a range of *V* values, the search calls ok at most ⌈log₂ *V*⌉ times.
5. For a real-valued answer near 10⁹, `while (hi - lo > 1e-9)` is a safe stopping rule.
6. The value found by "smallest *x* with count(*x*) ≥ *k*" might not be an element of the collection.
7. A generous upper bound *hi* (say 10¹⁸ instead of 10⁹) can never make the answer wrong, only slower.

:::exercise{#exr-6-bug} Find the bug
This method is meant to compute the largest possible smallest piece sum (@T:lst-6-maxmin) but sometimes never returns. It compiles. Find the smallest input on which it hangs, explain the cause with the values of *lo*, *hi* and *mid*, and fix it with one change.

```java
static long maxMinPieceBuggy(int[] a, int k) {
    long lo = 0, hi = 0;
    for (int x : a) hi += x;
    while (lo < hi) {
        long mid = lo + (hi - lo) / 2;
        if (piecesAtLeast(a, mid) >= k) lo = mid;
        else hi = mid - 1;
    }
    return lo;
}

static int piecesAtLeast(int[] a, long s) {
    int pieces = 0;
    long cur = 0;
    for (int x : a) {
        cur += x;
        if (cur >= s) {
            pieces++;
            cur = 0;
        }
    }
    return pieces;
}
```

:::answers
**Exercise 6.1.** (1) `a.length`; (2) `lo < hi`; (3) `(lo + hi) >>> 1` (or `lo + (hi - lo) / 2`); (4) `hi = mid`; (5) `lo = mid + 1`. The answer *n* ("every element is smaller than *x*") must be inside the range of possible results. With `hi = a.length - 1`, the array [0] and *x* = 1 return 0, although no element is ≥ 1 and the correct answer is 1.

**Exercise 6.2.** upperBound(*a*, 8): (lo, hi, mid, a[mid]) = (0, 9, 4, 6) → lo = 5; (5, 9, 7, 11) → hi = 7; (5, 7, 6, 9) → hi = 6; (5, 6, 5, 6) → lo = 6; result 6. lowerBound(*a*, 6): (0, 9, 4, 6) → hi = 4; (0, 4, 2, 4) → lo = 3; (3, 4, 3, 6) → hi = 3; result 3. The value 6 occurs upperBound(*a*, 6) − lowerBound(*a*, 6) = 6 − 3 = 3 times. `Arrays.binarySearch(a, 6)` may return any of 3, 4, 5 (the JDK returns 4 here, its first midpoint); `Arrays.binarySearch(a, 5)` returns −4, because the insertion point of 5 is 3.

**Exercise 6.3.** The remaining rows are (4, 7, 5, 4 days) → fails, lo = 6; (6, 7, 6, 3 days) → works, hi = 6; then lo = hi = 6 and the loop stops. The answer is 6, with the greedy days [3, 2], [2, 4], [1, 4].

**Exercise 6.4.** (1) False: it returns *some* matching index; the documentation gives no guarantee which. (2) True: when every element is smaller than *x*. (3) False: it must be rounded up, or `lo = mid` makes no progress when *hi* = *lo* + 1. (4) True: each call at least halves the range of candidates (@T:thm-6-search). (5) False: neighbouring doubles near 10⁹ are about 1.2 · 10⁻⁷ apart, so the gap may never drop below 10⁻⁹; use a fixed number of iterations. (6) False: @T:thm-6-kth shows it is always an element. (7) False in general: a huge *hi* can overflow sums or products inside the check (for example `mid * count`), which turns a correct predicate into a wrong one.

**Exercise 6.5.** ok(*T*) = "Σ ⌊*T*/*t*[*i*]⌋ ≥ *M*". Each term is non-decreasing in *T*, so if *T* works, *T* + 1 works. *lo* = 0 (or 1) and *hi* = min(*t*) · *M*: the fastest machine alone makes *M* products in that time, so ok(*hi*) is true. One check is O(*n*); the search makes about log₂(10¹⁸) ≈ 60 checks, so O(60 *n*) ≈ 1.2 · 10⁷ steps. Overflow: *hi* can be 10¹⁸, so the bounds are `long`, and the sum Σ *T*/*t*[*i*] can exceed `long` when *T* is large and many *t*[*i*] are small; stop adding as soon as the sum reaches *M*. On *t* = [3, 2, 5], *M* = 10, with *lo* = 0 and *hi* = 20: (0, 20, 10, 10 products) → hi = 10; (0, 10, 5, 4) → lo = 6; (6, 10, 8, 7) → lo = 9; (9, 10, 9, 8) → lo = 10. The answer is *T* = 10: after 10 minutes the machines have made 3 + 5 + 2 = 10 products, after 9 only 8.

**Exercise 6.6.** The smallest failing input is *a* = [1] with *k* = 1 (correct answer 1). Then *lo* = 0, *hi* = 1 and the rounded-down midpoint is 0; `piecesAtLeast(a, 0)` = 1 ≥ *k*, so `lo = mid` sets *lo* to 0 again and the loop repeats for ever. In general the method hangs as soon as the range has two values, because *lo* always passes. Fix: `long mid = lo + (hi - lo + 1) / 2;`.

**Exercise 6.7.** count(5) = 9, count(6) = 11, count(7) = 11, count(8) = 13, count(10) = 15. The search: (1, 20, 10, 15) → hi = 10; (1, 10, 5, 9) → lo = 6; (6, 10, 8, 13) → hi = 8; (6, 8, 7, 11) → hi = 7; (6, 7, 6, 11) → hi = 6; answer 6. The sorted table is [1, 2, 2, 3, 3, 4, 4, 4, 5, 6, 6, 8, 8, 9, 10, 12, 12, 15, 16, 20], whose 11th element is 6. The search looks for the *smallest* *x* with count(*x*) ≥ 11; 7 is not an entry of the table, so count does not change between 6 and 7.

**Exercise 6.8.** (1) *lo* = 1, *hi* = 10⁹ (the largest pile); bounds fit in `int` but the total of hours needs `long`; 30 iterations. (2) *lo* = 500 at most (the heaviest package), *hi* = the total ≤ 2.5 · 10⁷; `int` would do but `long` is the safe default; ⌈log₂ 2.5 · 10⁷⌉ = 25 iterations. (3) *lo* = max ≤ 10⁶, *hi* = total ≤ 10⁹; at most 30 iterations; sums inside the check reach 10⁹, close to the `int` limit, so use `long`. (4) A fixed number of iterations: 10⁹ / 10⁻⁶ = 10¹⁵ ≈ 2⁵⁰, so 50 halvings are enough in exact arithmetic; use 100 to be safe.

**Exercise 6.9.** Compare with @T:lst-6-search. `firstTrue` uses `mid = lo + (hi - lo) / 2` with `hi = mid` / `lo = mid + 1`; `lastTrue` uses `mid = lo + (hi - lo + 1) / 2` with `lo = mid` / `hi = mid - 1`. The rounding must keep *mid* strictly away from the end that its branch assigns, so that every branch shrinks the range.
