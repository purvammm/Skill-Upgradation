## Exercises

Work these after reading Theory Chapter 18 and before the problem worksheets. The first four make you produce a BFS order, a recursion's return values and a binary-lifting table by hand. These are the three things the day's problems are built from, and each is easy to get subtly wrong: a parent array in an unusual order, a branch that should be dropped, a jump that passes the root. The rest ask you to judge, design and debug on your own.

:::exercise{#exr-18-concept} Concept check
Answer true or false, and give a one-line reason or a counterexample.

1. A parent array of length *n* with exactly one entry −1, and every other entry a valid vertex number, always describes a tree.
2. In `gain`, a node could return `node.val + l + r` to its parent instead of `node.val + Math.max(l, r)`.
3. In `maxPathSum`, `best` may start at 0, because a single node is already a path.
4. When *q* lies in the subtree of *p*, the recursive `lca` of @T:lst-18-lca returns *p* without visiting *q*.
5. In `levelOrder`, the loop `for (int k = 0; k < q.size(); k++)` still produces one list per level.
6. For *n* = 10⁵ the `LCA` constructor chooses LOG = 17, and the table takes about 6.8 MB.
7. With the entry and exit times of @T:lst-18-euler, *u* is an ancestor of *v* exactly when tin[*u*] < tin[*v*] and tout[*v*] < tout[*u*].
8. On a chain of 10⁵ vertices, the sum of all pairwise distances fits in an `int`.

:::exercise{#exr-18-bug} Find the bug
This method computes subtree sizes from a parent array. It compiles, and on the tree of @T:fig-18-rooted it returns [6, 3, 2, 1, 1, 1]. (a) Describe an input with *n* = 10⁵ on which it fails, and what happens. (b) A classmate replaces the recursion by the loop `for (int v = n - 1; v >= 0; v--) if (par[v] != -1) size[par[v]] += size[v];` (after filling `size` with 1). Give a parent array with three vertices on which that loop is wrong. (c) Write the fix.

:::nobreak
```java
@SuppressWarnings("unchecked")
static int[] subtreeSizesRec(int[] par) {
    int n = par.length, root = -1;
    List<Integer>[] kids = new List[n];
    for (int v = 0; v < n; v++) kids[v] = new ArrayList<>();
    for (int v = 0; v < n; v++) {
        if (par[v] == -1) root = v;
        else kids[par[v]].add(v);
    }
    int[] size = new int[n];
    fill(root, kids, size);
    return size;
}

static void fill(int v, List<Integer>[] kids, int[] size) {
    size[v] = 1;
    for (int c : kids[v]) {
        fill(c, kids, size);
        size[v] += size[c];
    }
}
```

:::answers
**Exercise 18.1.** (1) `(1 << lg) < n`; (2) `par[v] == -1 ? v : par[v]`; (3) `up[k - 1][up[k - 1][v]]`; (4) `depth[a] - depth[b]`; (5) `up[k][a] != up[k][b]`; (6) `up[0][a]`. The recurrence for *v* reads the rows of up[*k* − 1][*v*], an ancestor of *v*. In BFS order every ancestor is processed earlier (@T:thm-18-order), so its rows are complete. In index order an ancestor with a larger number has not been filled yet, and its rows still hold 0, so jumps can land on vertex 0 instead of the true ancestor.

**Exercise 18.2.** The children lists are 3: [0, 1], 0: [2, 8], 1: [5, 6], 8: [4], 5: [9], 4: [7].

size = [5, 4, 1, 10, 2, 2, 1, 1, 3, 1] and depth = [1, 1, 2, 0, 3, 2, 2, 4, 2, 3]. The index loop reaches vertex 8 before vertex 4, so it adds size[8] = 1 to size[0] before 4 (and through it 7) has been added to size[8]. It returns size[0] = 3 and size[3] = 8; every other entry happens to be right. The cause is that 8 is the parent of the smaller number 4.

**Exercise 18.5.** (1) False: par = [−1, 3, 1, 2] has the cycle 1 → 3 → 2 → 1, and a BFS from the root reaches only one of the four vertices. Check that the BFS reaches all *n* (@T:thm-18-unique). (2) False: the parent continues the path through one child only; returning both branches would let the parent build a path that forks. In @exr-18-gain node −6 would return 10 instead of 2, and the root would report 16 for a "path" that forks below −6. (3) False: for a single node of value −5 the answer is −5, but `best` = 0 would stay 0. (4) True: the call at *p* returns at once, and *p* is the LCA by @T:def-18-lca. (5) False: `q.size()` changes inside the loop. On the perfect tree with values 1..7 in level order, it returns [[1, 2, 3, 4], [5, 6], [7]]. (6) True: 2¹⁶ < 10⁵ ≤ 2¹⁷, and 17 · 10⁵ · 4 bytes = 6.8 MB. (7) False: for the chain 0–1, tin = [0, 1] and tout = [1, 1], so tout[1] = tout[0]; the test is tin[*u*] ≤ tin[*v*] ≤ tout[*u*]. (8) False: by @T:thm-18-pairs it is Σ *v*(*n* − *v*) = 166 666 666 650 000 ≈ 1.7 · 10¹⁴; use `long`.

**Exercise 18.6.** mx[*k*][*v*] is the largest weight among the 2ᵏ edges above *v* (fewer if the root comes first; the root's own entry is 0). mx[0][*v*] = *w*[*v*], and mx[*k*][*v*] = max(mx[*k* − 1][*v*], mx[*k* − 1][up[*k* − 1][*v*]]), filled in BFS order next to up. In the query, every jump of *a* by 2ᵏ takes max with mx[*k*][*a*] *before* moving *a*; in the second phase each jump takes mx[*k*][*a*] and mx[*k*][*b*]; at the end add mx[0][*a*] and mx[0][*b*], the two edges into the LCA (unless *a* = *b* after the first phase). Build O(*n* log *n*), query O(log *n*), memory 2 · 17 · 10⁵ `int`s, about 13.6 MB. For @fig-18-wmax, mx[1] = [0, 4, 7, 4, 9, 7, 6, 2, 5]. The answers: (6, 4) = 9 on the path 6–3–1–4 (weights 6, 2, 9); (7, 8) = 7 on 7–3–1–0–2–5–8 (weights 1, 2, 4, 7, 3, 5); (8, 2) = 5 on 8–5–2. A harness compared the lifting answers with a walk along the path on 60 000 random queries.

**Exercise 18.7.** (a) A chain, par[*v*] = *v* − 1, with *n* = 10⁵: `fill` recurses 10⁵ deep and throws `StackOverflowError`. On the JDK used for this book it already failed on a chain of 10⁴ vertices, while a star of 10⁵ vertices (depth 1) worked. (b) par = [−1, 2, 0]: vertex 2 is the parent of 1. The index loop handles 2 first and adds size[2] = 1 to size[0] before vertex 1 has been added to size[2], so it returns [2, 1, 2] instead of [3, 1, 2]. (c) Build the BFS order and walk it backwards, as in `subtreeSizes` of @T:lst-18-bfs.

**Exercise 18.8.** (1) Binary lifting, @T:lst-18-lifting: 17 · 10⁵ = 1.7 · 10⁶ table entries to build, and at most 2 · 17 jumps per query, about 3.4 · 10⁶ in total. (2) Without a table: equalise the depths and climb both vertices one step at a time, at most 10⁵ steps per query, 10⁶ in all. Depths still come from the BFS order. (3) Subtree sizes in one backward pass, @T:lst-18-pairs: O(*n*). The total reaches 1.7 · 10¹⁴ on a chain, and one product `size[v] * (n - size[v])` can reach 2.5 · 10⁹, so cast to `long`. (4) Recursion, @T:lst-18-diameter: 10⁴ calls. LeetCode's tests for these problems pass with the recursive templates; do not carry that habit over to parent arrays. (5) Entry and exit times from one iterative DFS (@T:lst-18-euler), O(*n*), then O(1) per query with tin[*u*] ≤ tin[*v*] ≤ tout[*u*]. (6) 26 root-prefix counts per vertex (2.6 · 10⁵ integers) plus an LCA per query (@T:thm-18-prefix): 2 · 10⁴ · (26 + 28) ≈ 1.1 · 10⁶ steps. (7) `parentsFromEdges` (@T:lst-18-edges) and the forward depth pass: O(*n*), no recursion.

**Exercise 18.9.** Compare with @T:lst-18-arrays and @T:lst-18-bfs. The points that matter: insert children while walking *v* from *n* − 1 down to 0 so siblings come out in increasing order, use `order` itself as the queue, and in the size loop stop at *i* = 1 because `order[0]` is the root.
