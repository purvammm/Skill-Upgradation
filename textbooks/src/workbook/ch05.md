:::exercise{#exr-5-concept} Concept check
True or false, with a one-line reason.

1. In a min-heap stored in an array, the largest value is always at the last index.
2. Bottom-up heapify of 10⁶ values can make 10⁷ swaps.
3. `new PriorityQueue<>(list)` costs O(*n*), while adding the same *n* values one at a time can cost Θ(*n* log *n*).
4. `pq.remove(x)` on a `PriorityQueue` of size *n* costs O(log *n*).
5. Adding 4, 1, 3, 2 to a min-`PriorityQueue` and printing it shows `[1, 2, 3, 4]`, so a `PriorityQueue` keeps its array sorted.
6. `new PriorityQueue<Integer>((p, q) -> q - p)` is a correct max-heap for all `int` values.
7. In the IPO template, a project pushed into the heap stays affordable until the end of the run.
8. In the bricks-and-ladders greedy, a climb whose ladder was taken back never gets a ladder again.

:::exercise{#exr-5-bug} Find the bug
This version of heapify compiles and visits every internal node once, but it sometimes returns an array that is not a heap. Find an input of length 4 on which it fails, say which step of the proof of @T:thm-5-heapify no longer holds, and fix it with one change.

```java
// Turn a[0..n-1] into a min-heap: sift down every internal node
static void heapifyForward(int[] a) {
    for (int i = 0; i < a.length / 2; i++) siftDown(a, a.length, i);
}

static void siftDown(int[] a, int n, int i) {
    while (true) {
        int l = 2 * i + 1, r = l + 1, m = i;
        if (l < n && a[l] < a[m]) m = l;
        if (r < n && a[r] < a[m]) m = r;
        if (m == i) return;
        int t = a[i]; a[i] = a[m]; a[m] = t;
        i = m;
    }
}
```

:::answers
**Exercise 5.1.** (1) `a[--size]`; (2) `(i - 1) / 2`; (3) `2 * i + 1`; (4) `r < size && a[r] < a[m]`; (5) `return`; (6) `i = m`. The last leaf is the only element that can leave without breaking the shape: the array stays contiguous, so the tree stays complete and the index arithmetic stays valid. Moving children up instead would leave a hole wherever the chain of promotions ends, usually in the middle of the array.

**Exercise 5.2.**

| call | value sifted | swaps (index pairs) | array after the call |
|---|---|---|---|
| siftDown(3) | 2 | none | [8, 6, 7, 2, 5, 9, 1, 4, 3] |
| siftDown(2) | 7 | 2↔6 | [8, 6, 1, 2, 5, 9, 7, 4, 3] |
| siftDown(1) | 6 | 1↔3, 3↔8 | [8, 2, 1, 3, 5, 9, 7, 4, 6] |
| siftDown(0) | 8 | 0↔2, 2↔6 | [1, 2, 7, 3, 5, 9, 8, 4, 6] |

Five swaps in total. `poll()` returns 1 and moves the last leaf 6 to the root, giving [6, 2, 7, 3, 5, 9, 8, 4]. The 6 is swapped with 2 (indices 0↔1), then with 3 (1↔3), then with 4 (3↔7), which leaves [2, 3, 7, 4, 5, 9, 8, 6].

**Exercise 5.3.**

| i | h[i] → h[i+1] | climb | ladders on (heap after) | bricks pay | bricks left |
|---|---|---|---|---|---|
| 3 | 9 → 10 | 1 | {3, 6} | 1 | 6 |
| 4 | 10 → 6 | −4 | skip | | 6 |
| 5 | 6 → 13 | 7 | {6, 7} | 3 | 3 |
| 6 | 13 → 14 | 1 | {6, 7} | 1 | 2 |
| 7 | 14 → 18 | 4 | {6, 7} | 4 | −2 |

The method returns 7 at row 7, so rows 8 and 9 stay empty: building 7 (height 14) is reached, building 8 is not. At row 5 the ladder on the first climb (3) is taken back and given to the climb of 7. At row 3 the new climb of 1 is the smallest of three, so it pays bricks at once. With 3 ladders the method returns 9: at *i* = 9 the climb of 8 takes the ladder from the climb of 4, which then needs 4 bricks when only 2 are left. A brute force over all ladder assignments gives 7 and 9 as well.

**Exercise 5.4.** (1) False: [1, 3, 2] is a heap with its largest value at index 1. The largest value is always in some leaf, but not necessarily the last one. (2) False: heapify makes fewer than 2*n* swaps (@T:thm-5-linear), and for *n* = 10⁶ at most 999,993. (3) True: the collection constructor heapifies; on a decreasing input, 10⁶ calls of `add` made 17,951,445 swaps. (4) False: it searches the array linearly, O(*n*); see @T:tbl-5-pq. (5) False: the sorted print is a coincidence. Adding 5, 1, 4, 2, 3 prints `[1, 2, 4, 5, 3]`. (6) False: for 2 · 10⁹ and −2 · 10⁹ the subtraction overflows to 294,967,296, and the queue polls −2 · 10⁹ first. Use `Collections.reverseOrder()` or `Integer.compare(q, p)`. (7) True: profits are non-negative, so the capital never falls below the requirement of a project already unlocked. (8) True: the climb left the heap because at least *L* climbs as large as it were present, and the set of the *L* largest only gains larger climbs later, so it never returns (and the code never pushes it again).

**Exercise 5.5.** Sort the job numbers by arrival (the unlock key) and keep a pointer into that order, plus the current time *T* as a `long`. Each round: if the heap is empty and the next arrival is later than *T*, set *T* to that arrival (idle); push every job with arrival ≤ *T*; poll the heap's top, print it, and add its pages to *T*. The comparator is `(x, y) -> pages[x] != pages[y] ? Integer.compare(pages[x], pages[y]) : Integer.compare(x, y)`. Each job is pushed and polled once: O(*n* log *n*) time, O(*n*) memory. For the seven jobs the order is 0, 2, 1, 3, 4, 6, 5. Job 0 prints 0–4; at 4 the waiting jobs are 1, 2, 3, and job 2 (1 page) goes first, 4–5; jobs 1 and 3 both have 3 pages, so job 1 prints 5–8 and job 3 prints 8–11; the printer idles from 11 to 12; job 4 prints 12–17; then job 6 (1 page) prints 17–18 and job 5 prints 18–20. This method agreed with a direct O(*n*²) simulation on 5,000 random inputs.

**Exercise 5.6.** On [2, 3, 4, 1] it returns [2, 1, 4, 3]: the call for index 0 finds both children (3 and 4) larger and stops, and only then does the call for index 1 bring the 1 up to index 1, below the root 2. (With repeated values, [1, 1, 1, 0] fails in the same way.) On 1,000 random arrays of length 1 to 10 the forward version failed on 413. The proof of @T:thm-5-heapify needs both child subtrees of *i* to be heaps when *i* is processed, which is the starting condition of @T:lem-5-siftdown. Going forward, index *i* is processed before its subtrees are repaired. The fix is the order of the loop: `for (int i = a.length / 2 - 1; i >= 0; i--)`, which gives [1, 2, 4, 3].

**Exercise 5.7.** (a) @T:lst-5-ipo: a sort of O(*n* log *n*), about 1.7 · 10⁶ comparisons, then at most *n* pushes and *k* polls, (*n* + *k*) log₂ *n* ≈ 3.3 · 10⁶ heap steps. It fits easily. (b) Each `remove(x)` scans up to 10⁵ elements, so 10⁵ cancels can cost 10⁵ · 10⁵ = 10¹⁰ steps: far too slow. Use lazy deletion (@T:lst-5-lazy), O(log *n*) amortised per request, about 3 · 10⁵ · 17 ≈ 5 · 10⁶ steps, or a `TreeMap` of counts. (c) Heapify, for example `new PriorityQueue<>(list)`, makes at most 999,993 swaps for this *n*, and 20 polls at most 20 · 19 = 380 more. Adding the values one at a time can take up to 17,951,445 swaps, and sorting about 2 · 10⁷ comparisons; both also fit, but heapify does the least work. (d) The heap never holds more than 6 climbs, so @T:lst-5-ladders costs O(*n* log *L*), about 10⁵ · log₂ 6 ≈ 2.6 · 10⁵ steps. It fits easily.

**Exercise 5.8.** Check your version against this list: the array doubles when full; `add` writes at index `size` and sifts up from it; `poll` saves `a[0]`, writes `a[--size]` into it and sifts down from 0; `siftUp` stops at the root or when the parent is not larger; `siftDown` picks the smaller child, checks `r < size` before reading `a[r]`, and stops when neither child is smaller; `furthestBuilding` skips climbs ≤ 0, pushes every positive climb, polls into the bricks when the heap holds more climbs than there are ladders, and returns *i* (not *i* + 1) when the bricks go negative.
