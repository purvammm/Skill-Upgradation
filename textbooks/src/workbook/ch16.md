## Exercises

Do these after the mock and its post-mortem, or the next morning if you are tired. They practise the habits of Theory Chapter 16 on small new problems: stripping a story down to its model, bounding loops whose inner part varies, budgeting time and memory, choosing types, and testing the edge cases before you submit. None of them uses or hints at a mock problem.

:::exercise{#exr-16-model} From story to model
For each story, write the model of @T:def-16-model (objects, question type, limits), the complexity the limits allow (@T:tbl-16-limits), the technique you would try first and its chapter (@T:tbl-16-map), and one trap.

1. A shop has recorded its profit on each of *n* ≤ 2 · 10⁵ days; a day's profit is between −10⁹ and 10⁹. The owner wants to know how many periods of consecutive days had a total profit of exactly *K*.
2. A teacher has *n* ≤ 10⁵ students and a list of *m* ≤ 2 · 10⁵ pairs of students who quarrel. She has two rooms. Can she place every student in a room so that no quarrelling pair shares a room? Print YES or NO.
3. *n* ≤ 10⁵ documents with up to 10⁹ pages each must be printed in their given order on *k* ≤ *n* printers. Each printer receives one block of consecutive documents. Make the largest number of pages given to any printer as small as possible.
4. A build tool knows *n* ≤ 10⁵ modules and *m* ≤ 2 · 10⁵ rules of the form "module *x* must be built before module *y*". Print an order in which every module can be built, or IMPOSSIBLE.

:::exercise{#exr-16-aggregate} Aggregate counting
Each method counts the steps of its inner loop. For each one, give a bound in terms of *n* (the length of the array, or the argument) and the event you charge the work to, as in @T:thm-16-pointers. Then count the steps by hand for the input shown: `loopA` with *a* = [3, 1, 4, 1, 5, 9, 2, 6] and *k* = 8, `loopD` with the same *a*, and the others with *n* = 1000.

```java
static long loopA(int[] a, int k) {             // every a[i] >= 1
    long steps = 0, sum = 0;
    int l = 0;
    for (int r = 0; r < a.length; r++) {
        sum += a[r];
        while (sum > k) {
            sum -= a[l];
            l++;
            steps++;
        }
    }
    return steps;
}

static long loopB(int n) {
    long steps = 0;
    for (int len = 1; len < n; len *= 2)
        for (int i = 0; i < len; i++) steps++;
    return steps;
}

static long loopC(int n) {
    long steps = 0;
    for (int i = 0; i < n; i++) {
        int j = 0;
        while (j < i) {
            j++;
            steps++;
        }
    }
    return steps;
}

static long loopD(int[] a) {
    long steps = 0;
    ArrayDeque<Integer> st = new ArrayDeque<>();
    for (int x : a) {
        while (!st.isEmpty() && st.peek() <= x) {
            st.pop();
            steps++;
        }
        st.push(x);
        steps++;
    }
    return steps;
}

static long loopE(int n) {                       // a binary counter, incremented n times
    int[] bits = new int[32];
    long flips = 0;
    for (int t = 0; t < n; t++) {
        int i = 0;
        while (bits[i] == 1) {
            bits[i] = 0;
            i++;
            flips++;
        }
        bits[i] = 1;
        flips++;
    }
    return flips;
}
```

:::exercise{#exr-16-tests} Design the edge cases
A new problem: given *n* ≥ 1 integers with |*a*[*i*]| ≤ 10⁹ and 1 ≤ *k* ≤ *n*, print the largest sum of *k* consecutive elements. The samples are [2, −1, 3, 4, −2] with *k* = 2 (answer 7) and [1, 2, 3, 1, 2, 3] with *k* = 3 (answer 6). The solution below passes both samples.

```java
static long maxWindowSumBuggy(int[] a, int k) {
    int sum = 0;
    for (int i = 0; i < k; i++) sum += a[i];
    long best = 0;
    for (int i = k; i < a.length; i++) {
        sum += a[i] - a[i - k];
        best = Math.max(best, sum);
    }
    return best;
}
```

:::answers
**Exercise 16.1.** (1) Objects: an array of profits. Question: count. Limits: *n* = 2 · 10⁵ allows O(*n* log *n*) or O(*n*). Technique: prefix sums with a `HashMap<Long, Integer>` of earlier prefixes (Chapter 2), O(*n*). Traps: the profits can be negative, so a sliding window does not work; the prefix sums reach 2 · 10¹⁴ and the count can reach *n*(*n* + 1)/2 = 20 000 100 000, so both need `long`. (2) Objects: a graph whose vertices are students and whose edges are quarrels. Question: decide. Technique: the bipartite check by BFS colouring (Chapter 15), O(*n* + *m*): 10⁵ vertices and 4 · 10⁵ adjacency entries. Trap: the graph may be disconnected, so start a colouring from every uncoloured vertex. (3) Objects: an array of page counts. Question: optimise, "minimise the largest". Technique: binary search on the answer with a greedy check (Chapter 6). The total can be 10⁵ · 10⁹ = 10¹⁴, so the search takes 47 rounds of an O(*n*) check, about 4.7 · 10⁶ steps. Traps: sums in `long`, and the lower end of the search is the largest single document, not 0. (4) Objects: a directed graph with an edge *x* → *y* for each rule. Question: construct. Technique: Kahn's algorithm (Chapter 15), O(*n* + *m*) = 3 · 10⁵ steps. Traps: the direction of the edge, and printing IMPOSSIBLE when fewer than *n* modules are output (a cycle).

**Exercise 16.2.**

| method | bound | the work is charged to | count on the given input |
|---|---|---|---|
| loopA | ≤ *n* | each step moves *l* forward, and *l* never passes *n* | 6 |
| loopB | < 2*n* | the sum 1 + 2 + 4 + ⋯ + 2ʲ with 2ʲ < *n* is 2ʲ⁺¹ − 1 | 1023 |
| loopC | *n*(*n* − 1)/2 | nothing: *j* restarts at 0 for every *i* | 499 500 |
| loopD | ≤ 2*n* | each element is pushed once and popped at most once | 14 |
| loopE | < 2*n* | bit *i* is set and cleared at most once per 2ⁱ increments | 1994 |

In `loopA` the window shrinks by 1, 2 and 3 steps at *r* = 3, 4 and 5; in `loopD` there are 8 pushes and 6 pops. `loopC` is the quadratic one: its inner counter is declared inside the outer loop and restarts at 0, so "at most *i* steps" adds up to 0 + 1 + ⋯ + (*n* − 1). In `loopA`, *l* survives from one *r* to the next and only moves forward, which is what @T:thm-16-pointers needs. For `loopE`, bit *i* changes once every 2ⁱ increments, so *n* increments flip at most *n* + *n*/2 + *n*/4 + ⋯ < 2*n* bits; the exact total is 2*n* − (number of 1-bits of *n*), 2000 − 6 = 1994 for *n* = 1000. Measured at *n* = 10⁶: `loopA` with all values 1 and *k* = 0 makes 1 000 000 steps, `loopD` on an increasing array 1 999 999, and `loopE` 1 999 993.

**Exercise 16.3.**

| idea | operations or bytes | fits? | better choice |
|---|---|---|---|
| `HashMap` counting 2 · 10⁶ values | at most 10⁶ + 1 keys at about 77 bytes: up to 77 MB; 2 · 10⁶ merges at 0.23 s per 10⁶: about 0.46 s | yes, but slow and large | `int[1000001]`: 4 MB and about 0.04 s |
| `int[1000000][2]` | about 29 bytes per row, 29 MB | yes, but wasteful | `int[2][1000000]` or two arrays: 8 MB |
| `long[5000][5000]` | 2 · 10⁸ bytes = 200 MB | no, with the JVM's own memory | two rows of `long[5000]`: 80 000 bytes |
| sorting `Integer[]` of 10⁶ | about 0.71 s | risky on a slower judge | `int[]` with `Arrays.sort`: about 0.13 s |
| 3 · 10⁸ steps of `x * y % MOD` | 3 × 0.43 s ≈ 1.3 s | no | reduce the number of steps; the modulo is the expensive part |
| all pairs *i* < *j*, *n* = 10⁵ | 4 999 950 000 steps, about 17 to 50 s | no | find an O(*n* log *n*) idea; keep the pairs as the stress-test brute force |
| recursive DFS, depth up to 10⁵ | 10⁵ nested calls; the default stack held between about 7 400 and 24 700 | no: `StackOverflowError` | an explicit `ArrayDeque` stack (Chapter 15) |

The times come from @T:tbl-16-time and the stack depths from @T:sec-16-budgets, all measured on the machine used for the book; a judge can be two or three times slower, which turns "about 0.7 s" into a risk.

**Exercise 16.5.**

| input | k | correct answer | method returns |
|---|---|---|---|
| [10⁹] | 1 | 1 000 000 000 | 0 |
| [7, 7, 7, 7, 7] | 3 | 21 | 21 |
| [1, 2, 3, 4, 5] | 3 | 12 | 12 |
| [5, 4, 3, 2, 1] | 3 | 12 | 9 |
| [10⁹, 10⁹, 10⁹, 10⁹, 10⁹] | 3 | 3 000 000 000 | 0 |
| [−10⁹, 10⁹, −10⁹, 10⁹, −10⁹] | 3 | 1 000 000 000 | 1 000 000 000 |

Three tests fail. **Bug 1:** the first window is never compared with `best`, which starts at 0. The smallest input (*n* = 1, where the second loop never runs) and the reverse-sorted array (whose best window is the first one) expose it. **Bug 2:** `sum` is an `int`; three values of 10⁹ add up to 3 · 10⁹, which wraps around to −1 294 967 296, and the maximum-values test exposes it (the method then returns its starting value 0). Fix: declare `long sum`, set `long best = sum;` after the first loop, and write `sum += (long) a[i] - a[i - k];` (the difference alone, at most 2 · 10⁹, happens to fit an `int`, but the cast removes the doubt). The generator has no array whose values are **all negative**. For [−5, −3, −8] with *k* = 1 the answer is −3, and any version that keeps `best = 0`, even with the first window compared, returns 0. The fixed method matched a brute force over all windows on 5000 random small arrays and on 5000 arrays with values up to 10⁹ in absolute value; the buggy one was wrong on 3058 of the small ones.
