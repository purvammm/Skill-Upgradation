**Exercise 1.1.** (1) `st == null || !st.hasMoreTokens()`; (2) `return null`; (3) `new StringTokenizer(line)`; (4) `fs.nextLong()`; (5) `out.flush()`. The `while` loop in `next()` keeps reading lines until the tokenizer has a word, so a line break is treated like a space. Whether the four numbers share a line or have one line each, `next()` returns them in the same order.

**Exercise 1.2.**

| char | action | stack (bottom → top) |
|---|---|---|
| ( | push ) | ) |
| [ | push ] | )] |
| ] | pop ], matches | ) |
| { | push } | )} |
| ( | push ) | )}) |
| ) | pop ), matches | )} |
| } | pop }, matches | ) |
| ) | pop ), matches | (empty) |
| ] | stack is empty: return `false` | (empty) |

The `expect.isEmpty()` half of the condition returns `false`: a closer arrived when no opener was waiting. Without the last character the loop ends with an empty stack and the method returns `true`.

**Exercise 1.3.** [12, 15): floor 8 (12), ceiling none, accepted (touching 12 is allowed). [10, 13): floor 8 (12), ceiling 12 (15); rejected because [8, 12) ends after 10. [0, 3): floor none, ceiling 3 (8), accepted because 3 is not less than 3. [15, 16): floor 12 (15), ceiling none, accepted. [14, 16): floor 12 (15), ceiling 15 (16); rejected because [12, 15) ends after 14. Final map: {0: 3, 3: 8, 8: 12, 12: 15, 15: 16}.

**Exercise 1.4.** (1) −2,147,479,015: the true product 2,147,488,281 exceeds 2³¹ − 1 and wraps by 2³². (2) −2 and 2: `%` takes the sign of the left operand, `floorMod` does not. (3) `true` and `false`: 127 is in the `Integer` cache −128..127, 200 is not, so two different objects are created. (4) `false` and `true`: `t` is built at run time, so it is a new object with the same text. (5) [5, 7]: `remove(1)` with an `int` argument removes index 1; `remove(Integer.valueOf(1))` would remove a value. (6) It throws a `NullPointerException`: `ArrayDeque` refuses `null`. (7) 195 (an `int`: 97 + 98) and `'z'`. (8) False: `toString` shows the internal heap array; only the first element is guaranteed to be the smallest.

**Exercise 1.5.** (1) 2 · 10⁵ · (2 · 10⁵ − 1)/2 = 19,999,900,000 ≈ 2 · 10¹⁰ pairs: far too slow. (2) 2²⁰ · 20 = 20,971,520 ≈ 2 · 10⁷ steps: fits. (3) About 10⁵ · log₂ 10⁵ ≈ 1.7 · 10⁶ for the sort and as much again for the searches: fits easily. (4) 3000³ = 2.7 · 10¹⁰ triples (or about 4.5 · 10⁹ if only *i* < *j* < *k*): too slow; *n* ≤ 500 is the usual limit for O(*n*³). (5) 25 · 10⁶ cells × 8 bytes = 2 · 10⁸ bytes, about 200 MB: too much for most limits.

**Exercise 1.6.** Keep the free spots in a `TreeSet<Integer>`, initially 1..*m*. "Arrive *p*" is `ceiling(p)`: if it is `null`, print −1; otherwise remove that spot and print it. "Leave *s*" is `add(s)`. Each event costs O(log *m*), so the total is O(*m* log *m* + *q* log *m*). For the events given the arrivals print 2, 3, 5, 6, 3, −1, 1, 4. (After `leave 3` the free spots are {1, 3, 4}; the arrival preferring 6 finds no free spot ≥ 6; after `leave 6` the arrival preferring 4 takes 4.)

**Exercise 1.7.** `cnt.get(x) == cnt.get(y)` compares two `Integer` objects by reference. Counts up to 127 come from the `Integer` cache, so equal counts are the same object and the test passes. With *x* = 1 and *y* = 2 each occurring 128 times the method returns `false` (it returns `true` with 127 each). Fix: compare values, for example `return cnt.getOrDefault(x, 0).intValue() == cnt.getOrDefault(y, 0).intValue();`, which also handles a value that does not occur at all.

**Exercise 1.8.** Compare your code with @T:lst-1-lists line by line, especially the order `nxt = head.next; head.next = prev; prev = head; head = nxt;` and the check `fast != null && fast.next != null`. The meeting step is the smallest multiple of λ that is at least max(μ, 1): for μ = 4, λ = 6 it is 6; for μ = 10, λ = 3 it is 12.
