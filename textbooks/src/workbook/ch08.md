:::exercise{#exr-8-concept} Concept check
Answer true or false, and give a one-line reason or a counterexample.

1. `1 << 32` evaluates to 4 294 967 296.
2. `-17 >> 1` is −9, while `-17 / 2` is −8.
3. `(x & (x - 1)) == 0` correctly tests "*x* is a power of two" for every `int` *x*.

5. If every value of an array occurs twice, except two different values *u* and *v* that occur once each, the XOR of the array is 0.
6. A trie that stores *n* distinct *B*-bit numbers has exactly *n* · *B* + 1 nodes.
7. XORing all the non-zero numbers of a basis together gives the maximum subset XOR.

:::exercise{#exr-8-bug} Find the bug
This shortened `countXorLess` has lost one line of @T:lst-8-trie: its author reasoned that the loop stops after bit 0 anyway. static int[][] child = new int[100 * 31 + 1][2];   // child[node][bit], 0 = missing; node 0 is the root
static int[] cnt = new int[100 * 31 + 1];

static long countXorLessBuggy(int x, int k) {

:::answers
**Exercise 8.1.** (1) `((x >> b) & 1) ^ 1`; (2) `res |= 1 << b`; (3) `child[node][want ^ 1]`; (4) `cnt[child[node][xb]]`; (5) `child[node][xb]`; (6) `if (node == 0) break;`. Every *y* in the child *x*<sub>*b*</sub> agrees with *x* at bit *b*, so *x* ⊕ *y* has 0 there, while *k* has 1, and the two agree on all higher bits (the walk has followed *k*'s bits so far). By @T:lem-8-top, all of them are smaller than *k*. In the child *x*<sub>*b*</sub> ⊕ 1 the XOR bit is 1, equal to *k*'s, so those numbers are still undecided and the walk continues there.

**Exercise 8.2.** The trie has 19 nodes: the root, 2 nodes at depth 1 (prefix 0 with count 3, prefix 1 with count 3), 4 at depth 2 (00: 1, 01: 2, 10: 1, 11: 2), 6 at depth 3 and 6 leaves. The bound 6 · 4 + 1 = 25 is not reached because the numbers share prefixes.

|---|---|---|---|---|---|
| 3 | 1 | 0 | yes | 8 = 1000 | 0 |
| 2 | 1 | 0 | yes | 12 = 1100 | 00 |
| 1 | 0 | 1 | yes | 14 = 1110 | 001 |
| 0 | 1 | 0 | no | 14 = 1110 | 0011 |

`maxXor(13)` = 14, reached at *y* = 3 = 0011.

| bit b | x_b | k_b | action | count after |
|---|---|---|---|---|
| 3 | 1 | 0 | go to child 1 (prefix 1) | 0 |
| 2 | 1 | 1 | add child 1 (prefix 11, count 2), go to child 0 (prefix 10) | 2 |
| 1 | 0 | 1 | add child 0 (prefix 100, count 1), go to child 1: missing, stop | 3 |
| 0 | — | — | not reached | 3 |

`countXorLess(13, 6)` = 3. The six XORs are 13 ⊕ 9 = 4, 13 ⊕ 5 = 8, 13 ⊕ 12 = 1, 13 ⊕ 3 = 14, 13 ⊕ 14 = 3 and 13 ⊕ 6 = 11. The maximum 14 comes from *y* = 3, and the three XORs below 6 come from 9, 12 and 14. The count 2 at bit 2 is the subtree 11 = {12, 14}, and the count 1 at bit 1 is the subtree 100 = {9}.

The maximum subset XOR is 29 = 11101₂. The rank is 4, so there are 2⁴ = 16 distinct XORs, each from 2⁶⁻⁴ = 4 subsets; a brute force over all 64 subsets confirms both numbers and the maximum. `canMake(13)`: 01101 → ⊕ 11 → 00110 → ⊕ 7 → 00001 → ⊕ 1 → 0, so yes (for example 17 ⊕ 28 = 13). `canMake(14)`: 01110 → ⊕ 11 → 00101 → ⊕ 7 → 00010, and *b*[1] is empty, so 2 remains and the answer is no. **Exercise 8.5.** (1) False: Java takes the shift distance mod 32, so `1 << 32` is `1 << 0` = 1; write `1L << 32`. (2) True: `>>` rounds down (⌊−8.5⌋ = −9), while integer division rounds towards zero. (3) False: it is also true for 0 and for `Integer.MIN_VALUE`, whose bits are a single 1 followed by 31 zeros (and MIN − 1 wraps to MAX); require *x* > 0. (4) False: it returns the *value* 32; the index 5 is `31 - Integer.numberOfLeadingZeros(40)`. (5) False: by @T:thm-8-odd the XOR is *u* ⊕ *v*, and *u* ⊕ *v* = 0 would force *u* = *v* by law (5) of @T:thm-8-laws. (6) False: *n* · *B* + 1 is an upper bound; the trie of @exr-8-trace has 19 nodes, not 25. (7) False: in @exr-8-faded, 26 ⊕ 11 ⊕ 7 ⊕ 1 = 23, but the maximum is 29; the greedy must skip *b*[3] and *b*[0]. (8) True: the rank is 4, and each reachable value comes from 2<sup>*n*−*r*</sup> = 2² = 4 subsets (@T:sec-8-basis, "What the basis cannot answer").

**Exercise 8.6.** xor(*a*[*l*..*r*]) = *X*[*r* + 1] ⊕ *X*[*l*], so count the pairs *p* < *q* of prefix indices with *X*[*p*] ⊕ *X*[*q*] < *k*. Keep a binary trie with counts of the prefixes seen so far, seeded with the empty prefix *X*[0] = 0. For *q* = 1..*n*: compute *X*[*q*], add `countXorLess(X[q], k)`, and only then insert *X*[*q*], so that no prefix is paired with itself. Since 10⁶ < 2²⁰, *B* = 20 bits suffice for both the values and *k*. Time: *n* + 1 inserts and *n* queries of 20 steps, about 4 · 10⁶. Memory: at most 20(*n* + 1) + 1 ≈ 2 · 10⁶ nodes, about 24 MB in the flat layout of @T:lst-8-flat with counts. The answer can reach *n*(*n* + 1)/2 ≈ 5 · 10⁹, so it needs a `long`.

For the example the prefixes are *X* = [0, 5, 4, 2, 0, 7]. The pairs with XOR below 4 are (0, 3) with 2, (0, 4) with 0, (1, 2) with 1, (1, 5) with 2, (2, 5) with 3 and (3, 4) with 2. So the answer is 6: the subarrays *a*[0..2], *a*[0..3], *a*[1..1], *a*[1..4], *a*[2..4] and *a*[3..3]. A brute force agrees, and the trie solution agreed with a brute force on 7000 random arrays.

**Exercise 8.7.** The `if (node == 0) break;` line is missing. Store only the number 2: `countXorLessBuggy(0, 1)` returns 1, but 0 ⊕ 2 = 2 is not less than 1, so the answer is 0. For bits 30..2, *k*<sub>*b*</sub> = 0 and the walk follows the zeros of 2. At bit 1, *k*<sub>*b*</sub> = 0 and *x*<sub>*b*</sub> = 0, but 2 has a 1 there, so child 0 is missing and `node` becomes 0, which is the index of the **root**. At bit 0, *k*<sub>*b*</sub> = 1, and the walk adds the count of the root's child 0, which holds the whole trie. (Another example: store only 0 and query (0, 3); it returns 2 instead of 1.) Fix: put `if (node == 0) break;` back after the `if`/`else`. On 5000 random small tries the buggy version was wrong 1987 times and the fixed one never.

**Exercise 8.8.** (1) Binary trie with *B* = 30: insert everything, then query every number, about 2 · 2 · 10⁵ · 30 = 1.2 · 10⁷ steps. There are at most 2 · 10⁵ · 30 + 1 = 6 000 001 nodes: 48 MB for the flat `next` array of @T:lst-8-flat (`maxXor` needs no counts), against about 170 MB for `int[nodes][2]`. Trap: sizing the arrays below *n* · *B* + 1. (2) Per-bit counting (@T:lst-8-pairxor), 30 · 10⁶ = 3 · 10⁷ steps and O(1) extra memory. Trap: the exact sum can reach about (*n*²/4)(2³⁰ − 1) ≈ 2.7 · 10²⁰, beyond `Long.MAX_VALUE` ≈ 9.2 · 10¹⁸. `pairs` (at most 2.5 · 10¹¹) fits in a `long`, but `pairs << b` does not, so add `pairs % MOD * ((1L << b) % MOD) % MOD` instead. (3) XOR basis: 10¹⁸ < 2⁶⁰, so the 61 slots of @T:lst-8-basis suffice; about 10⁵ · 61 ≈ 6 · 10⁶ steps and 61 `long`s. Trap: read the values as `long`, and test bits with `(x >> i) & 1`, never `1 << i`. (4) Prefix XOR with a count array `int[1 << 20]` (4 MB) in place of the `HashMap` of @T:lst-8-subxor: every prefix and `prefix ^ k` are below 2²⁰, so they are valid indices. About 10⁶ steps. Trap: the count can reach about 5 · 10¹¹, so keep the total in a `long`. (5) The rank can be 20 > *N*/2 = 10, so the basis may use too many elements. Brute force over all 2²⁰ subsets with a size check (Chapter 9): about 20 · 2²⁰ ≈ 2 · 10⁷ steps. (6) The rank is at most 20 ≤ *N*/2 = 50, so the basis maximum is the XOR of at most 20 original numbers (@T:thm-8-size) and is the answer: about 100 · 21 steps.
