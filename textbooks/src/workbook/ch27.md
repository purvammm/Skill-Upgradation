:::exercise{#exr-27-check} Run the checklist on a submission
A problem says: the input has *t* test cases (*t* ≤ 10⁴); each has *n* (with the sum of *n* at most 2 · 10⁵) and then *n* values up to 10⁹, and the samples put every value on its own line. For each test case, print the number of pairs *i* < *j* with *a*[*i*] = *a*[*j*]. This submission compiles and looks reasonable.

```java
import java.io.*;
import java.util.*;

public class Main {
    static Map<Integer, Integer> seen = new HashMap<>();

    public static void main(String[] args) throws IOException {
        BufferedReader br = new BufferedReader(new InputStreamReader(System.in));
        PrintWriter out = new PrintWriter(new BufferedWriter(new OutputStreamWriter(System.out)));
        int t = Integer.parseInt(br.readLine().trim());
        while (t-- > 0) {
            int n = Integer.parseInt(br.readLine().trim());
            StringTokenizer st = new StringTokenizer(br.readLine());
            int pairs = 0;
            for (int i = 0; i < n; i++) {
                int x = Integer.parseInt(st.nextToken());
                int before = seen.getOrDefault(x, 0);
                pairs += before;                  // x pairs with every earlier copy
                seen.put(x, before + 1);
            }
            out.println(pairs);
        }
    }
}
```

Go through the nine items of the checklist in order. For every item that fails, write the item, an input that shows the failure and what the program does on it, and the fix.

**Exercise 27.1.** There is no single right card; it must be yours. A model to compare with:

*Time.* 0–15 read all, notes, rank by sureness. 15–60 surest. 60–120 second (minute 100: brute force and move on). 120–165 hard: brute force if no idea in 15 minutes, then optimise; with four problems, both brute forces first, both submitted by 150, then optimise one. 165–180 no new code, check every submission compiles.

*Rules.* Start the surest problem at 15. No idea after 15 minutes: fallback submitted. Wrong answer and no new explanation for 15 minutes: stress test for 10, then move on. Minute 100: Q2 finished or fallback in. Minute 150: everything has a submission. A passing solution is never touched again. Minute 165: no new code.

*Checklist.* Format, samples, edges (*n* = 1, equal, max), `long` and mod, input order as in the samples and stub unchanged, test-case resets, recursion depth, flush and no debug prints, right version.

*Personal rules* (example from a log with overflow, misread and off-by-one entries): cast the first factor of every product to `long`; write the output format of the first sample before coding; test *n* = 1 before every submission.

**Exercise 27.2.** Four items fail.

* Item 5, input: the program reads all *n* values from one line, but the samples put each value on its own line. On the input `2 / 3 / 1 / 1 / 1 / 2 / 1 / 1` (one number per line) the second `st.nextToken()` throws `NoSuchElementException`. Fix: read with FastScanner, whose `next()` ignores line breaks.
* Item 8, output plumbing: there is no `out.flush()`, so the program prints nothing at all, even on the sample. Fix: `out.flush();` after the loop.
* Item 6, many test cases: `seen` is static and never cleared, so the second test case sees the first one's counts. With the input and flush fixed, the sample above prints 3 and 7 instead of 3 and 1. Fix: create the map inside the `while` loop (its cost is proportional to the values of that test case only).
* Item 4, types: `pairs` is an `int`. For *n* = 2 · 10⁵ equal values the answer is 2 · 10⁵ · (2 · 10⁵ − 1)/2 = 19,999,900,000, and the program prints −1,474,936,480. Fix: `long pairs`.

With the four fixes the method agrees with an O(*n*²) brute force on 5,000 random arrays. Items 1–3, 7 and 9 pass: the format is one number per line, there is no recursion, and there is only one version.

**Exercise 27.3.**

1. Start Q3: it is the problem you are surest of, and the rule at minute 15 says "whatever its number" (row 1 of the rules; the 0–15 row of the time table says to rank by sureness, not labels).
2. Stress-test against the brute force you already have; the all-equal case is small enough to compare by hand too. The rule is "a wrong answer and no new explanation": you have spent less than 15 minutes on this bug, so keep at it, using the oracle, until minute 60 at most.
3. Write and submit Q2's brute force now, then move to Q3 (row "minute 100"). Writing it takes 10 minutes or so, and it is still the cheapest marks on Q2.
4. The four-problem plan: brute forces for Q3 and Q4 first, about 15 minutes each, both submitted by minute 150, then optimise the one with the clearest next step, which is probably Q3. Starting the 40-minute Q3 idea now would leave Q4 blank at minute 150.
5. Keep working on the full solution until 165: the minute-150 rule is met because every problem has a submission. If the full solution does not pass your tests by 165, the brute force stays as the submission.
6. Do nothing. Q2 passes, so it is not touched again, and after minute 165 no new code is written.

**Exercise 27.5.** A model row. *Limits:* *n*, *q* ≤ 10⁵, prices and budgets ≤ 10⁹ (too large to index an array), counts ≤ 10⁵ fit an `int`. *Idea:* sort the prices once; for each budget the answer is the upper bound of the budget, the first index whose price is larger (Chapter 6). *Complexity:* O(*n* log *n* + *q* log *n*), about 3.4 · 10⁶ comparisons. *Brute force:* for each customer, count the prices ≤ budget in a loop, O(*nq*), which finishes for *n* · *q* up to about 10⁷, for example *n* = *q* = 3,000. *Edges:* a budget below every price (answer 0) or above every price (answer *n*), repeated prices equal to the budget (upper bound, not lower bound), *n* = 1. *Sure:* 5 of 5, and a good candidate for the first problem.

**Exercise 27.6.**

1. Misread statement. Rule: before coding, write the output of the first sample next to your own trace of it, including whether positions start at 0 or 1.
2. Stack overflow. Rule: any traversal of a tree or graph with more than 10⁴ vertices uses a BFS order or an explicit stack, never recursion.
3. Ran out of time. Rule: minute 100, Q2 finished or its brute force submitted; minute 150, every problem has a submission.
4. Overflow. Rule: every sum and product is `long`, and every solution is run once on the maximum size with maximum values before submitting.
5. Wrong idea. Rule: a greedy is either proved by an exchange argument or stress-tested against a brute force before it is submitted.
6. Input reading. Rule: check the reading order against every sample before writing the logic, and trust the samples over the format text (the plan's Lesson 2).
