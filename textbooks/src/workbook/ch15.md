:::exercise{#exr-15-bug} Find the bug
This version of @T:lst-15-01bfs copies the rule of plain BFS: a vertex is final as soon as it is reached. It compiles, and it is correct on every graph whose costs are all 1. Find a directed graph with three vertices on which it returns a wrong distance, say which value it returns and what is correct, and fix it.

```java
static int[] zeroOneBfsBuggy(List<int[]>[] g, int src) {
    int[] d = new int[g.length];
    Arrays.fill(d, Integer.MAX_VALUE);
    d[src] = 0;
    ArrayDeque<Integer> dq = new ArrayDeque<>();
    dq.add(src);
    while (!dq.isEmpty()) {
        int u = dq.pollFirst();
        for (int[] e : g[u]) {
            int v = e[0];
            if (d[v] != Integer.MAX_VALUE) continue;      // already reached: skip it, as in BFS
            d[v] = d[u] + e[1];
            if (e[1] == 0) dq.addFirst(v);
            else dq.addLast(v);
        }
    }
    return d;
}
```

**Exercise 15.1.** (1) `indeg[v]++`; (2) `indeg[u] == 0`; (3) `head < tail`; (4) `--indeg[v] == 0`; (5) `tail == n ? order : null`. The positions `head..tail − 1` are the queue: they hold vertices that have been output but whose edges have not been processed yet; positions before `head` are finished. A counter only goes down, by one per edge into *v*, so it passes through the value 0 exactly once, after the last of those edges has been processed. That is why each vertex is appended at most once, even with duplicate edges.

**Exercise 15.5.** (1) False: it is set once, when the vertex is pushed, and never changed; @T:thm-15-bfs proves that this first value is already the distance. (2) True. In a tree, every neighbour of *v* except its parent is a child, which can only be discovered through *v*, so *v* is discovered from its parent and gets the right value by induction; on 3000 random trees the stack version always agreed with BFS. On the 5-cycle 0–1, 0–2, 2–3, 3–4, 4–1 it gives vertex 4 the value 3, although 0–1–4 has length 2. (3) True: each vertex is its own component, and @T:lst-15-components starts 10⁵ rounds. (4) False: the 4-cycle is coloured 0, 1, 0, 1; only odd cycles prevent a two-colouring (@T:thm-15-odd). (5) False: in the graph 0 → 1, 1 → 0, 1 → 2, vertex 2 is on no cycle, but its counter never reaches 0, so it is not output either. (6) True: with `g[5]` = [3, 6] instead of [6, 3], @exr-15-kahn outputs 0, 2, 5, 3, 6, 1, 4, which is also a topological order. (7) False: each vertex is pushed at most twice (@T:thm-15-01), so it is popped at most twice. (8) False: all sources go into one queue and each vertex is still pushed once, so the cost stays O(*n* + *m*).

**Exercise 15.6.** A vertex is a pair (cell, *h*), where *h* = 0 if the hammer is unused and *h* = 1 if it has been used: 2*RC* vertices. From (*r*, *c*, *h*) a move to a neighbouring open cell keeps *h*; a move into a wall cell is allowed only from *h* = 0 and leads to *h* = 1. Every move costs 1, so plain BFS on the pairs applies, with `dist[2][R][C]`. Start at (0, 0, 0) and answer min(dist[*R* − 1][*C* − 1][0], dist[*R* − 1][*C* − 1][1]), ignoring −1 values. Time: 2*RC* = 2 · 10⁶ vertices with 4 moves each, about 8 · 10⁶ checks; memory 2*RC* `int`s, 8 MB.

On @fig-15-wwall, the first arrival at (0, 2) comes after 2 steps, straight through the wall at (0, 1), so the naive version fixes (0, 2) as "hammer used". Every cell to its right is first reached from (0, 2) and is also marked "used", so the wall at (1, 5) above T can no longer be broken, and the naive search returns −1. Its first arrival was the wrong one to keep: the walk around the wall, (0, 0) → (1, 0) → (2, 0) → (2, 1) → (2, 2) → (1, 2) → (0, 2), takes 6 steps but keeps the hammer. With the pairs, the search keeps both arrivals, (0, 2, 1) at 2 and (0, 2, 0) at 6, and continues (0, 3), (0, 4), (0, 5), breaks (1, 5) at step 10 and reaches T at step **11**. Without the hammer T cannot be reached at all. On 3000 random grids the pair BFS matched a brute force that removes each wall in turn and runs a plain BFS; the naive version was wrong on 88 of them, and on this grid it fails whatever order the four directions are tried in.

**Exercise 15.7.** Take 0 → 1 with cost 1, 0 → 2 with cost 0 and 2 → 1 with cost 0. Popping 0 reaches 1 with *d* = 1 (back) and 2 with *d* = 0 (front). When 2 is popped, the free edge would give 1 the cost 0, but 1 is already "reached" and is skipped. The method returns *d*[1] = 1; the correct value is 0 (path 0 → 2 → 1). In 0-1 BFS the first value given to a vertex need not be final, because a later free edge can improve it. Fix: replace the `if (d[v] != ...)` test and the next line with `int nd = d[u] + e[1]; if (nd >= d[v]) continue; d[v] = nd;`, as in @T:lst-15-01bfs. When every cost is 1 the deque only ever adds at the back, so the method is plain BFS, which is why it passed those graphs. On 4000 random graphs with costs 0 and 1 the buggy method disagreed with Bellman–Ford on 390, and on the graph of @exr-15-01 it gives *d*[2] = 1.

**Exercise 15.8.** (1) Grid BFS, @T:lst-15-grid: 10⁶ cells, at most 4 · 10⁶ neighbour checks, and `dist` as `int[1000][1000]` is 4 MB. Trap: check the bounds before reading the cell. (2) As `List<Integer>[]` about 26 MB, as head/next/to arrays about 8.7 MB, as measured in @T:sec-15-repr; both fit. Trap: for an undirected graph store each edge twice. (3) An explicit stack or the BFS queue: 2 · 10⁵ pushes. Trap: a recursive DFS needs 2 · 10⁵ nested calls on a path, far beyond the default stack. (4) One multi-source BFS with the 1000 hospitals as sources (@T:thm-15-multi): about *n* + 2*m* = 700 000 steps. Trap: 1000 separate BFS runs would cost about 7 · 10⁸. (5) 0-1 BFS: each cell is pushed at most twice, so at most 2 · 10⁶ pushes and 8 · 10⁶ edge checks. Dijkstra would also work but adds a heap factor of about log₂ 10⁶ ≈ 20. Trap: compare `nd < d[v]` on every relaxation, not "already seen". (6) Kahn's algorithm: about *n* + *m* = 3 · 10⁵ steps; possible exactly when all 10⁵ courses are output. Trap: the pair [*a*, *b*] gives the edge *b* → *a*. (7) Costs 1 and 2 are not "0 or *c*", so 0-1 BFS does not apply directly. Split every cost-2 edge *u* → *v* into *u* → *x* → *v* through a new vertex *x*, then run plain BFS: at most 3 · 10⁵ vertices and 4 · 10⁵ edges. Dijkstra (Chapter 17) also works. Trap: answer only for the original vertices.
