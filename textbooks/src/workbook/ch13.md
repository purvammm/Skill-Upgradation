:::exercise{#exr-13-concept} Concept check
Answer true or false, and give a one-line reason.

1. After patience sorting finishes, `tails` is a longest increasing subsequence of *a*.
2. For the longest non-decreasing subsequence, each element replaces the first tail strictly greater than it.
3. In the mountain formula, an index with up[*i*] = 1 can be the peak if down[*i*] is large.
4. A Fenwick tree of maxima can process an update that lowers a stored value.
5. For envelopes that nest when both sides are strictly smaller, envelopes of equal width are sorted by height descending.
6. Adding a remainder modulo *K* as an extra state multiplies the work of the DP by about *K*.

:::exercise{#exr-13-bug} Find the bug
This method should return the length of the longest **strictly** increasing subsequence of ranks in 1..*V*. It compiles and passes the sample [3, 1, 2, 4]. Find an input where it fails, say what it returns there, and fix it with one change.

```java
static int lisRanks(int[] rank, int V) {
    int[] fw = new int[V + 1];
    int best = 0;
    for (int x : rank) {
        int cur = 1;
        for (int i = x; i > 0; i -= i & -i) cur = Math.max(cur, fw[i] + 1);
        for (int i = x; i <= V; i += i & -i) fw[i] = Math.max(fw[i], cur);
        best = Math.max(best, cur);
    }
    return best;
}
```

:::answers
**Exercise 13.1.** (1) `len`; (2) `>=`; (3) `tails[lo] = x`; (4) `if (lo == len) len++`. For the non-decreasing version blank (2) becomes `>`: equal values may follow each other, so *x* must go after every tail equal to it, which is the first tail strictly greater than *x* (the upper bound).

**Exercise 13.2.**

| x | position p | p + 1 | tails after |
|---|---|---|---|
| 4 | 0 | 1 | [4] |
| 10 | 1 | 2 | [4, 10] |
| 4 | 0 | 1 | [4, 10] |
| 3 | 0 | 1 | [3, 10] |
| 8 | 1 | 2 | [3, 8] |
| 9 | 2 | 3 | [3, 8, 9] |
| 1 | 0 | 1 | [1, 8, 9] |
| 5 | 1 | 2 | [1, 5, 9] |

The LIS length is 3; @T:lst-13-recover returns 3, 8, 9 (4, 8, 9 also works). The final `tails` = [1, 5, 9] is not a subsequence: 1 and 5 come after 9 in *a*. The second 4 lands on the existing 4 and changes nothing, which is the strict version at work. The non-decreasing version on the same array gives length 4 (for example 4, 4, 8, 9).

**Exercise 13.3.** up = [1, 2, 2, 3, 3, 1, 4, 2] and down = [2, 3, 2, 3, 2, 1, 2, 1]. A peak is allowed at indices 1, 2, 3, 4 and 6, with up + down − 1 = 4, 3, 5, 4, 5. The longest mountain has length 5, so the fewest removals are 8 − 5 = 3. Two examples: 2, 5, 6, 4, 1 (peak 6 at index 3) and 2, 3, 6, 7, 2 (peak 7 at index 6). Indices 0, 5 and 7 cannot be peaks because one side has length 1.

**Exercise 13.4.** Ranks [3, 1, 5, 1, 2, 4], *V* = 5.

| a[i] | rank | prefixMax(rank − 1) | cur | fw[1..V] after |
|---|---|---|---|---|
| 30 | 3 | 0 | 1 | [0, 0, 1, 1, 0] |
| 10 | 1 | 0 | 1 | [1, 1, 1, 1, 0] |
| 50 | 5 | 1 | 2 | [1, 1, 1, 1, 2] |
| 10 | 1 | 0 | 1 | [1, 1, 1, 1, 2] |
| 20 | 2 | 1 | 2 | [1, 2, 1, 2, 2] |
| 40 | 4 | 2 | 3 | [1, 2, 1, 3, 2] |

The answer is 3 (10, 20, 40). The second 10 has rank 1, and its query covers ranks 1..0, an empty range, so it cannot extend the first 10: in a strictly increasing subsequence equal values may not follow each other. Note how raising rank 3 also wrote node 4, and raising rank 1 wrote nodes 1, 2 and 4.

**Exercise 13.5.** (1) False: for [3, 4, 1] it ends as [1, 4], which is not a subsequence. (2) True: equal values may follow each other, so *x* goes after all tails equal to it. (3) False: the peak may not be the first element of the mountain, so up[*i*] ≥ 2 is required. (4) False: a node stores a maximum and cannot recover the second-largest value after the largest is lowered. (5) True: then two envelopes of equal width can never both be in a strictly increasing run of heights. (6) True: every state of the plain DP is split into *K* states, and each transition is done once per remainder.

**Exercise 13.6.** Sort by *w* ascending and, for equal *w*, by *h* descending, so that two blocks of equal width can never both be chosen. Compress the heights to ranks. The Fenwick tree is indexed by height rank and stores, at each node, the largest tower value ending with a height in its range (a `long` sum, not a length). For each block, query the prefix maximum over ranks below its own (strict), add *v*, and raise its rank. Time O(*n* log *n*), memory O(*n*). For the six blocks the answer is 20, for example (1, 3, 4) + (2, 4, 3) + (3, 5, 6) + (4, 6, 7) = 4 + 3 + 6 + 7 = 20; a brute force over all subsets agrees.

**Exercise 13.7.** The query starts at `x` instead of `x - 1`, so it includes elements with the **same** rank and builds a non-decreasing subsequence. For ranks [1, 1] (two equal values) it returns 2 instead of 1. Fix: `for (int i = x - 1; i > 0; i -= i & -i)`.

**Exercise 13.8.** (1) The quadratic DP of @T:lst-13-quad with "*a*[*i*] % *a*[*j*] == 0" in place of "<": about 3000²/2 = 4.5 · 10⁶ pairs. (2) Patience sorting, @T:lst-13-tails: about 2 · 10⁵ · 18 ≈ 3.5 · 10⁶ comparisons. (3) Compression plus a Fenwick tree of maximum sums (`long`), @T:lst-13-weighted: O(*n* log *n*). (4) State (last value, XOR so far); since values are below 1024, there are 1024 XOR states, each with a Fenwick tree over values: about 1000 · 1024 · 10 ≈ 10⁷ steps for the queries and as many for the updates, about 2 · 10⁷ in all. (5) Brute force over all 2²⁰ ≈ 10⁶ subsets, checking each in O(*n*): about 2 · 10⁷ steps.

**Exercise 13.9.** Compare with @T:lst-13-ending. The two places that matter are the comparison `strict ? tails[mid] >= x : tails[mid] > x` and the line `end[i] = lo + 1` after the update.
