:::exercise{#exr-26-bug} Find the bug
This version of the capped maximum compiles and passes the second sample, [1, 2, 4, 7] → 7. Run it by hand on the first sample, [1, 2] with *B* = 2: write the row after the first pass, the value it returns, and the cause. Then fix it with one change.

```java
static int maxXorCapped(int[] a, int B) {
    int size = 1 << B, cap = a.length / 2;
    int[] cur = new int[size], next = new int[size];
    Arrays.fill(cur, Integer.MAX_VALUE);
    cur[0] = 0;
    for (int v : a) {
        for (int x = 0; x < size; x++) next[x] = Math.min(cur[x], cur[x ^ v] + 1);
        int[] t = cur; cur = next; next = t;
    }
    for (int x = size - 1; x > 0; x--) if (cur[x] <= cap) return x;
    return 0;
}
```

:::answers
**Exercise 26.1.** No single answer: check your table against three tests. The old rule and the new rule differ, and the new one names a line of code or a check you can perform ("cast the first factor of every product of two `int`s to `long`", "print the parsed input to standard error and compare it with the first sample before writing the logic", "run *n* = 1, all values equal and the largest values before submitting"), not an intention ("be careful with overflow"). The "differences found" column names concrete lines of the template, such as a loop bound or the order of two statements, and says whether the reason sentence was right. Every re-solve was timed against the plan's limits (Easy 20, Medium 40, Hard 60 minutes). A failed re-solve is a new error-log entry with the re-solve date three days later, Day 29.

**Exercise 26.2.** (1) `Integer.MAX_VALUE / 2`; (2) `cur[0] = 0`; (3) `Math.min(cur[x], cur[x ^ v] + 1)`; (4) the swap `int[] t = cur; cur = next; next = t`; (5) `f[x] <= cap` (with `f` the returned array). With `Integer.MAX_VALUE`, the expression `cur[x ^ v] + 1` overflows to `Integer.MIN_VALUE` whenever *x* ⊕ *v* is unreachable, and that negative value wins the minimum (Exercise 26.5 shows the damage).

**Exercise 26.3.**

| | x = 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|---|
| f0 | 0 | ∞ | ∞ | ∞ | ∞ | ∞ | ∞ | ∞ |
| f1 (a = 3) | 0 | ∞ | ∞ | 1 | ∞ | ∞ | ∞ | ∞ |
| f2 (a = 5) | 0 | ∞ | ∞ | 1 | ∞ | 1 | 2 | ∞ |
| f3 (a = 6) | 0 | ∞ | ∞ | 1 | ∞ | 1 | 1 | ∞ |
| f4 (a = 1) | 0 | 1 | 2 | 1 | 2 | 1 | 1 | 2 |

The answer is 7 = 6 ⊕ 1, two elements. In row f3, 6 drops from 2 (the set {3, 5}) to 1 (the element 6 itself). The rank is 3: 5 and 3 enter the basis, 6 = 5 ⊕ 3 is rejected, and 1 enters. Since 3 > cap = 2, `solve` runs the knapsack branch, but the answer equals the basis maximum 7, because 7 happens to be reachable with two elements. A rank above the cap means only that the basis cannot *promise* the answer. `solve` returns 7, as does a brute force.

**Exercise 26.4.**

| bit | x_b | k_b | action | subtree taken: prefix, range of s | sums tested (mark primes) |
|---|---|---|---|---|---|
| 3 | 0 | 0 | XOR bit must be 0: go to child 0 (prefix 0) | none | none |
| 2 | 1 | 1 | take child 1, then go to child 0 (prefix 00) | 01: *s*[3..5], the values 4, 5, 6 | 11 prime, 12, 13 prime |
| 1 | 1 | 0 | XOR bit must be 0: go to child 1 (prefix 001) | none | none |
| 0 | 1 | 1 | take child 1, then go to child 0 (prefix 0010) | 0011: *s*[2..2], the value 3 | 10 |

The query finds 4 candidates with XOR below 5 (7 ⊕ 4 = 3, 7 ⊕ 5 = 2, 7 ⊕ 6 = 1, 7 ⊕ 3 = 4) and 2 prime sums, so the count goes from 3 to 5. The values 1 and 2 are never looked at: 7 ⊕ 1 = 6 and 7 ⊕ 2 = 5 are not below 5, and the walk stops in the leaf of 2 without taking it. The query for 12 adds nothing, so the program prints 5: the pairs (4, 7), (1, 2), (6, 7), (6, 5) and (3, 2), with sums 11, 3, 13, 11 and 5.

**Exercise 26.5.** After the first pass (*v* = 1) the row is [−2147483648, 1, −2147483648, −2147483648]: for *x* = 0, 2 and 3 the term `cur[x ^ v] + 1` is `Integer.MAX_VALUE + 1`, which wraps to `Integer.MIN_VALUE`, and the minimum takes it. Even *x* = 0 is overwritten. Every negative entry passes `cur[x] <= cap`, so the method returns 3 instead of 2. Fix: fill the array with `Integer.MAX_VALUE / 2` instead. On 5,000 random inputs with even *N* ≤ 12 the buggy version was wrong 663 times.

**Exercise 26.6.** State: *g*[*k*][*x*] = the number of subsets of the elements seen so far with exactly *k* elements and XOR *x*, starting from *g*[0][0] = 1. Transition for a new element *v*: *g*[*k*][*x*] += *g*[*k* − 1][*x* ⊕ *v*] for every *k* ≥ 1 and every *x*, modulo 10⁹ + 7 (take *v* or not). In place, loop *k* downwards from *c* to 1: row *k* reads only row *k* − 1, which has not been updated yet in this pass, exactly as the capacity loop of Chapter 11 runs downwards. The order of *x* does not matter, because each write goes to row *k* and each read comes from row *k* − 1. Answer: Σ over *k* ≤ *c* of *g*[*k*][*T*]. Cost: *N* · *c* · 2¹⁰ ≤ 40 · 40 · 1024 = 1,638,400 updates and (*c* + 1) · 2¹⁰ numbers. For [1, 2, 3, 1] and *T* = 0: with *c* = 2 the answer is 2 (the empty set and the two 1s); with *c* = 3 it is 4 (adding {1, 2, 3} with either copy of 1). This design matched a brute force over all subsets on 3,000 random cases.

**Exercise 26.7.** (1) True: the rank is at most 20 ≤ *N*/2, so by @T:thm-26-basis the basis maximum is reachable within the cap. (2) False: for [3, 5, 6, 1] the rank is 3 > 2, yet the answer is the basis maximum 7 (Exercise 26.3). (3) False: two rows of 2²⁰ `int`s, 8 MB, are enough. (4) True: the values below a node share a prefix, so they lie in an interval, and in sorted order they are consecutive (@T:lem-26-range). (5) False: then every pair has XOR below *K*, the trie lists all *n*(*n* − 1)/2 pairs and adds its own overhead. (6) False: the sums go up to 2 · max(*A*), so the sieve must too. (7) True: a path of 15 vertices has 987 matchings, a star 15, and 10,000 random trees with 15 vertices had at most 923.
