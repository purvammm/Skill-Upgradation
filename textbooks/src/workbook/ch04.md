:::answers
**Exercise 4.1.** (1) `Integer.compare(x[0], y[0])`; (2) `cur[0] <= last[1]`; (3) `Math.max(last[1], cur[1])`; (4) `Integer.compare(x[1], y[1])`; (5) `cur[0] >= end`. Merging needs every interval that can touch the current block to arrive while that block is the last one, which sorting by start guarantees. Scheduling needs the choice that leaves the most room, which is the earliest end (@T:thm-4-schedule). `merge` returns [1, 3] for [1, 2], [2, 3], because touching intervals merge.

**Exercise 4.2.** The events, in order, with busy after each: 1 start (1), 2 start (2), 3 start (3), 3 end (2), 4 start (3), 4 end (2), 5 end (1), 6 start (2), 6 end (1), 7 start (2), 8 end (1), 9 end (0). The best is 3, so 3 rooms are needed (for example at time 3, meetings [1, 4], [2, 3] and [3, 5] all contain 3). If a room freed at *t* can be reused at *t*, ends sort first and the maximum drops to 2.

**Exercise 4.3.** [3, 5]: the earliest-freed room ends at 3, which is not < 3, so a new room; heap {3, 4, 5}. [4, 6]: reuse the room freed at 3; {4, 5, 6}. [6, 8]: reuse the room freed at 4; {5, 6, 8}. [7, 9]: reuse the room freed at 5; {6, 8, 9}. Three rooms, matching Exercise 4.2.

**Exercise 4.4.** Take any order with neighbours *i* before *j* and *t*ᵢ > *t*ⱼ, and let *T* be the time when the first of them starts. Every other job finishes at the same time in both orders. In the given order the two finish at *T* + *t*ᵢ and *T* + *t*ᵢ + *t*ⱼ; after swapping, at *T* + *t*ⱼ and *T* + *t*ⱼ + *t*ᵢ. The sum changes by *t*ⱼ − *t*ᵢ < 0, so the swap strictly improves it. An optimal order therefore has no such pair, which means it is sorted by *t* (and ties do not matter). For *t* = (3, 1, 2) the six orders give 3 1 2 → 13, 3 2 1 → 14, 1 3 2 → 11, 1 2 3 → 10, 2 3 1 → 13, 2 1 3 → 11; the sorted order 1, 2, 3 gives the minimum 10.

**Exercise 4.5.** Amount 6: the greedy takes 4 + 1 + 1 (three coins), but 3 + 3 uses two. (Amount 10 also fails: 4 + 4 + 1 + 1 against 4 + 3 + 3.) For coins {1, 5, 10, 25} the rule agreed with an exact dynamic programme (Chapter 11) for every amount up to 500. That is the way to gain confidence: compare the greedy with an exact method on every small input, which still is evidence, not proof.

**Exercise 4.6.** The order is 9, 89, 898, 8, 0, giving 98989880. The comparisons between neighbours: 9 + 89 = 989 > 899; 89 + 898 = 89898 > 89889; 898 + 8 = 8988 > 8898; 8 + 0 = 80 > 08. *v*(89) = 89/99 ≈ 0.898990 and *v*(898) = 898/999 ≈ 0.898899, so "89" comes first, as the concatenations say. For [0, 0] the sorted strings start with "0", so the method returns "0", not "00".

**Exercise 4.7.** State: *reach*, meaning every total 0..*reach* can be paid with the coins used and added so far. If the next coin *c* satisfies *c* ≤ *reach* + 1, use it: *reach* += *c* (@T:lem-4-reach). Otherwise the total *reach* + 1 cannot be paid, so add the coin *reach* + 1, which extends the range furthest: *reach* = 2 · *reach* + 1. Stop when *reach* ≥ *n*. Each added coin more than doubles *reach*, so at most about log₂ *n* + 1 coins are added; the loop is O(*m* + log *n*) for *m* coins. For [1, 5, 10] and *n* = 20: use 1 (reach 1), add 2 (reach 3), add 4 (reach 7), use 5 (reach 12), use 10 (reach 22). Two coins are added, which a brute force over all choices of added coins confirms.

**Exercise 4.8.** (1) False as a statement about the algorithm (quicksort is not stable), but it cannot be observed, because equal `int` values are identical. (2) True: object sorts use TimSort, O(*n* log *n*) in the worst case. (3) False: the difference can reach 2 · 10⁹, which exceeds 2³¹ − 1 and overflows. (4) False: boxing and comparator calls made it about five times slower in this book's measurements (410–570 ms against 11–91 ms). (5) False: log₂(5!) = log₂ 120 ≈ 6.9, so some input needs at least 7 comparisons. (6) False: some false greedies only fail on larger inputs (Theory review question 3 needed 9 or more intervals); test sizes up to about 10 and prove the rule.

**Exercise 4.9.** After pass 1: [2, 3, 4, 0, 1, 2, 1]. After pass 2: [2, 2, 1, 0, 1, 2, 1]. Neighbours differ by at most 1 everywhere, and each entry is at most its cap (for example index 2 is 1 ≤ 5, forced down by the 0 at index 3).
